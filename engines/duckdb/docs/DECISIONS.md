# Decisions: duckdb

Why the DuckDB engine is built the way it is. Decisions that bind every app are in the root [`docs/DECISIONS.md`](../../../docs/DECISIONS.md).

One bullet per decision, under its area, oldest first: what was chosen, the numbers that chose it, and *[where they came from]*. A decision that replaces another marks the old one *Superseded* rather than deleting it. Decisions moved here from an app keep their dates and sources.

## Engine and bridge

DuckDB-Wasm, the worker, the three bridge calls (`CLAUDE.md`, rule 2), and the Arrow reader. The bullets up to 2026-10-08 moved here from Tycho's `docs/DECISIONS.md` when the engine left it; their sources are Tycho's milestones, and their results files are under `apps/tycho/perf/results/`. "Rust" in them is now `crate/`, "the JS side" `web/`.

- **2026-09-23** · `@duckdb/duckdb-wasm` pinned to **1.32.0**, the newest stable release. npm's `latest` tag points at a dev build (1.33.1-dev57). *[M2]*
- **2026-09-23** · Arrow IPC decoded by a **hand-rolled reader** (`crate/src/arrow.rs`, then in Tycho), not arrow-rs: arrow-ipc + arrow-array + arrow-schema 60 with default features off cost +127.3 KiB brotli (+4.8%) more. Unsupported types decode as named placeholder columns. *[M2 `apps/tycho/perf/results/2026-09-23-m2.md`]*
- **2026-09-23** · **The engine loads on the first bridge call**, not through a fourth call. The post-paint callback sends the warm-up `SELECT 42 AS x`, which starts the load; its answer is checked in Rust before the UI says "Engine ready". *[M2]*
- **2026-09-23** · DuckDB's own prebuilt worker, run inside a small blob: classic worker that turns unhandled rejections into worker errors. DuckDB-Wasm 1.32.0 never rejects `instantiate` when its worker fails, which hung the UI on "Engine loading…". No `duckdb.worker.ts` file: Vite's dev server serves worker entries as ES modules, which can't `importScripts`. *[M2 negative controls]*
- **2026-09-23** · One DuckDB connection per query. Results come from the pending-query API (`startPendingQuery`/`pollPendingQuery`/`fetchQueryResults`) as raw IPC bytes, concatenated in JS; no Arrow decoding in JS. `cancel` aborts an `AbortSignal`, which calls `cancelPendingQuery` between poll slices. *[M2]*
- **2026-09-23** · Bundles: EH or MVP by DuckDB's `selectBundle` (every engine we test gets EH). The COI (threads) bundle isn't used. *[M2]*
- **2026-09-23** · DuckDB extension autoload and autoinstall are **off**. Parquet isn't built into DuckDB-Wasm, and by default it would be fetched from extensions.duckdb.org on first use. M3 self-hosts it. *[M2 code review]*
- **2026-09-23** · `registerFile(url)` first sends a one-byte range request and requires `206`: it rejects missing files, servers without range support, and SPA fallbacks (Vite answers unknown paths with `index.html`), and reads the real size from `Content-Range` (a compressed HEAD's `Content-Length` isn't the file size). *[M2 code review]*
- **2026-09-23** · Every engine call races the worker's `error` event, at load and after, so a worker that dies mid-query rejects that query instead of leaving it pending. *[M2 code review]*
- **2026-09-24** · DuckDB opens with `filesystem: { reliableHeadRequests: true, allowFullHTTPReads: false, forceFullHTTPReads: false }`. With 1.32.0's defaults it misreads its own `bytes=0-0` probe and downloads the whole file (all 35 MB to show a schema); with these settings it reads only the footer (34.8 KB). *[M3 `apps/tycho/perf/results/2026-09-24-m3.md`]*
- **2026-09-24** · The Parquet extension (EH + MVP, v1.4.3) is self-hosted from Tycho's `web/public/duckdb-ext/`, fetched by `just tycho extensions` and checked against SHA-256 pins in its `web/duckdb-extensions.json` (now this engine's). DuckDB's extension repository points at our origin; autoload stays on. Rust prefetches it with `LOAD parquet` right after the warm-up ("Parquet ready" in the overlay). *Its "autoload stays on" was superseded 2026-09-25: autoload is off, `LOAD` is the only way in (below).* *[M3]*
- **2026-09-25** · One `LOAD parquet` at a time (`Engine::load_parquet`): the prefetch and every file open share one attempt, a success is remembered, a failure lets the next caller retry. **Extension autoload is now off** (superseding M3's "autoload stays on"): `LOAD` is the only way an extension loads, and a query needing an unloaded one fails with a clear error. Two failing loads of one extension at once crash DuckDB-Wasm 1.32.0 without a worker error. *[M4 (M3 retry check, two code reviews)]*
- **2026-09-27** · `SET GLOBAL parquet_metadata_cache = true` after `LOAD parquet`: each footer is parsed once, not by every query (~165 ms each at 1,378 row groups). `GLOBAL` because each query has its own connection. *[M5 `apps/tycho/perf/results/2026-09-27-m5.md`]*
- **2026-10-07** · DuckDB's reads are counted inside its worker: `startWorker`'s wrapper wraps `XMLHttpRequest` (GET bodies) and `FileReaderSync` (slices of a dropped `File`) and adds them to a per-file `SharedArrayBuffer` counter. The counter rides on `registerFile`'s `FileInfo` (`bytesRead`), and Rust reads it with `Atomics.load`, so **no fourth bridge call**. SQL can't see the bytes: DuckDB-Wasm's own file statistics are a JS API (a fourth call), and its readahead happens below DuckDB's reads. *[M7 part A]*
- **2026-10-08** · **Engine failures retry, not reload.** A failed load and a worker that stops after loading both show in the empty state with Retry, which starts a new worker. The bridge forgets a failed load at once, and a stopped engine once a call has been rejected with `EngineStopped`; Rust's `Engine` refuses calls while it's down, so only Retry's warm-up starts the new one (a stray page read did, unseen, before). A stopped worker closes the open file; the app learns at its next call. No fourth bridge call. *[M7 part D]*
- **2026-10-08** · **Files stay registered; footers are a documented cost.** `db.dropFile` and toggling `parquet_metadata_cache` free nothing (44.2 MiB in DuckDB after 20 opens of a 1,378-group file, every variant). `registerFile` and Tycho rule 2 keep their wording. *[M7 part D]*
- **2026-10-08** · **No in-flight tracking in `Engine`.** Built (`Engine::idle`, a new open waiting for the last one's cancelled reads) and measured against a build without it: same "Read", same first rows (1236 ms). DuckDB's worker runs messages in order, and every poll of a cancelled query is queued before the next open's counter and register messages, so its reads land on the old counter. That's also why part A's read-counter key collision can't happen. Removed. *[M7 part D]*
- **2026-10-08** · Code review fixes: every bridge call's answer is watched for `EngineStopped` even when nobody awaits it (an open replaced mid-flight drops its futures); a failed engine-chunk import is retried under `?retry=<n>` (Chromium remembers failed dynamic imports); re-registration only for read failures (`EngineError::is_read_failure`) on the shown table; an empty chunk is out of memory only above 1 GiB; `?scan_kib=` removed. Declined: batching the per-chunk memory query (no measurable cost). *[M7 part D, code review]*

- **2026-10-13** · **Moved out of Tycho, as the repo's first engine:** `crate/` (`seiza-duckdb`, from Tycho's `crate/src/engine/` and `arrow.rs`) and `web/` (`@seiza/duckdb`, from Tycho's `bridge.ts`, `engine.ts`, the extension pins and their script, and its Vite config's 404 rule, now the `duckdb()` plugin). Tycho's app wasm: 2838.7 KiB brotli against 2838.0 before. *[Tycho M9 part B `apps/tycho/perf/results/2026-10-13-m9-b.md`]*
- **2026-10-13** · **Events, not `seiza` calls.** The client reported its load to the panel itself (`seiza::perf::set_load_step`, `seiza::marks`); it now hands the host `EngineEvent`s (Loading, Ready, Failed, ParquetReady, ParquetFailed) with their times, through the handler passed to `start`, which `retry` reuses. `EngineStatus` stays a global the host observes. The order is guaranteed: Ready (or Failed), then exactly one Parquet event for the prefetch, then a `ParquetReady` for a later load that succeeds after a failed prefetch. `run` reports the prefetch's result, taking a load an early open started if it finished first; a load reports itself only once the prefetch has settled. The host needs no `show_parquet_ready` after an open. *[Tycho M9 part B, code review: a load an early sample click started could report before Ready, which then reset the step, and nothing reported it again]*
- **2026-10-13** · **Its marks are `duckdb:engine-start` and `duckdb:engine-ready`** (were `tycho:…`), set by `web/` and read back by `crate/` for the events' times; the crate reads the page clock and those marks with its own two small functions, since it can't depend on `seiza`, and sets no mark itself. *[Tycho M9 part B]*
- **2026-10-13** · **What only a host knows comes in as an option.** Tycho's pause switch (a 503 with `X-Tycho-Paused: 1`) was checked inside `engine.ts`; now `createBridge({ refusal })` maps any non-206 answer to the range probe to the host's message. `scripts/extensions.ts` takes the host's public dir; the read counter's worker message is `__duckdbCountReads`. Rejected: a repo-wide `X-Seiza-Paused` header, which would have changed the deployed Worker for a rename. *[Tycho M9 part B]*

## Table source

The `table` feature: DuckDB as a `seiza-table` source. The first bullet moved here from Tycho's `docs/DECISIONS.md` (its "Table and paging") when the table left it.

- **2026-09-25** · Paging strategy **B** (`read_parquet(..., file_row_number = true)` filtered to the page): 49.6 ms and 1.39 MB for a jump to 90%, vs 60.5 ms (A, `LIMIT/OFFSET`, same bytes) and a 1.1 s, 37.7 MB ingest before any row (C). *[M4 `apps/tycho/perf/results/2026-09-25-m4.md`]*
- **2026-10-13** · **A `table` feature, not a crate of its own** (root `CLAUDE.md`, "Tiers": an adapter lives in the engine, behind a feature named for the component). `QueryResult` is a `TablePage` (a `Value` maps to a `CellValue`: floats stay numbers, text stays borrowed, the rest is its `Display`); `QueryRows<Q: PageQuery>` reads pages with `Q`'s SQL and maps `EngineError`s (`Cancelled`, and `is_read_failure` to `read_failure`); `ParquetFile` is the Parquet query; `ColumnInfo::table_column` maps DuckDB type names to `ColumnKind`s. The file summary (`ParquetSummary`, `open_parquet`) came with it, taking the metadata keys to read from the host (Tycho's `tycho.credit` and `tycho.fetched` stay Tycho's). The SQL helpers (`sql::string_literal`, `column`, `text`, `count`) and `ColumnInfo` are in the base crate, for any host's own SQL. *[Tycho M9 part C]*

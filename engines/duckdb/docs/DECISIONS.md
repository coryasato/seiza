# Decisions: duckdb

Why the DuckDB engine is built the way it is. Decisions that bind every app are in the root [`docs/DECISIONS.md`](../../../docs/DECISIONS.md).

One bullet per decision, under its area, oldest first: what was chosen, the numbers that chose it, and *[where they came from]*. A decision that replaces another marks the old one *Superseded* rather than deleting it. Decisions moved here from an app keep their dates and sources.

## Engine and bridge

DuckDB-Wasm, the worker, the three bridge calls (`CLAUDE.md`, rule 2), and the Arrow reader. The bullets up to 2026-10-08 moved here from Tycho's `docs/DECISIONS.md` when the engine left it; their sources are Tycho's milestones, and their results files are under `apps/tycho/perf/results/`. "Rust" in them is now `crate/`, "the JS side" `web/`.

- **2026-09-23** · `@duckdb/duckdb-wasm` pinned to **1.32.0**, the newest stable release. npm's `latest` tag points at a dev build (1.33.1-dev57). *[M2]*
- **2026-09-23** · Arrow IPC decoded by a **hand-rolled reader** (`crate/src/arrow.rs`, then in Tycho), not arrow-rs: arrow-ipc + arrow-array + arrow-schema 60 with default features off cost +127.3 KiB brotli (+4.8%) more. Unsupported types decode as named placeholder columns. *[M2 `apps/tycho/perf/results/2026-09-23-m2.md`]*
- **2026-09-23** · **The engine loads on the first bridge call**, not through a fourth call. The post-paint callback sends the warm-up `SELECT 42 AS x`, which starts the load; its answer is checked in Rust before the UI says "Engine ready". *[M2]*
- **2026-09-23** · DuckDB's own prebuilt worker, run inside a small blob: classic worker that turns unhandled rejections into worker errors. DuckDB-Wasm 1.32.0 never rejects `instantiate` when its worker fails, which hung the UI on "Engine loading…". No `duckdb.worker.ts` file: Vite's dev server serves worker entries as ES modules, which can't `importScripts`. *[M2 negative controls]*
- **2026-09-23** · One DuckDB connection per query. Results come from the pending-query API (`startPendingQuery`/`pollPendingQuery`/`fetchQueryResults`) as raw IPC bytes, concatenated in JS; no Arrow decoding in JS. `cancel` aborts an `AbortSignal`, which calls `cancelPendingQuery` between poll slices. *[M2]*
- **2026-09-23** · Bundles: EH or MVP by DuckDB's `selectBundle` (every engine we test gets EH). The COI (threads) bundle isn't used. *[M2]*
- **2026-09-23** · DuckDB extension autoload and autoinstall are **off**. Parquet isn't built into DuckDB-Wasm, and by default it would be fetched from extensions.duckdb.org on first use. M3 self-hosts it. *[M2 code review]*
- **2026-09-23** · `registerFile(url)` first sends a one-byte range request and requires `206`: it rejects missing files, servers without range support, and SPA fallbacks (Vite answers unknown paths with `index.html`), and reads the real size from `Content-Range` (a compressed HEAD's `Content-Length` isn't the file size). *[M2 code review]*
- **2026-09-23** · Every engine call races the worker's `error` event, at load and after, so a worker that dies mid-query rejects that query instead of leaving it pending. *[M2 code review]*
- **2026-09-24** · DuckDB opens with `filesystem: { reliableHeadRequests: true, allowFullHTTPReads: false, forceFullHTTPReads: false }`. With 1.32.0's defaults it misreads its own `bytes=0-0` probe and downloads the whole file (all 35 MB to show a schema); with these settings it reads only the footer (34.8 KB). *[M3 `apps/tycho/perf/results/2026-09-24-m3.md`]*
- **2026-09-24** · The Parquet extension (EH + MVP, v1.4.3) is self-hosted from Tycho's `web/public/duckdb-ext/`, fetched by `just tycho extensions` and checked against SHA-256 pins in its `web/duckdb-extensions.json` (now this engine's). DuckDB's extension repository points at our origin; autoload stays on. Rust prefetches it with `LOAD parquet` right after the warm-up ("Parquet ready" in the overlay). *Its "autoload stays on" was superseded 2026-09-25: autoload is off, `LOAD` is the only way in (below).* *[M3]*
- **2026-09-25** · One `LOAD parquet` at a time (`Engine::load_parquet`): the prefetch and every file open share one attempt, a success is remembered, a failure lets the next caller retry. **Extension autoload is now off** (superseding M3's "autoload stays on"): `LOAD` is the only way an extension loads, and a query needing an unloaded one fails with a clear error. Two failing loads of one extension at once crash DuckDB-Wasm 1.32.0 without a worker error. *[M4 (M3 retry check, two code reviews)]*
- **2026-09-27** · `SET GLOBAL parquet_metadata_cache = true` after `LOAD parquet`: each footer is parsed once, not by every query (~165 ms each at 1,378 row groups). `GLOBAL` because each query has its own connection. *[M5 `apps/tycho/perf/results/2026-09-27-m5.md`]*
- **2026-10-07** · DuckDB's reads are counted inside its worker: `startWorker`'s wrapper wraps `XMLHttpRequest` (GET bodies) and `FileReaderSync` (slices of a dropped `File`) and adds them to a per-file `SharedArrayBuffer` counter. The counter rides on `registerFile`'s `FileInfo` (`bytesRead`), and Rust reads it with `Atomics.load`, so **no fourth bridge call**. SQL can't see the bytes: DuckDB-Wasm's own file statistics are a JS API (a fourth call), and its readahead happens below DuckDB's reads. *[M7 part A]*
- **2026-10-08** · **Engine failures retry, not reload.** A failed load and a worker that stops after loading both show in the empty state with Retry, which starts a new worker. The bridge forgets a failed load at once, and a stopped engine once a call has been rejected with `EngineStopped`; Rust's `Engine` refuses calls while it's down, so only Retry's warm-up starts the new one (a stray page read did, unseen, before). A stopped worker closes the open file; the app learns at its next call. No fourth bridge call. *[M7 part D]*
- **2026-10-08** · **Files stay registered; footers are a documented cost.** `db.dropFile` and toggling `parquet_metadata_cache` free nothing (44.2 MiB in DuckDB after 20 opens of a 1,378-group file, every variant). `registerFile` and Tycho rule 2 keep their wording. *[M7 part D]*
- **2026-10-08** · **No in-flight tracking in `Engine`.** Built (`Engine::idle`, a new open waiting for the last one's cancelled reads) and measured against a build without it: same "Read", same first rows (1236 ms). DuckDB's worker runs messages in order, and every poll of a cancelled query is queued before the next open's counter and register messages, so its reads land on the old counter. That's also why part A's read-counter key collision can't happen. Removed. *[M7 part D]*
- **2026-10-08** · Code review fixes: every bridge call's answer is watched for `EngineStopped` even when nobody awaits it (an open replaced mid-flight drops its futures); a failed engine-chunk import is retried under `?retry=<n>` (Chromium remembers failed dynamic imports); re-registration only for read failures (`EngineError::is_read_failure`) on the shown table; an empty chunk is out of memory only above 1 GiB; `?scan_kib=` removed. Declined: batching the per-chunk memory query (no measurable cost). *[M7 part D, code review]*

- **2026-10-13** · **Moved out of Tycho, as the repo's first engine:** `crate/` (`seiza-duckdb`, from Tycho's `crate/src/engine/` and `arrow.rs`) and `web/` (`@seiza/duckdb`, from Tycho's `bridge.ts`, `engine.ts`, the extension pins and their script, and its Vite config's 404 rule, now the `duckdb()` plugin). Tycho's app wasm: 2838.7 KiB brotli against 2838.0 before. *[Tycho M9 part B `apps/tycho/perf/results/2026-10-13-m9-b.md`]*
- **2026-10-13** · **Events, not `seiza` calls.** The client reported its load to the panel itself (`seiza::perf::set_load_step`, `seiza::marks`); it now hands the host `EngineEvent`s (Loading, Ready, Failed, ParquetReady, ParquetFailed) with their times, through the handler passed to `start`, which `retry` reuses. `EngineStatus` stays a global the host observes. The order is guaranteed: Ready (or Failed), then exactly one Parquet event for the prefetch, then a `ParquetReady` for a later load that succeeds after a failed prefetch. `run` reports the prefetch's result, taking a load an early open started if it finished first; a load reports itself only once the prefetch has settled. The host needs no `show_parquet_ready` after an open. *[Tycho M9 part B, code review: a load an early sample click started could report before Ready, which then reset the step, and nothing reported it again]*
- **2026-10-13** · **Its marks are `duckdb:engine-start` and `duckdb:engine-ready`** (were `tycho:…`), set by `web/` and read back by `crate/` for the events' times; the crate reads the page clock and those marks with its own two small functions, since it can't depend on `seiza`, and sets no mark itself. *[Tycho M9 part B]*
- **2026-10-13** · **What only a host knows comes in as an option.** Tycho's pause switch (a 503 with `X-Tycho-Paused: 1`) was checked inside `engine.ts`; now `createBridge({ refusal })` maps any non-206 answer to the range probe to the host's message. `scripts/extensions.ts` takes the host's public dir; the read counter's worker message is `__duckdbCountReads`. Rejected: a repo-wide `X-Seiza-Paused` header, which would have changed the deployed Worker for a rename. *[Tycho M9 part B]*
- **2026-10-14** · **The extension directory is a host option:** `extensionDir`, one directory name under the host's Vite base (`duckdb-ext` by default), the same name for `createBridge`, `duckdb()`, and `scripts/extensions.ts`, so the observatory can serve the engine from `/observatory/duckdb/` on the apex origin it shares. The bridge prefixes `import.meta.env.BASE_URL`, the plugin its `base`; a name with a slash throws. Rejected: a full repository path for the bridge and the plugin and a directory for the script (the first draft), which a code review found could disagree silently (a trailing slash, a missing base) and turn the 404 rule off. Tycho passes nothing: its app wasm is byte-identical, and its engine chunk is the one JS file that changes. *[Observatory M0 part A, code review]*

- **2026-10-19** · **`extensionBase`: the path the extension directory sits under,** Vite's `BASE_URL` by default. The observatory's contenders have bases of their own (`/observatory/contenders/tall-table/<stack>/`) and load one engine from `/observatory/duckdb/`, so its second load is cached; the bundles' URLs are the host's build's to set (Vite's `renderBuiltUrl`), the extensions' this option's. It must start and end with `/`; `extensionDir` stays one name. Tycho sets neither: its engine chunk +32 B brotli. *[observatory M5 part A; `apps/tycho/perf/results/2026-10-19-observatory-m5-a.md`]*
- **2026-11-23** · **A lockdown is a host's option, off by default** (`start_locked`, `Lockdown`): a directory and the statements to run before the lock, then `allowed_directories`, `enable_external_access = false`, `lock_configuration = true`, after the Parquet extension has loaded (`LOAD` is refused after). Tested in Node on 1.32.0 (Tycho's research, `docs/research/tycho-workbench.md`, "Security") and repeated in Chromium, Firefox, and WebKit on the release build (Tycho's `perf/lockdown.ts`): refused, a URL, a file outside the directory, a `../` path, `COPY` outside it or to a URL, `ATTACH` of a file or URL, `LOAD json`, and every `SET` and `RESET`. The browser corrected the research twice: `ATTACH ':memory:'` runs locked (no I/O), and so do `INSTALL` and a `LOAD` of a loaded extension (no-ops in DuckDB-Wasm). Dropped files (`BROWSER_FILEREADER` handles) read under the directory, as do `SUMMARIZE` and `parquet_metadata`. **`EngineStatus::Ready` waits for the lock,** so a host that opens files only while ready never opens one unlocked. **A failed step resumes on the same worker:** the engine is `Failed` and `retry` runs the steps not yet run (the worker isn't down, so rule 4's replacement doesn't apply); a stopped worker starts them again. `retry` no longer forgets a loaded Parquet extension, which only a new worker loses. The directory is the host's (rule 1); the observatory's contenders don't ask, and send what they sent (`just observatory check`). *[Tycho M12 part A]*
- **2026-11-27** · **`query` takes a `background` option, off by default: a background query polls its slices only while no foreground query is in flight.** DuckDB-Wasm runs pending queries round-robin, a slice each, and the slices are polled from JS (`runQuery`'s `pollPendingQuery`), so the bridge can hold a query's next slice. Timed on Tycho's release build (Chromium): five page reads in a row beside a profile query took ~1.0 s each on the 1 GB asteroids (0.51 s alone) and up to 478 ms on the 100 MB ones (35 ms alone); with the profile query as background, 560–635 ms and ≤ 210 ms, the profile query itself no slower (5.8 s, then 5.2 s). What a page still waited was the background slice already running (60–135 ms on the 1 GB file), which can't be stopped; so a host can also shorten every slice (`sliceMs`, DuckDB-Wasm's `queryPollingInterval`, its own default when unset): at 10 ms, a page beside a background query took 495–568 ms on the 1 GB file and 35–64 ms on the 100 MB one, as fast as one alone (499 and 38 ms), and neither a page alone nor the profile query was slower. The setting is global, not a background query's, so it's the host's to choose: Tycho sets 10 ms, the observatory's contender sets none. Still three calls (`CLAUDE.md`, rule 2): an option on one. A host that sends none, as the observatory's contender, sends what it sent. A background query can wait as long as foreground ones keep coming; the host says so where it shows the answer. *[Tycho M16 part A]*

## Table source

The `tall-table` feature: DuckDB as a `seiza-tall-table` source. The first bullet moved here from Tycho's `docs/DECISIONS.md` (its "Table and paging") when the table left it.

- **2026-09-25** · Paging strategy **B** (`read_parquet(..., file_row_number = true)` filtered to the page): 49.6 ms and 1.39 MB for a jump to 90%, vs 60.5 ms (A, `LIMIT/OFFSET`, same bytes) and a 1.1 s, 37.7 MB ingest before any row (C). *[M4 `apps/tycho/perf/results/2026-09-25-m4.md`]*
- **2026-10-13** · **A `table` feature, not a crate of its own** (root `CLAUDE.md`, "Tiers": an adapter lives in the engine, behind a feature named for the component). `QueryResult` is a `TablePage` (a `Value` maps to a `CellValue`: floats stay numbers, text stays borrowed, the rest is its `Display`); `QueryRows<Q: PageQuery>` reads pages with `Q`'s SQL and maps `EngineError`s (`Cancelled`, and `is_read_failure` to `read_failure`); `ParquetFile` is the Parquet query; `ColumnInfo::table_column` maps DuckDB type names to `ColumnKind`s. The file summary (`ParquetSummary`, `open_parquet`) came with it, taking the metadata keys to read from the host (Tycho's `tycho.credit` and `tycho.fetched` stay Tycho's). The SQL helpers (`sql::string_literal`, `column`, `text`, `count`) and `ColumnInfo` are in the base crate, for any host's own SQL. *[Tycho M9 part C]* *Its names were superseded 2026-10-14, when the component became `seiza-tall-table`: the feature is `tall-table`, the module `tall_table`, and `ColumnInfo::table_column` is `tall_table_column` (`components/tall-table/docs/DECISIONS.md`, "Component API").*

- **2026-11-26** · **A filtered or sorted view is the engine's `view::ViewRows`, beside `QueryRows`, not in it:** `QueryRows` is the observatory's contender's source, and its page SQL is pinned by the SQL fixture, so the view is a delegate of its own over a `RowSource` (a source's rows as one numbered relation, a range of them reading only their storage), its indexes and copies in an in-memory database the host attaches `(COMPRESS)` before its lockdown. *[Tycho M15 part A]*
- **2026-11-26** · **A filter is an index of row numbers in the source's order; a sort is a sorted copy of the rows in view; each checked against the count it was built from.** Timed in DuckDB-Wasm on Tycho's release build (Chromium, an M-series Mac), on GCAT (71,431 rows, 36 columns; Parquet and as a CSV), the asteroids ×3 (108 MiB, 4.7 M rows) and ×27 (970 MiB, 42.3 M rows, 1,378 groups), and the asteroids CSV (178 MB, 1.57 M rows in 31 chunk tables); the file-order page for comparison: 26–32 ms, 35–39 ms, 512–548 ms, and 3–5 ms in a CSV. **A filter's index** built in 5–14 ms on GCAT, 156–860 ms at ×3, 1.3–8.3 s at ×27 (its `CREATE TABLE … AS` answers the count, so no count of its own), 10–124 ms on the CSV, holding ~1–16 MiB; a page joins the index's slice to the source's rows between the slice's first and last row number, written into the SQL: 22–35 ms on GCAT, 31–215 ms at ×3, 0.53–0.67 s at ×27 (the same join without the bounds: 25 s a page, every row group read). **A sort's index** (row numbers in sort order) built fast (0.9–1.6 s at ×3) but its pages read rows scattered through every row group: ~2 s a page at ×3, 25–33 s at ×27, 125–170 ms in the CSV and growing with it. **A sorted copy** pages by `rowid` in 2–8 ms everywhere; it reads the whole file once whatever the filter keeps: 0.3 s and ~4 MiB on GCAT, 7.5–8 s and ~145 MiB at ×3, 21–25 s for a 1.1 M-row filter at ×27 (38 MiB), 1.9–2.0 s and ~55 MiB on the CSV. A top-N for the first page alone (2.6 s at ×3, 7–25 s at ×27) wasn't worth a second path. What a host refuses (a file too large to copy, rows still loading) is the source's to say (`RowSource::refuse_sort`, `busy`). *[Tycho M15 part A; the runs' script, not kept: each way's SQL through `?bench`'s bridge]*
- **2026-11-26** · **Find scans the rows in view in windows, each its own query, from 16,384 rows doubling to 1,048,576:** a cancel stops it between windows and page reads go between them. Timed in DuckDB-Wasm as the sort's runs: on GCAT a window answered in 13–35 ms and a match 47,847 rows in was found in 45 ms; on the asteroids ×27 the first window cost ~0.58 s (every row group's readers set up, as a page's are), 1 M rows ~2.3 s, 2 M rows ~4.1 s, and a scan finding nothing ~87 s at 2 M-row windows. A window holds the worker while it runs, so the cap is 1 M rows (a page read waits ~2.3 s at most, the scan ~10% longer for the windows' setup); a cell matches as the table's rule says, `lower(CAST(… AS VARCHAR))` containing `lower(term)`, the term a string literal (no `LIKE`). The count of matching cells and the current match's place are SQL the host sends itself (`find_count_sql`, `find_place_sql`), whole scans it cancels on a new term: ~40 ms each on GCAT, 67 s on the asteroids ×27, whatever the term. *[Tycho M15 part A]*
- **2026-11-27** · **A filter on a Parquet file's text column is written as a `CASE` projection, not a `WHERE`.** In DuckDB-Wasm 1.32.0 a text comparison in a `WHERE` on a Parquet file is about 10× slower than the same test as `CASE WHEN … THEN true ELSE false END`, which the scan can't push down (on the 1 GB asteroids, `class = 'MCA'`: figures of one column 20.1 s against 1.9 s; the row numbers of an index 10.4 s against 1.6 s; at 100 MB 2.0 s against 0.2 s). Native DuckDB 1.4.5 runs both alike, and a comparison on a number pays little (`n_obs_used > 2000`, 1.0 s). Timed on Tycho's release build (Chromium). *[Tycho M16 part A]*

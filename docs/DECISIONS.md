# Decisions: repo-wide

Decisions that bind every app: the toolchain and pins, the repo's structure, `shared/`, `shared-web/`, the measurement and comparison protocols, and hosting. An app's own decisions are in `apps/<app>/docs/DECISIONS.md`; a component's or engine's, in its own `docs/DECISIONS.md`.

One bullet per decision, under its area, oldest first: what was chosen, the numbers that chose it, and *[where they came from]*. A decision that replaces another marks the old one *Superseded* rather than deleting it. Most entries came out of Tycho, so sources name Tycho's milestones; its results are in `apps/tycho/perf/results/`. *[design discussion]* marks a decision made in planning, before any code or measurement.

## Rendering and first paint

- **2026-09-23** · Web platform: single-threaded, WebGL2 forced (not the WebGPU-first `Auto`), `CanvasFontFallback::Emoji`. *Superseded the same day by `Auto` (next entry).* *[M0; M1 measures `Auto` vs `WebGl`]*
- **2026-09-23** · UI font: IBM Plex Sans Regular (what `gpui-pre-web` maps `.SystemUIFont` to), fetched by the JS host in parallel with the wasm, not `include_bytes!`. *[M0]*
- **2026-09-23** · Graphics backend: GPUI `Auto` (WebGPU, WebGL2 fallback), replacing forced WebGL2. Chromium 173.5 vs 291.0 ms ref (−40%), 3460 vs 3765 ms throttled; WebKit 296 vs 412 ms; Firefox falls back at no cost. *[M1 `m1-backend-*`]*
- **2026-09-23** · Preload the wasm and UI font from the HTML (`as=fetch crossorigin`): −10 ms ref, −188 ms throttled. *[M1 `m1-no-preload`]*
- **2026-09-23** · UI font stays the full face: a Latin subset saves 42 KiB br and 21 ms throttled (0.6%) but drops Greek and Cyrillic, which dropped files may contain. *[M1 `m1-font-subset`]*
- **2026-09-23** · First-frame mark: a microtask queued by the first render with a non-zero viewport (was: a rAF requested from the first render, a frame late on WebGPU). Verified every run by a GPU-call probe. *[M1]*
- **2026-09-23** · `AppShell` renders gpui-kit 0.6.4's overlay layers (`Root::render_*_layer`): without it, dialogs and notifications update state but never draw. +26.4 KiB brotli. *Superseded 2026-10-07: 0.7's `gpui_kit::open_window` wraps the content in `Root`, which hosts them.* *[Tycho M0]*

## Shell and input (`shared/`)

- **2026-09-23** · The theme follows live light/dark changes (`observe_window_appearance` → `Theme::sync_system_appearance`); gpui-pre-web fires the observer on `prefers-color-scheme`. Since 2026-10-09 a press of the theme button stops following until a reload (above). *[Tycho M0]*
- **2026-10-08** · `shared/` binds gpui-base's macOS input shortcuts in Mac browsers (`navigator.platform`), where its `cfg(target_os = "macos")` never holds on wasm: Cmd+A/C/X/Z, Cmd+arrows with and without Shift, Opt+arrows with and without Shift, Cmd/Opt+Backspace and Delete. Not elsewhere: Alt+←/→ is Back/Forward. Not Cmd+V: unbound, it reaches the browser's permission-free paste event. Cmd+A/C/X are bound before `gpui_kit::init`, so the menu keeps labelling the Ctrl keys (the latest binding labels an action; wasm spells Cmd "Win"); the rest after, to outrank the wasm build's Shift+Alt+←/→. *[M7 part C, code review]* *Since 2026-10-16, only for an app that asks (`Bootstrap::mac_input_bindings`).*
- **2026-10-09** · **Theme toggle: a Sun/Moon icon button in `shared/`'s title bar, and Cmd/Ctrl+Shift+L.** The icon shows the theme a press switches to. The icons are embedded with gpui-kit-assets' `icon_assets!(Icons, [Sun, Moon])` (in the 0.7.1 pin), not the default `Assets`, which fetches each icon from a CDN on first use on the web: +11.6 KiB brotli against a text label (accepted). A press stops following the system until a reload (`ThemeChoice`, in memory). Keyboard: the shortcut only; gpui-kit 0.7.1 binds nothing to Tab, and binding focus-next app-wide would change the table and jump input. *[M7 part G, review]* *Superseded in part 2026-10-16: the button, the shortcut, and the icons are Tycho's (`apps/tycho/crate/src/shell.rs`), and `shared/` stops following the system when Tycho says so.*
- **2026-10-09** · Buttons take the web's pointer cursor (`cursor_pointer`), only while they can be pressed; gpui-kit gives buttons the desktop arrow. *[M7 part G, review]*
- **2026-10-16** · **The title bar and the theme toggle are Tycho's, not `shared/`'s.** `shared/` keeps only what every host needs: the bootstrap, a window root that fills the canvas with the app's view, arms the first-frame mark, and follows the system appearance until the app calls `seiza::stop_following_system_appearance`, and the perf panel behind the `panel` feature (on by default; `seiza::perf::toggle` for an app's own button). An app's icons come in through `Bootstrap::assets` (none by default: nothing is fetched). Tycho draws its own title bar (`apps/tycho/crate/src/shell.rs`) and passes its markup to the placeholder, whose `shared-web` half now draws only what the app gives it. Rejected: a `shell` feature in `seiza`, which kept app chrome in the foundation and needed `shell` to imply `panel` to leave Tycho's code alone. Checking Tycho afterwards by bytes is the wrong test: any change to `seiza`'s features changes its `-C metadata` hash (symbol and `TypeId` hashes follow), gpui's `#[track_caller]` calls carry line numbers, and HEAD built from another directory came out 1.3 KiB apart raw. The check is the placeholder match (light and dark, DPR 2 and 1, the theme toggle's behavior) and the size effect. *[observatory M2 part A, `apps/tycho/perf/results/2026-10-16-observatory-m2-a.md`]*
- **2026-10-16** · **The Mac input bindings stay in `shared/`, opt-in:** `Bootstrap::mac_input_bindings()`, for an app with a gpui-kit Input. They're a gpui-kit web workaround, and their order around `gpui_kit::init` is the bootstrap's. The call stores the two bind functions as function pointers, so a host that never makes it links none of them: a bare host's wasm is +991 B raw, +353 B brotli with the call. (A `bool` on `Bootstrap` would likely keep them: it's read inside the boxed closure `run_embedded` calls, where LTO can't see it's always false. Not measured.) *[observatory M2 part A]*

## Observation panel and marks (`shared/`)

- **2026-09-24** · "Sample → schema" is timed to the presented frame: `shared/`'s after-present mark is now public (`seiza::mark_after_current_task(name)`). *[M3]*
- **2026-09-25** · The overlay's common rows (`shared/`): "Frame time (2 s)" (p50/p95/max of rAF intervals) and "Memory" (app wasm, JS heap), sampled only while the overlay is visible, starting after first paint. *[M4]*
- **2026-10-07** · The perf panel is a cached GPUI view refreshed at 4 Hz: fling frames replay its drawing. Work per frame is timed from the shell's render to a microtask queued there, which runs after GPUI's draw-and-present callback; the sparkline is drawn with quads, not paths (paths would link lyon into every app). *[M7 part A]*
- **2026-10-08** · The open panel publishes its bounds (`__seizaPerfOverlayRect`) so scripts can check a target is clear of it. *[M7 part C]*
- **2026-10-08** · The observation panel keeps clear of edge controls an app names (`seiza::perf::set_clearance`; Tycho: its padding, border, scrollbar, and a gap) rather than moving or docking. *[M7 part D]*
- **2026-10-08** · **One copy of the clock and marks: `seiza::marks`** (`now`, `mark`, `mark_at`, `mark_time`, `mark_after_current_task`). Readers take the last entry, since a retry sets marks again. +0.6 KiB brotli after the review (one `performance.mark` call, `startTime` off the returned entry). *[M7 part E]*
- **2026-10-09** · The panel's "Placeholder" row is filled at a later refresh when the paint mark arrives after the first frame: Element Timing entries reach their observer asynchronously, and one run of 20 in the baseline attempt missed the row (+1.0 KiB). A baseline recorded at load 2–4 (210.3 ms) was discarded: the user's open apps keep the machine there, so it measured them, not the code. *[M7 part G]*

## Static placeholder shell (`shared-web/`)

Whether an app has one is the app's decision (Tycho: yes, M7 part E); how it's built is shared.

- **2026-10-09** · **Placeholder font: an inlined, renamed Plex subset.** A subset of IBM Plex Sans Regular to printable ASCII plus `…`, made once with fonttools, renamed ("Seiza Placeholder"; the OFL reserves "Plex" and counts a subset as a modified version), committed as WOFF2 in `shared-web/fonts/`, and inlined as a base64 `@font-face` placed after the wasm and font preloads. A check fails if a placeholder uses a character outside that set. Set `font-synthesis: none` and match the weights GPUI actually draws (only Regular is loaded; `EmptyTitle` asks for `font_medium`). The screenshot check allows a tolerance, since GPUI rasterizes its own glyphs. Rejected: system fonts (a visible swap); sharing GPUI's font bytes through `FontFace` (the text waits for the 196 KiB face, giving back most of the throttled win); a subset of the exact placeholder text made at build time (needs fonttools in the build, and every copy edit regenerates it); a separate preloaded subset file (an extra request on a cold cache). *[M7 part G, design discussion]*
- **2026-10-09** · **The placeholder stays hidden until its font has loaded** (`document.fonts.load`, then `sz-ready`): Chrome sometimes painted it once laid out in the fallback font's metrics, text invisible (`font-display: block`), then re-laid it out, so the buttons and title bar jumped. No `-webkit-font-smoothing`/`text-rendering` overrides: they drew it thinner than GPUI on macOS. *[M7 part G, review]*
- **2026-10-09** · **The placeholder hands over by a 120 ms fade, not a cut.** `shared/` adds `sz-leaving` in the `gpui:first-frame` microtask (first frame already presented, so still no blank frame); the placeholder removes itself after. GPUI and the browser rasterize the same font differently (GPUI's text crisper, up to ~2 px lower at DPR 1) and round half-pixels in opposite directions, so a cut always jumped somewhere. Rejected: tuning offsets with a hard cut (residual 1–2 px text jumps at DPR 1, worse at some window sizes); a title-bar-only placeholder. *[M7 part G, review]*
- **2026-10-09** · **The placeholder copies GPUI's layout rounding:** line heights rounded to whole device pixels, half down, set per DPR by its inline script; the centered column nudged −0.03 px so exact x.5 positions round down as GPUI's do. Found by sampling GPUI's published button bounds across window sizes. Box edges then match exactly at DPR 1 and within one device px at DPR 2 (GPUI measures glyphs at the device scale). *[M7 part G, review]*

## Measurement protocol

- **2026-09-23** · Reference run at a true DPR 2: the perf suite hides `devicePixelContentBoxSize` so gpui-pre-web uses its Safari sizing path. *[M1]*
- **2026-09-23** · Perf and check runs serve `web/dist` brotli-compressed (quality 11, cached) through `vite preview`. *[M1]*
- **2026-09-23** · `just <app> check` is the budget gate: lint, release build, and a 10-run reference pass against `perf/baseline.json`. It fails when TTFP regresses more than 10% or the wasm (brotli) grows more than 15%, unless a row in `perf/budget-notes.md` accepts the size; `--write-baseline` retires older acceptances. *[Tycho M1]*
- **2026-10-10** · **Budgets apply to the local build only; production is recorded** (user's decision, repo-wide: root CLAUDE.md, measurement protocol). Production TTFP is split at wasm ready (`perf.ts --vs-local`, interleaved with the local build): before it is the network (connection, HTML, the 2.9 MB wasm over the link), zero for local preview, so "TTFP within 15% of local" couldn't hold on any remote host (15% of 195 ms is ~one TLS handshake); after it is the app's work, which matched local (+2.7% ref, +0.1% throttled). The table's load budgets (first rows, jump) likewise: a first page in production is ~8 sequential round trips, and a Gaia page 5.6 MB over the link. Optimizing production gets its own session, as a goal. *[M8]*
- **2026-10-13** · **An interleaved A/B is gated on its own spread, not the load average.** Each side's TTFP (max − min) / median must stay under 6% so the run can resolve a 3% difference; `placeholder --ab` fails a noisier run and records the load average before and after. On macOS the load average counts runnable threads, and an idle M1 with only a terminal and Claude Code up sat at 1.6–2; the run itself raises it. At load ~2 Tycho's two A/Bs of 2026-10-13 spread 3.9% and 4.4% with the sides 0.2–0.5% apart, while a run during heavy browsing (gpui-kit 0.7.3) spread 29%. A baseline write (`check --write-baseline`) still wants heavy apps closed: it's an absolute number, with nothing interleaved to cancel the load. *[Tycho M9]*

## Repo structure

- **2026-10-12** · **Four tiers: components, engines, utility apps, and the observatory.** A *component* is a generic UI library in the style of GPUI Kit's components (a view, a state entity, a delegate trait for its data), in `components/<name>/`, plainly named (`table`). An *engine* is a non-UI data layer that GPUI and React consumers share (`duckdb`), in `engines/<name>/` (`crate/` and/or `web/`). A *utility app* is a tool people use, star-named, on its own subdomain (Tycho). The *observatory* (`apps/observatory/`) compares components with React. Dependencies run one way: `shared/` ← components, engines ← apps. Grouped by role, not by product family, because a component will serve more than one app (a trace viewer would want a span table). Rejected: "showcase" for the apps, since Tycho is meant to grow into a real tool, not stay a demo. *[design discussion]* *Its example name was superseded 2026-10-14: the table component is `tall-table` (`seiza-tall-table`) and its DuckDB adapter the `tall-table` feature (`components/tall-table/docs/DECISIONS.md`, "Component API").* *Its React side was generalized 2026-10-14: the observatory compares components with DOM contenders, the first the TanStack contender ("Comparison protocol").*
- **2026-10-12** · Components and engines depend on neither `seiza` nor any app, so they stay publishable as crates. They report what happened through events; the host app turns those into panel rows and marks. *[design discussion; Tycho's `table/` and `engine/` call `seiza::perf`, `seiza::marks`, and `seiza::url` directly, which the extraction removes]*
- **2026-10-12** · An adapter between an engine and a component lives in the engine, behind an optional feature named for the component (as crates ship optional `serde` support): `seiza-duckdb`'s `table` feature will hold the Parquet `RowSource`. Components and engines stay peers, and the observatory's GPUI contender runs the same adapter Tycho does. Tycho's CSV source stays in Tycho (chunked ingest is the app's behavior), wrapping the adapter. *[design discussion]* *Its feature name was superseded 2026-10-14: the table component is `tall-table` (`seiza-tall-table`) and its DuckDB adapter the `tall-table` feature (`components/tall-table/docs/DECISIONS.md`, "Component API").*
- **2026-10-12** · A component's capabilities beyond its base (sorting, filtering, resizing, selection) are Cargo features, off by default. A utility app turns on what it needs and usually gets a feature first; the observatory adds a feature level only when both its sides are built. Each feature's cost (wasm brotli, frame cost, data cost) is measured against the base. Cargo unifies features across the packages in one build, so every wasm is built on its own (`-p <crate>`), and the observatory's base contender gets a size check. *[design discussion]*
- **2026-10-12** · Component and engine docs: `README.md` (for a crate user: API, features, limits, canvas tradeoffs), `CLAUDE.md` (rules, gotchas), `docs/DECISIONS.md`. No `PLAN.md`, `LESSONS.md`, or `perf/`: their work is a milestone in the app that drives it, measured and recorded there. Decisions and gotchas that move out of an app go to the new home whole, and the app's file keeps a pointer. *[design discussion]*
- **2026-10-13** · **A component or engine reads the page clock itself, and sets no mark from Rust.** It can't depend on `seiza`, whose `marks` module is the one copy for every other crate, so it reads `performance.now()` and its own JS side's marks with a few lines of its own and puts the times in its events; the host sets the marks (Tycho's `tycho:parquet-ready` from `seiza-duckdb`'s `ParquetReady`). Marks an engine's JS side sets are named for the engine (`duckdb:engine-ready`), not an app. Rejected: a clock the host passes in, which every event's time would then depend on the host wiring correctly. *[Tycho M9 part B]*

- **2026-10-14** · **The observatory only consumes components and engines.** It may ask one to expose what its metrics need, never to change how a utility app behaves; a change to a component's internals for it stays small, keeps today's defaults, and records its effect on each app that builds it. For the tall table that is one internal change (the two settle times become `Paging` fields), plus its fixtures and their tests; for the engine, the extension path as an option; for `seiza`, `shell` and `panel` features, on by default (*superseded 2026-10-16: the title bar left `seiza` for Tycho, and `seiza` has only `panel`*). Everything else the metrics need the table already publishes: `Filled`, `TallTableProbe` (`top`, `loaded`, `pending`), `ColumnProbe.budget`, the scrollbar's bounds. Replays drive input, so no scroll-only API is needed. *[design discussion]*

- **2026-10-16** · **The workspace's `seiza` entry has its defaults off;** a member that wants the panel names it (Tycho: `features = ["panel"]`). Cargo ignores a member's `default-features = false` while the workspace entry keeps defaults on, so this is the only way a host builds `seiza` without `panel`. *[observatory M2 part B]*
- **2026-10-16** · **What a second app needed moved out of Tycho:** publishing a control's bounds (`seiza::targets::publish`, from Tycho's `targets.rs`, which re-exports it), and from Tycho's perf scripts the first-draw probe (`shared-web/perf/harness.ts`, `firstDrawProbe`) and the placeholder's screenshot match (`shared-web/perf/placeholder-shots.ts`, which now takes what to hold back for each shot). Tycho's wasm moved within its build jitter (+134 B raw, 2,841.6 KiB brotli) and its checks pass (Tycho's `perf/results/2026-10-16-observatory-m2-b.md`). *[observatory M2 part B]*
- **2026-10-19** · **The apex site and Tycho share no UI.** Tycho, on its own subdomain, keeps its own look (gpui-kit's default theme, its own shell); the apex site (seiza.io: the landing page, the observatory's page, later sections) has its own theme, toggle, and components. Either can be redesigned without touching the other, so the site's tokens and components live in the site's own directory, never in `shared-web/`, which stays app-agnostic (bootstrap, Vite config, placeholder, fonts, perf harness). What they still share is the gpui-kit pin: a bump changes Tycho's and the GPUI contender's defaults together. *[design discussion, observatory M5 part 0]*
- **2026-10-19** · **The apex site's builds: a `site/` directory that the observatory's page joins.** `site/ui/` (`@seiza/site-ui`) is the site's shell, one source for every page on seiza.io: the top navbar, the theme toggle, a footer, the token file, the Tailwind setup, and the shadcn components. Its markup is React rendered to HTML at build time, so the shell never waits on JS and a page without React (the landing page, an Astro build later) renders the same components; its behaviors (the toggle, a mobile menu) are plain JS with thin React wrappers, and the `<head>` script applies the theme before first paint. A page's own navigation is the page's (the observatory's component list is in `apps/observatory/web/`, inside the shell). `site/landing/` (base `/`, no React shipped) and `site/worker/` (the one Worker for the apex, moved from `apps/observatory/worker/` with its range handler, which has no observatory-specific logic) come when the landing page ships; until then the observatory's Worker serves the apex and the seiza.io WAF rule stays `/observatory/` only. `site/ui/` exists before its second user, against "code starts in an app": the shell is site-wide by design, and its home outside `shared-web/` is already fixed (above), so building it in the observatory first would draw the same line later and move every import. URLs: `/observatory/<component>` per component (`/observatory/tall-table`, later `/observatory/trace-viewer`), each prerendered to its own HTML file (no catch-all route in the Worker, one prefix in the WAF rule); the contenders' bare pages at `/observatory/contenders/<component>/<stack>/` (both contenders' base is `/observatory/` today, so both `index.html`s would land on the page's URL); the engine and the data at `/observatory/duckdb/` and `/observatory/data/` as now; the site's font at a fixed `/fonts/` path every build shares, so it's cached across them. A contender is fetched only when its iframe is created, after the page's first paint; the page's bundle holds the shell, the observatory's UI, and a list of contenders (name, label, URL), with the metrics module loaded after first paint. The page gets budgets of its own (first-paint JS, first paint from paint timing, as the TanStack contender's). Estimated for the landing page on Fast 4G (not measured): ~0.7 s to first paint with its ~3–4 KiB of CSS inlined, against ~0.85 s for one site build (its shared CSS a file, one more round trip) and ~1.2 s for a landing page rendered by React in the browser; the font (69 KiB TTF at brotli 11, ~30 KiB as a Latin woff2) loads with `swap`, after paint. Rejected: one Vite build for the apex (the observatory's page away from its perf and budgets, every deploy redeploys the landing page); the landing page as a separate build with no shared package (the shell copied into each); Astro now (a second toolchain for what Vite and the prerender plugin already do; the shell still works under it later). *[design discussion, observatory M5 part 0]*

## Comparison protocol

- **2026-10-12** · **The observatory compares a component's base level, in a minimal GPUI host, with a 1:1 React equivalent.** Rejected: a utility app against a React clone of it. A utility app keeps growing, so the comparison would drift with every feature, and each feature would need a React twin. *[design discussion]* *Its DOM side was named 2026-10-14: the TanStack contender (below).*
- **2026-10-12** · **Only the UI differs, and the paging numbers say how.** Both sides use the same engine and the same SQL. The component's paging numbers (for the table: 1024-row pages, prefetch 2, 3 queries in flight, 64 MiB cache, no prefetch while a visible page loads) are the controlled variable; everything else is idiomatic to each stack. Each side decodes results in its own language, counted as UI cost. A shared scenario fixture (scroll and jump steps → the page requests they should make) runs against both caches, as a native Rust test and a TS test, which must request the same pages in the same order. Rejected: "the same limits, otherwise what a competent developer would do", which left the controlled variable to interpretation. *[design discussion]* *Its list of paging numbers was extended 2026-10-14 (the settle times, and the cache counted in Arrow IPC bytes), and the fixtures moved into the component (below).*
- **2026-10-12** · **Same scope at build time.** A feature level is a GPUI build and a React build with identical features; neither bundle carries code for a feature it doesn't have. The GPUI contender drops `seiza`'s title bar and observation panel (features to add; their bytes are measured when they are; *since 2026-10-16 the title bar is Tycho's, and the contender turns off `panel`*), so it carries no chrome the React side lacks. *[design discussion]*
- **2026-10-12** · **Placeholders on both sides, each idiomatic:** the GPUI side keeps the HTML placeholder shell; React prerenders its real first screen to static HTML. Rejected: one shared skeleton for both (first pixels a tie by construction, so the metric says nothing) and none on either (hides the GPUI side's actual answer to its first-paint cost). *[design discussion]*
- **2026-10-12** · **Three metrics, defined by meaning: first pixels, first usable UI, first rows painted.** Each side is checked its own way: GPUI's marks against its GPU calls (as `gpui:first-frame` is), the DOM's with Element Timing on the first real cell plus a presented-frame check. *[design discussion]* *Superseded 2026-10-14: per-use cost is the headline; first pixels is a footnote (below).*
- **2026-10-12** · **Contender pages are bare** (no site chrome) and publish the same marks, targets, and replay hooks (load, fling, jump to 90%). The observatory runs one at a time, since two in one tab share a main thread and a GPU, and draws the results itself, so no in-app panel costs either side frames. Playwright runs are cold; replays in a visitor's browser are labelled warm. The page shows where React wins (likely first pixels and bundle size). *[design discussion]* *Its page model was superseded 2026-10-14: one contender per same-origin iframe, readouts from one metrics module, the DOM side named for its stack (below). Bare pages and cold published runs stand.*

- **2026-10-14** · **Per-use cost is the observatory's headline; TTFP is scoped.** A data component is judged over a session of use, not at page load. Its costs split into one-time (download, boot, first pixels, bundle size) and per-use (open data, scroll, jump), and per-use costs dominate a data tool. The headline metrics: time to first usable, time to data, input to visible response, behavior under load, reach and correctness, and cost (memory, main-thread CPU, bytes), defined in the root `CLAUDE.md`, "Comparison protocol". First pixels and bundle size are footnotes, where the DOM side likely wins. Root rule 1 still gates every build, each contender's included, through its budgets. *[design discussion]*
- **2026-10-14** · **Contenders are named for their stack: GPUI | TanStack.** The first DOM contender is the TanStack contender: React, TanStack Virtual, its own CSS, and the Arrow library, with no Wasm of its own and no UI kit, sharing only the theme's CSS variables. - **2026-10-14** · **The DOM side scrolls natively,** with a spacer scaled under the browser's element-height cap and the content moving 1:1 with the input within a page, re-anchored at page boundaries. Native scrolling runs on the compositor, the DOM's strongest card; GPUI's scrolling waits on the main thread (gpui-pre-web 0.3.9's wheel listener is non-passive and prevents the default). At 30 px rows the asteroids are 47.0 M px tall, past Chromium's ~33.5 M px cap (~1.12 M rows) and Firefox's ~17.9 M px (~0.6 M rows), a 1.4× and 2.6× stretch; scaled evenly, one wheel row would move the DOM side 1.4 rows and the fling and "keeps up" metrics wouldn't compare. Rejected: a scroll model of its own, like the component's (main-thread scrolling on both sides: a strawman). The design is sized in a throwaway spike first, with TanStack over the full count against a moving window. *[design discussion]*
- **2026-10-14** · **Two more controlled paging numbers, and one way to count the cache.** Prefetch leans ahead until the rows rest 250 ms, and a scrollbar drag loads once the pointer rests 80 ms: both change which pages are requested, so both are controlled, and they become `Paging` fields (`scroll_settle`, `drag_settle`) with those defaults. The 64 MiB cache counts each page's Arrow IPC bytes: the component's `heap_bytes()` is already the IPC buffer's length (`engines/duckdb/crate/src/arrow.rs`), and a DOM contender counts the same buffer's `byteLength`, so both evict the same pages. *[design discussion]*
- **2026-10-14** · **Fixtures live in the component** (`components/<name>/fixtures/`), run by native tests inside the crate (its private `PageCache` and `fit_float` need no new public API), and by TS tests against each DOM contender, each with a negative control: paging scenarios (scroll, jump, rest, and drag steps → page requests in order), cell text, and the page SQL with the summary queries. Rejected: a live reveal slider (both contenders fight over the main thread and GPU, a visitor can't tell which side is live, and wide tables need the full width); one engine in the page shared by both (a `postMessage` relay in every page read on both sides, the page itself inside what's measured). *[design discussion]*

Per-frame work comes from the trace on both sides: `shared-web/perf/`'s `workRecorder` times only rAF callbacks that made GPU calls, and the DOM's style, layout, and paint run outside them. Script-made wheel events reach GPUI's listeners but never scroll a native scroller, so in-page replays drive the DOM side through its scroll position. - **2026-10-12** · **Utility apps on their own subdomains; the observatory at `seiza.io/observatory`.** Each utility app keeps its own Worker and custom domain (`tycho.seiza.io`).

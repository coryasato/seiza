# Tycho

> *Tycho Brahe catalogued a thousand stars in a lifetime. Tycho scrolls 25 million before your coffee cools.*

**Tycho** is a local-first data workbench in the browser. Drop a CSV or Parquet file, or click a sample, and scroll through every row instantly. The data is queried locally with DuckDB-Wasm and drawn by GPUI (via GPUI Kit) on a canvas with WebGPU, or WebGL2 where WebGPU isn't available. Nothing is uploaded.

The project's goal is to show that **WebAssembly + GPU-rendered UI builds heavy web apps better than the DOM**. Every claim needs a number on screen to back it up. Tycho is a utility app (root `CLAUDE.md`, "Tiers"): a tool people use, which grows features as it needs them. Its DuckDB layer is the repo's first engine, `engines/duckdb/`, and its table the first component, `components/tall-table/`.

## Tycho rules

These add to the repo-wide rules.

1. **Never block the shell on DuckDB.** Paint first. Start loading the engine from `shared/`'s post-paint callback. The UI must stay usable (and say "engine loading…") until DuckDB is ready.
2. **Keep the bridge narrow.** Three calls cross the Rust ↔ JS boundary (`registerFile`, `query`, `cancel`): the engine's rule, `engines/duckdb/CLAUDE.md`, rule 2. Get schema, row count, and metadata with SQL through `query`.
3. **Query per viewport.** The table fetches only the visible rows plus a buffer. The app never loads the whole result into memory.
4. **v1 scope is fixed.** No SQL editor, charts, sort/filter, or GROUP BY. If one of these seems necessary, stop and ask. (Column resizing, selection, and sorting are a researched-first goal after v1; see `PLAN.md`, "Long-term goals".)

## Stack

- **UI:** `shared/` (crate `seiza`) on the workspace's pinned `gpui-kit`.
- **Engine:** `engines/duckdb/` (`seiza-duckdb` in Rust, `@seiza/duckdb` in the host): DuckDB-Wasm in a Web Worker, self-hosted, loaded on the first bridge call, extensions pinned and loaded one `LOAD` at a time, HTTP files read by range only. Its rules, architecture, and DuckDB-Wasm gotchas are in `engines/duckdb/CLAUDE.md`. Tycho's side is `crate/src/engine.rs`: it starts the engine from the post-paint callback, turns its events into the panel's "Engine ready" and "Parquet ready" steps and the `tycho:parquet-ready` mark, and runs `?selftest` once the Parquet prefetch settles. (DuckDB's wasm bundles are over Cloudflare's 25 MiB static-asset limit; see Hosting.)
- **Hosting:** Cloudflare, one Worker (`worker/`) + R2, at **https://tycho.seiza.io** (never the account's default Workers subdomain, which names its owner: `workers_dev = false`). The Worker runs first for the page, `/assets/*`, and `/duckdb-ext/*`, and serves the quality-11 `<file>.br` that `just tycho deploy` writes beside each one (Cloudflare's own compression sent the app wasm as 3.7 MiB of zstd against 2.8 MiB; ~1 s on Fast 4G), with the page `no-transform` (Cloudflare's Web Analytics injects a beacon script otherwise). DuckDB's two wasm bundles are over the 25 MiB static-asset limit: R2 holds them under `assets/` (their `.br` fit in static assets). `/data/*` comes from R2 by range. The WAF guards it before the Worker runs (a path allowlist and a per-IP rate limit, set in the dashboard), and `just tycho pause` turns the samples off. Details in `docs/hosting.md`.
- **JS host:** `web/` (Vite, built on `shared-web/` and `@seiza/duckdb`) holds `index.html`, `src/main.ts` (creates the bridge, whose `refusal` turns the Worker's pause answer into the samples-paused message, and boots the wasm), and `vite.config.ts` (the engine's `duckdb()` plugin, the `/data/*` proxy, the placeholder). New logic goes in Rust unless it must touch a JS-only API.
- **Table:** `components/tall-table/` (`seiza-tall-table`): its scroll model, page cache, cells, tooltip, and rules are in `components/tall-table/CLAUDE.md`; its DuckDB source (the page SQL, `QueryResult` as a page, the Parquet summary) is `seiza-duckdb`'s `tall-table` feature. Tycho's side is `crate/src/table.rs`: the source (`Source::Parquet`, a `ParquetFile`; `Source::Csv`, the CSV's `Chunks`), the paging overrides from the URL, the panel's activity settings, and the table's events turned into marks and probes (`publish`). The `tycho:first-rows` and `tycho:viewport-filled` marks are set from `TallTableEvent::Filled`, which the table emits while the frame renders, so they land right after it's presented; set them nowhere else. Pages are 1024 rows (the component's default), read with a `file_row_number` filter from files written with 30,720-row groups (asteroids) or 61,440 (Gaia: the readahead makes both cost the same bytes per page, and half the row groups halve each page's setup).
- **Files from the device:** `crate/src/files.rs`. GPUI can't deliver browser drops (gpui-pre-web only `preventDefault`s them on its canvas), so Tycho listens on `window` and hops into GPUI through its foreground executor. The file dialog is a hidden `<input type=file>` clicked from a GPUI click handler. `files::sniff` checks `PAR1` at both ends before anything reaches the engine. Every open registers under its own SQL name (`file-<n>.parquet`), never the file's: `read_parquet` would glob a name like `x[1].parquet`. A new open replaces the current one: its task is dropped, its queries cancelled, and its table closed (`TallTableState::close`).
- **CSV:** `crate/src/csv.rs`. A CSV isn't queried where it lies (no index: a page at 90% of 1 GB took 5.1 s). It's cut into chunks at record boundaries (Rust scans quote-aware, in 1 MiB reads that yield between frames), each chunk a `File` slice registered through `registerFile`, and each copied into **its own table**, `CREATE TABLE tycho_csv.f<n>.c<k> AS SELECT * FROM read_csv(…, auto_detect = false, …)`, in an attached compressed in-memory database (`ATTACH ':memory:' AS tycho_csv (COMPRESS)`). The dialect and types come from `sniff_csv` on the first chunk (1 MiB), with RFC 4180 quoting forced (except for a TSV the sniffer found unquoted); the scanner, like DuckDB, opens a quoted field only at a field's start, so `12" pizza` is literal. A later chunk whose value doesn't fit a type widens that column to VARCHAR and goes again (the page SQL casts the earlier chunks). Chunks aim at 200 ms (`Sizer`, 1–8 MiB); the next chunk's end is scanned while DuckDB reads the current one. The table (`table::Source::Csv`, `csv::Chunks`) grows after every chunk. Rows are paged by `rowid`, except in a file with its own `rowid` column (which hides DuckDB's): its tables add `row_number() OVER () - 1 AS __tycho_row` (`csv::row_column`). Replacing a CSV that's still loading stops its task (`csv::Stop`: no further query is sent, the running one is cancelled), and the task drops its schema once that query answers; replacing one that's done or stopped drops the schema in `Workbench::close_current`. Every chunk stays registered with DuckDB for the session (unregistering is a fourth bridge call; a registration holds no bytes). Don't append chunks to one table or turn compression off without re-reading `docs/DECISIONS.md`, "Files and CSV".
- **Jump to row:** the header strip's input (`workbench.rs`; parsing in `jump.rs`, tested natively). Enter puts the row at the table's top (or as near as the file's end allows), highlights it, and gives the table focus; anything else gets an inline line beside the input and no scroll. Full-width digits and thousands separators are accepted. It's gpui-base's unstyled single-line `Input`, styled here, with the right-click menu built in `edit_menu` (+88 KiB brotli). Not gpui-kit's `Input`: that one links its textarea and code-editor engines too (+194 KiB; see `docs/DECISIONS.md`). The workbench restores lost focus to itself (`cx.on_focus_lost`), so its Cmd/Ctrl+G binding survives the table going away.
- **Errors and limits:** the engine failing to load or its worker stopping shows in the empty state with Retry (`engine::retry`); a stopped worker closes the open file, and the app hears of it at its next call. A Parquet page read that fails to read the file (`EngineError::is_read_failure`, `TallTableEvent::ReadFailed`) makes the workbench register the file again under a new SQL name (`<name>-r<n>.parquet`, at most every 5 s, doubling to a minute) and point the table at it (`table::read_from`, then `TallTableState::retry_failed`). Files over `limits.rs`'s sizes (Parquet 10 GB, CSV 6 GB) are refused before anything is read, and a CSV load stops at `csv::MEMORY_BUDGET` (1.5 GiB of DuckDB memory, checked after every chunk; above 1 GiB, a chunk of bytes that becomes no rows stops it too). The observation panel keeps clear of the table's scrollbars (`seiza::perf::set_clearance`).
- **Static placeholder shell:** `web/vite.config.ts` passes `shared-web`'s placeholder its empty state (`placeholderBody`): the heading, description, and "Engine loading…" as text, and the three buttons as gpui-kit skeletons with GPUI's widths (99, 233, 144 px, read from `__seizaTargets` with `?bench`). Change a label or a button in `render_empty` and the placeholder must change with it: `just tycho placeholder` fails until it matches (box edges per button, text per line, surfaces, at DPR 2 and 1). The skeletons exist because GPUI draws glyphs differently from the browser and labels visibly jumped at the swap; don't turn them back into text.
- **Arrow:** results cross the bridge as Arrow IPC stream bytes and are read by the engine's hand-rolled reader (`seiza_duckdb::arrow`). New column types go there, with a test.

## DuckDB-Wasm gotchas

They're the engine's: `engines/duckdb/CLAUDE.md`, "DuckDB-Wasm 1.32.0 gotchas" (cancelled reads that still occupy the worker, the ~1.39 MB readahead per page read, row groups that a `file_row_number` filter doesn't prune, `sniff_csv`, in-memory tables and their silent ceiling, file names a failed read breaks, and more). Check them before debugging the table, a CSV load, or a failed read.

## Perf script gotchas

- **Headless DPR 2 halves wheel deltas:** `mouse.wheel(0, 1000)` arrives as `deltaY` 500. Scroll through `shared-web/perf/`'s `wheel()`, which corrects for it.
- **WebKit can deliver a scripted press before hover updates,** and GPUI fires a press only on a hovered element. Wait two frames after moving to a control (`hoverSettles` in `table.ts`).
- **Canvas controls have no DOM.** The app publishes their bounds to `globalThis.__seizaTargets` (`crate/src/targets.rs`), and scripts click through `shared-web/perf/`'s `clickTarget` and `targetRect`.
- **The open observation panel swallows clicks under it** (the window's lower right: at 1440×900, about the right 400 px from y ≈ 340 down). Its bounds are `globalThis.__seizaPerfOverlayRect` (`[x, y, w, h]`, gone while hidden). Click only targets clear of it (check, as `perf/jump.ts` does), or hide it first (`setPanel` in `table.ts`), and have every check confirm the result, not the click: a click on the panel fails silently. It keeps clear of the table's scrollbars (at 1440×900: x 1015–1399, the vertical track at x 1407), but not of the cells, nor of anything the empty state lays out wide (Retry once sat under it after a long status line).
- **Jump to row from a script:** Cmd/Ctrl+G focuses the input with its text selected (or click `jump-input`), type, Enter. `__tychoTable.marked` is the row it landed on (0-based); `__tychoWorkbench` has `jumpText`, `jumpRefusal` (the inline line, bounds `jump-refusal`), and `focused` (`jump`, `table`, `workbench`, or null).
- **Dropping a file from a script:** set it by path on a scratch `<input type=file>` (Chromium reads it from disk, no copy), then dispatch `dragenter`/`dragover`/`drop` with a `DataTransfer` holding it (`perf/harness.ts`, `dropFile()`). What the workbench shows (state, file, rows, notice, and a CSV's `ingest` state, `readBytes`, `chunks`) is in `globalThis.__tychoWorkbench` with `?perf` or `?bench`; each frame showing a CSV's count grow marks `tycho:csv-rows`, and the one showing it done `tycho:csv-done`.
- **The perf panel publishes at its refresh (~4 Hz), not every frame:** `globalThis.__seizaPerfOverlay` (rows) and `__seizaPerfOverlayAt` (when they were taken; the live rows cover the 2 s before it). Compare a live row against your own measurement over that window (`perf/panel.ts`). Load steps publish as rows under their own names ("Engine ready", "Sample → schema", …).
- **Per-frame work time, measured outside the app:** `shared-web/perf/`'s `workRecorder` (an init script) times every rAF callback that made a GPU call. It matched the panel within 5% at p50 and p95. The panel times from the shell's render to a microtask after the present.
- **A/B against HEAD in a worktree, but not on a shared `target/`.** The justfile reads the wasm from the repo's `target/`, so a worktree build pointed there overwrote the main tree's fingerprints, and the next `just tycho build` called the main tree fresh and shipped HEAD's wasm (same hash). Give the worktree its own `target/`, or `cargo clean -p tycho -p seiza --release --target wasm32-unknown-unknown` after it, and check the built wasm's hash differs from HEAD's. Run each A/B side's `perf.ts` asynchronously when the same process hosts the preview servers: `execFileSync` blocks the servers and every navigation times out.
- **The placeholder hides the canvas until the first frame and fades out over 120 ms after it.** A script that screenshots the app or reads canvas pixels must wait for `#seiza-placeholder` to be gone, not just for `gpui:first-frame` (`placeholder-shots.ts`, `placeholder.ts`). Its checks run with `reducedMotion: 'reduce'`, which stops the skeleton pulse and the fade.
- **Headless DPR 2 hides what a DPR 1 display shows.** GPUI and the browser round half-pixels in opposite directions; at DPR 2 that's half a CSS pixel, at DPR 1 a whole one. The placeholder's jump was invisible in every DPR 2 check and plain on a DPR 1 screen. `placeholder-shots.ts`'s `shoot` takes `{ dpr }`.
- **Budgets come from `perf/budgets.json`** (`limits('table', [...])` in `perf/harness.ts`); change a limit there, never in a script, and `just tycho report` shows it in the docs. **Label a before-run `<…>-before…`, an A/B `<…>-ab` or `<…>-ab-<detail>`, and a negative control `<…>-control…`:** the report skips those (`budgets.json`'s `exclude`), and otherwise takes the newest file holding a metric's path, so a control's numbers would become the docs' "Now".
- **Check the machine before calling a slowdown a regression.** `just tycho paging` (raw queries through the bridge, no table code) is a quick control: if it's slower by the same proportion, it's load.

`just tycho deploy` needs `wrangler login` (one account: the account ID comes from it, or CLOUDFLARE_ACCOUNT_ID) and `TYCHO_R2_PROFILE`, an AWS CLI profile holding an R2 API token's S3 keys; neither the profile's keys nor the account ID go in the repo. `table`, `jump`, and `csv` take `--url` like `cold`; `panel` doesn't (its "Read" check counts bytes at the local server).

`just tycho data` needs network once (the JPL API, ~2.5 min; Gaia: AWS Open Data, ~50 min, and the ESA archive's count for the cut); after that it reuses `data/raw/`. `dev`, `preview`, `sample`, `table`, and `worker-check` need the local R2 it fills. `wrangler dev` keeps it under `worker/.wrangler/state/` (gitignored). Vite's dev and preview servers proxy `/data/*` to `wrangler dev` on port 8787, so the page stays same-origin under COEP.

`?bench` in the URL exposes the bridge as `globalThis.__tychoBridge` for the perf scripts; `?page=`, `?prefetch=`, and `?budget_mib=` override the table's paging (`crate/src/table.rs`, `paging`). With `?perf` or `?bench`, the table publishes what it shows to `globalThis.__tychoTable` and marks `tycho:viewport-filled` after each frame that fills the viewport; `tycho:first-rows` (the overlay's "first rows") is always marked.

With `?cells` too, every drawn cell's exact and shown text goes to `globalThis.__tychoCells` each frame (never in perf runs); with `?perf` or `?bench`, where the cells are is `globalThis.__tychoTableLayout` (republished only when the layout changes; the scroll position is `__tychoTable.top` and `.scrollX`) and the shown tooltip's text is `__tychoTable.tooltip`.

`?selftest` in the URL runs the engine self-test once DuckDB is ready; results show in the panel and in `globalThis.__tychoSelftest`. The perf panel ("Observation panel": load waterfall, frame interval and work per frame, memory, bytes read, rows/s, cache hits, pages) is on with `?perf` in the URL; toggle it with the title bar's button or Cmd/Ctrl+Shift+P. With `?bench`, the app's `WebAssembly.Memory` is `globalThis.__tychoWasmMemory`. (Firefox on macOS keeps Cmd+Shift+P for a private window; use Ctrl+Shift+P or `?perf` there.) `just tycho perf`, `cold`, and `check` serve `web/dist` through `vite preview`, brotli-compressed like production. `check` builds first; before `perf` or `cold`, run `just tycho build` yourself.

`web/pkg/` is generated by `just tycho wasm` (gitignored). After changing Rust, rerun `just tycho dev` (or `just tycho wasm` while Vite keeps running) and reload the page.

# Tycho

> *Tycho Brahe catalogued a thousand stars in a lifetime. Tycho scrolls 25 million before your coffee cools.*

**Tycho** is a local-first data workbench in the browser. Drop a CSV or Parquet file, or click a sample, and scroll through every row instantly. The data is queried locally with DuckDB-Wasm and drawn by GPUI (via GPUI Kit) on a canvas with WebGPU, or WebGL2 where WebGPU isn't available. Nothing is uploaded.

The project's goal is to show that **WebAssembly + GPU-rendered UI builds heavy web apps better than the DOM**. Every claim needs a number on screen to back it up.

This is Tycho's context. Milestones, datasets, hosting details, decisions, and measurements live in `PLAN.md`. ## Tycho rules

These add to the repo-wide rules.

1. **Never block the shell on DuckDB.** Paint first. Start loading the engine from `shared/`'s post-paint callback. The UI must stay usable (and say "engine loading…") until DuckDB is ready.
2. **Keep the bridge narrow.** Only three calls cross the Rust ↔ JS boundary:
   - `register_file(name, source) -> FileInfo`, where `source` is a dropped `File` or an HTTP URL
   - `query(sql, request_id) -> ArrowIpcBytes`
   - `cancel(request_id)`

   Get schema, row count, and metadata with SQL through `query`. Don't add a fourth bridge call without writing down the decision in this file and in `PLAN.md`'s decisions log. The engine loads on the first call; the post-paint callback's warm-up query (`SELECT 42 AS x`) is what starts it. A load that fails is forgotten, and so is an engine whose worker stopped once a call has been rejected with `EngineStopped`; the next call starts a new one. Rust's `Engine` refuses calls while it's down (`EngineStatus::Failed`/`Stopped`), so that next call is always Retry's warm-up, and it watches every call's answer for `EngineStopped` even when nobody awaits it (`Engine::watch`). A failed engine-chunk import is retried under `?retry=<n>`: Chromium remembers a failed dynamic import (M7). `FileInfo` carries `bytesRead`, a live counter (a `SharedArrayBuffer` that DuckDB's worker wrapper adds to as it reads; Rust reads it with `Atomics.load`), so the panel's "read X of Y" isn't a fourth call (M7).
3. **Query per viewport.** The table fetches only the visible rows plus a buffer. The app never loads the whole result into memory.
4. **v1 scope is fixed.** No SQL editor, charts, sort/filter, or GROUP BY. If one of these seems necessary, stop and ask. (Column resizing, selection, and sorting are a researched-first goal after M8; see `PLAN.md`, "Long-term goals".)

## Stack

- **UI:** `shared/` (crate `seiza`) on the workspace's pinned `gpui-kit`.
- **Engine:** `@duckdb/duckdb-wasm`, pinned. Runs in a Web Worker. **Self-host** the DuckDB bundles and extensions from our own origin, not jsDelivr, so they work under COEP and first-load timing doesn't depend on a third-party CDN. (Check the bundle sizes against Cloudflare's 25 MiB static-asset limit; see Hosting.) Extensions are pinned by version and SHA-256 in `web/duckdb-extensions.json`; bump them with DuckDB-Wasm. Autoload is off: Rust loads Parquet with one explicit `LOAD` at a time (`Engine::load_parquet`), which every Parquet query waits for; new extensions need the same. HTTP files are read by range only (`engine.ts`, `RANGE_READS_ONLY`): with DuckDB-Wasm's defaults, a URL is downloaded whole.
- **Hosting:** Cloudflare, one Worker (`worker/`) + R2 for data. Details in `PLAN.md`.
- **JS host:** `web/` (Vite, built on `shared-web/`) holds `index.html`, `bridge.ts` (the three calls; loads nothing until the first), and `engine.ts` (DuckDB-Wasm: bundle choice, worker, queries, cancel, and the read counters: the worker's wrapper counts DuckDB's sync XHRs and `FileReaderSync` reads per registered file). New logic goes in Rust unless it must touch DuckDB's JS API.
- **Table:** `crate/src/table/`, not gpui-kit's `DataTable`, whose `uniform_list` places rows in f32 pixels and loses precision past ~16 M px (4 px steps at the asteroids' 47 M px, 64 px at Gaia's 25 M rows). The scroll position is an f64 row index (`scroll.rs`); `pages.rs` is the page cache (tested natively); `mod.rs` draws only the visible rows and columns and owns the scrollbars, wheel, and keys. Pages are 1024 rows, read with a `file_row_number` filter (`dataset::page_sql`) from files written with 30,720-row groups (asteroids) or 61,440 (Gaia, M7: the readahead below makes both cost the same bytes per page, and half the row groups halve each page's setup); prefetch 2 pages, 3 queries in flight, 64 MiB cache. No prefetch page starts while a visible page is loading (`PageCache::plan`; M5). Don't swap in `DataTable` without re-reading M4 in `PLAN.md`.
- **Files from the device:** `crate/src/files.rs`. GPUI can't deliver browser drops (gpui-pre-web only `preventDefault`s them on its canvas), so Tycho listens on `window` and hops into GPUI through its foreground executor. The file dialog is a hidden `<input type=file>` clicked from a GPUI click handler. `files::sniff` checks `PAR1` at both ends before anything reaches the engine. Every open registers under its own SQL name (`file-<n>.parquet`), never the file's: `read_parquet` would glob a name like `x[1].parquet`. A new open replaces the current one: its task is dropped, its queries cancelled, and its table closed (`RowTable::close`).
- **CSV:** `crate/src/csv.rs` (M6). A CSV isn't queried where it lies (no index: a page at 90% of 1 GB took 5.1 s). It's cut into chunks at record boundaries (Rust scans quote-aware, in 1 MiB reads that yield between frames), each chunk a `File` slice registered through `registerFile`, and each copied into **its own table**, `CREATE TABLE tycho_csv.f<n>.c<k> AS SELECT * FROM read_csv(…, auto_detect = false, …)`, in an attached compressed in-memory database (`ATTACH ':memory:' AS tycho_csv (COMPRESS)`). The dialect and types come from `sniff_csv` on the first chunk (1 MiB), with RFC 4180 quoting forced (except for a TSV the sniffer found unquoted); the scanner, like DuckDB, opens a quoted field only at a field's start, so `12" pizza` is literal. A later chunk whose value doesn't fit a type widens that column to VARCHAR and goes again (the page SQL casts the earlier chunks). Chunks aim at 200 ms (`Sizer`, 1–8 MiB); the next chunk's end is scanned while DuckDB reads the current one. The table (`RowSource::Csv`, `csv::Chunks`) grows after every chunk. Rows are paged by `rowid`, except in a file with its own `rowid` column (which hides DuckDB's): its tables add `row_number() OVER () - 1 AS __tycho_row` (`csv::row_column`). Replacing a CSV that's still loading stops its task (`csv::Stop`: no further query is sent, the running one is cancelled), and the task drops its schema once that query answers; replacing one that's done or stopped drops the schema in `Workbench::close_current`. Every chunk stays registered with DuckDB for the session (unregistering is a fourth bridge call; a registration holds no bytes). Don't append chunks to one table or turn compression off without re-reading M6 in `PLAN.md`.
- **Jump to row:** the header strip's input (`workbench.rs`; parsing in `jump.rs`, tested natively), M7. Enter puts the row at the table's top (or as near as the file's end allows), highlights it, and gives the table focus; anything else gets an inline line beside the input and no scroll. Full-width digits and thousands separators are accepted. It's gpui-base's unstyled single-line `Input`, styled here, with the right-click menu built in `edit_menu` (+88 KiB brotli). Not gpui-kit's `Input`: that one links its textarea and code-editor engines too (+194 KiB; see `PLAN.md`). The workbench restores lost focus to itself (`cx.on_focus_lost`), so its Cmd/Ctrl+G binding survives the table going away.
- **Errors and limits (M7):** the engine failing to load or its worker stopping shows in the empty state with Retry (`engine::retry`); a stopped worker closes the open file, and the app hears of it at its next call. A Parquet page read that fails to read the file (`EngineError::is_read_failure`, `TableEvent::ReadFailed`) makes the workbench register the file again under a new SQL name (`<name>-r<n>.parquet`, at most every 5 s, doubling to a minute) and point the table at it (`RowTable::read_from`). Files over `limits.rs`'s sizes (Parquet 10 GB, CSV 6 GB) are refused before anything is read, and a CSV load stops at `csv::MEMORY_BUDGET` (1.5 GiB of DuckDB memory, checked after every chunk; above 1 GiB, a chunk of bytes that becomes no rows stops it too). The observation panel keeps clear of the table's scrollbars (`seiza::perf::set_clearance`).
- **Arrow:** results cross the bridge as Arrow IPC stream bytes and are read by `crate/src/arrow.rs`, a hand-rolled reader (arrow-rs cost +127 KiB brotli; see `PLAN.md`). New column types go there, with a test.

## DuckDB-Wasm 1.32.0 gotchas (check before debugging)

- **A started page read can't be cancelled.** DuckDB's worker reads over HTTP with synchronous XHRs, and `cancel` lands between query slices. A cancelled query still occupies the worker until it answers. So the page cache counts cancelled requests as in flight until they answer (`PageCache::draining`), and a scrollbar drag loads only when the pointer rests (`DRAG_SETTLE`).
- **Every page read costs at least ~1.39 MB.** The HTTP readahead (`WebFileSystem`'s `ReadAheadBuffer`) reads 16 KB, 64 KB, 256 KB, 1 MB, then 4 MB and 16 MB while the reads stay sequential, so a page read stops at the step that covers its row group: 1.39 MB for the asteroids' 0.7 MB groups, 5.59 MB for Gaia's 3.8 MB groups (at 30,720 or 61,440 rows), 22.4 MB from 122,880 (M7). No `db.open` option or Parquet setting changes it (`useDirectIO` and `disable_parquet_prefetching` were tested). On Fast 4G that's four round trips, ~2.1 s per page for the asteroids. It's also why "first rows under 2% of the file" can't hold for the 38 MB sample.
- **Two failing loads of one extension at once crash the worker** ("table index is out of bounds"), with no worker `error` event, and every later query hangs. That's why autoload is off and `Engine::load_parquet` runs one attempt at a time.
- **With default settings, a URL is downloaded whole** (`RANGE_READS_ONLY` in `engine.ts`; M3). The Worker must answer a ranged `HEAD` with 206.
- **A `file_row_number` filter doesn't prune row groups.** DuckDB 1.4 sets up every row group's column readers for each page query, so a page costs ~0.4 ms per row group (19 columns) in the worker, whatever its size: 50 ms on the 52-group sample, ~540 ms on a 1 GB file with 1,378 groups, ~120 ms on the same file at 345 groups. Native DuckDB 1.4.5 scales the same way. Measured in M5. Gaia's 11 columns cost ~0.16–0.2 ms a group: 166 ms a page at 817 groups, 68 ms at 409 (its 61,440-row groups), 34 ms at 205 (M7).
- **The Parquet metadata cache is off by default, and `SET` is per connection.** Every query has its own connection, so the cache is set with `SET GLOBAL parquet_metadata_cache = true`, right after `LOAD parquet` (`Engine::load_parquet`). Without it, every query re-parses the footer (~165 ms at 1,378 row groups).
- **`sniff_csv` reads only the file's head** (20,480 rows). With no quotes in it, it picks *no* quote, and a quoted comma or newline later breaks the parse; its types can be wrong later too (the asteroids' `pdes` is numeric for 895,910 rows). `csv.rs` forces `"` and widens on a conversion error, whose message names the column (`Error when converting column "pdes"`). Its `Quote`/`Escape`/`Comment` fields read as the text `(empty)`, and `NewLineDelimiter` is escaped text (`\n`).
- **Appending to one growing table stalls.** INSERTs of 4–8 MiB chunks into one table took 200–600 ms every few chunks, inside DuckDB (not parsing, not GC, not memory growth; M6), and small appends cost memory (1.2 GB for 1 GB at 4 MiB). One `CREATE TABLE AS` per chunk never passed ~255 ms.
- **In-memory tables aren't compressed** unless the database is attached with `(COMPRESS)`: 1 GB of CSV took 2.1 GiB of DuckDB memory in plain per-chunk tables, 300 MiB compressed.
- **A query sent during a `CREATE TABLE … AS` waits for it**, rather than round-robining: a page read during a CSV load waits up to one chunk (so chunks aim at 200 ms).
- **Queries run round-robin.** DuckDB-Wasm runs one query slice at a time across all pending queries, so two 500 ms queries both finish at ~1 s. That's why prefetch waits for the visible pages.
- **A failed HTTP range read breaks that file's name for good.** After one read fails (the network dropped), every later read of those bytes under that SQL name fails with "TProtocolException: Invalid data", online or not, even after registering the URL again under the same name, and with `enable_external_file_cache` off. Registering it under a new name reads fine (M7). That's why the workbench re-registers under `<name>-r<n>.parquet`.
- **Past ~2.1 GiB of in-memory tables, `CREATE TABLE … AS` stores nothing and says nothing.** `memory_limit` is 3.1 GiB, but at ~2.1 GiB of tables (an 8.6 GB CSV, chunk 848 of 988) each chunk's table came back empty with a normal answer, until one finally errored (or never did). Hence `csv::MEMORY_BUDGET` and the empty-chunk check (M7).
- **Nothing frees a parsed Parquet footer.** `db.dropFile` after the next open, and `SET GLOBAL parquet_metadata_cache = false` then `true`, left DuckDB's memory exactly where keeping the file did: +2.2 MiB per open of a 1,378-group file (~16 MiB per open across the tab; `perf/results/2026-10-08-m7-footers.json`). A documented cost; files stay registered.
- **The worker takes messages in order, so cancelled reads can't leak into the next open.** A cancelled query's queued poll still runs (and reads) before the next open's register message, so its bytes land on the old file's read counter, never the new one, even when the new open reuses the counter's key (same URL, or the same dropped file). Waiting for them before an open changed neither "Read" nor first rows (M7 part D, with a negative control).
- **A stopped worker rejects only the calls made after it stopped.** With nothing in flight, the app learns at its next query (a scroll, an open). Scripts that kill the worker (`page.workers()`, throw in a `setTimeout`) must then make a call, e.g. press End.
- **Playwright doesn't see DuckDB's requests** (sync XHRs inside its worker). Count `/data/` bytes at the server: `perf/harness.ts`'s counting proxy.

## Perf script gotchas

- **Headless DPR 2 halves wheel deltas:** `mouse.wheel(0, 1000)` arrives as `deltaY` 500. Scroll through `harness.ts`'s `wheel()`, which corrects for it.
- **WebKit can deliver a scripted press before hover updates,** and GPUI fires a press only on a hovered element. Wait two frames after moving to a control (`hoverSettles` in `table.ts`).
- **Canvas controls have no DOM.** The app publishes their bounds to `globalThis.__tychoTargets` (`crate/src/targets.rs`), and scripts click through `harness.ts`'s `clickTarget` and `targetRect`.
- **The open observation panel swallows clicks under it** (the window's lower right: at 1440×900, about the right 400 px from y ≈ 340 down). Its bounds are `globalThis.__seizaPerfOverlayRect` (`[x, y, w, h]`, gone while hidden). Click only targets clear of it (check, as `perf/jump.ts` does), or hide it first (`setPanel` in `table.ts`), and have every check confirm the result, not the click: a click on the panel fails silently. Since M7 part D it keeps clear of the table's scrollbars (at 1440×900: x 1015–1399, the vertical track at x 1407), but not of the cells, nor of anything the empty state lays out wide (Retry once sat under it after a long status line).
- **Jump to row from a script:** Cmd/Ctrl+G focuses the input with its text selected (or click `jump-input`), type, Enter. `__tychoTable.marked` is the row it landed on (0-based); `__tychoWorkbench` has `jumpText`, `jumpRefusal` (the inline line, bounds `jump-refusal`), and `focused` (`jump`, `table`, `workbench`, or null).
- **Dropping a file from a script:** set it by path on a scratch `<input type=file>` (Chromium reads it from disk, no copy), then dispatch `dragenter`/`dragover`/`drop` with a `DataTransfer` holding it (`perf/harness.ts`, `dropFile()`). What the workbench shows (state, file, rows, notice, and a CSV's `ingest` state, `readBytes`, `chunks`) is in `globalThis.__tychoWorkbench` with `?perf` or `?bench`; each frame showing a CSV's count grow marks `tycho:csv-rows`, and the one showing it done `tycho:csv-done`.
- **The perf panel publishes at its refresh (~4 Hz), not every frame:** `globalThis.__seizaPerfOverlay` (rows) and `__seizaPerfOverlayAt` (when they were taken; the live rows cover the 2 s before it). Compare a live row against your own measurement over that window (`perf/panel.ts`). Load steps publish as rows under their own names ("Engine ready", "Sample → schema", …).
- **Per-frame work time, measured outside the app:** `harness.ts`'s `workRecorder` (an init script) times every rAF callback that made a GPU call. It matched the panel within 5% at p50 and p95 (M7). The panel times from the shell's render to a microtask after the present.
- **Check the machine before calling a slowdown a regression.** `just tycho paging` (raw queries through the bridge, no table code) is a quick control: if it's slower by the same proportion, it's load.

`?bench` in the URL exposes the bridge as `globalThis.__tychoBridge` for the perf scripts; `?page=`, `?prefetch=`, and `?budget_mib=` override the table's paging (`crate/src/table/mod.rs`, `Paging`). `?selftest` in the URL runs the engine self-test once DuckDB is ready; results show in the panel and in `globalThis.__tychoSelftest`. The perf panel ("Observation panel": load waterfall, frame interval and work per frame, memory, bytes read, rows/s, cache hits, pages) is on with `?perf` in the URL; toggle it with the title bar's button or Cmd/Ctrl+Shift+P. With `?bench`, the app's `WebAssembly.Memory` is `globalThis.__tychoWasmMemory`. `web/pkg/` is generated by `just tycho wasm` (gitignored). After changing Rust, rerun `just tycho dev` (or `just tycho wasm` while Vite keeps running) and reload the page.

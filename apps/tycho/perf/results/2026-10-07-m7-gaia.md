# M7 part B: the Gaia sample (2026-10-07)

**Machine:** local (Apple M1, Darwin 25.6.0). **Machine load:** 2–4 throughout.

**Files**
- `2026-10-07-m7-paging-gaia.json`: `just tycho paging --dataset gaia --strategies B --runs 5`. Raw page queries through the bridge (no table code) on the sample at four row-group sizes.
- `2026-10-07-m7-table-gaia.json`: `just tycho table --sample gaia --memory`. The M4 checks on Gaia, 10 reference + 10 throttled runs, plus two full memory passes.
- `2026-10-08-m7-browsers-gaia.json`, `2026-10-08-m7-browsers-asteroids.json`: `just tycho table --sample <sample> --browsers-only`, the table check in Chromium, Firefox, and WebKit.
- `2026-10-08-m7-sweep-gaia.json`: `just tycho table --sample gaia --sweep`. Page size {256, 1024, 4096} × prefetch {1, 2, 4}, 5 reference runs each. (The scripts date files in UTC; it ran the evening of 2026-10-07 local time.)

## The data

`just tycho data gaia` reads Gaia DR3's HATS Parquet on AWS Open Data (`s3://stpubdata/gaia/gaia_dr3/public/hats/gaia`, 2,016 partitions, 1,812,731,847 rows) with native DuckDB, 8 partitions at a time. It keeps the 10 columns of every star with G < 15 in one extract per partition (`data/raw/gaia/`, 2.3 GB). The fetch took **47.6 min**. The magnitude filter can't skip data: each partition is sorted by `source_id` (sky position), so every row group holds every magnitude, and the fetch reads all 1.8 billion rows of the ten columns (~45 bytes a row, ~90 GB).

| | Rows |
|---|---|
| Extracts, G < 15 | 36,935,463 (36,909,335 distinct `source_id`, the ESA archive's count) |
| Sample, G < 14.5 | **25,067,889** (the archive's count, checked by prep) |
| Duplicates dropped at G < 14.5 | 17,842: identical copies within two partitions (Norder=3/Npix=29, Norder=4/Npix=115), never across partitions |

The archive counts came from the ESA Gaia archive's TAP service (`SELECT COUNT(*) FROM gaiadr3.gaia_source WHERE phot_g_mean_mag < X`): 7.4 M at 13, 11.2 M at 13.5, 16.8 M at 14, **25.1 M at 14.5**, 36.9 M at 15. Prep asks once per cut and keeps the answer in `data/raw/gaia/archive-counts.json`.

`gaia-dr3-bright.parquet`: 11 columns (`distance_pc` = 1000 / parallax where parallax > 0), ZSTD, sorted by `source_id`, **61,440-row groups (409)**, 1,572,736,231 bytes (~63 bytes a row). SHA-256 in `data/MANIFEST.json`.

## Row-group size (strategy B, medians of 5)

| Row group | Groups | File | First page | Next page | Jump to 90% | Bytes per page read |
|---|---|---|---|---|---|---|
| 30,720 | 817 | 1,554.5 MB | 233.9 ms | 165.8 ms | 193.1 ms | 5,586,944 |
| **61,440** | **409** | 1,572.7 MB | **135.7 ms** | **67.5 ms** | **103.1 ms** | **5,586,944** |
| 122,880 | 205 | 1,572.6 MB | 176.8 ms | 34.2 ms | 134.5 ms | 22,364,160 |
| 245,760 | 103 | 1,572.5 MB | 182.5 ms | 36.0 ms | 142.2 ms | 22,364,160 |

"Next page" reads no bytes (it's in the readahead buffer), so it is the per-page CPU cost alone: ~0.17–0.2 ms per row group with 11 columns, as M5 found (~0.4 ms with 19).

The bytes are exact sums of DuckDB-Wasm's readahead steps: 16 KiB + 64 KiB + 256 KiB + 1 MiB + 4 MiB = 5,586,944, and + 16 MiB = 22,364,160. The buffer grows ×4 while reads stay sequential, so a page read stops at the step that covers its row group's column chunks. The asteroids' 0.7 MB groups stop at 1 MiB (1.39 MB, M4). Gaia's groups are 1.9 MB at 30,720 rows and 3.8 MB at 61,440, so both stop at 4 MiB. From 122,880 (7.7 MB) they need the 16 MiB step.

**Decision: 61,440.** It reads the same bytes as 30,720 at less than half the CPU, and a quarter of the bytes of 122,880, whose lower CPU (34 ms) doesn't pay for 22 MB per jump. Getting Gaia under the 1 MiB step would need ≤ ~16,000-row groups: ~1,600 groups, ~300 ms of setup per page.

## Cell-string cache: not needed

A throwaway build timed the formatting alone: every visible loaded cell's `Value::to_string`, in its own loop before the draw, per render. Steady scroll at the top of the file, one run each:

| | Cells | Characters | Format p50 / p95 | Work p50 / p95 |
|---|---|---|---|---|
| Asteroids, reference | 230 | 1,528 | 0.045 / 0.075 ms | 11.75 / 13.69 ms |
| Gaia, reference | 264 | 3,732 | 0.075 / 0.100 ms | 13.10 / 15.03 ms |

Formatting is 0.4–0.6% of a draw, so a cache could save at most ~0.1 ms per frame. Gaia's cells hold 2.4× the characters for +11% work. The cost of loaded rows over placeholder rows (12.6 vs 5.7 ms) is in laying out and drawing the text, not in making the strings. (Throttled format times aren't meaningful: CDP's CPU throttling pauses the thread in slices, so a 0.05 ms loop reads 0.04 ms at p50 and 0.9 at p95.)

## A script bug part A's panel caused

`perf/table.ts`'s steady scroll was meant to start at row 400,000 with a thumb drag right after the fling. Since part A, the fling leaves the thumb at the bottom of its track, under the open observation panel. The press landed on the panel, the drag never started, and the "steady scroll" wheeled against the last row. That's why the first Gaia runs read 20–23 ms of work per draw. (That no-op wheel still redraws, at ~22 ms a draw on both samples; it goes to part D.) Its memory pass hit the same wall: pass 2 starts by pressing the thumb at the bottom, and every step then waited out a 5 s timeout (the first attempt was stopped after an hour). Now the steady step presses Home before the drag and fails unless it starts within 1% of row 400,000, and the memory passes drag with the panel hidden. A visitor has the same problem: with the panel open, the thumb can't be grabbed at the bottom (part D).

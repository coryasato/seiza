## Why not gpui-kit's `DataTable`

`DataTable` scrolls with GPUI's `uniform_list`, which places rows at `item_height * index + scroll_offset` in f32 pixels. At 1.5 M rows × 30 px that's 47 M px, where f32 steps by 4 px: rows would jitter by ±2 px near the end and wheel deltas under 2 px would vanish. At Gaia's 25 M rows (M7) the step is 64 px. The DOM has a similar ceiling (Chromium caps element heights at ~33.5 M px).

`crate/src/table/` keeps the scroll position as an f64 row index (exact to 2^53 rows), draws only the visible rows and columns, and owns both scrollbars (track click, thumb drag), the wheel, and the keys (arrows, Page Up/Down, Space, Home/End, Cmd+↑/↓). A unit test scrolls a 25 M-row table by 1 px at the bottom and checks the offset to 1e-6 rows. The cost: no column resizing, selection, or sorting (sorting is out of v1 scope anyway), and most of M4's +16.3 KiB brotli.

## Paging strategy and row-group size

`just tycho paging`, 5 runs each, a new browser per run, engine warm, footer already read. Page = 1024 rows. Bytes counted at the server.

| Row group | Strategy | First page | Next page | Jump to 90% | Before any row |
|---|---|---|---|---|---|
| 122,880 | A: `LIMIT/OFFSET` | 98.9 ms, 5.59 MB | 31.6 ms, 0 B | 75.9 ms, 5.00 MB | |
| 122,880 | B: `file_row_number` filter | 91.4 ms, 5.59 MB | 29.3 ms, 0 B | 68.8 ms, 5.00 MB | |
| 122,880 | C: ingest, then `rowid` | 19.7 ms, 0 B | 3.5 ms | 2.8 ms | 1083 ms, 35.5 MB |
| **30,720** | A | 81.1 ms, 1.39 MB | 28.1 ms, 0 B | 60.5 ms, 1.39 MB | |
| **30,720** | **B (chosen)** | **70.3 ms, 1.39 MB** | **21.1 ms, 0 B** | **49.6 ms, 1.39 MB** | |
| 30,720 | C | 19.5 ms | 3.5 ms | 2.8 ms | 1091 ms, 37.7 MB |
| 16,384 | B | 83.2 ms, 1.39 MB | 29.3 ms, 0 B | 48.6 ms, 1.39 MB | |
| 8,192 | B | 106.7 ms, 1.39 MB | 51.6 ms, 0 B | 64.8 ms, 344 KB | |

(A and C at 16,384 and 8,192 are in the JSON; same pattern.)

- **B over A:** same bytes (DuckDB skips row groups for `OFFSET` too), 10–25 ms faster.
- **B over C:** C downloads the whole file (1.1 s, 35–42 MB) before the first row, and holds it in DuckDB's memory, against Tycho rule 3.
- **30,720-row groups:** the fastest first, next, and jump pages, 3.6× fewer bytes per jump than 122,880, for a 6.3% bigger file. Smaller groups are slower (more row groups to plan) and bigger (+11.6% at 16,384, +17.7% at 8,192), and cut bytes only at 8,192 on the jump.
- **The 1.39 MB floor is DuckDB-Wasm's HTTP readahead**, not the Parquet reader. `WebFileSystem`'s `ReadAheadBuffer` reads a sequential region in growing requests (16 KB, 64 KB, 256 KB, 1 MB) and none of `db.open`'s options change it (`useDirectIO: true` and `disable_parquet_prefetching` tested: no effect). The next page comes from that buffer: 0 bytes.

**The M3 "first rows under 2%" goal can't hold with DuckDB-Wasm 1.32.0 on this file.** Footer (35 KB) + the first page's readahead (1.39 MB) is 3.8% of 37.7 MB, at any row-group size. It would take a file of ~72 MB or more, or a readahead setting DuckDB-Wasm doesn't expose.

**Reproducing it.** The bench files are the sample rewritten with native DuckDB (`data/`'s `@duckdb/node-api`) and loaded into local R2 under `bench/`:

```sql
COPY (SELECT * FROM read_parquet('asteroids.parquet')) TO 'asteroids-rg<N>.parquet'
  (FORMAT parquet, COMPRESSION zstd, ROW_GROUP_SIZE <N>,
   KV_METADATA {'tycho.credit': 'Asteroid data: NASA/JPL Small-Body Database', 'tycho.fetched': '2026-09-24'});
```

for N in 122880, 30720, 16384, 8192, then `wrangler r2 object put tycho-data/bench/asteroids-rg<N>.parquet --file … --local` from `worker/`. `just tycho paging` reads them; `--setup` runs a SQL statement first (how `disable_parquet_prefetching` was tested).

(The sweep ran before the drag fix, so its jumps are ~50 ms slower than the final 133 ms.)

**The sweep doesn't separate the configs.** Every one meets every budget. Frame times are identical. A 3 s top-to-bottom fling outruns any prefetch (~84% placeholder frames everywhere), and a steady 1,800 rows/s never shows a placeholder at any config. First-rows and jump differences are within run-to-run noise. The choice, **1024 × 2**, rests on structure: 1024 divides the 30,720-row groups, so a page never reads two groups; smaller pages evict in finer steps under the memory budget; prefetch 2 leaves headroom above 1,800 rows/s. A faster steady-scroll test (a trackpad flick, ~10k rows/s) is what would separate prefetch depths; not needed for M4.

## The throttled jump: a drag's stale reads

The first protocol run's throttled jump was **4.3 s**. The server log showed why: the drag passed through ~45% on its way to 90%, the table asked for that page, and DuckDB started reading it. A cancel can't stop that: DuckDB-Wasm's worker reads with synchronous XHRs, and `cancel` lands between query slices. On Fast 4G each page read is a 4-request readahead ramp at 165 ms latency each, ~2.1 s, and the target page waited behind the stale one.

Fix: while the scrollbar thumb is dragged, the table loads pages only once the pointer rests for 80 ms, or on release (`crate/src/table/mod.rs`, `DRAG_SETTLE`). Placeholders fill the rows meanwhile. Throttled jump **4.3 s → 2.2 s**; reference **184 → 133 ms** (the stale read no longer runs first); memory after two passes 101 → 86 MiB wasm (fewer pages loaded only to be evicted).

**Throttled steady scrolling shows placeholders in every frame.** At 1,800 rows/s a 1024-row page is needed every 0.57 s, and a page costs ~2.1 s on Fast 4G. Frames stay smooth (p95 16.7 ms); the rows just arrive late. This is the readahead ramp's four sequential round trips, and it's a limit to note for M8's real network, not an M4 budget (budgets apply to the reference run).

## A harness bug: wheel deltas at DPR 2

Under Playwright's `deviceScaleFactor: 2`, Chromium delivers `mouse.wheel(0, 1000)` to the page as `deltaY` 500. The first sweep and protocol run therefore flung at half speed, reached the bottom only through the last catch-up event, and scrolled "steadily" at 900 rows/s. It showed up as an intermittent "fling didn't reach the last row" failure (7 of 10 runs). Fixed with `harness.ts`'s `wheel()`, which scales by `devicePixelRatio`; the final catch-up event now sends only the distance the 3 s loop didn't cover. Everything above was re-measured after the fix. The half-speed sweep had pointed to 4096 × 2 (55% fling placeholders vs 89%); at full speed that difference is gone.

### The M3 retry check hung: two failing extension loads crash DuckDB

The first run of `sample.ts` on M4 failed "Parquet extension blocked, then retried": the retry after unblocking hung. Eight repeats: **4 of 8 hung**, and exactly the runs where the click came before the engine's `LOAD parquet` prefetch had settled. The click's queries then autoloaded the (blocked) extension while the prefetch's load was also failing. DuckDB-Wasm 1.32.0 crashes inside its worker when that happens ("RuntimeError: table index is out of bounds"), fires no worker `error`, and never answers another query. Clicking only after the prefetch settled: 0 of 8 hung.

Fix: at first, `dataset::open` waited for the prefetch to settle (8 of 8 then passed). The code review found the gap: after a failed prefetch, the three metadata queries still autoloaded the extension together. The final fix is `Engine::load_parquet()`: the prefetch and every file open share one `LOAD parquet` attempt, a success is remembered, a failure lets the next caller retry, and the metadata queries run only after it, so none autoloads. Retry after unblocking, clicking early or after the prefetch failed: **8 of 8** pass, and DuckDB logs no crash at all (before, even passing runs logged `unreachable` and `function signature mismatch` from the concurrent autoloads). This likely predates M4 (the engine code didn't change); the bigger footer made the overlap more likely. A worker that dies without an error is worth a watchdog in M7's error states.

## Cross-browser

`just tycho table --browsers` (Playwright's Chromium, Firefox, and WebKit builds): the sample opens, the scrollbar jumps to 90%, a quick click on the track moves the table once and the table stays put when the pointer moves off, a 3000 px wheel moves exactly 100 rows, and End shows row 1,567,523. A pointer the browser cancels mid-drag ends the drag. First rows / jump: Chromium 246 / 136 ms, Firefox 193 / 105 ms, WebKit 337 / 173 ms.

### A quick click on the scrollbar left the drag on

WebKit found it: its check's "wheel" moved the table from 90% to 44%. The drag's move and release listeners were registered at paint, and only when a drag was already active. A click delivers the press and the release before the next paint, so the release was never seen, the drag stayed on, and the next pointer move dragged the table. A negative control (the old code with the new check) fails in Chromium and Firefox too: after a track click, moving the pointer off took the table from row 1,545,662 to 783,750. The listeners now register every frame and act only while a drag is active.

WebKit also needed the harness to wait a frame between moving to a control and pressing it: GPUI fires a press only on a hovered element, and WebKit's scripted press can arrive before hover updates. A person always hovers first.

## After code review (same day)

Ten findings, all fixed; every number above was re-measured after them.

1. **The 3-in-flight limit leaked on wheel and keyboard scrolling.** A cancelled page stopped counting the moment it was cancelled, though DuckDB keeps reading a started page. Cancelled requests now count until DuckDB answers them (`PageCache::draining`, shown in the overlay's "Pages" row). The whole page's memory after two passes fell from 273.1 to 233.6 MiB. Throttled steady scrolling still shows placeholders in every frame: it's the network, not the queue.
2. **The Parquet race fix was incomplete.** After a failed prefetch, the three metadata queries still autoloaded the extension together. Now one shared `LOAD parquet` attempt runs first (`Engine::load_parquet`), and DuckDB logs no crash in the retry scenario (see "The M3 retry check hung").
3. **A failed page never retried.** It's now forgotten once scrolled out of view, so coming back asks for it again (unit test).
4. **A drag whose release never arrived stayed on.** A mouse move with no button held now ends it. The browser check fires `pointercancel` mid-drag; the old code fails it in all three engines (the table jumped from row 1,545,662 to 133,456).
5. **The memory pass could skip positions.** It read the table's state before the next frame had drawn the new position. It now waits for the table to move before checking whether rows are pending. Result: 89.4 MiB (was 90.2 MiB), the pass taking 88 s instead of 73 s.
6. **Scroll direction never reset,** so an idle table kept prefetching ahead. It resets to still 250 ms after the rows stop.
7. **Toggling the overlay between two frames could start a second frame-timing loop.** Each loop now has an id and stops when it isn't the live one.
8. **The test hooks ran for everyone.** `__tychoTable` and the `tycho:viewport-filled` marks now run only with `?perf` or `?bench`; `tycho:first-rows`, which the overlay reads, stays.
9. **The table read the engine global and then overwrote it with the one passed in.** One constructor now takes the engine.
10. **Sideways scrolling re-planned page loads,** and each finished page computed the wanted pages twice. Only row changes load pages now, and a finished page computes them once.

## After the second code review (same day)

Ten more findings at high effort. Nine are fixed, and the tenth is half-fixed with the rest deferred. Per the review scope, these weren't re-measured: none touches the paging path except as noted.

1. **Autoload was still on,** so the one-`LOAD`-at-a-time fix held only for callers that used it. Autoload is now off (`engine.ts`), and a query needing an unloaded extension fails with DuckDB's clear "exists in the json extension" error, after which the next query works. An A/B (autoload on vs off, 2 rounds × 4 runs) shows no change to click → schema or schema → rows.
2. **A press on either scrollbar didn't focus the table** (its handler stops the event before the table's own focus handler). It now focuses it. Checked: with focus moved to the header strip, a scrollbar press and then End reach row 1,567,523.
3. **"Parquet ready" stayed "failed"** after a retry loaded the extension. A successful file open now updates it (`show_parquet_ready`). Checked with early and late clicks.
4. **An early click registered the file before starting the extension load.** Both are now sent before either is awaited.
5. **`table.ts` could leave a stray `wrangler dev` running** when port 8787 was busy. It now checks the port first and closes its Worker if the rest fails to start.
6. **A 0-row file never marked "first rows."** An empty table now counts as filled.
7. **`?budget_mib=` of 4096 or more wrapped to 0 on wasm32.** The math is now checked.
8. **URL parsing was copied four times.** `seiza::url::{has_param, param}` in `shared/` replaces them; `seiza` is now a regular dependency of the crate (it compiles natively).
9. **The overlay's 500 ms refresh ran for the page's whole life,** even while hidden. It now starts and stops with the overlay's toggle (`frames::sync`). Checked: hidden, there's no frame row; shown, hidden, and shown again, the row comes back.
10. **Half fixed, half deferred.** The test probe (`__tychoTable`) is now built only while measuring. Caching formatted cell strings per page is deferred to M7 (a note there): frames hold 16.7 ms p95, and the guides say measure before adding a cache.

**A slowdown that wasn't the code.** A functional run after these fixes showed first rows ~310 ms, against 239 ms before. Splitting it with the app's marks showed both halves slower: click → schema ~125 ms (was ~107) and schema → rows ~170 ms (was ~132). The autoload A/B ruled out the engine change. A control that bypasses the table entirely (`just tycho paging`: the same query through the bridge) was just as much slower: first page 106 ms against 70.3 ms this morning, and the jump 63 against 49.6 ms. Load average 4.8. That's machine load, not a regression; the numbers above stand.

Functional runs on the final code: `just tycho table --browsers-only` passes in Chromium, Firefox, and WebKit; `just tycho engine --runs 1` passes, blocked-engine controls included; lint and all 31 unit tests pass. App wasm 2653.9 KiB brotli.

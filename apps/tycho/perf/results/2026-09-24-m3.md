## Where the 34.8 KB goes

Server-side counts (a counting proxy between Vite's `/data` proxy and `wrangler dev`; Playwright doesn't see DuckDB's sync XHRs from its worker), same in every run:

| Request | Range | Bytes | From |
|---|---|---:|---|
| GET | `bytes=0-0` | 1 | `engine.ts` `remoteSize`: must be a 206 (rejects 404s and SPA fallbacks) |
| HEAD | `bytes=0-` | 0 | DuckDB sizes the file (the Worker answers 206 + Content-Length) |
| GET | last 1,990 B | 1,990 | DuckDB: Parquet footer length + magic |
| GET | 16 KiB | 16,384 | DuckDB: footer (metadata) |
| GET | 16 KiB | 16,384 | DuckDB: footer (metadata) |

The three metadata queries (`DESCRIBE`, `parquet_file_metadata`, `parquet_kv_metadata`) run in parallel, each on its own connection, and still share one footer read.

**Throttled is latency-bound:** 1009 ms is five sequential round trips at Fast 4G's 165 ms latency, plus CPU. Two of the five are probes (ours and DuckDB's). Dropping ours would save one round trip, but it's what turns a 404 or an SPA fallback into a clear error (M2 decision). Recorded only; revisit if the throttled number matters.

## DuckDB-Wasm downloaded the whole file by default

The first trial showed **100% of the file** (35.4 MB) coming down in one request before the schema showed. DuckDB-Wasm 1.32.0's HTTP open logic, with default settings, sizes a file with a `bytes=0-0` GET, then reads the total from the wrong header (it splits `Content-Length` on `/`, where it meant `Content-Range`). It finds no size, and falls back to a plain GET of the whole file. Tested against the Worker:

| `db.open({ filesystem })` | Result |
|---|---|
| default, or `reliableHeadRequests: true` alone | whole file downloaded |
| `allowFullHTTPReads: false` alone | fails: "No files found" |
| `reliableHeadRequests: true, allowFullHTTPReads: false, forceFullHTTPReads: false` | **range reads**: ranged HEAD, then only the footer |

The working setting sizes the file with `HEAD` + `Range: bytes=0-` and requires a 206, so the Worker now answers a ranged HEAD with the headers the ranged GET would get. With full reads off, a server without range support fails instead of silently downloading everything. That's what Tycho wants, since it controls the server.

## Surprises

- **R2 returns the whole object for a Range header it can't satisfy.** Passing `request.headers` to `R2Bucket.get` (PLAN.md's original suggestion) with several ranges, or a start past the end, returned all 35 MB with no error in Miniflare. That would have gone out as a "206". The Worker parses `Range` itself and passes R2 an explicit `{offset, length}` or `{suffix}`. An offset past the end throws `10039`, which the Worker turns into a 416.
- **WebKit lays the first frame out before the window has its real size.** The button's first published bounds were `x −91, y 1271` at a 1440×900 viewport, corrected a frame later. The harness waits for on-screen bounds. This may mean WebKit's first-frame mark lands on a frame laid out at the wrong size; worth checking against `perf.ts`'s probe before quoting WebKit TTFP.
- **The CSV fixture defeats DuckDB's sniffer**, as it should: the tricky rows come after 1.5 million quote-free rows, so auto-detection picks no quote character and fails on row 1,567,525. With `quote='"'`, all 8 tricky rows round-trip. M6's CSV path must not rely on sniffing a prefix.
- **3,569 asteroids (0.23%) have a year-only `first_obs`** (`2015-??-??`) in the source. They're NULL in the Parquet, counted in `MANIFEST.json`.
- **Vite normalizes dot segments before proxying**, so `/data/%2e%2e/…` never reaches the Worker in dev. The dot-segment check runs against the Worker directly (`just tycho worker-check`).

## After code review (same day)

Ten findings; all addressed, and the numbers above were re-measured after them.

1. **Autoload asked our origin for extensions we don't host** (`json`, `icu`), and Vite's SPA fallback answered with `index.html`. Missing `/duckdb-ext/*` files are now 404s in dev and preview (`web/vite.config.ts`). Verified: `SELECT '{"a":1}'::JSON` fails with "Extension Autoloading Error … 'json'" and the next query works. M8's Worker needs the same rule (PLAN.md, M8).
2. **Retry after a failure:** registering the same URL again turned out to be fine in DuckDB-Wasm 1.32 (checked in the browser). `sample.ts` now proves the retry end to end (extension blocked, then unblocked).
3. **The byte count missed requests still streaming when the frame appeared.** It now counts every request that started before the frame, in full. The negative control above shows it catches a whole-file download.
4. **Over-long ranges were passed to R2 unclamped**, and only Miniflare was seen to clamp them. On R2's 10039 error the Worker now re-reads the size and retries clamped, or answers 416 when the start is past the end. Unit tests against a strict fake R2 (`worker/test/`) cover it; `just tycho worker-check` runs them.
5. **`decode()` on a non-UTF-8 key/value entry would fail the whole summary.** The query now matches keys as bytes and uses `try(decode(value))`.
6. **The manifest's year-only count counted every NULL `first_obs`.** It now counts the source pattern: still 3,569, and 0 rows have no date at all.
7. **`wrangler dev` startup accepted another server already on the port.** The launcher and the counting proxy now fail with "port 8787 is in use".
8. **The measurement protocol was copied into three scripts.** It's in `perf/common.ts` now (flags, Fast 4G, profiles, DPR shim, throttling, summaries, machine info).
9. **`format_bytes` could print "1024.0 KiB".** It moves up a unit at 1023.95.
10. **Native DuckDB was installed by every `npm install`.** `data/` is no longer a workspace: `just tycho data` (or `data-deps`) installs it with its own lockfile, and lint typechecks `data/` only when it's installed.

## Carried to M4

- **The transfer check vs row-group size.** The check's "footer + first row group" is ~9.5% at 122,880 rows per group (13 groups), and ~15.7% in practice with readahead. Row group 0 costs ~27 bytes per row, so first rows under 2% (709 KB) would need row groups of roughly 20k rows or fewer, and readahead held in check. Otherwise the check needs rewording. PLAN.md already schedules the row-group size for M4.
- **Data file caching.** `/data/*` is served with `Cache-Control: no-cache` (stable names; a cached copy mixed with ranges from a re-upload would be corrupt). M8 decides whether to switch to content-hashed names and `immutable`.

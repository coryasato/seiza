# Request bursts for the WAF rate limit (2026-10-12)

**Machine:** local (Apple M1, Darwin 25.6.0), load average 2.8. Chromium headless=new, 1440×900 at DPR 2, unthrottled, a fresh browser (cold cache) per scenario, one run each: this is a peak count, not a timing.

**Files:** `2026-10-12-waf-burst.json` (`just tycho burst --label waf-burst`).

## What it measures

The most requests one visitor sends in any 10 s, the window the WAF's per-IP rate limit counts in (`docs/hosting.md`, "Abuse guards"). Every request the Worker would run counts: `/data/*` at the server (the counting proxy), the page, assets, and extensions from the browser. Local reads are faster than R2's 55–125 ms, so these bursts overstate production's: the safe side for a limit.

## Results

| Scenario | Busiest 10 s | of them `/data/*` | All requests |
|---|---|---|---|
| visit: load, asteroids, fling to the bottom, End, Home | 26 | 18 | 26 |
| jumps: Gaia, 20 jumps to random rows ~0.5 s apart | **93** | 90 | 114 |
| pagedown: Gaia, PageDown held 10 s | 21 | 13 | 21 |
| reloads: 5 reloads 1 s apart | 48 | 0 | 48 |

A page load is 8 Worker requests (page, app JS, wasm, font, engine JS, DuckDB's worker JS, its wasm, the Parquet extension). Random jumps are the worst case: each lands in a new row group and pays DuckDB's readahead chain (~4.5 requests per jump). Paging down stays inside one row group's readahead, so it barely reads.

The deploy's production check sends ~55 requests per attempt, spread over its downloads; it stays under any limit set from this peak.

## Reproducing it

```sh
just tycho build
just tycho burst --label waf-burst
```

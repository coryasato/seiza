# M6 results: drop a CSV with progressive loading (2026-09-30)

**Machine:** local (Apple M1, macOS 26.6.2 / Darwin 25.6.0). **Toolchain:** as M5. **Machine load:** 2.5–4.1 throughout (other work on the machine).

**Data:** `just tycho drop-files csv` (`data/drop_files.ts`) writes `drop/asteroids-x6.csv` (gitignored): `fixtures/asteroids.csv`'s header, then its body 6 times, byte for byte. **1,021.7 MiB, 9,405,186 rows**, SHA-256 in `data/MANIFEST.json`. The row count is native DuckDB's with the quote set (see "The sniffer"). The fixture itself: 170.3 MiB, 1,567,531 rows, its last 8 rows hand-written (`fixtures-src/tricky_rows.csv`).

**Files:**
- `2026-09-30-m6-csv.json`: the M6 checks, `just tycho csv` (reference and throttled, n=10 each; fixture; supersede; formats; Firefox and WebKit), on the final build, after the code-review fixes (below). A run before the fixes read within noise of it (first rows 179.6 ms, load 15.7 s, worst gap 267.7 ms).
- `2026-09-30-m6-ingest-*.json`: the experiment behind the decision, `just tycho ingest`, on the final build: `baseline` (raw, whole, chunks appended with per-chunk sniffing), `append` / `append-compressed` (appended, `auto_detect = false`), `tables` / `tables-compressed` (one table per chunk).
- `2026-09-30-m6-table.json`, `2026-09-30-m6-drop-unsupported.json`: M4's table checks and M5's unsupported-file check, re-run as regression guards.

## The decision (`just tycho ingest`)

All in DuckDB-Wasm 1.32.0 through the bridge, engine warm, the 1 GB CSV set from disk. Every row read the file's 9,405,186 rows unless noted. Page = 1,024 rows. "Gap" is the longest the row count went without an update. "Page during" is a page read sent while a chunk ran. Memory is DuckDB's own (`duckdb_memory()`) / every agent.

| Approach | Load | MB/s | First rows | Page at 90% | Chunk p50 / p95 / max | Gap | DuckDB / all MiB |
|---|---|---|---|---|---|---|---|
| Raw `read_csv … LIMIT/OFFSET` | none | — | 147 ms (first page) | **5,267 ms** | — | `count(*)` 3,134 ms | — / 224 |
| One `CREATE TABLE AS`, whole file | 8.3 s | 128.9 | after 8.3 s | 21 ms | — | 8.3 s | — / 2,003 |
| Appended, 4 MiB, sniff each chunk | 21.7 s | 49.3 | 149 ms | 6 ms | 59 / 204 / 391 | 402 | 1,207 / 1,438 |
| Appended, 8 MiB, sniff each chunk | 25.7 s | 41.7 | 185 ms | 4 ms | 93 / 409 / 441 | 459 | 587 / 900 |
| Appended, 32 MiB, sniff each chunk | 14.0 s | 76.4 | 384 ms | 5 ms | 299 / 549 / 557 | **633** | 931 / 1,148 |
| Appended, 4 MiB, fixed options | 19.3 s | 55.6 | 154 ms | 5 ms | 46 / 211 / 471 | 484 | 1,207 / 1,439 |
| Appended, 16 MiB, fixed options | 25.5 s | 42.0 | 316 ms | 5 ms | 339 / 545 / 575 | **613** | 592 / 909 |
| Appended, 4 MiB, fixed, compressed | 25.7 s | 41.8 | 151 ms | 6 ms | 46 / 217 / 664 | **674** | 338 / 531 |
| Per-chunk tables, 4 MiB, uncompressed | 10.9 s | 98.4 | — | — | 35 / 43 / 101 | — | **2,603** / 2,822 (count wrong, below) |
| **Per-chunk tables, 8 MiB, compressed** | 19.4 s | 55.2 | — | — | 164 / 212 / **335** | — | **300** / 504 |
| Per-chunk tables, 16 MiB, compressed | 19.0 s | 56.4 | — | — | 257 / 293 / 352 | — | 310 / 504 |

- **Raw-file queries are out.** First rows are fast, but every page re-parses from the top: 5.3 s to a page at 90%, 3.1 s just to count the rows for the scrollbar.
- **One whole-file table** is fastest to finish, but shows nothing for 8.3 s and peaks at 2 GiB.
- **Appending chunks to one table stalls.** Chunks alternate between ~90 ms and 250–600 ms at the same chunk indices every run, so the gap budget fails at most sizes (and in the append-compressed runs). What the stall isn't: GC (the worker's GC totalled 40 ms in a trace of 24 chunks, while one call inside DuckDB's wasm took 382 ms), wasm memory growth (growing the heap first changed nothing), or parsing (parsing each chunk without storing it: a steady ~45 ms per 8 MiB, no stalls). Smaller row groups on the attached database (`ROW_GROUP_SIZE` 30,720 or 61,440) didn't help either. Appends also cost memory in proportion to the chunk count (1.2 GB at 4 MiB against 0.6 GB at 16 MiB).
- **One table per chunk doesn't stall**, and compressed it's the smallest layout measured. The app's own number is better than the table's 19.4 s (15.4 s, 69.5 MB/s): it finds the next chunk's end in Rust while DuckDB reads the current one, where the experiment scans in JS between chunks.
- **`auto_detect = false`** (every option fixed from one sniff): fast chunks went from 55 to 35 ms at 4 MiB (appended, uncompressed, no page reads during).
- **A page read sent during a chunk finishes when the chunk does**, in every configuration ("page during" equals the chunk time). DuckDB-Wasm round-robins query slices (M5), but not with these statements. So the chunk time is the worst page latency during a load, and the app aims chunks at 200 ms.
- **Uncompressed per-chunk tables counted short** in the experiment (7,650,902 and 9,025,294 rows), at 2.1–2.6 GiB of DuckDB memory. Not investigated: it may be the experiment's hand-rolled count reader, or DuckDB close to wasm's memory limit. That layout is out on memory alone. The app reads each chunk's count from its CTAS's `Count` column through the real Arrow reader, and its counts were exact in all 20 protocol runs and the fixture.

## The sniffer

DuckDB's `sniff_csv` reads the file's first 20,480 rows. The asteroid CSV has no quoted field until its last 8 rows, so the sniffer reports **no quote character**, and reading the whole fixture with defaults fails at line 1,567,525 ("Expected Number of Columns: 18 Found: 19"), in native DuckDB 1.4.5 too. Its types are head-only as well: `pdes` sniffs BIGINT and meets "1988 PF1" at row 895,912.

- The app forces RFC 4180's `"` when the sniffer reports none. A file without quotes reads the same either way.
- A chunk that fails a conversion names the column ("Error when converting column "pdes""). That column becomes VARCHAR from then on, and the chunk goes again: a failed `CREATE TABLE AS` leaves nothing behind. Earlier chunks keep BIGINT, and page reads cast them (`* REPLACE (CAST("pdes" AS VARCHAR) AS "pdes")`). The header says so: "pdes is shown as text: a value after row 862,001 isn't a BIGINT."
- Any other chunk error stops the load and keeps the rows before it. The header gives DuckDB's reason and the offending line, not its chunk-relative line number.

## Throttled frames

At CPU 4×, a fling during the load reaches p95 33.3–50.0 ms (worst 66.7). M5's throttled fling with no load held p95 16.7 ms, worst 33.3 ms. The budget applies to the reference run, which holds at 16.7 ms. The likely cost is the record scan: each 1 MiB window is read into a JS `ArrayBuffer`, copied into wasm, and scanned byte by byte on the main thread (the Arrow decoding of each page is the other candidate). Carried to M7: its per-frame work time shows which, and smaller windows are the first thing to try.

## Code review fixes

A `/code-review` of the milestone found, and M6 fixed (each has a check in `just tycho csv` now):

- **A finished or stopped CSV's tables were never dropped.** The load task dropped them only when stopped mid-load; once it had finished, a replacement left ~300 MiB (for the 1 GB file) in DuckDB for the session. The supersede check only ever replaced a *loading* CSV. Now the workbench drops the schema itself when the load is done or stopped; checked by "Parquet over a loaded CSV" and "… whose load stopped".
- **A CSV with a `rowid` column** hid DuckDB's `rowid`, and pages were read by the file's values (natively: a page read returned nothing). Such files' tables now number their rows (`row_number() OVER ()`, streaming, file order checked over 1.57 M rows); other files keep `rowid`, since the numbering cost ~2.6× natively.
- **A quote inside a field** (`12" pizza`) toggled the scanner into a quoted state, so the rest of the file could become one chunk (DuckDB itself reads it literally). The scanner is now a field state machine: a quote opens a field only at its start. A TSV the sniffer found unquoted stays unquoted.
- **A stop between queries** (during a registration) didn't stop the next chunk, which DuckDB then ran in full ahead of the new file. `csv::Stop` refuses to send once stopped.
- **A chunk's time included the next chunk's scan** when that was slower, and a failed scan returned while the chunk's CREATE TABLE still ran. The two are awaited together now (`futures::join`).
- Two display slips: the overlay read "stopped · stopped at N%", and a one-chunk file's finish time was overwritten.

Known and recorded, not fixed: every chunk stays registered for the session (a fourth bridge call to unregister; no bytes held), and the byte-at-a-time scan (carried to M7 with the throttled frames).

# Hosting

How Tycho is served: one Cloudflare Worker on one origin, with static assets and R2. Paths are relative to `apps/tycho/`. Why each choice was made is in [`DECISIONS.md`](DECISIONS.md), "Hosting"; the Cloudflare gotchas every app shares are in the root `CLAUDE.md`.

**Decided 2026-09-22.** One Worker (`worker/`) handles one origin.

- **Names (2026-09-24):** Worker `tycho` (public on a custom domain; the account's `*.workers.dev` subdomain exposes a personal handle, so it's never committed), R2 bucket `tycho-data`, bound as `TYCHO_DATA`. `wrangler.toml` doesn't commit the account ID; wrangler takes it from `wrangler login` (or `CLOUDFLARE_ACCOUNT_ID` with an API token), and API tokens never go in the repo.
- **Origin (2026-10-10):** **https://tycho.seiza.io**, a Workers custom domain on the `seiza.io` zone (`routes` in `wrangler.toml`), with `workers_dev = false` and `preview_urls = false`. Workers Logs stay on (`[observability]`).
- **Deploy:** `just tycho deploy` (`worker/scripts/deploy.ts`): release build; R2 uploads first (the samples when R2's stored SHA-256 differs from MANIFEST.json's; the oversize build files), through R2's S3 API with the AWS CLI profile named by `TYCHO_R2_PROFILE` (multipart; Gaia's 1.5 GB took 26 s); a quality-11 `.br` beside every wasm, JS, font, and HTML file; `.assetsignore` for the oversize files; `wrangler deploy`; then `check.ts` against production, retried for a minute while the version propagates.

- **Worker static assets** serve the build (web/dist). The limit is **25 MiB per file**, so `just tycho build` checks the release wasm and each DuckDB bundle against it. DuckDB's two wasm bundles (33 and 38 MiB) are over it: they're in R2 under `assets/<name>` (their own path) and the Worker serves them; their `.br` (5 and 6 MiB) are static assets. `_headers` (written by `shared-web`'s Vite config) sets COOP/COEP/CORP on every asset and `immutable` on `assets/`.
- **Precompressed build files:** the Worker runs first (`run_worker_first`) for `/`, `/index.html`, `/assets/*`, and `/duckdb-ext/*`. To a browser that takes br (`cf.clientAcceptEncoding`) it returns the file's quality-11 `.br` as is (`encodeBody: 'manual'`); otherwise the file itself, which Cloudflare compresses (zstd or gzip), from static assets or R2. Cloudflare's own compression sent the app wasm as 3.7 MiB of zstd (3.6 as br) against 2.8 MiB at quality 11: +1.1 s TTFP throttled. The page goes out `no-cache, no-transform`: the zone's Web Analytics injected a beacon script (`static.cloudflareinsights.com`) that loaded before first paint, and `no-transform` stops that. A path no asset matches (a missing `/duckdb-ext/*` extension) is a 404, never `index.html` (`not_found_handling = "none"`).
- **R2** holds the datasets (and oversize engine files) and is read through a Worker binding at `/data/*`. R2 has **no egress fees**, which matters when every visitor may pull hundreds of MB of Gaia rows. That's the main reason to choose it over Google Cloud Storage/Firebase.
- **The Worker's range handling is ours to get right:**
  - Parse `Range` in the Worker and call `env.TYCHO_DATA.get(key, { range: { offset, length } | { suffix } })`. Don't pass `request.headers`: for several ranges or a start past the end, R2 returns the whole object with no error (seen in Miniflare).
  - Set `Content-Range` ourselves from `object.range` + `object.size`, since R2's example code doesn't.
  - Return `206`.
  - Answer `HEAD` with `Content-Length` and `Accept-Ranges: bytes`, and a ranged `HEAD` with the 206 headers the ranged GET would get: DuckDB-Wasm sizes files with `HEAD` + `Range: bytes=0-` and needs the 206.
  - Add COOP/COEP (or `Cross-Origin-Resource-Policy: same-origin`) to these responses too.
  - Set `Cache-Control: public, max-age=31536000, immutable` on content-hashed files. The data files keep stable names and go out as `no-cache, no-transform` (see `DECISIONS.md`, "Hosting").
  - Multi-range requests aren't needed; answer them with a single range or `416`.
  - **Edge cache:** HEADs and closed ranges up to 4 MiB are kept in Cloudflare's per-colo cache (Cache API), keyed by `DATA_VERSIONS` (the sample's content SHA, set at deploy) + method + `Range`; the 206 is stored as a 200 with its status and headers alongside. A miss is kept only if the R2 object's stored `sha256` matches the key's version: a deploy uploads data before the new Worker is live, and the old one must not store new bytes under the old key (code review). The 4 MiB cap bounds what a tee to a slow client can buffer in the isolate; DuckDB's 16 MB readahead step goes uncached. `X-Tycho-Cache: hit|miss|bypass` says which path answered. The first visitor at a data center still reads R2.
- **Compression:** production serves br at quality 11 (above). Without the Worker's `.br`, Cloudflare compresses `application/wasm` itself, as zstd when the browser offers it (Chromium does), at a low level. Parquet is already compressed: it goes out with `Cache-Control: no-transform` so Cloudflare doesn't re-encode it and break byte ranges.
- **Local dev:** `wrangler dev` runs the same Worker (the `[assets]` directory included; `scripts/dev.ts` creates an empty `web/dist` before the first build), so the headers and range behavior in dev match production. Vite's dev and preview servers proxy `/data/*` to it.

## Abuse guards

Cost scales with Worker requests and R2 reads, not bytes, and Cloudflare has no hard spending cap. Every path the app uses runs the Worker (`/`, `/index.html`, `/assets/*`, `/duckdb-ext/*`, `/data/*`), and only requests that reach the Worker are billed, so the guards stop requests before it, at the zone's WAF (dashboard settings; the rules are written here because they aren't in the repo).

- **Path allowlist (WAF custom rule, Block):** anything that isn't one of the app's paths, or isn't a `GET` or `HEAD`, never reaches the Worker. Probes (`/.env`, `/wp-login.php`) cost nothing and stay out of Workers Logs, which keep every real request (no sampling):
  ```
  (http.host eq "tycho.seiza.io" and (not http.request.method in {"GET" "HEAD"} or not (http.request.uri.path in {"/" "/index.html"} or starts_with(http.request.uri.path, "/assets/") or starts_with(http.request.uri.path, "/duckdb-ext/") or starts_with(http.request.uri.path, "/data/"))))
  ```
  A new path in the app goes into this rule before it deploys: `check.ts` requests every file in web/dist in production (a blocked one fails) and expects a probe to get the WAF's 403.
- **Rate limit (WAF rate limiting rule, Block):** requests to `tycho.seiza.io`, counted per IP over 10 s, blocked for 10 s past the limit (the free plan's only rule shape). The limit is several times the heaviest human burst measured, 93 requests in 10 s (20 random jumps on Gaia; `perf/results/2026-10-12-waf-burst.md`), so people sharing one IP stay under it. Measure again with `just tycho burst` before tightening it. Counting is per data center and approximate.
- **Pause switch:** `just tycho pause` sets the Worker secret `DATA_PAUSED` to `1`: every `/data/*` request answers 503 with `X-Tycho-Paused: 1` (and `no-store`), nothing reads R2 or the edge cache, and opening a sample shows a message saying the samples are paused and to drop a file instead (`web/src/engine.ts`, `remoteSize`). The page and dropped files keep working. A sample already open when the pause starts gets DuckDB's generic read error on its next page instead: only the open checks for the pause. `just tycho resume` sets it to `0`. A secret, not a var: it takes effect in seconds without a build and survives `just tycho deploy` (whose production check fails at once while paused, without retrying). It stops R2 reads, not Worker requests: a 503 is still a billed invocation.

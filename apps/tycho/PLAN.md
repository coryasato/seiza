# PLAN.md — Tycho

What's next for Tycho: milestone status, the next milestone's "done when" checks, the goals after it in order, and open questions. Only what's still open lives here. Context and rules are in `CLAUDE.md` here and at the repo root.

**Goal:** a data workbench for files too big for a spreadsheet, running entirely in the browser: open a file, understand it, check what you need, and export the part you want. The data never leaves the visitor's machine. Tycho is a utility app (root `CLAUDE.md`, "Tiers"): a public tool, built around a *controller* that sits between DuckDB-Wasm and the tall table, holds one *view state*, and can be driven by a person or by an outside LLM. Tycho hosts no model and takes no API key.

**The test for every feature:** does it help someone with a large file and a question? The first release is built for the quick checker ([`docs/personas.md`](docs/personas.md)).

**Tycho is being rebuilt.** This plan was rewritten on 2026-11-17 and replaces the old one whole: its carried-over perf reruns, its production-performance goal, and its open questions are not carried over. The reset (M11) is done: `CLAUDE.md` and the docs beside them describe the app as it stands, the ground the goals below replace piece by piece; Tycho's measurements are retired, and the wasm's size is the one number `check` gates.

## M12: the engine locked down, the page's frame in the DOM, the controller thin

Opened 2026-11-23 from goal 1, and planned in four parts, one session each. It is local, as every goal before "Ship the rebuild" is.

**What it is:** the first pieces of the new Tycho. The engine is locked down so no query can read or write past the files Tycho registers (the research's "Security", layer 2). The page's frame moves out of the canvas into the DOM, so the table is the only thing GPUI draws (`docs/DECISIONS.md`, "Scope", 2026-11-20, "Only the table is canvas"). The controller holds one view state, thin: what needs nothing new from the engine. The engine's end-to-end checks come back on the new page.

**Decided at its opening** (`docs/DECISIONS.md`, 2026-11-23): the frame is built here, not with the command bar, so the engine's checks are written once; the lockdown is taken as the research proposed it, the input taking no file until the lock is on; in this milestone the controller is driven by the table's own events and read through a probe, with no entry that writes it from the page; the capability schema waits for "The instructions, and the clipboard and agent routes".

**Not in it:** the command bar and the log (goal 2); jump to row, which leaves with the canvas's title bar and comes back as the command bar's `jump`; the side panels, the views list, the toolbar, and the Share menu (each with the goal that fills it); the first screen's URL row ("Open from a URL"); sort, filter, find, and hide (their goals); a link that holds a view (no goal holds it yet: open question 12).

### Part A: the lockdown

- [x] **A1. The engine takes a lockdown as a host's option, off by default:** a directory, and the SQL a host needs run before the lock. Its start runs, in order: the warm-up, `LOAD parquet`, the metadata cache, the host's SQL, `SET allowed_directories = ['<dir>/']`, `SET enable_external_access = false`, `SET lock_configuration = true`, and reports the lock as an event of its own. A failed step leaves it unlocked and says so, and Retry starts the whole of it again. The engine's `CLAUDE.md`, `README.md`, and `docs/DECISIONS.md` say what it does and why; the observatory's contenders, which don't ask for it, send what they sent (`just observatory fixtures` unchanged, `just observatory check` passing). *Done 2026-11-23:* `Lockdown` (`new`, `before`, `path`, `steps`; tested natively) and `start_locked`; `EngineStatus::Ready` waits for the lock, with `EngineEvent::Locked`, and a failed load or step is `Failed` with `LockFailed`, `retry` running on from the step that failed on the same worker (the engine's rule 9). `retry` no longer forgets a loaded Parquet extension. `start` is the same path with no lockdown: the observatory's fixtures pass unchanged, and in `just observatory check` everything that runs the engine's Rust passes: lint, the builds, the sizes, the GPUI contender's cold checks, the wall's GPUI side (its engine-failure case included: "worker 404: filled true, failed true"), admin, the placeholders, reach, and the engine files. Three steps failed on JS the change doesn't touch (no file under `engines/duckdb/web/`, `apps/observatory/`, or `shared-web/` changed): the wall's TanStack side (9–13 batches at 8 tables with no frame of their own), `tanstack-parity`'s Chromium track press, and `page.ts`'s first paint (83.4 and 101.5 ms against 72.5, the second with nothing else running). Left for the observatory to look at, not this part.
- [x] **A2. Tycho locks it, and opens nothing before the lock:** every name it registers is under `tycho/` (files, their re-reads, CSV chunks); `ATTACH … tycho_csv` moves from each CSV open into the lockdown's SQL; a drop, the picker, and the sample's button take no file until the lock is reported, and say why while they wait; a failed `LOAD parquet` shows Retry and opens nothing. *Done 2026-11-23:* `engine::lockdown` and `engine::path`; every name is `tycho/…`. A file chosen before the lock waits in the workbench, unregistered, as "Waiting for the engine to load…", and opens once the engine is ready (`docs/DECISIONS.md`, "Engine and bridge"); a failed `LOAD` shows Retry and keeps it held. The panel gains an "Engine locked" step and the `tycho:engine-locked` mark.
- [x] **A3. The lockdown holds in a browser** (open question 4), in Chromium, Firefox, and WebKit, by a check `just tycho` runs: refused, an `https://` path in a query, a file outside the directory, a `tycho/../` path, `COPY … TO` outside it and to a URL, `ATTACH` of a file or URL, `LOAD` of an extension not loaded, and `SET` and `RESET`; working, a dropped Parquet file and a dropped CSV (their `BROWSER_FILEREADER` handles), the sample, `SUMMARIZE`, `parquet_metadata`, a re-read under a new name, and a file registered after the lock. Also tried, for the goals that need them, and recorded in the decision: a remote file registered under the directory, and a file written by `COPY … TO` inside it. *Done 2026-11-23:* `just tycho lockdown [url]` (`perf/lockdown.ts`) passes on the release build in all three browsers: nothing but the lockdown's 7 statements before `tycho:engine-locked`, every refusal refused ("Permission Error: … file system operations are disabled by configuration", "Cannot change configuration option … the configuration has been locked"), and everything listed opening or reading; with `LOAD` failed on purpose, a CSV dropped during the load waits, unregistered, and opens 3–168 ms after Retry locks the engine. The spec's ATTACH and LOAD were too broad: `ATTACH ':memory:'`, `INSTALL`, and a `LOAD` of the loaded extension run locked, and reach nothing (the engine's `docs/DECISIONS.md`). Tried: `COPY` inside the directory writes and reads back in all three; a remote file under it reads in Firefox and WebKit (71,431 rows) and fails in Chromium with a 416 (`docs/LESSONS.md`). Smoke passes on the same build (no request before the first frame). After the code review: a drop or pick held while the sample downloads no longer shows as the sample; a held file stays held when the worker stops before the lock, and opens after Retry; a worker stopping during the lockdown reports `LockFailed`, so the "Engine locked" step and `?selftest` settle; the panel times "Parquet ready" and "Engine locked" from this start's `Ready`, and a Retry on the same worker reports the loaded extension at its own ready time, not the first start's; the check waits for a new `tycho:file-shown` mark, not the probe's name. Lockdown and smoke pass again on the release build in three browsers, and `just tycho lint`. The first two have no automated check: the probe doesn't show which button spins, and a worker can't be stopped on cue mid-lockdown.

### Part C: the controller, thin

- [ ] **C1. One serializable view state:** the source (its kind, name, and rows; never a URL or the data), the columns and their types, their order, widths (only where they differ from the default), the pinned count, and formats. In Tycho's crate, in Rust (the research, "The controller"). It compiles to calls on the table, and a state naming a column the file doesn't have is refused whole, never applied in part (`docs/DECISIONS.md`, "Scope", 2026-11-21, "A link to a view of a dropped file").
- [ ] **C2. The table's `resize`, `reorder`, `pin`, and `format` are adopted through it:** what the table owns and reports (`ColumnWidthsChanged`, `ColumnsMoved`, `Pinned`) becomes the state, and the state gives it back after `set_columns` (a CSV's widened column keeps its order, width, and pin). Formats start from each column's type; nothing in this milestone changes them but the state.
- [ ] **C3. It is checked:** native tests for the state's round trip, the events into the state, the state into the table's calls, and a refused state; a read-only probe, `globalThis.__tychoView`, publishes it, and a browser check drags a column, resizes one, and pins one and reads each back. The wasm's size against the baseline is in the part's notes (`just tycho check`).

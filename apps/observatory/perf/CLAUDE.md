# The observatory's perf scripts (`perf/`)

The scripts that measure and check both contenders and the page, and their gotchas. Budgets are `budgets.json`; the protocol is the root `CLAUDE.md`'s. Claude Code loads this file when a file under `perf/` is read. The observatory's rules and the map of its folders are in `apps/observatory/CLAUDE.md`, the repo's in the root `CLAUDE.md`; both apply here. Paths are relative to `apps/observatory/`.

## The scripts

- **`perf/contender.ts`** opens either bare page cold with `?measure`, holds the recorders and each side's input path (the gesture scroll, `gesture`; the file read whole, `readWhole`), and runs a metric: both profiles, both contenders alternated, a scenario at its stops (`--scenario`, `--stop`: its level's builds, each stop's file labeled `<label>-<scenario>-<stop>`), written to `perf/results/`. Each metric is a `perf/metric-<name>.ts`; what it reads and how is `docs/contender-contract.md`, "Reading the metrics", and the justfile's `metric` comment lists them and their flags.
- **On a scenario's level every scripted scroll is the gesture** (`response`'s wheel, `cost`'s fling, `memory`'s sideways session; `docs/DECISIONS.md`, "Measurement").
- **Memory compares equal work:** the same pages read on both devices (a scenario's: the file read whole, then its session; a feed's: `?ticks=`; live tail's: `?rows=100000`).
- **`--summarize <file,…> --label <name>`** computes a results file's summaries again from its runs by the script as it is now, never measuring again, into a new file (`summarizedFrom`); a run lacking what the summary reads fails it.
- **Shared by the metrics:** the throttle's busy-loop control (`perf/throttle-control.ts`: `feed`, `tail`, `soak`) and live tail's scroll-back probe (`perf/tail-metric.ts`). `perf/gpui-parts.ts` splits the GPUI page by part, from a build with its names kept.

## Perf script gotchas

- **The contenders' checks serve their builds themselves** (`perf/harness.ts`, `serveGpui` and `serveTanstack`: `vite preview` of each `web/dist`, the page at its base; `servePage`: the page's build with both contenders', the page at `<server>/observatory/`), each script on fixed ports of its own, so any two can run at once. A new script takes ports no other uses: `grep -ohE '\b4[0-9]{3}\b' perf/*.ts | sort -u` lists the taken ones (4096 is a row count). The checks and read `count(*)` and the last key from data/'s native DuckDB (`just observatory data` installs it). The GPUI contender's placeholder text sits 1 device px above GPUI's at DPR 2 (inside the ink's ±1), so a "text 1 px down" control can't fail the match; `perf/placeholder.ts`'s control moves it up.
- **The production scripts route the page in.** `perf/data-read.ts` opens a page at each data file's own origin with Playwright routing every path but the data to Tycho's local release build (`?bench` exposes its bridge), so the reads are same-origin under COEP and both sides run one engine. The routes reach DuckDB's worker too. Run `just tycho build` first.
- **Native scrollers under Playwright** (`docs/dom-scroll-model.md`, "Scripting it"): drive them with raw `page.mouse.wheel` deltas, not `wheel()`; but a bare `mouse.wheel` reaches a native scroller's compositor only every other frame in headless Chromium, so a reading of how often the DOM side draws (the wide sheet's "keeps up") drives both sides with Chromium's gesture scroll instead (CDP `Input.synthesizeScrollGesture`, `gestureSourceType: 'mouse'`; GPUI gets it as wheel events) (`docs/DECISIONS.md`, "Measurement"); Firefox applies at most one page per wheel event, so no scripted fling crosses the table there; the harness's `fling()` ends with a catch-up event a native scroller clamps, so a DOM fling sends equal events; headless Chromium hides scrollbars (`--hide-scrollbars`) and headless Firefox has none with width, so a thumb drag needs Chromium launched without it (`ignoreDefaultArgs: ['--hide-scrollbars']`, as `perf/contender.ts` does), WebKit a styled `::-webkit-scrollbar`, or a headed Firefox with `ui.useOverlayScrollbars: 0`.
- **The parity check's overlay scrollbars** (`perf/tanstack-parity.ts`): macOS's take a press only while shown, so `showBar` brings the bar up first and `downOnBar` presses again (up to three times) when the press's target wasn't the scroller; Firefox's track press runs headed (`--firefox`, classic scrollbars); WebKit's scripted wheel can arrive a whole drag settle late, so an input inside a drag counts only if it arrived inside it. It waits for reads to finish (`quiet`) before timing a drag: a page landing sends its prefetch's reads, drag or not, as the tall table's does. Firefox warns of a "scroll-linked positioning effect": the scroll model's design (`docs/dom-scroll-model.md`), ignored with the engine's warning.
- **Input latency and frame work come from Chromium's trace** (`docs/contender-contract.md`, "Reading the metrics"), not the page's Event Timing observer (rounded to 8 ms, nothing under 16 ms, no wheel). GPUI on WebGL2 in Chromium: an init script deleting `Navigator.prototype.gpu` makes its `Auto` backend fall back; check the backend from its first GPU call (`shared-web/perf/`'s `firstDrawProbe` records its API); a timing run carries no GPU-call wrapper (`perf/contender.ts`'s `gpuiProbe` stays hooked and belongs to latency runs only).
- **The tall table's fixtures are the component's** (`components/tall-table/fixtures/`, its README the formats), but `cells.json`'s drawn cells come from here: `perf/cell-fixture.ts` picks rows from data/'s file with native DuckDB, jumps the contender's release build (`?measure&cells`, 2560 px wide so every column draws) to each, and fails unless each drawn value is DuckDB's; a file of text alone (the admin table's) is sampled as text, every column, its rows picked by their characters (each column's longest and shortest, the first row of each set of non-ASCII blocks, so every script and the flags), each drawn text DuckDB's to the byte. It keeps the hand-written `rounding` cases, `number_px`, and the `resize` section, and fails if `number_px` doesn't give the budgets the contender drew.
- **Element Timing entries arrive after the paint, in an observer's task, and the browser buffers only 150:** a script reading cells' paints records them from an init script (`perf/tanstack-contract.ts`'s `recorder`) and waits for a row's entries before calling them missing.
- **DuckDB's worker isn't in the page's resource timing,** so a check that times the engine's start reads the engine's JS chunk (`assets/engine-*.js`), which the open imports first. **Firefox warns about DuckDB-Wasm's `eh` bundle** (the deprecated `try` instruction): the engine's, not the view's; `tanstack-view` ignores that one warning.
- **The metric scripts** (`perf/metric-*.ts`) run Chromium with its scrollbars shown, as `tanstack-parity` does, and bring an overlay bar up (a wheel there and back) before a track press on both sides. A script that measures keys presses the probe key first: the first key changes the probe's state on both sides. The fling goes out on a fixed schedule without awaiting each wheel (Playwright's `mouse.wheel` waits for the page's handling, so an awaited loop paces itself by each side's cost), and Chromium coalesces wheel events on a native scroller, so the input is the events' summed `deltaY`, not their count. Chromium's compositor frame reporter (`PipelineReporter`) doesn't see GPUI's canvas frames, so late frames come from the main thread's frames. The DOM's probe key changes nothing visible, so its `EventLatency` reaches no frame; GPUI makes no GPU calls for an unchanged scene, so its `contender:input` isn't always right after a GPU call. Memory needs `--enable-blink-features=ForceEagerMeasureMemory` (else `measureUserAgentSpecificMemory` waits for a GC, up to 20 s) and a cross-origin-isolated page.
- **Memory includes the canvas:** `measureUserAgentSpecificMemory` counts a canvas's backing store under the type `Canvas` (GPUI's window at 1440×900, DPR 2: 2880×1800×4 bytes, 19.8 MiB), and a wasm's linear memory under `JavaScript`; the GPU's memory is in neither side's reading. A wasm memory only grows, so a garbage collection never shrinks GPUI's.
- **The wasm's names** are stripped in the release build (`strip = true`); `gpui-parts` relinks with `CARGO_PROFILE_RELEASE_STRIP=none` and runs wasm-bindgen without `--keep-debug`: wasm-opt aborts on the DWARF std's objects carry (`compile unit size was incorrect`).
- **The throttled network doesn't reach a same-process frame's worker.** The page's `Network.emulateNetworkConditions` throttles its frame's own requests, but not those of the frame's dedicated worker (DuckDB's: its bundles and every data read), and a worker target answers the command `Not supported`; a same-origin frame has no CDP session of its own. So a script that compares the page with the bare contender throttled sends both through `shared-web/perf/serve.ts`'s `startThrottlingProxy` (the same latency and shared download) with only the CPU throttled by CDP (`perf/readout-cost.ts`, on port 4338 in front of 4337); the bare page's data reads timed within 3% of Chromium's own throttling (`docs/DECISIONS.md`, "Measurement").
- **The trace books the frame tree's rendering on the top frame:** `Paint`, `PrePaint`, and `Layerize` name the top frame however much of them is the contender's frame, so the page's own time (`readout-cost`) counts its timers, script, style, and layout, never those phases.
- **Anything from a frame's realm keeps the whole frame alive.** A closure over a frame's `window`, an array its realm made (live tail's ring), or even a plain object literal a frame's script created and the page holds keeps the destroyed frame's window and document from being collected. The page drops its references when it replaces a frame (`live.ts`'s `release`); a script that tracks frames from an init script makes its records with a function from the top's realm (`perf/session-memory.ts`'s `tracker`).
- **A stale NXDOMAIN:** a resolver that looked seiza.io up before it had records can keep the miss for the zone's negative TTL (30 min). `worker-check` and `data-read` take `--resolve-via 1.1.1.1`.

## Files

```
  perf/             # harness.ts, page.ts (the page), contender.ts + metric-*.ts (the per-use metrics on either contender; tail-metric.ts and throttle-control.ts, what some of them share), ab.ts (an interleaved A/B of a metric against a kept build), readout-cost.ts (what the page's readouts cost the contender), cold.ts, placeholder.ts, reach.ts, sizes.ts, gpui-parts.ts, cell-fixture.ts, wide.ts (and wide-tools.ts, its resize, selection, copy, and copy line), market.ts, tail.ts, wall.ts (wide.ts at the wide level, market.ts at the market level, tail.ts at the tail level, wall.ts at the wall level; wall-grid.ts, the wall's tables as published and what the same grid and colors are, which wall.ts and tanstack-parity.ts share), tanstack-view.ts, tanstack-contract.ts, tanstack-parity.ts, tanstack-sizes.ts (the TanStack contender), admin.ts (the admin table's capabilities, both), engine-files.ts (both), data-read.ts, burst.ts (requests per 10 s, for the rate limit), session-memory.ts (the tab's memory over a scripted session on the page), budgets.json, baseline.json, results/
```

## Commands

What each check covers, item by item, is in its script's header comment and the justfile's comment above its recipe (with its flags); read those before running or changing one.

```
just observatory page [flags]          # the page with both contenders in its frames: its budgets, hosting, every route's behavior and numbers (--check, --shots, --url)
just observatory cold [flags]          # the GPUI contender's cold load at a level, reference + throttled, median of 10 (--level, --check, --url)
just observatory placeholder [flags]   # the GPUI contender's placeholder shell against its first frame (--level, --controls)
just observatory sizes [flags]         # the GPUI wasm with and without the panel, the panel-leak and home-path checks (--check)
just observatory gpui-parts [--label]  # the GPUI page by part, brotli
just observatory engine-files [flags]  # both builds' duckdb/ byte-identical and loaded from /observatory/duckdb/ (--controls)
just observatory reach [flags]         # End reaches the last row, and the contract
just observatory tanstack-view [flags]     # the TanStack view in three browsers (--gpui)
just observatory tanstack-parity [flags]   # the TanStack contender's parity with the tall table, item by item, at each level
just observatory tanstack-contract [--label] # the TanStack contender's hydration, probe, and contract at each level
just observatory tanstack-sizes [flags]    # the TanStack contender's JS by the build manifest (--level, --check)
just observatory wide | market | tail | wall [flags] # both contenders at that level: cells, colors, marks, controls, and (wide) the tools
just observatory admin [flags]         # the admin table's capabilities on both base builds, and the fonts path
just observatory cell-fixture [--check] # cells.json's drawn cells from the GPUI contender's builds
just observatory metric <name> [flags] # one per-use metric on the bare pages, cold (--side, --runs, --profile, --scenario, --stop, --fonts, --summarize)
just observatory ab --build <dir> --label <name> # an interleaved A/B of a metric against a kept build
just observatory readout-cost [flags]  # what the page's readouts cost the contender
just observatory burst [flags]         # the most requests one visitor sends in any 10 s
just observatory session-memory [flags] # the tab's memory over a scripted session on the page
just observatory data-read [flags]     # DuckDB-Wasm reading the data in production beside Tycho's R2 path (needs `just tycho build`)
```

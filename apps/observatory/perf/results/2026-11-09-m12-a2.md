# M12 part A2: the fonts spike (2026-11-09)

Measured on Apple M1, Darwin 25.6.0 arm64, machine `local`: the GPUI contender's base release build (gpui-kit 0.9.0, gpui-pre-web and gpui-pre-wgpu 0.3.11, cosmic-text 0.19.0 shaping with harfrust 0.5.2) on A1's draft countries file, in Playwright 1.63.0's Chromium 153.0.8010.12, headless, 1440×900 at DPR 2, reference profile. The DOM's drawing is the same Chromium (HarfBuzz) with the same faces. HarfBuzz 14.3.0's `hb-shape` for the offsets. A spike: fonts in → drawn is n = 7, not a protocol run. Load average not recorded.

Raw: none committed. Screenshots in `raw/2026-11-09-m12-a2-shots/` (gitignored): `default.png` (the first screen without fonts), `fonts-sheet.png` (four names per script, GPUI over the DOM, with ink widths and profile correlations), `marks-*.png` (the names a lost offset changes, zoomed). The spike's code was throwaway and is reverted: an export adding fonts after first paint and marking the frame drawn with them, `?cjk` for `EmojiAndCjk` through a `Bootstrap` option, and `?file=` opening the countries file on the base build.

## What changed

Nothing kept. The spike's builds: the base wasm with a minimal runtime toggle (the font export and the `EmojiAndCjk` parameter) against the clean base, and Tycho with the `Bootstrap` option against without it (below).

## The default: the gap, and the flags

On the base build, unchanged: Latin, Greek, and Cyrillic draw in IBM Plex Sans. Every other script's characters draw as the face's notdef box, one per character (`default.png`: Afghanistan's, Algeria's, Armenia's, Bahrain's, Bangladesh's, Bhutan's names). Every flag draws in color through gpui-pre-web's Canvas fallback for emoji, which `shared/` turns on: the canvas's "flags missing on GPUI" is wrong, as the PLAN said.

## Which route reaches the faces: the first, automatic fallback

The 13 Noto faces added with `add_fonts` after first paint, and nothing else changed: every script's names draw in its face, and each name's drawn width matches the DOM's within 1 px (30 names, four per script where it has four). Han and Hangul draw through the browser with `EmojiAndCjk` (widths equal to the DOM's).

The second route, `FontFallbacks` on the host's root style, drew the same: every name's width and ink profile identical to the first's, and the logged shaping of Sri Lanka's name gave the same faces and glyphs either way. It adds nothing, so the host sets no fallback list.

### What's drawn wrong: GPUI drops the marks' offsets

gpui-pre-wgpu 0.3.11 (`cosmic_text_system.rs`, `layout_line_no_separators`) places each glyph at cosmic-text's `glyph.x` and `glyph.y` and never adds `x_offset` and `y_offset`, which carry the font's mark positioning (GPOS); cosmic-text's own `LayoutGlyph::physical` adds them. A mark the font places by an offset draws at its pen position instead.

The shaping itself is right: harfrust gave Sri Lanka's name HarfBuzz's glyphs (58, 130, 96 in one cluster, then the rest), and HarfBuzz puts 130 and 96 at −865 and −748 units, back over the ශ; GPUI drew them after it.

Every text in the file shaped by HarfBuzz in the face GPUI would use (733 texts: names, English names, and capitals; IBM Plex Sans for Latin, Greek, and Cyrillic): **29 carry a positioned mark**, 25 Arabic names, Cambodia's, Israel's, Myanmar's, and Sri Lanka's. None in IBM Plex Sans: the default view is unaffected. Most offsets are under a pixel at 14 px (54 units = 0.76 px). The visible ones:
- **Sri Lanka** (Sinhala): the rakaransaya and the ii sign 12 px right of where they belong; the name doesn't read as written.
- **Palestinian Territories** (الأراضي): the final ي's two dots below draw inside it (−232 units, 3.2 px), so it reads as ى, another letter.
- **Cambodia** (Khmer): the vowel under the subscript 4 px too high (−296 units).
- **Morocco**, **Afghanistan**, and the Arabic names with a dot at 256,−168 units (3.6 px, 2.4 px): a dot visibly off its letter, still legible.

One web search found no upstream issue; the trackers themselves (gpui-kit's, Zed's) aren't searched yet. Zed's Linux text system builds its glyphs the same way (zed-industries/zed#30660).

## Fonts in → drawn

From the export's call (the 13 faces' bytes in hand) to the mark right after the frame drawn with them: **median 24.5 ms** (22.6–35.9, n = 7, cold, reference). Their fetch from the local server before it: ~25 ms (unthrottled, not a network measure). `add_fonts` parses 1.8 MiB of faces in that task.

Tycho never sets the option, and its wasm grows 23 bytes; brotli grows 1.3 KiB, since the moved code compresses differently. The JS that fetches the faces would be the toggle's own, after first paint.

## What changed

- **`perf/metric-memory.ts`** (`just observatory metric memory`, ports 4335–4336). It opens the file, then walks to the last row with the replay's jump, 4 pages a step over the file's last 144 pages. It waits out each landing until no data read is in flight and the cache's bytes have held for 1 s. Memory is read once open and at the end, both as measured and after a forced GC: `measureUserAgentSpecificMemory` by type, the workers apart, Chromium's JS heap and DOM nodes, and the wasm's linear memory (an init script keeps every `WebAssembly.Memory` the page instantiates). It also records each file's wire bytes. The gate: every run of a side ends on the same `state.cacheBytes`, on both devices. Added after a code review, checked with one run of each side (the same readings): the by-type split moved into `memoryOf` (metrics module); any page memory type other than `JavaScript` or `Canvas` fails the run; a landing not quiet within 120 s fails it; a type a run lacks is left out of its median. The workers' reading is the measured one (`workerMiBEnd`; the GC is the page's), where the JSON above names it `workerMiBEndAfterGc`.
- **`perf/gpui-parts.ts`** (`just observatory gpui-parts`). It splits the GPUI page by part, brotli: the HTML (the placeholder's inlined font against the rest), the JS (wasm-bindgen's glue, minified alone by Vite's minifier, against the bundle), and the wasm by crate group. Its guard: gpui, the component, the data layer, and the host must each land in their own part. It caught a first version that counted gpui as the host's, because `gpui-pre` builds a library named `gpui`.
- **`perf/budgets.json`**: two recorded rows, "Page memory at equal work", reference and throttled (the README's table). No contender, page, or component changed. The wasm is unchanged (`tall_table_gpui_bg-gwnmFiJ4.wasm`, 2698.0 KiB brotli).

|---|---|---|---|---|
| Page memory, all of it | 55.5 | 45.7 | 16.1 | 16.2 |
| … the canvas's backing store (`Canvas`) | 29.7 | 19.8 | — | — |
| … the rest (`JavaScript`, the budgets' row) | **25.8** | **25.8** | **16.1** | **16.2** |

Spread over the 10 runs: TanStack 16.06–16.17 MiB. GPUI 45.5–85.2 MiB fast and 45.5–65.6 slow, all of it the canvas (below). Its `JavaScript` and wasm readings are steady.

**What each side's reading holds.**
- **GPUI:**
  - The canvas's backing store, counted by Chromium under `Canvas`: 2880×1800×4 bytes, 19.8 MiB per buffer.
  - The wasm's linear memory under `JavaScript`. It holds the page cache's Arrow bytes, the font database, the scene, and the framework's state. It never shrinks.
  - The JS glue's heap, 3.4 MiB.
- **TanStack:** its JS heap, the cache's Arrow buffers (`ArrayBuffer`s, outside Chromium's `JSHeapUsedSize` but inside `measureUserAgentSpecificMemory`'s `JavaScript`), and the DOM. It has no `Canvas` entry.
- **Neither side:** GPU memory (textures, the glyph atlas), which the API doesn't see.

Between open and the end, 10.9 MiB of pages went into the cache. GPUI's wasm grew 10.8 MiB (12.0 → 22.8) and TanStack's page 12.3 MiB (3.8 → 16.1). The forced GC changed no reading by more than 0.3 MiB: `ForceEagerMeasureMemory` already measures what's live.

**GPUI's canvas holds 1, 2, or 3 window-sized buffers, varying by run, not by device.** Readings were 19.8, 39.6, or 59.3 MiB. Fast device: 1 buffer in 6 runs, 2 in 3, 3 in 1. Slow device: 1 in 6, 2 in 4. Once open it was already 2 in three fast runs. Chromium seems to keep a presentation buffer per frame in flight, but that wasn't traced here. That count is the whole of the 55.5 vs 45.7 difference between devices, and the whole spread.

**So the slow-device row holds, with the canvas named apart.** Without the canvas, fast and slow agree to 0.1 MiB on both sides. Part C's open question, the throttled fling reading less memory on TanStack (9.2 → 4.8 MiB) and more on GPUI (42.3 → 55.8), comes from two things:
- **The data read:** 21.4 vs 5.8 MiB of pages. On TanStack page memory follows the Arrow buffers it holds.
- **GPUI's canvas buffer count and its wasm's high-water mark.** A wasm memory keeps every page it grew to, so a fling's transient decoding stays counted.

The decision this leads to, for the card: `docs/DECISIONS.md`, "Measurement" (2026-10-20).

### Experiment: scattered jumps (rejected)

The first session jumped to 24 fractions, 1/25 to 24/25. Both sides agreed with each other on every run, but the devices didn't: 14,062,832 cache bytes fast, 13,724,512 slow (−2.4%), so the gate failed 20 of 20 slow runs.

The cause is the paging's design, the same on both sides (`paging.ts`, `rowsMoved`). Prefetch leans ahead while the rows move and evens out once they rest 250 ms, and it cancels reads that are no longer wanted. A fast device's lean-ahead pages land inside the rest; a slow one's are cancelled or never start. The walk avoids this: each landing's even prefetch (2 pages either side) reaches the next landing, so any lean-ahead page is a walk page anyway, and nothing lies past the last row.

At those near-equal pages the readings already agreed: GPUI `JavaScript` 28.5 vs 28.0 MiB, TanStack 18.6 vs 18.3.

## The wasm by part

`gpui-parts`: the release wasm relinked with its names kept (`CARGO_PROFILE_RELEASE_STRIP=none`, wasm-opt with `-g`). Its code section is 0.06% larger than the shipped file's, with 7 more functions of 22,480. Each function body's crate is the first non-std crate in its demangled name. Each crate's part comes from `cargo tree`: the framework if gpui-kit reaches it, else `seiza` and the contender (the host), the component, or the data layer. Each part's bodies were compressed alone (brotli 11) and scaled to the whole file's 2698.0 KiB; compressed alone they sum to 2689.3.

| Part | Functions | Raw KiB | Brotli KiB | Share |
|---|---|---|---|---|
| Framework: gpui-kit and everything it pulls in (gpui, wgpu and naga, the text stack, image and SVG decoders, …) | 19,383 | 6928.6 | 1997.9 | 74.1% |
| Static data: strings and tables, unnamed (the data section) | — | 2198.9 | 513.5 | 19.0% |
| Rust's runtime and the JS bindings (core, alloc, std, wasm-bindgen, js-sys, web-sys, unnamed shims) | 2775 | 398.6 | 123.1 | 4.6% |
| The module's other sections (types, imports, exports, tables) | — | 96.9 | 38.6 | 1.4% |
| The data layer: seiza-duckdb and Arrow | 142 | 30.4 | 11.2 | 0.4% |
| The component: seiza-tall-table | 117 | 16.0 | 7.4 | 0.3% |
| The host: the contender and `seiza` | 70 | 14.7 | 6.4 | 0.2% |

So the card can split the wasm into framework, component, and data layer. The component and the data layer together are 18.6 KiB of 2698, against TanStack's 106.9 KiB of JS. The static data can't be split by name: wasm-opt merges segments, and nothing in them names a crate. A scan found no embedded font or image file in it.

The largest crates by code (raw): gpui 964 KiB, naga 575 (WGSL's compiler, wgpu's), gpui-component 278, gpui-base 263, wgpu 262, read-fonts 230, skrifa 224, regex-automata 219, zune-jpeg 216, wgpu-core 212, usvg 195, taffy 184, harfrust 180, tiny-skia 171, image-webp 151, image 151, gpui-web 147. The full list is in the JSON's `topCrates`.

## Experiments and controls

- The scattered session (above): the equal-work gate's negative control in effect, failing 20/20 slow runs where the pages differed.
- `gpui-parts`' part guard failed its first version (gpui counted as the host's) and passes now.
- Not done: the canvas buffer count wasn't traced to its cause. It's Chromium's, not either contender's.

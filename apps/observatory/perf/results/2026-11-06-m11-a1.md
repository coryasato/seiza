# M11 part A1: live tail's file, its row groups, and the replay's path (2026-11-06)

Measured on Apple M1, Darwin 26.6.2 arm64, machine `local`, native DuckDB (`@duckdb/node-api`, `data/`'s lockfile): a spike that sizes the file, not a protocol run. No browser ran; the reads in the browser are part A2's.

Raw: `2026-11-06-m11-a1-file.json` (the draft `data/prep-nasa.sql` at five row group sizes: the file's bytes, row groups, footer, and a 1,024-row page's read time).

## What changed

Nothing built in the contenders. `data/prep-nasa.sql` drafted (part B wires it into `prep.ts`, which pins the source's SHA-256 first).

## The file

From NASA-HTTP's July 1995 log (20,676,672 bytes gzipped, SHA-256 `199109ed…27488`, 1,891,714 lines), by the rules in [`docs/DECISIONS.md`](../../docs/DECISIONS.md), "Scenarios", 2026-11-06:

| Step | Lines left |
|---|---|
| Read (8 lines not UTF-8 skipped by the reader, the only kind of skip allowed) | 1,891,707 |
| Parsed (the 3 lines with control bytes and the truncated last line fail the log's shape) | 1,891,703 |
| Kept (query strings cut; 617 with `@` and 103 failed `~` paths dropped) | **1,890,983** |

- **Columns:** `time` `TIMESTAMP` (the log's wall time, every line −0400, checked), `request` `VARCHAR` (at most 333 characters), `status` `USMALLINT` (200 to 501), `bytes` `UINTEGER` (at most 6,823,936; NULL on 19,607 rows).
- **Span:** 1995-07-01 00:00:01 to 1995-07-28 13:32:25, 2,381,544 s; the rows never run backwards (checked).
- **Byte-identical:** two builds gave the same SHA-256 (`9bb2d937…0ca2` at 30,720 rows a group).

A page read is the page SQL (`file_row_number` between its bounds) for 1,024 rows at 40 places through the file, the footer cached, one process. The wide sheet's 2,048 (its first page's bytes) doubles this file: zstd compresses a small group of short strings badly, and the footer grows with every group. **The draft takes 30,720:** 9.27 MiB, ~157 KB a group (the first page's read by range), the fastest native read. A2 checks it in DuckDB-Wasm.

## The replay's path

- **At 100k rows/s** the tail needs a new page about every frame (~1,700 rows arrive a frame, a page is 1,024), ~60 reads a second, a lap of the file every ~19 s. By range, each read sends ranged requests (4 a page on the wide sheet), so the requests would scale with the rate against the zone's rate limit and the Worker's billed requests. Decided: the open by range, then the file fetched whole and registered in the engine as a `File` (`@seiza/duckdb`'s `registerFile` takes one), the feed starting once it's in hand ([`docs/DECISIONS.md`](../../docs/DECISIONS.md), "Scenarios").

## Experiments and controls

- A `latin-1` read of the gzipped log failed ("File is not latin-1 encoded"); the reader's own UTF-8 check skips the 8 lines instead, and prep fails if it skips one for any other reason.

## Reproducing it

The draft runs from a scratch script that substitutes `${raw}`, `${rowGroup}`, and `${fetched}` as `prep.ts` will; part B adds `just observatory data --only nasa`.

# M1 part A: the DOM scroll model, sized (2026-10-15)

Measured on Apple M1, Darwin 25.6.0 arm64, machine `local`, with Playwright 1.63.0: Chromium 153.0.8010.12 (headless=new), Firefox 155.0, WebKit 26.6, all headless at 1440×900. The TanStack runs follow the reference protocol (Chromium, DPR 2 with the DPR shim, a cold browser per run, median of 10, variants alternating); the other scenarios are behavior checks, one run per browser and setting, at DPR 1 with the browsers' scrollbars shown. Load average 2.12 → 2.33 over the suite (a busy machine; the TanStack comparison is between variants run alternately, so both saw the same load). No throttled run: nothing here is a budget.

On the throwaway page in `spike/` (fake rows, no DuckDB): a scaled native scroller over 1,567,523 rows of 30 px, laid out by TanStack Virtual (`@tanstack/react-virtual` 3.14.19, `virtual-core` 3.19.4) under React 19.3.1. The design it led to: [`../docs/dom-scroll-model.md`](../docs/dom-scroll-model.md).

These are the second run of the suite, after a code review fixed the model (below, "Review fixes"); the first run's files were overwritten. Raw (`just observatory spike --label m1-a`, `just observatory spike-sizes --label m1-a`): [`…-caps.json`](2026-10-15-m1-a-caps.json), [`…-reach.json`](2026-10-15-m1-a-reach.json), [`…-continuity.json`](2026-10-15-m1-a-continuity.json), [`…-bar.json`](2026-10-15-m1-a-bar.json), [`…-tanstack.json`](2026-10-15-m1-a-tanstack.json), [`…-sizes.json`](2026-10-15-m1-a-sizes.json), and the negative control [`…-stale-control-reach.json`](2026-10-15-m1-a-stale-control-reach.json).

Chromium and WebKit clamp; Firefox drops the height altogether. ## Reaching the last row

Spacer 2^24 px (stretch 2.80 overall), re-anchored past 1,800 px of drift, 1:1 zones of 2^20 px at the ends. "Last row" means row 1,567,522 visible with its bottom flush with the viewport's (gap 0 px); Home and Ctrl+Home also checked row 0 at the top.

| | End, Ctrl+End | Wheel from 40,000 px above the end (50 × 1,000 px) | Thumb dragged to the bottom | Steady fling (180 × 261,254 px) | Harness-style fling (last event up to 2.2 M px) |
|---|---|---|---|---|---|
| Chromium, `scrollBy` | yes | yes | yes | yes, 263 re-anchors | 1.32 M px short |
| Chromium, `scrollTop =` | yes | yes | yes | yes | 1.36 M px short |
| WebKit, `scrollBy` | yes | yes | yes | yes, 233 re-anchors | 1.35 M px short |
| WebKit, `scrollTop =` | yes | yes | yes | **260,503 px short** | 22.17 M px short |
| Firefox, both | yes | yes | — (no scrollbar headless) | 46.87 M px short (868 px per event) | 46.93 M px short |

Every probed frame's top row matched the model (a row read with `elementFromPoint` at each rAF): in the steady fling, 0 of 373–388 frames blank or off in all three; through the top band (120 × 600 px of wheel from Home, past the content's first rebase while the window is pinned at row 0), 0 of 253–259. **Negative control:** without the forced render when the rows' bases move (`?stale`), 336 of 374 steady-fling frames in Chromium showed the wrong rows, up to 25.1 M px off.

## What a re-anchor looks like

From the middle of the table: 200 wheel events of 120 px (24,000 px), then 30 Page Downs 60 ms apart with the browser's own smooth keys (`keys: 'native'`), so a re-anchor lands mid-animation. The control (`none`) never re-anchors.

| | Wheel moved (shown / model) | Re-anchors | Frames backward | Frames off the model | Page Down moved |
|---|---|---|---|---|---|
| Chromium none | 24,001 / 24,001 | 0 | 0 | 0 | 25,800 |
| Chromium `scrollBy` | 24,001 / 24,001 | 9 | 0 | 0 | 25,800 |
| Chromium `scrollTop =` | 24,001 / 24,001 | 9 | 0 | 0 | 25,800 |
| Firefox none | 24,000 / 24,000 | 0 | 0 | 0 | 26,040 |
| Firefox `scrollBy` | 24,000 / 24,000 | 9 | 0 | 0 | 26,040 |
| Firefox `scrollTop =` | 24,000 / 24,000 | 9 | 0 | 0 | **19,884** (input lost) |
| WebKit none | 24,000 / 24,000 | 0 | 0 | 0 | 13,301 |
| WebKit `scrollBy` | 24,000 / 24,000 | 9 | 1 (−137 px, during a Page Down) | 0 | 11,833 |
| WebKit `scrollTop =` | 24,000 / 24,000 | 9 | 0 | 0 | 11,771 |

No frame was blank. At rest the shown position equals the model's in every run. A re-anchor is invisible at a wheel's pace in all three: no frame moves back, nothing is lost, and the thumb moves back by at most 1,800 / 16,776,316 of its track (~0.1 px). The exceptions are all during an animated or fast scroll, and all against the `scrollTop` assignment: it lost Page Down input in Firefox and fling distance in WebKit, so the model uses `scrollBy`. With `scrollBy`, WebKit showed one frame back during a Page Down (−137 px, n = 1; −129 px in the first run). WebKit's Page Downs cover about half the distance of the others in the control too: a press 60 ms after the last cuts its animation short. The contender's own keys are instant, so this only bears on smooth scrolls the browser animates itself (a track press, a trackpad's momentum).

## Telling a thumb drag apart

With scrollbars shown (Chromium without Playwright's `--hide-scrollbars`, WebKit with a styled `::-webkit-scrollbar`):

| | Thumb drag (10 × 20 px) | Track press |
|---|---|---|
| Chromium | `pointerdown`, `pointerup` in the bar; no `pointermove`; 10 scrolls, all put down to the thumb; 319,632 rows | `pointerdown`/`pointerup`; 6 scrolls of a page, 1:1; 26 rows |
| WebKit | the same; 8 scrolls to the thumb and 1 after `pointerup` (a step under a screen, 1:1); 318,738 rows | the same; 12 scrolls, 1:1; 29 rows |
| Firefox (headed, below) | `pointerdown`, `pointerup` in the bar; 20 scrolls, all put down to the thumb; to row 515,461 | `pointerdown`/`pointerup`; 10 scrolls of a page, 1:1; 29 rows |

Wheel and keys were each put down to their own source in all three browsers, and the contender's keys moved the same everywhere: 5 ↓ moved 5 rows, a Page Down 30. The model doesn't depend on the pointer events: a step bigger than a screen with no wheel, key, or touch behind it is the thumb, and the 80 ms settle is 80 ms without a scroll event. Headless Firefox draws only overlay scrollbars of no width, whatever `ui.useOverlayScrollbars` or `layout.testing.overlay-scrollbars.always-visible` say, so Firefox ran headed.

**Firefox, headed** (Playwright's Firefox 155 in a visible window, `ui.useOverlayScrollbars: 0`, a 15 px scrollbar with a 20 px thumb, 1440×900 at DPR 1; a one-off script, its output quoted):

```
thumbDrag  {"first":515461,"last":515491,"contiguous":true,"sources":{"bar":20},"inBar":["pointerdown","mousedown","pointerup","mouseup"]}
trackPress {"first":515490,"last":515520,"contiguous":true,"sources":{"other":10},"inBar":["pointerdown","mousedown","pointerup","mouseup"]}
to bottom − 2 px (inside window):  20 events, all "bar"; last scrollTop 16776316, top row 1567493; rows 1567489–1567522 rendered
past window bottom (+40 px):       reached 16776316, then the last event scrollTop 0 (Firefox's own), no pointerup; rows 0–33
```

The drag (with a 300 ms pause in it) is told apart and reaches the last row when released over the window. Released 40 px below the window, Firefox itself put `scrollTop` back to 0 and sent no `pointerup`; the model followed. Likely Firefox's thumb snap-back for a pointer far from the scrollbar, here a synthetic one off the window; not confirmed with a real mouse.

With the browser's keys, WebKit under Playwright didn't arrow-scroll a focused div at all, and Chromium's arrow moved 40 px: the contender handles its keys itself.

## TanStack Virtual: the full count against a moving window

Median (min–max) of 10 cold runs each, Chromium, DPR 2. The fling is the steady one (180 equal events, top to bottom), traced: main-thread time is the sum of `ThreadControllerImpl::RunTask` on the page's main thread between two marks.

| | Full count (1,567,523) | Window (4,096) |
|---|---|---|
| Navigation to rows | 52.3 ms (49.5–70.6) | 39.0 ms (35.8–57.0) |
| Mount to rows | 20.7 ms (19.1–24.3) | 8.3 ms (7.7–9.5) |
| JS heap + ArrayBuffers after mount, GC'd | 32.33 MiB | 2.51 MiB |
| Building the measurements (detached, 20 runs) | 28.4 ms (17.8–31.0) | 0.37 ms (0.31–0.45) |
| Holding them (detached) | 29.91 MiB | 83.9 KiB (83.5–93.1) |
| Fling: main-thread busy per frame | 4.22 ms (4.04–4.27) | 4.20 ms (4.09–4.27) |
| Fling: busy share of the window | 25.3% | 25.2% |
| Fling: scroll handler (model + React render), p50 / p95 | 1.66 / 1.92 ms | 1.64 / 1.90 ms |
| Fling: frame interval p95, frames over 50 ms | 16.7 ms, 0 | 16.7 ms, 0 |

The handler's median rose from the first run's ~1.1 ms because a re-anchor's own scroll event (no step, nothing to do) is no longer counted as a handled scroll; the main thread's total per frame didn't move.

**Chosen: the moving window.** The full count costs 30 MiB and a ~28 ms task at mount, and buys nothing in the fling. An earlier run of the window variant looked twice as cheap in the fling (1.76 against 3.51 ms per frame, n = 1) because it wasn't rendering: the stale-rows bug the frame probe and its negative control above now catch.

## Review fixes

A code review of the first run found, and this run fixes:
- The forced render checked only the window's base; rows are placed against the content's base, which also moves on its own (the top and end bands, every rebase of the full count). It now checks both. The probes found no wrong frame from it before or after (each probed step moved 20+ rows, so TanStack re-rendered anyway); it bites on a sub-row step across a rebase.
- Ctrl+Home and Ctrl+End reached the browser, which ran the scroller to its end and left the content mid-table; they are now the model's ends (checked above).
- The model now does what the design note says: the contender's keys (it had only Home, End, Cmd+↑/↓), jumps through `scrollBy` in `scrollBy` mode (they assigned `scrollTop`), the thumb mapping for any scroll while the pointer is down on the scrollbar, and a re-anchor's own zero-step scroll event ignored (it had counted toward sources and restarted the idle timer).
- The continuity metric now leaves out blank frames (none occurred in either run).

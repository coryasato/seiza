# M9 part D: the wide sheet's numbers (2026-11-03)

Measured on Apple M1, Darwin 25.6.0 arm64, machine `local`, Chromium 153.0.8010.12 headless=new, 1440×900 at DPR 2, cold (a fresh browser per run), **median of 10 runs** per side, stop, and profile, both contenders alternated; reference and throttled (CPU 4×, Fast 4G). gpui-kit 0.9.0, React 19.3.1, TanStack Virtual 3.14.19, Arrow 17.0.0, DuckDB-Wasm 1.32.0 (each file's `versions`). The wide level's release builds of both contenders, built right before the runs. One sitting, 10:52 to 13:25; load average 7.3 at the start (the builds), 2.2–3.5 after.

Raw (`<metric>` per file, each labelled `wide-sheet-<stop>`):
- `2026-11-03-m9-d-scroll-wide-sheet-rows-26.json`, `-rows-22`, `-rows-20`, `-rows-18`: keeps up, at each stop (`perf/metric-scroll.ts`).
- `2026-11-03-m9-d-{usable,data,response,reach,cost,memory}-wide-sheet-rows-20.json`: the once-a-scenario metrics at the default stop. The cost file is a re-run after the review (below), which overwrote the first.

## What was built

- **`metric-scroll`**, keeps up at each stop: the file read whole first (`readWhole`: the replay's jump to each of its 11 pages, each landing quiet), then the three gesture scrolls (`SCROLLS` in the metrics module: down 37,500 px at 18,750 px/s, sideways 12,000 at 6,000, fast 120,000 at 60,000), each traced on its own and ended by its own rest (nothing drawn for 300 ms since its start). A scroll that draws under two frames fails, as does a vertical one that falls short of its distance. Readings: the frames that drew new cells over the display's frames (`drewShare`), their work, the busy share, the DOM's compositor frames; `keepsUp` over the median down and sideways shares.
- **The metric scripts take `--scenario` and `--stop`** (`perf/contender.ts`): the level's builds, `?scenario=&stop=`, a file a stop. On the level every scripted scroll is the gesture: response's wheel (300 px at 10,000 px/s), cost's use (the gesture to the last row at 60,000 px/s), memory's session (the file read whole, then five gestures across every day and back). Reach reads the file's last key from its first column. The base's fling script doesn't run on the level.
- **`compositorFrames`** in `shared-web/perf/trace.ts`, one definition (whole, in part, dropped; `presented` = whole + in part): `readout-cost` reads `presented` as before, the spike the parts.

## The finding: the gesture reached GPUI at half its distance

Under DPR 2 emulation a 6,000 px `Input.synthesizeScrollGesture` reached GPUI's listeners as 3,000 px of `deltaY` and moved its view 3,000 px; the native scroller moved 6,000 (at 6,000 and 60,000 px/s). Part A2's spike sent the gesture unscaled, so **its GPUI side scrolled half as far, at half the speed**, as its TanStack side. `gesture` now scales GPUI's distance and speed by `devicePixelRatio` (checked: 6,000 px on both sides), as `wheel()` scales a wheel. The smoke run before the fix had GPUI's cost fling stop short of the last row; after it, every vertical scroll on GPUI moved its distance exactly.

Traced, the native scroller moved the fast gesture ~3.3% past its distance in every run (123,958–123,972 px for 120,000); untraced it moved exactly 120,000 (and down's 37,500 exactly either way). More distance for the DOM side, so the script allows up to 5% past and records `movedPx`.

## The review's fixes

`/code-review high` found ten; all are fixed.
- **The sideways scroll's distance wasn't checked.** Now it is: the DOM's `scrollLeft`, and the sum of GPUI's wheel `deltaX`. GPUI moves by its deltas, and its state has no horizontal position. A smoke run at ~710 and ~940 read 12,000 px on both sides, so the suite's sideways shares were taken at the full distance.
- **The scroll's busy share took in idle time.** Its window ran to the rest wait's first poll plus 100 ms, so the share was diluted. It now runs from the first frame that drew to the end of the last. The busy shares in this note's scroll files read low: the smoke run put them ~4–7 points higher (GPUI down at ~710: 72.3% against 67.5%; TanStack 49.2 against 45.2). The shares of frames drawn, their work, and keeps up don't depend on that window.
- **Cost's use window started early on GPUI.** It began at the zero-delta wheel that warms up `wheel()`'s device scale, which the gesture doesn't need. The gesture path now sends no warm-up, and the window starts at the first wheel with a delta. Cost was re-run in full: GPUI's use went 2,770 → 2,730 ms reference and 3,573 → 3,556 throttled; TanStack's moved −48 and −39 ms, within the runs' spread.
- **The rest, all with no effect on the numbers:**
  - The gesture moved to `shared-web/perf/harness.ts` (`gesture`, with `scaleByDpr`), beside `wheel()`.
  - The memory script uses the shared data-read counter, and reads the file's columns only on a scenario's level.
  - One `jump` helper replaces four copies.
  - The doc comments were placed and worded: `lastCell` is the first column, the wide sheet's station names aren't unique, and `end` at `count(*)` places the row.
  - No milestone ID in a decision's body.

## Against the plan's checks

- Every check passed but the two above, which are readings (GPUI's usable confirmed 8/10; 6 GPUI key inputs unread).
- The scroll metric's own checks held in all 160 runs: each scroll drew at least two frames, each vertical scroll moved its distance, every run's cache bytes matched.

## Reproducing it

```sh
just observatory gpui-build wide && just observatory tanstack-build wide
just observatory metric scroll --scenario wide-sheet --label m9-d-scroll        # every stop
for m in usable data response reach cost memory; do
  just observatory metric $m --scenario wide-sheet --label m9-d-$m              # the default stop
done
```

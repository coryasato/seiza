# M11 part C2: the TanStack contender at the tail level (2026-11-08)

Measured on Apple M1, Darwin 25.6.0 arm64, machine `local`, Chromium headless=new (Firefox and WebKit for `tanstack-parity`). Sizes are brotli at quality 11 from the release builds. `tail` at DPR 1 (2560×1700 for the cells, so every column and ~55 rows draw; 1440×900 for the marks); the contract and parity at the protocol's 1440×900, DPR 2 in Chromium. No cold runs: the level's per-use numbers are part D's.

Raw: `2026-11-08-m11-c2-tanstack-sizes-tail.json` (the level's JS, written as its baseline from the final build), `2026-11-08-m11-c2-tail.json` (both sides' tail check: the cells, the marks, the scroll back, the reopen, the failures, and the two sides compared), `2026-11-08-m11-c2-tanstack-contract.json` (the contract, the base's, the market level's, and the tail level's), `2026-11-08-m11-c2-tanstack-parity.json` (parity in three browsers, the tail level's following and colors). ## Experiments and controls

- **The cells after a fixed replay, both sides** (`tail`, the top stop, the clock paused once the tail is past the file's end): at the tail (lap 1), a lap's seam (rows 1,890,963–1,891,017, both laps), and the first rows, light and dark, every drawn cell against native DuckDB's row of the file: TanStack 220 of 220 cells in each view and theme (55 rows; GPUI's 216, 54 rows: the 55th is only partly in its body), the time the log's text moved on by its laps and muted, an error status in the error color, the bytes grouped. The control (no lap's shift) fails the tail's 55 and the seam's 35. The columns at 196, 470, 72, 90 px (the control, the kinds' widths, 4 off).
- **The same on both sides:** at the seam and the first rows, light and dark, 216 cells at rows both sides drew, 0 differing in exact text, shown text, or color (within one 8-bit step). The columns at the same `x` and `width` (time at 0, 196; request at 196, 470; status at 666, 72; bytes at 738, 90).
- **The clock at each side's receiver** (the default stop, 3 s): each message's rows since the last against the rate times the time between their stamps, within 1.1 rows on TanStack and 0.9 on GPUI (the limit, 2: the clock carries a fraction, and the stamp is taken after the count). Every message reached by a tail mark within 250 ms: TanStack 147 (p50 17.9 ms, max 56.4), GPUI 148 (p50 19.8, max 63.6).
- **The marks:** TanStack's 157 tail marks all set in a frame's callback (the commit that draws the tail), rising; GPUI's 23 sampled all right after a presented frame. Unmeasured, on both sides: no tail mark, no batches, no `__contenderTail`, no `__contenderFollowing`, no pause.
- **The scroll back under the clock** (`tail`): a wheel up lets go and the top holds for a second as 10,080 rows arrive, no tail mark meanwhile; End follows again (53 tail marks after it).
- **The replay starting over:** a reopen from 14,821 rows to 0 at its fill, 9,824 a second later, the log's first count 175 (the new clock's). A pause asked at the fill, before the worker exists, holds the rows at 0 until it's lifted.
- **Failing:** the clock's worker or the file fetched whole answered 404 fails the view after it filled; an unknown stop, an unknown scenario, and live tail on the base build fail the load.
- **The contract** (`tanstack-contract`, the tail level): the first screen prerendered and hydrated in place; usable 47.6 ≤ open 521.2 < filled 681.1 ms; the probe key 1.1 ms after its event; under the clock 76 messages in 1.5 s in order, 74 tail marks, the tail at 14,352 of 14,727 rows, following; the pause holds the rows; `jump(0.9)` (still paused) lands at row 13,392 of 14,881, exactly ⌊0.9 × 14,881⌋, and lets go, the top held as the rows grow once the clock resumes; `fling()` (the clock paused: it goes the rows it started with) ends at the last row and follows again; `open()` starts the replay over (19,926 rows to 0, then 4,859), a new batches array; framed, every mark relayed (23), the tail ones too.
- **Parity** (`tanstack-parity`, the tail level, Chromium, Firefox, WebKit): following under the clock; a wheel up lets go and holds the top as ~9,800–10,100 rows arrive; End follows again; with the clock paused, let go and a wheel down to the end follows again. At the file's first error status (from native DuckDB), light and dark: 112 cells, the time muted, the error status in the error color, nothing else painted.
- **What the first runs found** (each fixed before the runs above): TanStack Virtual's window kept the first render's row count (it subscribes to the offset once), so it drew 5 rows past the end; Chromium's scroll anchoring moved the scroller ~200 rows behind the model's back; the replay's `jump(0)` didn't let go (a model jump wasn't a landing), so the pin pulled the view back down; in WebKit a wheel up under the clock never let go (its scroll event arrived outside the model's input window, or read the pin's position). `docs/DECISIONS.md`, "TanStack contender".
- **A flake on the base level:** three of five full `tanstack-parity` runs failed Firefox's base-level tooltip on a loading row (rested on a loading row, its tooltip showed `3087 Beatrice Tinsley (1981 QJ1)` where the file's row holds `50250 Daveharrington (2000 BW22)`; the cause wasn't pinned). The base build is byte-identical to before the part, and Firefox alone passed it twice; it showed only with all three browsers run back to back, the final labeled run among them (its file records it). Recorded, not fixed here.
- **After the code review** (ten findings; nine fixed, one answered): the reader's move to the drawn end now moves the paging to the end of the rows the model holds, never past them to rows not drawn yet (following still decides on the paging's end: the first cut of the fix let End land short of it and stop following, which `tail` caught); a touch moving up lets go at its move, as a wheel up does; the tail mark is judged from the rows its commit drew (the model's), not the paging's, which a landing's pin moves ahead; a row count's clamp in the draw is the view's own move, never a reader's landing; a clock failing after its start says it stopped, not that it didn't start; the contract judges `jump(0.9)` with the clock still paused (exactly ⌊0.9 × rows⌋), where the resumed clock could move the count it was judged by; the muted foreground and the error color move into `perf/harness.ts` for `tail` and `tanstack-parity`; the test names the data file by its constant; parity's header asks for the tail build. Answered: the TanStack tail mark is checked as set in a frame's callback, not against a presented frame, as market watch's refreshed mark is; Row shown in's presentation is read from the trace in part D (`docs/DECISIONS.md`, "Measurement", 2026-11-06). Every check above is from the runs after the fixes; the other levels' builds byte-identical again.
- **The engine** (`engine-files --controls`): every level's `duckdb/` on both sides the same files as the GPUI base's, `tanstack-tail` among them; its controls fail as before.

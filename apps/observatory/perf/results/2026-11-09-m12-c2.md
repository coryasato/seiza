# M12 part C2: the admin table's numbers (2026-11-09)

Measured on Apple M1, Darwin 25.6.0 arm64, machine `local`, Chromium 153.0.8010.12 headless=new, 1440×900 at DPR 2, cold (a fresh browser per run), both contenders alternated, reference and throttled (CPU 4×, Fast 4G); **median of 10 runs** per side and profile. gpui-kit 0.9.0, React 19.3.1, TanStack Virtual 3.14.19, Arrow 17.0.0, DuckDB-Wasm 1.32.0 (each file's `versions`). The base level's release builds of both contenders, built right before the runs from the reviewed code (part C1's review, commit `18f3751`), the faces fetched by their pins. One sitting, 22:04 to 22:32 local time: 220 runs in 28 minutes, against A3's estimate of ~46. Load average 1.46 before the builds, 3.94 as the first runs started (the builds just ended), then 1.3–2.3, and 1.50 at the end. Every run passed: no failures in any file.

The scripts date their files in UTC, so they are dated 2026-11-10.

Raw (each labeled `admin-table`, the toggle's `admin-table-fonts`):
- `2026-11-10-m12-c2-usable-admin-table.json`, `-fonts.json`: Ready in (`perf/metric-usable.ts`), first pixels beside it.
- `2026-11-10-m12-c2-data-admin-table.json`, `-fonts.json`: Rows in (`perf/metric-data.ts`); with fonts, Scripts drawn in, its split, its mark's check, and each face's bytes.
- `2026-11-10-m12-c2-scroll-admin-table.json`: Smooth, the read-through (`perf/metric-scroll.ts`).
- `2026-11-10-m12-c2-memory-admin-table.json`, `-fonts.json`: memory at equal work and Download by kind (`perf/metric-memory.ts`).

## The cards

Median of 10, the runs' range in brackets. The verdict follows M10's rule (`docs/DECISIONS.md`, "Measurement", 2026-11-06): a side is faster only where its median beats the other's by more than 5% and the two sides' runs don't overlap.

| Card | Profile | GPUI | TanStack | Verdict |
|---|---|---|---|---|
| Ready in (ms) | reference | 145.3 [141.7–173.3] | 42.4 [40.7–43.6] | TanStack 3.4× |
| Ready in (ms) | throttled | 3,563 [3,557–3,568] | 482.1 [479.1–484.2] | TanStack 7.4× |
| Rows in (ms) | reference | 194.2 [191.0–200.5] | 252.1 [243.8–265.4] | GPUI 1.30× |
| Rows in (ms) | throttled | 1,315 [1,300–1,327] | 1,507 [1,500–1,517] | GPUI 1.15× |
| Smooth (read-through, % of frames) | reference | 100 [99.2–100] | 100 [100–100] | even |
| Smooth (read-through, % of frames) | throttled | 100 [99.2–100] | 100 [100–100] | even |
| Memory at the end, less every canvas buffer (MiB) | reference | 11.8 | 4.8 | TanStack 2.5× |
| Memory at the end, less every canvas buffer (MiB) | throttled | 11.8 | 4.9 | TanStack 2.4× |
| A second canvas buffer (19.8 MiB), runs | reference | 2 of 10 | — | |
| A second canvas buffer (19.8 MiB), runs | throttled | 10 of 10 | — | |

- **Ready in** is the GPUI side's wasm against TanStack's prerendered, hydrated screen. GPUI's slowest reference run (173.3 ms) was the first, as the builds ended (load 3.9); without it the range is 141.7–152.0. Throttled, Fast 4G's download of the 2.7 MiB wasm is most of GPUI's 3.6 s.
- **Rows in** is open → every visible row painted, and GPUI's is shorter on both devices. TanStack's open comes sooner: `timeOrigin` → open is 498 ms against GPUI's 598 at the reference, and 6,859 against 9,775 throttled. So from the page's start, TanStack's rows appear first (~750 ms against ~792 at the reference).
- **Smooth:** both sides moved the view in every display frame of the 2 s read-through, 6,000 px on both. GPUI missed one frame in 2 of 10 runs at the reference and 1 of 10 throttled. TanStack's compositor applied a scroll delta in every frame of every run (60 whole frames a second, none partial or dropped). The work beside it, p50 (p95), and the main thread's busy share: GPUI 3.5 (4.5) ms, 26%, at the reference and 9.2 (11.7) ms, 66%, throttled; TanStack 2.9 (4.0) ms, 20%, and 2.6 (3.8) ms, 17%.
- **TanStack's work a frame doesn't grow under the CPU throttle** (2.6 ms throttled against 2.9 at the reference, in every run), though the wide sheet's grew about 7×. `frameWork` times `ProxyMain::BeginMainFrame`, which includes the commit's wait on the compositor thread, and the throttle doesn't slow that thread. In a frame where no row renders (only the scroll event and the contract's state write), that wait most likely dominates. Not checked: the frames' parts aren't in the results file. It doesn't touch Smooth, which reads the compositor's deltas.

## Memory: a second canvas buffer on a slow device

Page memory after a forced collection, MiB, median of 10, at the open and at the end of the scroll down and back. "Less window" subtracts one window-sized canvas buffer (19.8 MiB), C1's rule; the card now reads the page less every canvas buffer, its JavaScript type (`docs/DECISIONS.md`, "Measurement", 2026-11-09, decided with the user after these runs).

| | Reference: GPUI | Reference: TanStack | Throttled: GPUI | Throttled: TanStack |
|---|---|---|---|---|
| Open | 30.7 (less window 10.9) | 4.4 | 30.8 (11.0) | 4.4 |
| End | 31.5 (less window 11.8) | 4.8 | 51.4 (31.6) | 4.9 |
| "Canvas" at the end | 19.8 (39.6 in 2 of 10 runs) | — | **39.6 in 10 of 10 runs** | — |
| JavaScript at the end (of it, wasm) | 11.8 (8.8) | 4.8 | 11.8 (8.8) | 4.9 |

**Chromium counted the second buffer in every throttled default run.** In C1 the doubling came with fonts in every run, and without them in about one run in five. Here, at the reference, 2 of 10 default runs were doubled from the open, as before. Throttled, all 10 began single and ended doubled after the scroll. The JavaScript memory is the same on both devices (11.8 MiB), so the 20 MiB difference between them is that buffer alone. A likely cause, unchecked: the canvas's resource provider allocates a second buffer when a frame is drawn before the compositor has released the last one. A slow main thread or heavy glyph rasterization would both make that overlap more likely. Under C1's rule the buffer was GPUI's cost, so the throttled card would read 31.6 MiB and the toggle's memory cost +2.4 MiB against +22.1 at the reference, both from the buffer alone. **Decided with the user:** the card is the page less every canvas buffer (GPUI 11.8 MiB on both devices), and the runs holding a second buffer are reported on a line of their own, so the canvas's cost stays on the page without being read as GPUI's data or the fonts'.

The faces read 586.7 KiB here and 586.1 in the toggle's table below: both are body and headers, but this run counts each request by Playwright's `request.sizes()` and the data run by Resource Timing's `transferSize`, about 48 bytes of headers apart per face. The Download card is this run's, as every other kind's; the per-face sizes are the data run's. (This run's file names drop the face's hash: `fileOf` strips any 8-character suffix.) ## The fonts toggle (GPUI, `?fonts`)

| | Reference | Throttled |

| …against the default's | +2.3 | +2.4 |

- **Within 5%:** Ready in and Rows in with fonts are within 1.1% of the default's on both devices, inside the user's tolerance (A3). The startup's `EmojiAndCjk` costs nothing measurable.
- **The mark:** `contender:fonts` came right after its frame's last GPU call, in the same task, in all 20 runs (0.07–0.50 ms).
- **Scripts drawn in** is mostly Rows in: the faces' fetch and the draw add about 42 ms at the reference and 1.1 s throttled, nearly all of it Fast 4G's download of 586 KiB. Noto Serif Tibetan is 182.4 KiB of it. C1's smoke run read 945–1,005 ms on a busier machine.
- **Memory with fonts:** "Canvas" ended doubled in every run on both devices, as in C1. With fonts, the JavaScript memory is 14.1 MiB against the default's 11.8 (+2.3 MiB: the faces in the wasm's font database, whose memory grew 8.8 → 11.1). So the toggle's memory cost is the faces, +2.3 MiB at the reference and +2.4 throttled. Less only the window's buffer (C1's rule), it read +22.1 MiB at the reference, the second buffer included.

## Experiments and controls

None new. Each run's controls and guards are the scripts' own: the probe key confirmed Ready in in 10/10 runs per side and device, and GPUI's mark was guarded by its GPU work in 10/10. The fonts mark was checked against its frame's GPU work in 20/20. Every memory run held the same 16,776 cache bytes on both sides (`cacheBytesEndAllEqual`).

## Reproducing it

```sh
just observatory script-fonts
just observatory gpui-build
just observatory tanstack-build
for m in usable data scroll memory; do
  just observatory metric $m --scenario admin-table --label m12-c2-$m
done
for m in usable data memory; do
  just observatory metric $m --scenario admin-table --fonts --side gpui --label m12-c2-$m
done
```

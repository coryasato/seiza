# M13 part D2: the monitoring wall's numbers, and gpui-kit 0.9.0 against 0.9.1 (2026-11-11)

Measured on Apple M1, Darwin 25.6.0 arm64, machine `local`, Chromium 153.0.8010.12 headless=new, 1440×900 at DPR 2, cold (a fresh browser per run), **median of 10 runs** per side, stop, and profile, with the contenders alternated. Reference and throttled (CPU 4×, Fast 4G). Versions: gpui-kit 0.9.1, React 19.3.1, TanStack Virtual 3.14.19, Arrow 17.0.0, DuckDB-Wasm 1.32.0 (each file's `versions`). Both contenders' wall builds were made right before the runs from the reviewed code (part D1's review, then `fd4d5c7`).

Two sittings. The first, 10:40 to 11:46: the feed (10:40 to 11:21), then `data` and `memory` (to 11:35), then a first `usable` and a first A/B. After the code review, the second, 11:57 to about 12:25: `usable` again and the A/B again, interleaved (below). Load average was 5.3 at the first sitting's start (the builds finishing), then 1.2–2.8 through the first sitting's runs, and 1.3–3.3 through the second's. The machine read quiet by the spread gate (IQR over median under 3.5%): the throttle control's busy loop spread at most 1.4% in any setting, and time to data's runs 0.5–2.6%. Every published run passed.

Raw:
- `2026-11-11-m13-d2-feed-monitoring-wall-{4,6,8}.json`: the feed at each stop (`perf/metric-feed.ts`).
- `2026-11-11-m13-d2-{usable,data,memory}-monitoring-wall-6.json`: the once-a-scenario metrics at the default stop (`usable` from the second sitting).
- `2026-11-11-gpui-kit-ab-interleaved-0.9.{0,1}-response.json` and `…-scroll-wide-sheet-rows-20.json`: the A/B, each summarized by its metric script (`--summarize`) from its 10 interleaved runs. Each names its merged file (`summarizedFrom`); the merged files and their one-run files (`mergedFrom`) are in `raw/` (gitignored).
- Superseded and kept in `raw/` only: the first `usable` (one of TanStack's reference runs failed, below) and a TanStack-only rerun of that one side and profile, which wasn't alternated; the first A/B, whose versions ran back to back.

The feed's files were first written as `m13-d2-monitoring-wall-<stop>`. The scripts name a file `<label>-<scenario>-<stop>`, so every metric needs a label of its own, and a shared label would have overwritten the feed's 6-table file. The files were renamed to `-feed-` (and their `label` set to match) before the other metrics ran. `runMetric` now refuses a results file that's already there, before any run.

## gpui-kit 0.9.0 against 0.9.1 (the open question)

**What was measured:** GPUI only, reference, 10 runs a version. `metric response` on Big file (the base level: keys, track presses, and wheel events) and `metric scroll` on the wide sheet at `rows-20` (down, sideways, and fast gesture scrolls). gpui-pre 0.3.12 resets the cursor on every mouse and scroll event (`2026-11-10-gpui-kit-0.9.1.md`), so these are the input-heavy readings.

**The builds:** 0.9.0 is this tree with the bump commit's `Cargo.toml` and `Cargo.lock` changes reversed (gpui-pre 0.3.11), built at the base and wide levels and set aside, with the bump then restored. 0.9.1 is the tree as committed. Base wasm SHA-256: 0.9.0 `8edf8b46bd08…`, 0.9.1 `c6fdba9867c7…`. Each file's `versions` names the gpui-kit its runs' build was compiled from, read from that build's wasm (below), and the merge checked it in every round.

**Interleaved:** 10 rounds a metric, each round one cold run of each version, with the order alternating by round (0.9.0 first in odd rounds). Before each run, that version's `dist/` and `dist-wide/` were swapped into the contender's `web/`. Each run was its own invocation (`--runs 1`), as cold as any run of 10, and the 10 a version were merged and summarized by the metric script. Pairing each round's two runs cancels drift over the sitting. A first A/B, earlier in the day, ran each version's 10 back to back, with load at 5.6 between response's two sets; it's superseded, and its medians agreed with these.

Each version's median of its runs' medians, with the runs' range and IQR over median; then the paired difference (0.9.1 less 0.9.0, round by round): its median and the rounds up and down, with a sign test.

Every input was guarded (60/60 of each kind on each version), every scroll drew 100% of the display's frames, and no run failed.

- **Sideways work is two-valued, run by run:** about 4.8 ms or 5.1–5.25 ms. 0.9.0 drew 6 of its 10 runs at the lower value and 0.9.1 drew 3, which moves the set median by +3.7% (the first A/B's +3.9% is the same effect). Round by round the difference is +0.05 ms, and it goes either way. The two values are why the set spreads past the quiet gate on both versions on a quiet machine. The track press's 7.7% is the same kind of reading: one press a round reaching a later frame.
- **Verdict: no change.** No paired difference is distinguishable from zero (sign tests p ≥ 0.34). Its size is under 2% for every reading: ±0.5 ms for keys, ±0.2 ms for scroll-down and fast-scroll work, ±0.45 ms for sideways, and ±2–3 ms per round for track presses and wheels. The cursor reset on every event doesn't show in GPUI's input response or scroll work. By the open question's rule (re-measure the scenarios only if a reading moves past the spread), **the published scenarios keep their 0.9.0 labels and aren't re-measured.** The monitoring wall's numbers above were measured on 0.9.1, and their files say so.

## What changed in the scripts

- **The versions measured with:** `runMetric` (`perf/contender.ts`) records gpui-kit as the served GPUI build's own, read from its wasm by `shared-web/perf/protocol.ts`'s `wasmCrateVersion`. Under `trim-paths` the panic locations keep `<crate>-<version>/src/…`, and each build names exactly one gpui-kit (`gpui-kit-0.9.0` or `-0.9.1`; gpui-pre `0.3.11` or `0.3.12`). The control is a file that names none, which throws. Before this, `versions` came from `Cargo.lock` alone, so a build from another lock was recorded under the tree's version. The first A/B's 0.9.0 files had been corrected by hand; the interleaved runs were recorded right by the script.
- **Append-only:** `runMetric` refuses a results file that's already there, before any run, and so does `--summarize`. Its file's name and its `date` field now come from one reading of the clock. The control: `metric usable --scenario monitoring-wall --label m13-d2-usable` refused at once, naming the file.

## Reproducing it

```sh
just observatory gpui-build wall && just observatory tanstack-build wall
just observatory metric feed --scenario monitoring-wall --stop all --label m13-d2-feed
just observatory metric usable --scenario monitoring-wall --label m13-d2-usable
just observatory metric data --scenario monitoring-wall --label m13-d2-data
just observatory metric memory --scenario monitoring-wall --label m13-d2-memory

# The A/B. Build both versions at the base and wide levels, keeping each build's dist/ and dist-wide/ aside:
git diff 6bff554^ 6bff554 -- Cargo.toml Cargo.lock | git apply -R    # 0.9.0; `git checkout Cargo.toml Cargo.lock` after
just observatory gpui-build && just observatory gpui-build wide
# Then 10 rounds a metric. In each round, for each version (0.9.0 first in odd rounds), swap its builds into
# contenders/tall-table/gpui/web/ and run one cold run:
just observatory metric response --side gpui --profile reference --runs 1 --label abtmp-response-<v>-r<n>
just observatory metric scroll --scenario wide-sheet --stop rows-20 --side gpui --profile reference --runs 1 --label abtmp-scroll-<v>-r<n>
# Merge each version's 10 runs into one file, then summarize it with the metric script:
node perf/metric-response.ts --summarize <merged> --label gpui-kit-ab-interleaved-<version>-response
node perf/metric-scroll.ts --scenario wide-sheet --summarize <merged> --label gpui-kit-ab-interleaved-<version>-scroll
```

# M10 part B1: Shown in's method (2026-11-05)

Measured on Apple M1, Darwin 25.6.0 arm64, machine `local`, Chromium headless=new, 1440×900 at DPR 2, cold (a fresh browser per run), median of 3, reference and throttled (CPU 4×, Fast 4G): a spike of the method, not a protocol run (the published numbers come from part D, on the contenders). Load average 2.3–4.6 over the runs. The sides are A2's spike pages: `spike/market.html` (TanStack, Last, Bid, and Ask flashing for 400 ms) and the tall table's bare host built `live,custom-cells` on the improved table (`?shape=narrow&live=<rate>&flash`: its own feed, every float column flashing for 1 s).

Raw: `2026-11-05-m10-b1-control-tanstack.json` and `-control-tanstack-throttled.json` (TanStack and its control after the code review's fixes, below; they supersede the TanStack rows of the next two), `2026-11-05-m10-b1-control.json` (both sides and their controls, reference, 1k and 5k: GPUI's rows), `-control-throttled.json` (the same throttled, 1k), `-unmeasured.json` and `-measured-throttled.json` (TanStack at 5k without and with `?measure`: Element Timing's cost), `-present-spin.json` and `-present-nospin.json` (the presentation probe, 11 s traced, with and without the busy loop before the window). All from `spike/market-run.ts` and `spike/present-probe.ts`.

## What A2's control was reading

A2's Shown in (a batch's send to the trace's `AnimationFrame::Presentation` of the frame that holds the side's mark) put the DOM's commit → presentation at 44–60 ms, and a commit held a frame read the same. The presentation probe says the reading itself is sound: every animation frame has its own presentation, 4.4 ms (p50) after the frame ends, with the flash or without (180 frames in 3 s, none sharing a time), and each commit opens a frame span whose rendering runs at the next vsync, ~15 ms later. **What moved was the page's frame scheduling, set by what ran before the window.** The busy loop the runner timed right before it (A1's throttle control, a ~120 ms task) moved the DOM's commit → presentation from 19.5 to 31.4 ms, and it stayed there for all 11 s, second by second (`-present-spin.json` against `-present-nospin.json`). Run to run, a page settles in one such state or another, so a control across runs compares two states. The cause is untested; Chromium's compositor scheduler letting the main frame run a frame behind after a missed deadline, recovering only once frames go quiet (the CSS animations never let them), would fit.

GPUI's runs do the same at the reference: its mark → presentation settles at 1.1, ~12, or 28 ms in a run (throttled 6.7–6.9 in all three), so its Shown in p50 ran 13.9 to 41.4 ms across three runs of one setting.

## The control on both sides (B1-1)

The criterion: the frame-late variant moves Shown in by what it moves the side's mark, within 2 ms, the mark moving at least a frame. Read where both share one scheduling state.

| | Reference 1k | Reference 5k | Throttled 1k |
|---|---|---|---|
| **TanStack, within one page** (`?hold=alt`): held − free Shown in p50 | **+16.6 ms** (59.8 − 43.2) | **+16.9** (59.5 − 42.6) | **+15.5** (59.7 − 44.2) |
| its commit moved | +16.9 (28.8 − 11.9) | +17.0 (29.7 − 12.8) | +15.7 (36.8 − 21.2) |
| per run, Shown in against commit | 16.3 / 16.2; 16.4 / 16.1; 16.7 / 17.1 | 17.2 / 17.3; 16.8 / 16.8; 16.9 / 16.8 | 18.2 / 17.0; 15.3 / 14.8; 16.1 / 16.1 |
| keeps up, free page / held page | 99.8% / 99.2% | 99.8% / 99.4% | 98.9% / 97.3% |
| **GPUI** (`?delay=17`, runs of their own): its mark moved | +37.4 ms (50.3 − 12.9) | +37.3 (50.4 − 13.1) | +39.7 (54.2 − 14.4) |
| mark → presentation in each state, free / held | 1.11 / 1.09–1.11 | 1.07 / 1.23; 11.6–11.9 / 11.7 | 6.7–6.9 / 6.7–6.8 |
| keeps up, free / held | 99.7% / 98.1% | 100% / 98.1% | 100% / 99.7% |

- **TanStack passes,** one frame each (16.7 ± 4 ms), every run within 1.2 ms of its commit's move, 251–276 batches each side of the split a run. The held page sat in the slower state (its free batches 43–44 ms against a plain page's 30–32 at the reference): only a control inside one page could see the frame through it.
- **GPUI passes per state:** in every state a held run presents its mark as a free run does (within 0.2 ms), so Shown in moves by the mark's +37–40 ms. The delay moves it about two frames, not one: a re-read held 17 ms makes the next batch's read wait for it.
- **The reading kept:** A2's, the trace's presentation of the animation frame that holds the side's mark (`Trace.presentationOf`). It needs only the mark each side sets in the frame that first draws a batch.

## Element Timing, the other candidate

The DOM's changed text drawn anew each commit (a row's Bid size as a new element keyed by the batch, `elementtiming` set to it) reads the same presentation as the trace: 31.03 = 31.03 ms at 1k, 50.89 against 50.86 throttled. It's the same presentation feedback, not an independent reading. It matched fewer batches (342 of 511 at 5k, 137 of 491 throttled) and cost the DOM side main thread: at 5k, 385–391 ms a second against 347–351 unmeasured at the reference (+11%; throttled the main thread is saturated either way, keeps up 79.7–80.4% against 78.6–81.1%). Dropped.

## Its cost (B1-2)

The reading kept adds nothing to either side beyond the mark each side sets in the frame that shows a batch (the bare host's `tall-table:refreshed`, which it already sets; TanStack's commit time, recorded in a layout effect in every run here). Element Timing, which would have been the DOM's addition under `?measure`, failed this check (above).

## What changes in the runs

- **The throttle's busy-loop control runs after the window,** never before: before it, it put the DOM side in the slower state for the whole window. `market-run.ts` does so now.
- **A side's runs settle in different states.** Shown in is a median of 10 runs, as every metric is; its results file keeps each run's mark → presentation beside its Shown in, so the states show. Whether the published number should say more (each state's share, or the spread) is open (PLAN.md, "Open questions").

## After the code review

The review's fixes to the spike, and what they moved:
- **The held/free split went by the commit's sequence,** so when the hold stopped at a second's turn, the held batches that landed in the free frame's commit counted as free, once every two seconds. Each batch is now filed by the frame that took it (`record.held` holds every held batch). TanStack's control was run again (`-control-tanstack*.json`): held − free +16.6 / +16.9 / +15.5 ms against +16.5 / +17.2 / +17.3 before, each still the commit's move.
- **The on-screen filter fed keeps up too** (and the batches a second) on TanStack's side alone; now it counts only in Shown in (`shownInCounted`), so keeps up reads every batch on both sides. At 1k and 5k it had dropped next to none.
- **A row past the screen's bottom could count as on screen:** the sticky header is 31 px with its border, not 30; the page measures it now.
- Also: an empty split reads null, not 0; `?measure` keeps `--flash-all`'s Bid size flashing; the probe refuses to overwrite a results file and fails on a page error, on a port of its own (4358); the runner's header says what `--hold` runs on each side and that the busy loop comes after the window.

## Reproducing it

```sh
just tall-table build live,custom-cells
node apps/observatory/spike/market-run.ts --sides tanstack --rates 1000,5000 --profiles reference --runs 3 --hold --measure --label m10-b1-control-tanstack
node apps/observatory/spike/market-run.ts --no-build --sides tanstack --rates 1000 --profiles throttled --runs 3 --hold --measure --label m10-b1-control-tanstack-throttled
node apps/observatory/spike/market-run.ts --no-build --sides gpui --rates 1000,5000 --profiles reference --runs 3 --hold --label m10-b1-control
node apps/observatory/spike/market-run.ts --no-build --sides gpui --rates 1000 --profiles throttled --runs 3 --hold --label m10-b1-control-throttled
node apps/observatory/spike/market-run.ts --no-build --sides tanstack --rates 5000 --profiles reference,throttled --runs 3 --label m10-b1-unmeasured
node apps/observatory/spike/market-run.ts --no-build --sides tanstack --rates 5000 --profiles throttled --runs 3 --measure --label m10-b1-measured-throttled
OUT=m10-b1-present-spin SETTLE=1000 WINDOW=11000 SPIN=1 node apps/observatory/spike/present-probe.ts 400 0 1 run
OUT=m10-b1-present-nospin SETTLE=1000 WINDOW=11000 node apps/observatory/spike/present-probe.ts 400 0 1 run
```

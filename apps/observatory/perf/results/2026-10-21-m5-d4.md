# M5 part D4: the readout's cost, and M5's close-out (2026-10-21)

What the page's live readouts (the status bar, and the meter open or a pill) cost the contender they watch, against the page with the meter hidden and against the bare contender page (`docs/DECISIONS.md`, "Page", what a visible readout may cost). Measured on Apple M1, Darwin 25.6.0 arm64, machine `local`, Playwright's Chromium 153 headless=new, 1440×900 at DPR 2, cold (a new browser per run), 10 runs per variant, interleaved by round, reference and throttled. Every run drew on Metal (WebGPU `apple metal-3`, WebGL2 `ANGLE Metal Renderer: Apple M1`): no software renderer, so nothing re-ran headed. Load average 3.15 → 1.45 over the full run, 1.35 → 2.74 over the re-run, heavy apps closed.

Raw: `2026-10-21-m5-d4-readout-cost.json` (the full run: 2 controls, 160 runs, judged two-sided as first written), `2026-10-21-m5-d4-readout-cost-tanstack-reference.json` (TanStack's reference block re-run for its spread), `2026-10-21-m5-d4-readout-cost-judged.json` (the record: both files' runs, the re-run's TanStack reference winning, judged one-sided by `--from`).

## What changed

- `perf/readout-cost.ts` (new, `just observatory readout-cost`): the four variants (open, pill, hidden: the page at `/observatory/tall-table/?side=<side>` with the meter stored so; bare: the bare contender page), each flung as `metric-fling` does (the same profile, input path, and rest point), the contender opened with `?measure` in all four (the page's frame gets it by an init script), so all record the same state per frame. `--from` re-applies the gates to saved runs.
- `shared-web/perf/serve.ts`: `startThrottlingProxy`, a proxy that adds the profile's latency to each response and sends every body through one shared download rate. The throttled runs' network goes through it for all four variants; only the CPU is throttled by CDP ("Experiments and controls" says why).
- `shared-web/perf/harness.ts`: `frameRecorder` times its own callback (`__seizaFrameCosts`, read by `recorderCost`); `targetRect` and `waitMark` take a frame as well as a page. `perf/contender.ts`'s readers take either (`Scope`). Tycho's perf scripts still type-check.
- No page, contender, or `shared/` code changed: no bundle moved (the page's first-paint JS 79.8 KiB, GPUI's wasm 2698 KiB, as in part D3).

## Experiments and controls

- **Control, React commits:** the status bar's Meter pressed mid-fling (one run per side, reference, meter open) counted 1 commit on GPUI and 1 on TanStack, in both runs; the counter can fail. The hook is installed in the top window only, so the TanStack contender's own React commits in its frame are never counted.
- **The throttled network and the frame's worker:** with Chromium's emulation on the page (`Network.emulateNetworkConditions`, as `shared-web/perf/protocol.ts`'s `throttle` sets it), the TanStack contender's 9 data reads took 746, 172, 179, 185, 221, 186, 236, 428, 1226 ms on the bare page and 91, 3, 2, 3, 16, 1, 6, 3, 20 ms from the page's frame. The frame's own requests were throttled (its wasm 2994 ms in both); its dedicated worker's (DuckDB's bundles and data reads) weren't. CPU throttling did reach the frame (the same loop 69.8 ms in the top window, 69.1 in the frame). A worker target answers `Network.emulateNetworkConditions` with `Not supported`, and a same-origin frame has no CDP session of its own. Through `startThrottlingProxy` both pages' reads took 765, 170, 174, 183, 224, 184, 236, 441, 1253 and 772, 170, 174, 184, 221, 188, 236, 437, 1251 ms: within 3% of Chromium's own on the bare page, and the same in the frame. Before the fix, a throttled round read the page's GPUI fling in 182–187 frames against the bare page's 299 (its data arrived unthrottled).
- **The page's own time from the trace:** `Paint`, `PrePaint`, and `Layerize` name the top frame however much of them is the contender's frame (on a reference TanStack fling: 128 + 102 + 97 ms of the 343 ms the trace put on the top frame), so counting them read 27.6 ms a refresh. They're left out; the refresh is the top frame's timers with the style and layout they force, and the rest (its listeners, its rAF loop, the relayed marks) is reported apart, per frame.
- **The frame reporter:** a vsync can have more than one `PipelineReporter` (the compositor's and the main thread's): a throttled TanStack fling had 108 vsyncs with two. Counting reporters read 314 presented frames against 184 animation frames; each vsync is now counted once (presented if any presented, dropped if one dropped and none presented).
- **The gates as first written (two-sided):** TanStack throttled's open meter "failed" by dropping fewer frames than hidden (−2.07 points against 1.42), which made the fallback judge the pill, which failed (+4.48): read literally, the meter would have gone. Re-judged one-sided (`--from`), open passes.

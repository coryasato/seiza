Apple M1, Darwin 25.6.0 arm64, machine `local`, Node 26.0.0; the pages in Playwright 1.63.0's Chromium (headless=new), 1440×900 at DPR 2. Load average 2.9 at the results run.

Raw: `2026-10-17-m3-a-engine-files.json` (`just observatory engine-files --controls --label m3-a-engine-files`: the engine files of both builds with their SHA-256, the engine chunks, both pages' engine requests, the TanStack page's scripts against its first paint, the controls). - **The GPUI contender's build:** DuckDB's worker scripts and wasm moved from `assets/` to `duckdb/`, names unchanged. Its wasm untouched (the Rust is unchanged; 2,697.3 KiB brotli in this `check`); its entry chunk 115.32 kB raw as before, its hash and its engine chunk's changed (the paths inside). TTFP 165.2 ms vs the 187.6 ms limit (`check`, below).
- **`cells.json` gains two `rounding` cases** the TS port found (below): a tie rounded to even, and two shortest texts equally near. The component's native tests pass with them.

## The engine's JS chunk: not shared

The GPUI build's `engine-*.js` holds `engine.ts`, DuckDB-Wasm's JS, and the part of Arrow DuckDB-Wasm uses: 194.0 KiB raw, 38.9 KiB brotli. In the TanStack build Arrow is also imported by the data layer, so Rolldown moves it to a chunk both import: `engine-*.js` 28.1 KiB raw (7.5 brotli) plus the Arrow chunk 166.0 KiB raw (31.9 brotli), which the data layer (`table-*.js`, 2.7 brotli) shares. So the second contender to load fetches ~39 KiB brotli of engine JS again, against ~5.7 MiB brotli it finds cached (EH: wasm 5,065.1, worker 152.2, Parquet 487.2 KiB). Making them one file would mean bundling the GPUI side's Arrow the TanStack way, for no gain to either side.

## What the port found

- **Ties round to even in Rust, up in JS.** Rust's `{:.N}` and `{:.Ne}` round an exact tie to even (`123456789.125` to 2 decimals is `…12`, `0.125` is `0.12`, `2.5` to none is `2`); `toFixed` rounds it up. The port rounds the double's exact decimal value itself. No drawn cell in the data file hits it (none rounds); the new `rounding` case does.
- **Two shortest texts can be equally near.** `1658206780088562.25` reads back from both `…562.2` and `…562.3`; JS's `String` takes the even one, Rust's `{:?}` the upper. The port steps an even last digit up when the next is an equally near round-trip. The new case pins it.
- **A cross-check, once:** Rust's `fit_float` and `{:?}` (format.rs compiled alone) against the port on 100,010 doubles (40,000 random bit patterns, 40,000 data-like decimals of 1–17 digits from 1e−12 to 1e16, 20,000 dyadic fractions, and the edges: ±0, 1e−4, 1e16, the smallest subnormal, the largest double), each at budgets 1–20: 1,999,760 cases. Before the second fix, 7,500 mismatches, all the shortest-text tie (375 values × 20 budgets, each Rust's last digit one above JS's even one); after it, 0.
- **"After first paint" is the paint entry, not a frame callback.** The stub first started its loads in a `setTimeout` from `requestAnimationFrame`; Chromium's `first-paint` (the frame's presentation) came later, and the data layer, Arrow, and formatting chunks were all requested before it. It now waits for the paint timing entry (two frames where there's no paint timing).

## Experiments and controls

- **Paging controls**, each must fail at least one scenario: the same counts as the native test's (part C's note), control for control: scroll settle 0 ms 6 scenarios and 500 ms 3, drag settle 0 ms 2 and 160 ms 1, prefetch 1 and 3 7 each, 2 and 4 reads in flight 3 and 1, 512-row pages 7, a 128 MiB cache 1. Before due timers fired at a step's settle, 0 ms settles failed only 2 and 1: the script clock had fired timers only on `wait` steps.
- **Cell controls:** JS's `String` as the exact text fails 15 cells; the budgets a character smaller or larger fail 8 and 10. A copy of the port with `toFixed` fails exactly the tie case; a copy without the shortest-text tie-break fails exactly that case: each new case catches what nothing else in the fixture did.
- **SQL controls:** the first page by `LIMIT`/`OFFSET`, and the same query with a line break, each fail.
- **Engine-file controls:** the comparison fails a copy of `duckdb/` with one byte changed and with a file missing; the TanStack contender built with Arrow imported by its entry fails with `contenderBuild`'s error, and the same build without the import passes.

## After the code review

A review found, and this fixes: `table.ts` named a build check that doesn't exist (`perf/tanstack-chunks.ts`; it's `contenders/engine.ts`, its control in `engine-files`); an open whose metadata lacked `num_rows` or `num_row_groups` gave NaN rows and loaded nothing, silently (it now fails naming the column, as `seiza-duckdb`'s `count` does; a new test, 9 in the TS run); `fit_float`'s port expanded the double's exact value at every rounding step (now once per value); `engine-files` read each engine file twice; the stub's screen was 28 rows where the fixture's viewport is 27.5. After the fixes: the TS run, both typechecks, the 1,999,760-case cross-check (0 mismatches), `tanstack-build`, and `engine-files --controls` pass. Two findings belong to the view and are now part B's checks in `PLAN.md`: a hidden page may never see the paint entry the engine waits on, and a short page's missing rows would show as NULL. Kept as is: `scrollBy`'s `rows !== 0` guard (Rust's `scroll_by` has it), `contenderBuild` setting `assetFileNames` outright (no host sets its own), and `engine-files`' status check naming the data file's 11 columns and H (the file is pinned).

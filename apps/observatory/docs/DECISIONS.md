# Decisions: Observatory

Why the Observatory is built the way it is. Decisions that bind every app, the comparison protocol among them, are in the root [`docs/DECISIONS.md`](../../../docs/DECISIONS.md).

One bullet per decision, under its area, oldest first: what was chosen, the numbers that chose it, and *[where they came from]* (a milestone, a code review, a results file in `perf/results/`). A decision that replaces another marks the old one *Superseded* rather than deleting it.

## Data

- **2026-10-14** · **The data file: Tycho's asteroids, 11 of 18 columns, all 1,567,523 rows,** 21.76 MiB (Tycho's is 35.9 MiB, over the 25 MiB static-asset limit). Kept: one of each kind the table draws (spkid; full_name and class; neo and pha; H, diameter, albedo, a, e; first_obs), the readable name over the designations, and the two mostly-NULL floats, so both sides draw empty cells. Dropped for size: pdes, name, i, q, per_y, last_obs, n_obs_used. Tycho's writer settings (ZSTD, 30,720-row groups), so a page costs the reads Tycho's does. Built from Tycho's file, checked against its pinned SHA-256; rebuilds are byte-identical. *[M0 part B, `perf/results/2026-10-14-m0.md`]*

## Hosting

- **2026-10-14** · **Everything under `/observatory/`.** The page's Vite `base` is `/observatory/` from the first commit, so dev, preview, and production share paths, and the engine's extensions are served from `/observatory/duckdb/` (`@seiza/duckdb`'s `extensionDir`, added for it; `engines/duckdb/docs/DECISIONS.md`). Tycho keeps `/duckdb-ext`: its app wasm byte-identical, its engine chunk +206 B raw (+187 B brotli), `just tycho engine` passing. `shared-web`'s brotli preview strips the base as well, so preview serves the build as production will. *[M0 part A and its code review, `apps/tycho/perf/results/2026-10-14-observatory-m0-a-engine-review.json`]*
- **2026-10-14** · **The apex `seiza.io` is this Worker's custom domain** (wrangler made its DNS record; there was none). Everything outside `/observatory/` is a 404 until the landing page is decided (`PLAN.md`, open questions). *[M0 part B deploy]*
- **2026-10-14** · **The data is a static asset, served by range through a Worker and the edge cache.** Static assets ignore `Range` (200 and the whole file, MISS every time, whatever the headers, extension, or type), so DuckDB-Wasm can't read them. The Worker runs first for `/observatory/data/*` only: it puts the whole file into `caches.default` once per location, keyed by its SHA-256 (`DATA_SHA256`, set at deploy), and answers every request with `cache.match`, which serves ranges from it. First page 390.4 ms against Tycho's R2 path's 474.9 (median of 10, edge warm); the first request at a location under a new key 2.27 s (n = 1). Each read is a billed Worker request (the paid plan). Rejected: R2 as Tycho does it (proven, but R2 reads on misses and the pause switch back in play); slicing the static asset's stream per request (up to 22.8 MB through the Worker for each read). *[M0 part B, `perf/results/2026-10-14-m0.md`]*

## Scroll model

- **2026-10-15** · **The TanStack contender's scroller: a 2^24 px spacer, re-anchored with `scrollBy`.** One spacer height for every browser, 16,777,216 px: under Firefox's 17,895,696 px, past which Firefox drops an element's height to 0 (Chromium and WebKit clamp at 33,554,428). Wheel, keys, touch, and any step of at most a screen move the content 1:1 (V = s + D); past 1,800 px of drift from the canonical map, or pinned at an end, the scroller is re-anchored in the same task, which no frame showed at a wheel's pace in any of the three browsers. `scrollBy`, not a `scrollTop` assignment: the assignment lost Page Down input in Firefox (19,884 of 26,040 px) and fling distance in WebKit (a steady fling 260,503 px short where `scrollBy` reached the end). Jumps go through `scrollBy` too. The canonical map is 1:1 within 2^20 px of each end, so a steady fling (180 equal events) and a wheel from near the end both reach the last row exactly. Design: `dom-scroll-model.md`. Rejected: a spacer at each browser's own limit (a stretch that differs per browser for no gain: the stretch only scales a thumb drag); re-anchoring only at rest (a fling would run the scroller into its end). *[M1 part A, `perf/results/2026-10-15-m1-a.md`]*
- **2026-10-15** · **A thumb drag is told apart by its step, not by pointer events.** A step bigger than a screen with no wheel, key, or touch in the last 300 ms is the thumb (one pixel of thumb travel is ~19,000 px of scroller), mapped through the canonical map; the 80 ms drag settle is 80 ms without a scroll event. Chromium, WebKit, and Firefox (headed) also send `pointerdown`/`pointerup` for a scrollbar press (no `pointermove` during a drag in Chromium and WebKit), and any scroll while the pointer is down on the scrollbar is the thumb. *[M1 part A]*
- **2026-10-15** · **TanStack Virtual over a moving window of 4,096 rows, not the full count.** The full count held 29.91 MiB more (its `Float64Array` of starts and sizes) and built in a 28.4 ms task at mount (mount to rows 20.7 against 8.3 ms), for the same fling work (4.22 against 4.20 ms of main thread per frame, median of 10, Chromium at DPR 2). The subscriber forces a render when the window's or the content's base moves, since TanStack skips one when its index range is unchanged; without it, 336 of 374 fling frames showed the wrong rows. `@tanstack/react-virtual` pinned at 3.14.19 (`virtual-core` 3.19.4). *[M1 part A, `perf/results/2026-10-15-m1-a.md`]*
- **2026-10-15** · **The contender handles its keys.** ↑/↓ a row, a screen for Page Up/Down and Space (an instant `scrollBy`, so still on the compositor), the ends for Home/End with or without Ctrl and for Cmd+↑/↓, all through the model, as the component does; 5 ↓ moved 5 rows in all three browsers. Native arrows move 40 px in Chromium, WebKit under Playwright doesn't arrow-scroll a focused element, and the browser's Ctrl+End runs the scroller, not the content, to its end. *[M1 part A]*


## GPUI contender

- **2026-10-16** · **A bare host: the table, and before it the table's empty frame with one status line.** The first frame is that frame saying "Engine loading…" (the engine starts after it), "Opening asteroids.parquet…" once it's ready; the placeholder shell copies the frame (`.sz-frame`) and the line, and matches it in light and dark at DPR 2 and 1, every surface pixel within the limits and the line 0 px across, 1–2 device px up (the ink's tolerance). No chrome: the DOM side will draw the same. *[M2 part B, `perf/results/2026-10-16-m2-b.md`]*
- **2026-10-16** · **`first-pixels` and `usable` are set by the page, at the moments of the marks they mean** (`seiza:placeholder-painted`, `gpui:first-frame`), from a `PerformanceObserver` (`contenders/contract.ts`, `markAt`); `open` and `filled` are set in Rust from the host and the table's events. An observer sees each mark whenever it's set: Element Timing reports the placeholder's paint asynchronously, after the paint, so the post-paint callback isn't sure to find it already set. *[M2 part B]*
- **2026-10-16** · **The table probes every frame, measured or not** (`probe_frames(true)`): the replay's fling reads the rows and the row height from the probes, and a measured run, which needs `state`, has them on anyway, so what's measured doesn't change; only `?measure` writes anything to the page. Rejected: a row-height getter on the component (a change to it for the observatory that its own events already cover), or a fling sized by gpui-kit's row size (the component's choice, private). *[M2 part B]*
- **2026-10-16** · **Served under `/observatory/` by its own server until the deploy places it.** Base `/observatory/`, so the engine's extensions are at `/observatory/duckdb/` and the data at `/observatory/data/` (rule 2); the page is the build's `index.html` until the deploy decides where the bare pages sit beside the page. Locally the data is served by range from `data/` by a Vite plugin (`contenders/data.ts`) with the Worker's headers, not copied into the build. *[M2 part B]*
- **2026-10-16** · **The panel-leak check reads Cargo's resolution and the shipped bytes,** each with a control: `cargo tree -e features -i seiza` for the contender alone must not enable `panel` (built with Tycho, it must: Cargo unifies it); the shipped wasm must not hold `__seizaPerfOverlay`, the global only the panel writes (the build with `--features seiza/panel` must). The panel is 10.7 KiB brotli of the contender (2,706.1 against 2,695.4 KiB). *[M2 part B, `perf/results/2026-10-16-m2-b-sizes.json`]*

## TanStack contender

- **2026-10-17** · **Its data layer is a port of the tall table's, decision for decision:** the page SQL as text, `PageCache` as the component's, and the state's scroll, jump, drag, and settle paths (`TablePaging`, on an injectable clock), so the paging fixture's requests come from the same decisions in the same order; all three fixtures run against it with their controls, each paging control failing the same scenarios as natively. Rejected: a TS paging of its own shape tuned until the fixture passes (the fixture pins 7 scenarios, not every path). *[M3 part A, `perf/results/2026-10-17-m3-a.md`]*
- **2026-10-17** · **Cell text rounds the double's exact value, in `BigInt`s, with Rust's tie rules.** Rust's `{:.N}` and `{:.Ne}` round a tie to even where `toFixed` rounds up, and of two equally near shortest texts Rust's `{:?}` takes the upper where JS's `String` takes the even (375 of 100,010 test doubles); each is now a `rounding` case in `cells.json`. Against Rust's `fit_float` on 1,999,760 cases, 0 mismatches. The cost lands only on cells that don't fit, and none in the data file does. *[M3 part A]*
- **2026-10-17** · **`apache-arrow` 17.0.0, pinned exactly: the version DuckDB-Wasm 1.32.0 resolves,** so the build holds one copy of Arrow. *[M3 part A]*
- **2026-10-17** · **One engine path for both contenders: DuckDB-Wasm's bundles in `duckdb/`, content-hashed** (`contenders/engine.ts`, in both Vite configs), beside the extensions, so both load the same 6 files, byte-identical, from `/observatory/duckdb/`. The engine's JS chunk isn't shared: the GPUI build's holds the Arrow DuckDB-Wasm uses (38.9 KiB brotli); the TanStack build's data layer imports Arrow too, so Rolldown splits it out (7.5 KiB plus a 31.9 KiB Arrow chunk). A warm second contender fetches those ~39 KiB again and finds ~5.7 MiB cached. Kept: one shared file would mean bundling the GPUI side's Arrow the TanStack way, for nothing either side measures. *[M3 part A, `perf/results/2026-10-17-m3-a-engine-files.json`]*
- **2026-10-17** · **The build fails if Arrow or DuckDB-Wasm's JS is in a first-paint chunk** (the entry and what it imports statically), in both contenders' builds, with a control that imports Arrow from the entry. On the page, heavy loads start at the paint timing entry (two frames on where there's none), not in a frame callback: a `setTimeout` from `requestAnimationFrame` requested the data layer and Arrow before Chromium's `first-paint`, which is the frame's presentation. *[M3 part A]*
- **2026-10-17** · **The view's theme is generated from gpui-kit's resolved default theme,** not copied: a native example in the GPUI contender's crate (`examples/theme_css.rs`) writes the 18 colors the table, its tooltip, and the page use, and the radius, as CSS variables for light and dark (`ThemeColor::light()`/`dark()`, what `Theme::change` applies); `lint` fails if the committed file differs. A bump of the pin shows up as a stale file. Rejected: reading `default-theme.json` in TS (its fallbacks and token layer would be reimplemented, and could drift). *[M3 part B, `perf/results/2026-10-17-m3-b.md`]*
- **2026-10-17** · **The same face as GPUI's, IBM Plex Sans Regular, and the GPUI contender's boxes:** column widths by the component's rules (an integer column at GPUI's measured 8.4 px number advance), the 91.5 px gutter, 30 px rows, checked against the GPUI build's `ColumnProbe`s. DOM idioms where the DOM has them: a sticky header and a sticky row-number gutter in the native scroller (scrolled sideways on the compositor), native scrollbars themed with `scrollbar-color`, every column drawn (11; no horizontal virtualization). *[M3 part B]*
- **2026-10-17** · **The engine starts after the paint entry, or at once in a page that can't paint:** hidden now or before its paint (a background tab has no paint and no frames), or with an empty viewport (a `display: none` frame reports itself visible, never paints, and has a 0×0 viewport). Rejected after review: a 1,000 ms timeout for paintless pages, which on a throttled or busy run could start the engine before a slow first paint. *[M3 part B and its code review]*
- **2026-10-17** · **A cell past a short page's end is drawn empty, not `NULL`:** its value isn't known. The tall table draws `NULL` there (`PLAN.md`, open questions); no row of the static file is ever past its page's end. *[M3 part B]*
- **2026-10-18** · **Parity means the tall table's rule on each side's own geometry.** Page Down moves a screen less a row (the component's `page_rows`) of each side's viewport: 26.87 rows on the DOM (its rows' area, 836 px), 26.33 on GPUI (its body less a 16 px scrollbar strip, 820 px); the same keys checked on both contenders. *[M3 part C, `perf/results/2026-10-18-m3-c.md`]*
- **2026-10-18** · **A track press jumps by moving the scroller in its own `pointerdown`, keeping the browser's scrollbar.** No browser lets the page cancel a track's paging (`preventDefault` on `pointerdown` or `mousedown`: no change in Chromium, Firefox, or WebKit), so the model puts the thumb under the pointer first and the browser has nothing to page toward. The jump is exact in all three; the grab after it is the browser's: Chromium grabs with classic scrollbars, Firefox sends the page its moves (the model drags), and Chromium's overlay scrollbars and WebKit don't, so the content stays at the jump (their paging after it is ignored while the press is held). Pointer capture doesn't bring Chromium's or WebKit's moves. Rejected: a scrollbar of the page's own over the native one, which would match the component in every case but replace the browser's scrollbar, a DOM grid's idiom (native scrollbars, above). *[M3 part C]*
- **2026-10-18** · **The drag is the model's thumb mode, ended by a release, 80 ms with no scroll, or a wheel, key, or touch.** Reads match the tall table's (none while the pointer moves, once it rests 80 ms, at the release); the calls don't one for one, since a rest ends a drag and the next move starts another, which reads the same. *[M3 part C]*
- **2026-10-18** · **Shift+wheel's cancelable listener is on only while Shift is down,** so every other wheel stays passive and the compositor scrolls without waiting for the page; an uncancelable one (WebKit, in the frame Shift went down) scrolls the rows as the browser does, never both ways. *[M3 part C]*
- **2026-10-18** · **The tooltip is one element, found by the event's target, and a press outside the table doesn't blur it.** Hover is the cell under a real pointer move (a move to the same position, which a browser makes up after a scroll to update hover, is ignored: GPUI hears none); a cut is the drawn cell's `scrollWidth` over its `clientWidth`; it's placed by gpui-base's `Positioner` rules (above, else below, centered, 4 px inside the window, gpui-kit's 12 px margin). A press outside the table keeps the focus (`preventDefault` on the page's `mousedown`), as GPUI, which has no blur on a press, keeps its ring and keys. *[M3 part C]*
- **2026-10-18** · **The first screen is prerendered by the view itself, at build, and hydrated in place.** A Vite plugin renders `App` with the first screen (`renderToString`, in dev and build) into `index.html`; `hydrateRoot` keeps that element (checked: the node the HTML parsed is the one on screen after the commit). `contender:first-pixels` is the status line's Element Timing paint, which equals Chromium's `first-paint`; `usable` is the hydration commit. Rejected: a static copy of the first screen's markup (it would drift from the view; a mismatch only shows up as a hydration error). *[M3 part D, `perf/results/2026-10-18-m3-d.md`]*
- **2026-10-18** · **The engine starts once the HTML has painted and the hydration has committed, not at the paint alone.** The two land within ~11 ms of each other, in either order (the commit first by 1.6–7.2 ms in 3 of 6 runs, the paint first by 6.1–10.8 ms in 3). Starting at the paint would put the data layer's import and the engine's start in hydration's way, for at most those few ms of time to data. The GPUI contender starts it after its first frame, its usable moment: the same rule on both sides. *[M3 part D]*
- **2026-10-18** · **First usable is confirmed by a probe key that changes React state.** With `?measure`, a listener added in the hydration commit takes the first key into the state of a component of its own (so nothing else re-renders, and later keys cost nothing), and the commit that draws it marks `contender:input`, in the key's task (1.1–10.3 ms after the key's event in this part's runs). Control: with the entry's JS held back, the HTML painted and a key pressed then set no mark. Rejected: a handler that only marks (it wouldn't go through React's state); Tab and the focus ring (a prerendered page takes focus with no JS at all). The GPUI contender doesn't publish it yet. *[M3 part D]*
- **2026-10-18** · **A row that loads gets new cells, measured or not, so Element Timing reports its paint.** Element Timing reports an element only at its first paint, so placeholder cells are keyed apart from loaded ones. With `?measure` each loaded cell carries `elementtiming="row:<row>"`. The latest paint among the visible rows' new cells came 9.8–15.8 ms after `contender:filled` (open, End, in this part's runs), and every visible row had one. *[M3 part D]*
- **2026-10-18** · **The replay's fling steps the scroll model as an input, not a bare `scrollBy`.** A step is 261,254 px a frame (the table over 180 frames). With no wheel, key, or touch behind it, the model reads a step bigger than a screen as a thumb drag. `step` marks it the replay's, and it moves 1:1 like a wheel. *[M3 part D]*
- **2026-10-18** · **Two JS budgets, brotli, each at most 10% over its baseline:** the first-paint JS (the entry and its static imports: 72.1 KiB, up 1.6 KiB for the contract, hydration, and the probe) and the data layer with Arrow, which loads after first paint (34.7 KiB). The engine's own chunk (7.5 KiB) is recorded but not budgeted: it's `@seiza/duckdb`'s, and `engine-files` covers it. *[M3 part D, `perf/results/2026-10-18-m3-d-tanstack-sizes.json`]*

## Measurement

- **2026-10-15** · **Input to visible response comes from Chromium's trace, `EventLatency`, for every input kind on both sides, each reading guarded on every run.** It reports GPUI's prevented wheel (`MOUSE_WHEEL`) as well as keys and presses, and named the probe's frame (the first drawn at the new position) in 180 of 180 GPUI inputs on WebGPU and WebGL2. On the DOM's native scrolls the compositor moves the content before the main thread knows: the wheel's `EventLatency` (`FIRST_GESTURE_SCROLL_UPDATE`) ended 23–30 ms before the main-thread probe in 30 of 30, and a session's first track press ended 19 ms before it (2 of 30); in all 60 it ended on exactly the frame whose compositor first applied the scroll (`Scroll Delta This Frame`). A control scrolling the same page from a main-thread listener put `EventLatency` back on the probe's frame in 30 of 30. So the guards: GPUI's reading must match the probe; a DOM main-thread move (the contender's keys) the probe; a DOM native scroll the compositor's frame. A cold run measures a first press, where the main-thread probe is late. Rejected as the source: Event Timing as a page reads it (rounded to 8 ms, nothing under 16 ms: 3 of the DOM's 60 keys and presses missed; no wheel); the trace's `EventTiming` equals `EventLatency` for keys and presses and adds nothing. The page's live readouts may use Event Timing for keys and presses, labelled (*Superseded* 2026-10-19: they don't; "Page", the numbers). *[M1 part B, `perf/results/2026-10-15-m1-b.md`]*
- **2026-10-15** · **Per-frame work is each frame's `ProxyMain::BeginMainFrame` in the trace, on both sides, itemized, and the main thread's whole busy time beside it.** The frame covers the whole rendering update, split into input dispatched in it, animate (rAF callbacks and scroll events), lifecycle (style, layout, paint), and the rest (commit); the DOM's work is mostly lifecycle (2.64 of ~3.7 ms a frame), which `workRecorder` (rAF callbacks that draw) can't see. As an instrument it holds: on Tycho's fling its rAF part matched `workRecorder` to 0.02 ms per frame (p50, 10 cold runs, spread 0.07 ms); the whole frame adds 0.41 ms (input 0.16, the update after the callbacks 0.24). ~8% of busy time runs outside any frame on both sides (GPUI: the engine's page results, read in wasm in the message's task, and timers), so main-thread CPU cost is the busy total, not frames × per-frame work. Tycho's work per frame (`workRecorder`, the panel) is the rAF part only, ~0.4 ms less, and doesn't compare with these numbers. *[M1 part B]*
- **2026-10-15** · **The contender contract:** marks (`contender:first-pixels`, `usable`, `open`, `filled`), the state object `__contender.state` with `?measure`, the targets, and the replay hooks, in `contender-contract.md`. Contenders publish; one metrics module reads. *[M1 part B]*
- **2026-10-18** · **One metrics module, `metrics/metrics.ts`, pure, and one script per metric.** It computes every metric from what the contenders publish and from Chromium's trace, and owns the protocol's constants (the probe key, the two frames, the fling profile, which moved there from the contract). No Playwright, Node, or DOM at import, so the observatory's page can use it as the scripts do. The scripts (`perf/metric-usable`, `data`, `response`, `fling`, `reach`, `cost`) share `perf/contender.ts`: either bare page cold with `?measure`, each side's input path, both profiles, both contenders alternated. *[M4 part A, `perf/results/2026-10-18-m4-a.md`]*
- **2026-10-18** · **First usable is confirmed by the probe key's presented frame, from a light trace through the load; only GPUI's is guarded.** The frame is the animation frame `contender:input` lands in (GPUI) or the first that begins after it (the DOM's commit runs in the key's task; the next presentation after it was a frame already under way, 0.6 ms after the commit). GPUI's key `EventLatency` ended on that frame in every trial run. The DOM's probe changes a hidden element, so nothing is presented for it and its key's `EventLatency` reaches no frame: that reading is unguarded. The probe key is `x` on both sides: GPUI hears a modifier alone only on its release (Shift: 18.8 ms to the mark, `x`: 6.2, one trial each). GPUI takes it with `intercept_keystrokes` (before anything handles the key), only once `gpui:first-frame` is set (as the DOM side listens only from its hydration commit), and marks it from the host's next render: +1.7 KiB raw wasm, brotli unchanged (2697.3 → 2695.7 KiB). *[M4 part A]*
- **2026-10-18** · **Behavior under load is read from the frames the main thread ran, with the fling on a fixed schedule and its input by summed delta.** Chromium's compositor frame reporter doesn't see GPUI's canvas: in a GPUI fling it called 116 of 188 frames `STATE_NO_UPDATE_DESIRED` while GPUI drew each one, so late frames are rAF intervals over 1.5 refreshes, on both sides. Playwright's `mouse.wheel` waits for the page's handling, so an awaited loop paced the fling by each side's cost (~9 s on GPUI, ~6 s on TanStack for the same 180 events); the steps now go out every frame without waiting. Chromium coalesced 1–2 of the 180 wheel events on the native scroller (the distance whole), so how far the view trails is measured against the events' summed `deltaY`, in fling steps. *[M4 part A]*
- **2026-10-18** · **Cost is one session per run: the cold load, then the fling to rest.** Main-thread CPU from a trace started before navigation (the load and the use apart); memory with `performance.measureUserAgentSpecificMemory` (the pages are cross-origin isolated; Chromium's `ForceEagerMeasureMemory` so it doesn't wait for a GC), the page's own apart from its workers' (the engine's, the same on both sides), plus the JS heap and DOM nodes; bytes by kind (the page's, the engine's, the data). *[M4 part A]*

## Page

- **2026-10-19** · **The contenders' bases moved to `/observatory/contenders/<component>/<stack>/`; the engine, the data, and the font stay at one path each, outside them.** Both contenders had base `/observatory/`, so their `index.html`s would land on the page's URL. The engine's bundles are emitted under each build's `duckdb/` and referenced at `/observatory/duckdb/` (`renderBuiltUrl`), its extensions through `@seiza/duckdb`'s new `extensionBase`; dev and preview serve the shared paths (`shared-web`'s `serveDirs`, `contenders/data.ts`), and the deploy stages one build's `duckdb/` there (`engine-files` checks the two are byte-identical). The cold numbers held (`check`). Rejected: keeping base `/observatory/` and moving only each `index.html` (three builds' `assets/` and `_headers` in one directory). *[M5 part A]*
- **2026-10-19** · **The toggle is disabled until the shown contender's first `contender:filled`, after every flip, not only GPUI's at load, or until it marks `contender:failed`.** GPUI loads first by default, and the same rule for whichever side is shown means a flip never lands mid-load (destroying a frame whose engine is starting). A contender that can't fill (the engine didn't load, the file 404s) marks `contender:failed`, a mark added to the contract for it, so a failure never locks the visitor on one side; `perf/page.ts` checks both sides with the data file missing. Its prerendered state shows no side pressed: the HTML can't know `?side=`, and the frame waits for the page's first paint anyway. A flip writes `?side=`, so a reload shows the same side. *[M5 part A]*
- **2026-10-19** · **The page's theme reaches a frame as `?theme=` once, then only by message.** The frame's `src` is fixed when the frame is created (a later theme in its URL would reload it, discarding its state and warming its next load). The page sends the theme again at the frame's `load`: a change made while the frame loads reaches no listener (its control, without the re-send, fails `perf/page.ts`). The contenders' `THEME_SCRIPT` and the site's go first in the `<head>`: an inline script after a stylesheet waits for it to load. *[M5 part A; code review]*
- **2026-10-19** · **The page's budgets: first paint (paint timing's `first-paint`) +20% over baseline, first-paint JS +10%.** First paint is the page's own: it's HTML and CSS, so the browser's metric is right here, unlike a canvas's. Baseline 70.8 ms reference (spread 60.6–82 ms, machine load ~3.6), 437.4 ms throttled, 78.2 KiB first-paint JS (React, Base UI's parts, the shell, the page). +20%, not TTFP's +10%: the spread alone was ±15%. What it paints after: the CSS (≈27 ms) and then layout and paint of the whole route; holding back the JS or the font moved it by noise only. *[M5 part A; `perf/results/2026-10-19-m5-a-page.json`]*
- **2026-10-19** · **The site's surface grays are held within ΔE 2.5 (OKLab × 100) of the contenders' `theme.css`; the popover is apart by design.** `web/scripts/grays.ts` compares background, foreground, muted foreground, border, and ring in both modes, a token with alpha composited over its background first (the site's dark border, white at 10%: ΔE 1.44; the ring, Tailwind v3's gray against v4's: 0.75).

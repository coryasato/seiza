# The contender contract

What every contender page publishes, so one metrics module (`metrics/metrics.ts`), the Playwright scripts, and the observatory's page can measure any of them the same way (root `CLAUDE.md`, "Comparison protocol"). Contenders set marks and publish state; they compute no metric. How each metric is then read is under "Reading the metrics" below; the choices behind it are in [`DECISIONS.md`](DECISIONS.md), "Measurement".

The GPUI contender builds this from the tall table's events in its host; the TanStack contender from its own view. Names are the same on both sides.

## Where a contender lives

Each contender is a bare page at `/observatory/contenders/<component>/<stack>/` (the tall table's: `…/tall-table/gpui/`, `…/tall-table/tanstack/`), its build's base. What both load sits outside either base, at one path each, so the second to load finds it cached: the engine at `/observatory/duckdb/` (DuckDB-Wasm's bundles and extensions), the data at `/observatory/data/`, the font at `/fonts/`. The list is `contenders/paths.ts`.

## The measured-run switch

Always published, measured or not: every mark but the probe key's (the page's readouts and the replay hooks need `contender:filled`) and `globalThis.__contender` with `side` and `replay`. `?measure` in the URL adds what only a measurement reads: `__contender.state`, the targets, the probe key, and on the DOM side the `elementtiming` attributes on cells. Without it `state` is null. The cost of publishing is the same kind on both sides (a few property writes per frame).

## Marks

`performance.mark`s, set only by the contender. Two kinds:

- **Steps** (`contender:first-pixels`, `usable`, `open`): set once per load, again only on a retry. Readers take the last entry, as for every mark (root `CLAUDE.md`, "`shared/` and `shared-web/` conventions").
- **Events** (`contender:filled`, `input`): set every time it happens. A reader takes the first entry after the moment it times (the open, an input), as the harness's `waitMark(page, mark, since)` does; the last entry is only the latest fill.

## State

`globalThis.__contender` (always; `state` only with `?measure`):

```ts
interface Contender {
  side: 'gpui' | 'tanstack';
  /** What the last presented frame showed (GPUI: updated while the frame
   *  renders; TanStack: in the commit). Replaced, never mutated in place. */
  state: {
    rows: number;        // the row count the view uses (after the open's count(*))
    top: number;         // the content's position, CSS px from row 0's top
    first: number;       // first visible row, 0-based
    end: number;         // one past the last visible row
    loaded: number;      // visible rows with real data
    pending: number;     // visible rows drawn as placeholders
    lastCell: string | null; // the key (spkid) of the last row, when it's visible
    cacheBytes: number;  // the page cache's Arrow IPC bytes (the 64 MiB budget's unit)
  } | null;
  replay: Replay;
}
```

Market watch adds two, with `?measure` only, on both sides: `globalThis.__contenderRefreshed`, the highest generation drawn so far, raised in the frame that draws it, before its `contender:refreshed`; and

```ts
interface Contender {
  /** Each batch of the feed as the store folded it,
   *  appended in its message's task. */
  batches?: [seq: number, ticks: number, sent: number /* epoch ms, the worker's stamp */, generation: number /* its rows' last invalidation, 0 for none */, visible: 0 | 1 /* a tick reached a row on screen */][];
}
```

Live tail adds, with `?measure` only, on both sides: `globalThis.__contenderTail`, the end of the tail last drawn, set in the frame that draws it, before its `contender:tail`; `globalThis.__contenderFollowing`, whether the view follows the tail, set when the table starts watching and at each change; and

```ts
interface Contender {
  /** Each count the clock posted, appended in its message's task. */
  batches?: [rows: number /* the rows due */, at: number /* epoch ms, the worker's stamp */][];
  /** Pauses the clock's count (`true`) or resumes it (`false`): the
   *  scroll back's control, the same gesture without the feed. */
  pause?(on: boolean): void;
}
```

The monitoring wall adds market watch's two, with `?measure` only, on both sides, across its N tables (the stop's): `globalThis.__contenderRefreshed` is an array, each table's highest generation drawn so far (a table's generations count its own re-reads), each entry raised in the frame that draws it, before that frame's `contender:refreshed`; and a batch's entry names each table:

```ts
interface Contender {
  /** Each batch of the feed as the store folded it,
   *  appended in its message's task. */
  batches?: [seq: number, ticks: number, sent: number /* epoch ms, the worker's stamp */,
    generations: number[] /* per table, its rows' last invalidation, 0 for none */,
    visible: number /* a bitmask: bit t set when a tick reached a row on screen in table t */][];
}
```

Its `state` is the first table's, as above, with `tables: number` (the stop's N) beside it: no measure of the wall scrolls, so no other table's position is read.

The wide sheet adds, with `?measure` only, on both sides, each replaced (never mutated) when it changes, never a frame:

```ts
interface Contender {
  /** What became of the last copy, as the table's bridge spells it
   *  (`clipboard::Outcome`): `{state, id, …}`, `state` one of `declined`
   *  (`rows`, `columns`), `copying` (`rows`, `rowsDone`), `writing` or
   *  `written` (`bytes`), `refused` (`error`), `failed` (`reason`:
   *  `too-large`, `read`, `cancelled`, `closed`), `unavailable`; `id` null
   *  when declined. */
  copy?: { state: string; id: number | null; [detail: string]: unknown };
  /** `{kind, anchor, head}` (`rows`, `columns`, or `cells`; each cell
   *  `[row, column]`) or null, as the table's `fixtures/selection.json`
   *  spells it: replaced at each change. */
  selection?: { kind: 'rows' | 'columns' | 'cells'; anchor: [number, number]; head: [number, number] } | null;
  /** Each column's set width, CSS px, null where it's its kind's: replaced
   *  at each release or fit that changed one. */
  widths?: (number | null)[];
  /** Where the cells are: `{left, top, rowHeight, cellsWidth, pinned,
   *  columns: [{name, x, width, kind, budget}]}` (column `c`'s left edge
   *  `left + x`, less the sideways scroll past the pinned run), replaced at
   *  each layout change (a release or fit, the view's size), never a frame
   *  (with `?cells` too, on every level that publishes it). The drags'
   *  scripts read where to press from it once, at rest. */
  layout?: object;
}
```

GPUI's come from the table's events in `crate/src/wide.rs` (`Selected`, `ColumnWidthsChanged`, and `Layout`, which the table emits only when the layout changes), the copy's from the bridge's writer. TanStack's come from its ports (`src/wide-tools.ts`): the selection at each change, the widths at a release or fit that changed one, and the layout read from the DOM at each layout change but a drag's moves (the release reports it); and `copy` from its copy's DOM (`src/copy.ts`, the bridge's writer ported), at each copy event and as the browser settles a write.

The replay (live tail): the open reads the file by range under its own name (the summary), and the table opens at 0 rows, following; then the file is fetched whole in one request and registered in the engine as `nasa-http-jul95.whole.parquet` (`contenders/tail/data.ts`, `WHOLE_FILE`), which every page reads, and only then is the frame's clock worker (`contenders/tail/worker.ts`) started at the stop's rate. Each count it posts is set on the table (`set_rows`) in its message's task; following, the view moves on as the new rows' reads land. The fetch, the registration, or the worker failing fails the view (`contender:failed`), as does a file whose columns aren't the log's or whose rows aren't the replay's. `?rows=<n>` stops the clock at n rows (`contenders/tail/data.ts`'s `limitFrom`, handed to the worker's start message; 0, the default: never; anything but a count fails the load): memory's equal work at the level. A replay `open()` starts the replay over: the clock ended, the table reopened at 0 rows, and a new clock started (the file registered once). `__contender.batches` empties when the clock starts over; a pause asked before the worker exists holds from its start. The scroll back's probe is the state's `top` (`perf/contender.ts`'s `gpuiProbe`): let go, it holds as rows arrive. On the TanStack side the scroller's moves are the reader's (`src/tail.ts`'s `TailReader`): a move up lets go at its wheel, key, or touch move event, a move down decides at its scroll event from where it lands, End and a jump land, Home lets go, a thumb drag holds until its release; the tail pin and a resize move the scroller as the view's own moves, never the reader's.

The feed (market watch): the frame's worker (`contenders/market/worker.ts`) starts once the table first fills, its store seeded from the open's page; `?ticks=<n>` ends it after n ticks (0, the default: never). A batch is folded in its message's task, every tick, and its rows re-read from the store in that task, drawn in the next frame. The worker failing to load, throwing, or sending a batch the store refuses fails the view (`contender:failed`). A replay `open()` ends the feed: the new store would miss the ticks sent meanwhile.

The feed (the monitoring wall): market watch's, one worker a frame over the stop's N desks (`contenders/wall/desks.ts`: the first N of `contenders/wall/instruments.ts`' 8 desks of 50, the instrument a tick names its row in the wall's first N × 50) at the scenario's rate × N, started once every table has filled; one store of the N × 50 instruments, seeded from the open's read (a desk's 50 rows are one page, read once, then answered from the store). A batch is folded once, in its message's task, and each table's ticked rows re-read in that task, drawn in the next frame. `?ticks=<n>`, the failures, and a reopen as market watch's.

### The readout's ring

With `?readout` (market watch's and live tail's frames on the observatory's page; never a bare cold run, which can't send it), both sides keep this tab's Shown in on `globalThis.__contender.shownIn`: a `Float64Array` of `1 + 2 × SHOWN_RING` (512, `contenders/contract.ts`), its first element the samples written so far, then (drawn at, ms) pairs, epoch ms, sample `n` at `1 + 2 × (n mod 512)`. Each batch with a tick on screen waits (at most 256, the oldest dropped) until a frame draws its generation; that frame's time, taken while it renders (GPUI's `TallTableEvent::Refreshed`, TanStack's commit, as `contender:refreshed` is placed), is its drawn at, and drawn at − sent its ms. Preallocated on both sides, so it adds no garbage to the feed's; no mark and no message a frame. The page reads it at each refresh (`web/src/live.ts`) and shows the middle of the last 5 s (`liveReadings`' `shownMs`): to the frame that drew a batch, not its presentation, which a page can't read without a trace. A reopen (the replay's `open()`) starts a new ring on TanStack and empties the batches waiting on GPUI. On live tail each count the clock posts waits instead (its post stamp, keyed by its rows) until a frame's drawn tail reaches it (GPUI's `TallTableEvent::TailDrawn`, TanStack's commit that marks `contender:tail`), so a sample is Row shown in to the frame that drew it (at most 256 counts wait, about 4 s of them: a view that trails further drops its oldest, so this tab's reading tops out there; the page reads no sample sent while it was hidden, when no frame draws); following turning off or on drops the counts waiting (posted while the reader held the view, they'd read as the reader's time), and so does a reopen. On the monitoring wall a batch with a tick on screen waits until a frame has drawn every generation it names in the tables of its mask (the pooled reading, as Shown in pairs it below). GPUI's ring is one module the levels share (`crate/src/readout.rs`); TanStack's is market watch's `quotes.ts` class keyed by rows, a copy in `data/replay.ts` so market watch's chunk stays as it is.

The scripts record `state` with every frame through `shared-web/perf/`'s `frameRecorder` (`__seizaFrameSample = () => __contender.state`), as Tycho's `tableFrames` does: a frame showing placeholders, whether the view keeps up with the input, reach (`end === rows`, `lastCell` the file's last key), and the cache's bytes on both sides.

`state` is replaced only when something in it changed. GPUI writes it while the frame renders; TanStack in the animation frame after a commit or a move (so an idle page asks for no frames), from the paging's visible rows (`top` is the scroll model's V).

**The probe.** To find the first frame drawn at a new position, the scripts mark the frame in which `state.top` changes. On GPUI, `state` is read right after the task that made the frame's GPU calls (a microtask queued at its first call); on the DOM, in a rAF. Each is tied to that animation frame's presentation in Chromium's trace.

### The follow toggle

Live tail's frames only, with `?readout` only (`contenders/follow.ts`'s `followToggle`): a bare page, the cold runs' (`?measure` alone), neither heeds the page nor tells it anything. Two messages, same origin both ways:

- **The page asks** `{ seiza: 'follow', on }`: `true` follows the newest (the table's `follow`, as End does: the view jumps to the end and follows), `false` lets go with the view where it is (its `let_go`). The replay never stops; only the view does. GPUI: the wasm export `followTail`, run on the host in the message's task. TanStack: `follow.ts`'s `follow` (the view's next draw moves the scroller to the end) or `letGo`.
- **The frame tells** `{ seiza: 'following', on, rows }`: `rows` the clock's last count. Sent when following changes (the page's ask, the reader's scroll up, End, a scroll back to the bottom), and while let go at most every 250 ms (`FOLLOWING_EVERY_MS`) as the counts arrive, a count held back sent when the 250 ms are up (so the last one arrives though the clock stops): never a message a frame. The page assumes a frame follows until told otherwise, and counts the rows since following was let go itself. GPUI's reports come from the table's `Following` and the clock's counts (`crate/src/clock.rs`); TanStack's from the paging's `onFollowing` and the counts (`data/replay.ts`).

While let go no count is drawn, so the ring takes no sample (above) and this tab's Shown in reads "—" once the last 5 s hold none, as after a scroll up.

### The copy line

The wide sheet's frames only, with `?readout` only (`contenders/tools.ts`'s `toolsReporter`): a bare page, the cold runs' (`?measure` alone), neither exports the tools nor tells the page anything. The page says the selection and the copy in its status bar and offers a Copy button; the frame holds no words of its own (`docs/DECISIONS.md`, "Page"). Same origin both ways:

- **The frame tells** `{ seiza: 'tools', cells, copy, done, bytes, ms, reason? }` at each selection change and copy event: `cells` the cells selected (0 for none); `copy` the last copy's state as `__contender.copy` spells it, or null (a selection change clears an ended copy's, never a running one's); `done` a running copy's share of its rows, 0–1; `bytes` the text's while writing and once written; `ms` once written, the copy's start (the key's task, or the page's call) → the browser's write resolved, the page's own clock (the cold numbers time from the key's event instead); `reason` why a copy failed. A change of `copy` goes at once; anything else (a drag's selection, a copy's progress) at most every 100 ms (`TOOLS_EVERY_MS`), the last held back sent when the time is up: never a message a frame.
- **The page calls** `globalThis.__contenderTools.copy()` and `.cancel()` on the frame's window, inside its click: a press in the parent is the clipboard's gesture for the same-origin frame (WebKit honors only a call made in the event's task). `copy()` is the host's copy, which the key's limit doesn't hold (the cap does): the Copy button, and "Copy anyway" after a declined key. It focuses the frame's window first: Chromium refuses a clipboard write from a document without the focus, and the press gave it to the page. `cancel()` ends the copy running, the clipboard as it was.

GPUI: the wasm exports `tools` (the reporter, before `start`), `toolsCopy`, and `toolsCancel`, run on the table in the caller's task (`crate/src/wide.rs`); the confirming key is Cmd+C (Ctrl+C) again on the selection the key declined, the same copy, made in the key's task (a selection change in between declines again). TanStack: the same module over its own copy (`src/copy.ts`), the same confirming key.

## The cell probe

`?cells` (never in a measured run: the table then formats every cell twice) turns on the table's cell probe, and the GPUI contender publishes what it drew: `__contender.columns` (each column's `name`, `x` and `width` in CSS px, `kind`, and `budget`, the characters a float may take: the table's `ColumnProbe`s) and `__contender.cells` (every cell of the last frame: `row`, `column` by index, `exact`, `shown`). `perf/cell-fixture.ts` pins the tall table's cell fixture from them (`components/tall-table/fixtures/`); a DOM contender reads its budgets from that fixture, not from a page. On market watch's level the GPUI cells also carry `text` and `flash`, each drawn color as 8-bit `[r, g, b, a]` (the flash's null when none shows); on live tail's, `text` (null for a cell the scene doesn't paint). On the monitoring wall `columns` and `cells` are the first table's, and `__contender.tables` holds every table's, in desk order: `[{ columns, cells, layout, box }, …]`, each cell's `row` its table's (table t's row r is instrument 50t + r), with `text` and `flash` as market watch's; `layout` where the table's cells are in the window, `{ left, top, rowHeight }` (`left` right of the row numbers, `top` under the header, CSS px; GPUI's from the table's `TallTableLayout`, those three alone); and `box` the table's frame, `[x, y, width, height]` (GPUI's the table element's bounds at prepaint, TanStack's its `.frame`), which `perf/wall.ts` and `tanstack-parity` compare across the sides (`perf/wall-grid.ts`).

The TanStack contender publishes the same from the DOM on its feature levels, for the scripts that compare the two sides: on the wide level `__contender.layout` and `.cells` (`perf/wide.ts`), republished after each check; on the market level `__contender.columns` and `.cells` with `text` and `flash` as the GPUI side's (`perf/market.ts`, `tanstack-parity`), `cells` a getter read from the DOM each time, since a flash fades with no render (its colors the computed `color` and `background-color`, its `exact` the value the cell drew, `data-exact`, so a page landed since but not yet drawn isn't read). On the tail level the same two (`perf/tail.ts`, `tanstack-parity`), `text` the computed color of a cell the scene paints (the time, an error status) and null for any other, as the GPUI side's is null for a cell its text ramp doesn't paint; the time's `exact` its text, as the GPUI side's page gives it.

## Targets

`globalThis.__seizaTargets[id] = [x, y, width, height]` in CSS pixels, as every app does: `table` (the rows' area: right of the row numbers, under the header, to the scrollbar), `table-scroll-track` and `table-scroll-thumb` (the vertical scrollbar; GPUI from the table's `Scrollbar` event, TanStack from the scroller's geometry, the native bar's width (an overlay bar counted 16 px), and the scroll model's estimate of the thumb). Republished when they change. On the monitoring wall, the first table's: no measure of the wall scrolls or presses a track.

## Element Timing on cells (DOM only)

With `?measure`, each loaded cell carries `elementtiming="row:<row>"` (0-based), so the browser reports its first paint; on the monitoring wall `row:<50t + r>`, table t's row r as its instrument, so the names are unique across the tables. Element Timing reports an element once, when it's first painted, so a row that loads gets new cells: its placeholder cells are keyed apart from its loaded ones, measured or not, and never turn real in place. A reader needs its own `PerformanceObserver` from the page's start (an init script): the entries' buffer holds 150, and one screen of cells is ~330. On the wide level, only the cells created with a row's page (as it lands, or as the row comes into view) carry it: a column a sideways scroll brings into an already drawn row is a new element too, but its paint is the scroll's, not the row's data, so it carries none, and a row that loaded long ago reports no new paint.

## Theme

The page passes its theme in two ways, and a contender follows the system without either, so a bare page's cold runs don't change:

- **`?theme=light|dark`** when the frame loads, applied before the first screen paints: an inline script at the head of the `<head>` (`THEME_SCRIPT`, `contenders/contract.ts`) sets the root's `data-theme`, which the GPUI side's placeholder and body and the TanStack side's `theme.css` follow. The GPUI host reads it as it starts (`start`'s `theme`) and draws its first frame in it.
- **`{ seiza: 'theme', theme }` by `postMessage`** from the parent (same origin) for every later change (`followPageTheme`): the root's `data-theme` changes, and the GPUI host repaints its canvas in it (the wasm export `setTheme`; before the wasm has started, `start` reads the root's `data-theme`). The frame isn't reloaded, so its state and its warm cache stay. The page sends the theme again at the frame's `load`: a change made while the frame was loading reached no listener.

The GPUI host stops following the system once the page has given a theme (`seiza::stop_following_system_appearance`), as Tycho's toggle does.

## Replay hooks

`__contender.replay`, for the page's benchmark when it's built (in-page, warm, labelled so; deferred, `PLAN.md`'s long-term goals); the published numbers come from Playwright driving real input instead.

```ts
interface Replay {
  open(): Promise<void>;                 // close and reopen the file; resolves once the view is filled
  fling(): Promise<void>;                // top to bottom in ~3 s; resolves once it rests at the end and fills
  jump(fraction: number): Promise<void>; // to that fraction of the rows (0.9: the 90% jump); resolves once the view is filled
}
```

Each side replays through its own input path: GPUI through script-made wheel events dispatched on its canvas (they reach GPUI's listeners); TanStack through its scroller's position (the scroll model's `step`: a `scrollBy` each frame that the model takes 1:1, as a wheel's), since a script-made wheel event never scrolls a native scroller. "Filled" is the first `contender:filled` after the input, or at once when the view lands already filled (rows in the cache) or doesn't move, which sets no mark: the mark is a change to filled. One fling profile for both, the metrics module's (`FLING_FRAMES`, `flingStep`): equal steps per frame, so no step outruns a native scroller's room (`dom-scroll-model.md`, "Scripting it"). The Playwright scripts' fling is the same profile through real input.

The monitoring wall's replay is `open()` alone: a desk's 50 rows give a fling and a 90% jump no meaning, and the page offers neither. `fling` and `jump` reject. `open()` resolves at the next `contender:filled`, every table filled again (the feed doesn't start again: the new store would miss the ticks sent meanwhile).

## Reading the metrics

Chromium only, under the measurement protocol; the reasons and the numbers are in [`DECISIONS.md`](DECISIONS.md), "Measurement". `metrics/metrics.ts` computes each one from the marks, the recorded state, the cells' paints, and the trace; `perf/metric-*.ts` gather them, one script per metric, against either bare page (`perf/contender.ts`).

- **Time to first usable:** `contender:usable`, confirmed by the probe key pressed right after it: the frame that drew its change must be presented within two frames of the key's event (`firstUsable`). The frame, from a light trace through the load (`PROBE_CATEGORIES`): the animation frame `contender:input` lands in (GPUI), or the first that begins after it (the DOM's commit runs in the key's task) (`probePresented`). On GPUI the key's own `EventLatency` must end on that frame; the DOM's probe changes nothing visible, so its key reaches no presented frame and that reading is unguarded. First pixels is recorded beside it.
- **Time to data:** `contender:open` → every visible row painted with real data (`timeToData`): GPUI's first `contender:filled` after the open; on the DOM the latest Element Timing paint among the visible rows' cells (`rowsPainted`). On the monitoring wall, every table's: GPUI's `filled` across the tables, the DOM's latest paint among every table's visible rows (`row:<50t + r>`; nothing scrolled, each table shows the first table's rows). On live tail's level the log downloads first, so the measurement is the table keeping up, not the network, and the load is three numbers from a light trace through it, on both sides (`tailData`): download, `contender:open` → the file fetched whole (its response's end; network only, the same on both sides); data, the clock's first count (`__contender.batches[0]`'s stamp) → the presentation of the first frame that drew its rows (the UI's share); and open to data, the total. The table opens at 0 rows and its rows move, so the check is the content (`tailContent`): over the first 5 tail marks, each tail drawn is a count the clock had posted or a page's end below the latest, and every frame the recorder sampled drawing one shows each row up to it real.
- **Behavior under load:** the fling, `FLING_FRAMES` wheel steps one per frame on a fixed schedule (not paced by each event's handling), `state` recorded as each animation frame starts (`underLoad`): late frames (intervals over 1.5 refreshes), the share of frames showing placeholder rows, how far the view trailed the input in fling steps (by the wheel events' summed `deltaY`, since a browser coalesces them), and the last input → the view at rest at the end, filled. Late frames come from the main thread's frames on both sides: Chromium's compositor frame reporter (`PipelineReporter`) doesn't see GPUI's canvas frames. Per-frame work and main-thread CPU over the fling, from the trace (below).
- **Reach and correctness:** `state.rows` against native DuckDB's `count(*)`, End showing the last row filled with the file's last key (its first column, as `lastCell` reads it; on the wide sheet a station's name, not unique, so the view's `end` at `count(*)` is what places the row) (`reach`).
- **Keeps up, at a scenario's stops** (`metric-scroll`): the file read whole first (the replay's jump to each page, each landing quiet), then three gesture scrolls (`SCROLLS`: down and sideways steady, fast the fast fling), each from the top and the first day, traced on its own and ended by its own rest (nothing drawn for 300 ms since its start). The frames that drew new cells: GPUI's presented frames (`workRecorder`: the rAF callbacks that made GPU calls); the DOM's main frames whose animate part ran past 1 ms (`domDrawn`: the scroll event and the virtualizer's render; between them the compositor presents the frame in part, moved with no new rows). Their share of the display's frames from the first to the last at 60 Hz (`drewShare`), under two frames a failure; a side keeps up at a stop when both steady scrolls' median shares are at least 90% (`keepsUp`). Beside it the frames' work and, on the DOM, the compositor's frames per vsync (`compositorFrames`: whole, in part, dropped). On a scenario's level every scripted scroll is this gesture, the wheel's response and the cost's fling too.
- **Smooth, the admin table's** (`metric-scroll --scenario admin-table`): once the open's one page is in and quiet, one gesture from the top (`READ_THROUGH`, 6,000 px at 3,000 px/s, inside the table), traced with `cc` on both sides and ended by its rest. The frames that moved the view: GPUI's presented frames (`workRecorder`), as the wide sheet's; on the DOM, which renders every row, the presented vsyncs its compositor applied a scroll delta in, each once (`compositorScrolls`: each `Scroll Delta This Frame` with a delta, off the main thread, paired with the latest frame reporter begun before it on its thread, kept if that vsync presented, timed at the delta), its work the main thread's frames over the span. The reading is `drewShare`'s, one total on both sides; no keeps-up verdict.
- **The fonts toggle's own** (GPUI, the admin table with `?fonts`: `--fonts` on `metric-usable`, `metric-data`, and `metric-memory`): Ready in and Rows in as without it; Scripts drawn in, `timeOrigin` → `contender:fonts`, split into the rows (→ the first `contender:filled`), the faces' fetch (→ `contender:fonts-in`), and fonts in → drawn, the mark checked against its frame's GPU work by `presentedMark` with its recorder armed at `contender:fonts-in` (nothing before it wrapped); each face's bytes on the wire (Resource Timing's `transferSize`), each fetched once, after the rows; memory with them, the memory run's session with the scripts drawn before the open's reading. Their files carry `-fonts` after the scenario's label.
- **Shown in, under a feed** (market watch's): a batch's send time (its worker's stamp, in page ms) to the presentation of the first frame that draws it: the trace's `AnimationFrame::Presentation` for the animation frame holding the side's mark in that frame (`Trace.presentationOf`; GPUI's `contender:refreshed`, TanStack's commit), p50 over the window, a batch with no tick to a visible row not counted. On GPUI a batch is `__contender.batches`' entry and its frame the first refreshed mark whose `__contenderRefreshed`, read at the mark, reaches the batch's generation. Each run's mark → presentation is kept beside it: a page settles in a scheduling state a run, a frame or so apart (a long task before the window moves the DOM's), so a frame-late control compares variants within one page or one state, and nothing long runs before the window (the throttle's busy-loop control comes after it). Element Timing isn't used for it: it reads the same presentation and costs the DOM's main thread ([`DECISIONS.md`](DECISIONS.md), "Measurement"). The pairing is the same on both sides (`feedFrames`, `shownIn`): every batch's frame is the first refreshed mark at or after its send whose generation reaches the batch's. On the monitoring wall it's pooled across the tables: a batch's frame is the first refreshed mark at or after its send at which every table in its mask has drawn the generation the batch names for it (`__contenderRefreshed`'s entry, read at the mark), one reading a batch; "a tick on screen" is a mask that isn't 0 ([`DECISIONS.md`](DECISIONS.md), "Measurement").
- **Keeps up, under a feed** (`metric-feed`, market watch's stops and the monitoring wall's, its batches paired as above): each side cold with `?measure`, once the first `contender:refreshed` is set 1 s to settle, then 10 s traced. The batches sent in the window with a tick on screen, each paired with its frame as Shown in pairs it (above); the distinct frames among them over the lesser of those batches and the display's frames at 60 Hz (`feedFrames`); a side keeps up at a stop when the runs' median is at least 90%. A batch with no tick on screen draws nothing and isn't counted (at 100 updates a second about a quarter of the batches). Beside it, from the same window: late frames (the page's animation frames' intervals over 1.5 refreshes), work a frame and the main thread's busy time (the trace's frames, below), and **collection pauses:** V8's `MinorGC` and `MajorGC` on the main thread, counted, their total and longest, and how many overlap a late frame (`collections`). After the window, never before it, the throttle's control: a fixed busy loop timed on the page.
- **Row shown in and keeps up, under the replay** (`metric-tail`, live tail's stops): each side cold with `?measure`, once the first `contender:tail` is set 1 s to settle, then 10 s traced (the feed's categories), the trace running `TAIL_GRACE_MS` (1 s) past the window. Each count the clock posted in the window (`__contender.batches`) is paired with the first tail mark at or after its stamp whose `__contenderTail`, read at the mark (an init script wrapping `performance.mark`, as the feed's), reaches its rows (`tailFrames`); its reading is the stamp → the presentation of that mark's frame (`shownIn`). A count with no such mark by the trace's end is counted at the grace, a lower bound, so a view that trails the tail can't pass (`rowShownIn`). A side keeps up at a stop when the runs' median p95 is at most 100 ms (`TAIL_KEEPS_UP_MS`); beside it the frame share (the distinct tail marks in the window over the lesser of the counts and the display's frames), late frames, work a frame, the busy time, and collections, as the feed's. Each run's stamp → mark and mark → presentation are kept, as Shown in's.
- **The scroll back, under the replay** (`metric-tail`, after the window, in a trace of its own with `cc`): a 300 px gesture up at 10,000 px/s at the rest point, `input:<n>` before it and `input:<n>:end` once the view held; following must let go (`__contenderFollowing`) and `state.top` hold for 1 s as the rows grow. On the DOM, `readInputs`' wheel reading, guarded by the compositor's frame. On GPUI the probe's: the first wheel `EventLatency`'s start → the presentation of the first frame whose `top` moved while not following (`probe:let-go`, `perf/tail-metric.ts`'s `gpuiLetGoProbe`; `probeResponse`), since under the replay GPUI's wheel often reaches no frame in `EventLatency`, or ends after the frame that moved; "the top went up" isn't the rule, since a count set in the wheel's frame can pin the view down by more than the wheel moves it up. Its control: the clock paused (`__contender.pause`), End (following again), the same gesture, where GPUI's probe and its `EventLatency` must end within 1 ms. The throttle's busy-loop control comes after both.
- **The soak** (`metric-soak`, live tail at 100k): the replay for `--minutes` (10), a window as Row shown in's at the start (1 s after the first tail mark) and one ending at the soak's last second, memory right after each (the page's by type, its workers', the wasm's linear memory, the cache's bytes, which must stay under its 64 MiB cap), and at the end again after a forced collection.
- **Cost** over a session (the cold load, then the fling to rest): main-thread CPU from a trace started before the page loads, the load and the use apart; memory once open and at the end (`performance.measureUserAgentSpecificMemory`, the page's own and its workers' apart, plus Chromium's JS heap and DOM nodes); bytes received by kind: the page's own, the engine's (the same files on both sides), the data.
- **Memory at equal work** (`metric-memory`): the open, then (the base level) a walk to the last row by the replay's jump, 4 pages a step over the file's last 144 pages, each landing waited out until no data read is in flight and the cache's bytes hold for a second. Prefetch leans ahead while the rows move, and a fast device's lean-ahead pages land where a slow one's are cancelled, so scattered jumps read more on the fast device; on the walk each landing's even prefetch reaches the next, so both devices read the same pages: every run of a side must end on the same `state.cacheBytes`. Memory once open and at the end, as measured and after a forced garbage collection (the page's; the engine's worker isn't collected): the page's own by `measureUserAgentSpecificMemory`'s types and its workers' apart, Chromium's JS heap and DOM nodes, and the wasm's linear memory (an init script keeps every `WebAssembly.Memory` the page instantiates). What each side's reading holds: GPUI's page memory counts its canvas's backing store ("Canvas") and its wasm's linear memory, which holds the cache's Arrow bytes and never shrinks; TanStack's is its JS heap with the cache's Arrow buffers. Neither counts GPU memory. Also each file's bytes on the wire. A scenario's file is too short to walk: its equal work is the file read whole (every run's cache bytes the same), then a long sideways session (five gesture scrolls across every day and back), which reads nothing, with readings once open, once read, and at the end. Market watch's (one page of 50 rows) is the feed's: `?ticks=10000` at the stop's rate, every tick folded and its last re-read drawn on both devices, then a second for the last flash to fade, with readings once the table has filled (the feed just started) and at the end. The monitoring wall's is the same feed scaled to its tables: 10,000 ticks a table (`?ticks=60000` at 6), every table's last re-read drawn, the open's reading once every table has filled. Live tail's is the replay's: `?rows=100000` at the stop's rate, the tail drawn reaching it on both devices, then the cache quiet, with readings once the table has opened at 0 rows (the file then fetched whole) and at the end; every run of a side must end on the same cache bytes. The admin table's (250 rows, one page) is that page, read at the open, then the read-through gesture down and back, each landing filled (GPUI's `top` back to 0 within a pixel: it sums the wheel's float deltas), with readings once open and at the end; with `?fonts` the scripts are drawn before the open's reading, and the faces are a kind of bytes of their own. Each reading also gives the page less the window's canvas (`…LessWindow`: its largest canvas's width × height × 4, at most the measured "Canvas"); Chromium sometimes counts a second buffer for the same canvas, from the open or after the scroll back: in some default runs at the reference, and in most or every run with `?fonts` or on a slow device. The memory card is the page less every canvas buffer (its bytes less its "Canvas" type), and the runs holding a second buffer are counted on a line of their own (`docs/DECISIONS.md`, "Measurement"); `…LessWindow` is kept for context and feeds no card.
- **Input to visible response** (a key, a track press, a wheel event): Chromium's trace, `EventLatency` (categories `input` and `latencyInfo`): the event's own timestamp to the presentation of the frame it reached, for the input's type (`KEY_PRESSED`, `MOUSE_PRESSED`, and for the wheel `MOUSE_WHEEL` on GPUI and `FIRST_GESTURE_SCROLL_UPDATE` on a native scroller), the first that reached a frame (it carries a `display_trace_id`) (`readInputs`). The script starts the view mid-file (the replay's jump) and presses the probe key first, so no measured key is the first; each input sits in its own window, `input:<n>` right before it and `input:<n>:end` once the view moved, filled, and rested, before the next input's setup.
- **Every reading is guarded on every run** by an independent one that names the frame showing the new position: on GPUI the probe (it must match); on the DOM, for a main-thread move (the contender's keys) the probe, and for a native scroll (the wheel, a track press) the compositor's first frame that applied the scroll (`Scroll Delta This Frame` on the compositor thread, category `cc`, to the end of the next `SubmitCompositorFrameToPresentationCompositorFrame`). The main-thread probe can't guard a native scroll: the compositor moves the content first, by up to two frames, and on a session's first track press the main thread learns of it a frame after it's on screen.
- **→ that frame's rows being real:** GPUI, the presentation of the first `contender:filled` after the input, or the visible response itself when the frame that moved held no placeholder (the probe's mark says so: `probe:moved:<pending>`); TanStack, the latest Element Timing `renderTime` among the visible rows' cells created after the input (a visible row with no new cell was already real; after an open or a jump every visible row has one, landing within a few frames after `contender:filled`, `perf/tanstack-contract.ts` checks), or the visible response when no cell is new.
- **The page's live readouts** (`liveReadings`, `web/src/live.ts`): what a page can read of a frame, without `?measure` or a trace: usable from the frame's time origin (unconfirmed), open → the first `filled` after it (the DOM's at its commit), late frames from the page's rAF intervals while the visitor scrolls at the refresh they show, and the frame's own memory by `measureUserAgentSpecificMemory`'s attribution. Labelled "this tab", never mixed with the cold numbers.
- **Event Timing** (the page's `PerformanceObserver`) isn't used, not even by the page's live readouts: it rounds to 8 ms, drops anything under 16 ms, and has no wheel ([`DECISIONS.md`](DECISIONS.md), "Page"). The trace's `EventTiming` events carry the unrounded duration of every event and equal `EventLatency` for keys and presses.
- **Per-frame work:** the trace's `ProxyMain::BeginMainFrame` on the page's main thread, each frame's whole rendering update, itemized by its children: input dispatched in the frame (`WidgetBaseInputHandler::OnHandleInputEvent`), animate (`WebFrameWidgetImpl::BeginMainFrame`: rAF callbacks, scroll events), lifecycle (`WebFrameWidgetImpl::UpdateLifecycle`: style, layout, paint), and the rest (commit, bookkeeping). The rAF callbacks inside it (`FireAnimationFrame`) are what `workRecorder` and Tycho's panel time, and agree with them; the frame is more, on purpose.
- **Main-thread CPU:** the busy time of every task on the page's main thread (`ThreadControllerImpl::RunTask`), with the tasks outside any frame tallied by kind. Some work runs in no frame (on GPUI the engine's page results, read in wasm in the message's task, and timers), so frames × per-frame work undercounts it.
- **Trace categories:** `devtools.timeline` (the animation frames and their presentations, `FireAnimationFrame`), `blink.user_timing` (the marks, and the page clock's offset: `trace:origin`, set right after tracing starts), `input` and `latencyInfo` (`EventLatency`), `benchmark` (`BeginMainFrame`), `toplevel` (tasks); for latency also `cc` (the compositor's scrolling); for work also `blink` (the frame's parts, and what runs outside frames).

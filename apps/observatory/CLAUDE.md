# Observatory

The Observatory is seiza's comparison page, at `seiza.io/observatory`: it runs each component against a DOM equivalent, one at a time, on the same engine and data, and measures what each costs over a session of use. The first comparison is GPUI | TanStack: the tall table (`components/tall-table/`) against React + TanStack Virtual.

---

This is the Observatory's context. What's next is in `PLAN.md`; why things are built this way, in `docs/DECISIONS.md` (repo-wide decisions, the comparison protocol's above all, in the root `docs/DECISIONS.md`); finished milestones, in `docs/milestones.md`; budgets, in `perf/budgets.json` (the root `CLAUDE.md`, "Docs: one home per fact", says what goes where). The repo-wide rules in the root `CLAUDE.md` apply here too, its "Comparison protocol" first. Paths below are relative to `apps/observatory/`.

Current state only: say what to do and point to the decision behind it; don't retell its measurements.

## Observatory rules

These add to the repo-wide rules.

1. **Consume, don't reshape.** The observatory uses components and engines as they are. It may ask one to expose what its metrics need, or to take an option a host sets; it never changes how a utility app behaves, and every such change records its effect on each app that builds it (root `CLAUDE.md`, "Tiers").
2. **Everything lives under `/observatory/`** (`contenders/paths.ts`, the one list of paths). The apex origin is shared with the landing page and future pages: the page (`/observatory/`, `/observatory/<component>/`), the contenders (`/observatory/contenders/<component>/<stack>/`, each its build's base), the engine (`/observatory/duckdb/`, outside the contenders' bases: `@seiza/duckdb`'s `extensionDir` `duckdb` under `extensionBase` `/observatory/`), and the data (`/observatory/data/`) are served under it, and nothing registers a service worker outside it. The one exception is the site's: the font at `/fonts/` (root `CLAUDE.md`, "The apex site").
3. **The page is JS; the contenders are what they compare.** The page and the DOM contenders are JS throughout, on purpose (root `CLAUDE.md`, "Stack and pins"). The GPUI contender is a minimal Rust host of the component.

## Perf script gotchas

- **The contenders' checks serve their builds themselves** (`perf/harness.ts`, `serveGpui` and `serveTanstack`: `vite preview` of each `web/dist`, the page at its base; `servePage`: the page's build with both contenders', the page at `<server>/observatory/`), the GPUI contender's on ports 4311–4314, `engine-files` on 4315–4316, `tanstack-view` on 4317–4318, `tanstack-parity` on 4319–4320, `tanstack-contract` on 4321, `page` on 4334, `metric memory` on 4335–4336, `readout-cost` on 4337 (its throttling proxy on 4338), `burst` on 4339 (its counting proxy on 4340), and read `count(*)` and the last key from data/'s native DuckDB (`just observatory data` installs it). The GPUI contender's placeholder text sits 1 device px above GPUI's at DPR 2 (inside the ink's ±1), so a "text 1 px down" control can't fail the match; `perf/placeholder.ts`'s control moves it up.
- **The production scripts route the page in.** `perf/data-read.ts` opens a page at each data file's own origin with Playwright routing every path but the data to Tycho's local release build (`?bench` exposes its bridge), so the reads are same-origin under COEP and both sides run one engine. The routes reach DuckDB's worker too. Run `just tycho build` first.
- **Native scrollers under Playwright** (`docs/dom-scroll-model.md`, "Scripting it"): drive them with raw `page.mouse.wheel` deltas, not `wheel()`; Firefox applies at most one page per wheel event, so no scripted fling crosses the table there; the harness's `fling()` ends with a catch-up event a native scroller clamps, so a DOM fling sends equal events; headless Chromium hides scrollbars (`--hide-scrollbars`) and headless Firefox has none with width, so a thumb drag needs `spike/input.ts`'s `openWithScrollbars` (Chromium, WebKit) or a headed Firefox with `ui.useOverlayScrollbars: 0`.
- **The parity check's overlay scrollbars** (`perf/tanstack-parity.ts`): macOS's take a press only while shown, so `showBar` brings the bar up first and `downOnBar` presses again (up to three times) when the press's target wasn't the scroller; Firefox's track press runs headed (`--firefox`, classic scrollbars); WebKit's scripted wheel can arrive a whole drag settle late, so an input inside a drag counts only if it arrived inside it. It waits for reads to finish (`quiet`) before timing a drag: a page landing sends its prefetch's reads, drag or not, as the tall table's does. Firefox warns of a "scroll-linked positioning effect": the scroll model's design (`docs/dom-scroll-model.md`), ignored with the engine's warning.
- **Input latency and frame work come from Chromium's trace** (`docs/contender-contract.md`, "Reading the metrics"), not the page's Event Timing observer (rounded to 8 ms, nothing under 16 ms, no wheel). GPUI on WebGL2 in Chromium: an init script deleting `Navigator.prototype.gpu` makes its `Auto` backend fall back (`spike/latency.ts`, `hideWebGpu`); check the backend from its first GPU call (`gpuBackend`, which then unhooks itself, so timing runs carry no GPU-call wrapper; `gpuiProbe` stays hooked and belongs to latency runs only).
- **The tall table's fixtures are the component's** (`components/tall-table/fixtures/`, its README the formats), but `cells.json`'s drawn cells come from here: `perf/cell-fixture.ts` picks rows from data/'s file with native DuckDB, jumps the contender's release build (`?measure&cells`, 2560 px wide so every column draws) to each, and fails unless each drawn value is DuckDB's. It keeps the hand-written `rounding` cases. Regenerate it after a change to the data file, the font, or the table's cell text, then rerun `cargo test -p seiza-tall-table`.
- **Element Timing entries arrive after the paint, in an observer's task, and the browser buffers only 150:** a script reading cells' paints records them from an init script (`perf/tanstack-contract.ts`'s `recorder`) and waits for a row's entries before calling them missing.
- **DuckDB's worker isn't in the page's resource timing,** so a check that times the engine's start reads the engine's JS chunk (`assets/engine-*.js`), which the open imports first. **Firefox warns about DuckDB-Wasm's `eh` bundle** (the deprecated `try` instruction): the engine's, not the view's; `tanstack-view` ignores that one warning.
- **The metric scripts** (`perf/metric-*.ts`, ports 4322–4333 and 4335–4336) run Chromium with its scrollbars shown, as `tanstack-parity` does, and bring an overlay bar up (a wheel there and back) before a track press on both sides. A script that measures keys presses the probe key first: the first key changes the probe's state on both sides. The fling goes out on a fixed schedule without awaiting each wheel (Playwright's `mouse.wheel` waits for the page's handling, so an awaited loop paces itself by each side's cost), and Chromium coalesces wheel events on a native scroller, so the input is the events' summed `deltaY`, not their count. Chromium's compositor frame reporter (`PipelineReporter`) doesn't see GPUI's canvas frames, so late frames come from the main thread's frames. The DOM's probe key changes nothing visible, so its `EventLatency` reaches no frame; GPUI makes no GPU calls for an unchanged scene, so its `contender:input` isn't always right after a GPU call. Memory needs `--enable-blink-features=ForceEagerMeasureMemory` (else `measureUserAgentSpecificMemory` waits for a GC, up to 20 s) and a cross-origin-isolated page.
- **Memory includes the canvas:** `measureUserAgentSpecificMemory` counts a canvas's backing store under the type `Canvas` (GPUI's window at 1440×900, DPR 2: 2880×1800×4 bytes, 19.8 MiB), and a wasm's linear memory under `JavaScript`; the GPU's memory is in neither side's reading. A wasm memory only grows, so a garbage collection never shrinks GPUI's.
- **The wasm's names** are stripped in the release build (`strip = true`); `gpui-parts` relinks with `CARGO_PROFILE_RELEASE_STRIP=none` and runs wasm-bindgen without `--keep-debug`: wasm-opt aborts on the DWARF std's objects carry (`compile unit size was incorrect`).
- **The throttled network doesn't reach a same-process frame's worker.** The page's `Network.emulateNetworkConditions` throttles its frame's own requests, but not those of the frame's dedicated worker (DuckDB's: its bundles and every data read), and a worker target answers the command `Not supported`; a same-origin frame has no CDP session of its own. So a script that compares the page with the bare contender throttled sends both through `shared-web/perf/serve.ts`'s `startThrottlingProxy` (the same latency and shared download) with only the CPU throttled by CDP (`perf/readout-cost.ts`, on port 4338 in front of 4337); the bare page's data reads timed within 3% of Chromium's own throttling (`docs/DECISIONS.md`, "Measurement").
- **The trace books the frame tree's rendering on the top frame:** `Paint`, `PrePaint`, and `Layerize` name the top frame however much of them is the contender's frame, so the page's own time (`readout-cost`) counts its timers, script, style, and layout, never those phases.
- **A stale NXDOMAIN:** a resolver that looked seiza.io up before it had records can keep the miss for the zone's negative TTL (30 min). `worker-check` and `data-read` take `--resolve-via 1.1.1.1`.

# M20 part A: how a source answers "the next match after row r", a spike (2026-11-18)

Measured on Apple M1, Darwin 25.6.0 arm64, machine `local`, Node 26.12.1, native DuckDB 1.4.5 (`@duckdb/node-api` 1.4.5-r.1, Tycho's data tooling), one thread, the files on a local disk (warm in the OS cache after a first full scan). One run per query: orders of magnitude for the research (root [`docs/research/tall-table-features.md`](../../../../docs/research/tall-table-features.md), "Find (`find`)"), not a source's measured cost, which the DuckDB engine measures when Tycho adopts the feature. DuckDB-Wasm runs slower than native, and over HTTP every column a query casts is read (the engine's `CLAUDE.md`, "DuckDB-Wasm 1.32.0 gotchas").

The spike's scripts weren't kept (part A builds no shipped code); "Reproducing it" below says what they did.

## What was measured

A cell matches when `CAST("<col>" AS VARCHAR) ILIKE '%<term>%'`; a row matches when any searched column does. Each way of asking for the next match after row *r* (and the previous before it), from the top (*r* = 0) and the middle:

- **One query:** `SELECT min(file_row_number) FROM read_parquet(…, file_row_number = true) WHERE file_row_number > r AND (<any column matches>)` (`max` and `<` for the previous).
- **Windowed:** the same over `[a, a + w)`, `w` doubling from 65,536 rows to 4,194,304, stopping at the first window with a match.
- **The count:** `count(*)` of matching rows over the whole file (a bar's "3 of 12").

## What it says

- A single query's `min` (or `ORDER BY … LIMIT 1`) reads every row in range, so a match near *r* costs the whole scan: 2.4 s on the asteroids, 51 s on Gaia. Windows find a near match in one to three queries: 30–130 ms, ~1 s on Gaia.
- A term with no match costs the whole file either way, windowed or not (2.5 s, 47 s): a source's find is windowed so it can be cancelled between windows, and so page reads on a one-connection source run between them.
- The casts are the cost: one text column scans 10–14× faster than every column. Every shown column is searched (the owner's decision); the windows keep a near match quick whatever the columns.
- A count is the whole scan: a bar's count is the host's, at that cost.
- The two texts agree for ordinary values and differ at exponents and a few case folds: the source decides the next cell, the table its highlight, and the README says they can differ.

## Reproducing it

A Node script (ESM) over `@duckdb/node-api` from `apps/tycho/data/` (`createRequire` on its `package.json`), one connection with `threads = 1`, `:memory:`: `DESCRIBE` for the columns; per term, the count, then for *r* in {0, rows / 2} the one query, the windowed loop (next and previous), each timed with `performance.now()` around `runAndReadAll`. The files are `just tycho data`'s (`apps/tycho/data/MANIFEST.json`).

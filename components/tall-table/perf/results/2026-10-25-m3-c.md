# M3 part C: a re-read that lands in the turn that asks (2026-10-25)

Measured on Apple M1, Darwin 25.6.0 arm64, machine `local`, Chromium headless=new, 1440×900 at DPR 2, cold, median of 10, the reference run (root CLAUDE.md, "Measurement protocol"); as in part B, only the reference run is asked for here, and the throttled one comes with the frame work in part D. Load average 7.2 → 5.7 over the final runs (the latency's p50s spread 2.6% and 1.8%).

Raw: `2026-10-25-m3-c-size.json` (`just tall-table size --against 60ed458`), `2026-10-25-m3-c-live-before.json` (HEAD's table, this part's host mark), `2026-10-25-m3-c-live.json` (this part's build). The spikes' runs below were read from the console, not written.

## What changed

- **The table** (`live`, off by default): a re-read's load is polled once as it's sent, with a no-op waker; a ready answer lands in that turn (`answered`, then `page_done` once the plan's reads have all started), a pending one is spawned as before. First reads aren't polled. `invalidate_rows` plans its reads once, at the end of the update that made them (`App::defer`), not on each call.
- **No `replace_page`:** the push path part B specced was spiked and measured, and not built (below; `docs/DECISIONS.md`, "Features").
- **The bare host:** a batch's `tall-table:invalidated` mark is set from the moment its rows are picked (`mark_at`), so a read landing during the update counts and the feed's own picking doesn't. (The spikes below were marked a step earlier, before the picking: at 1k updates/s, 16 picks.)
- **Bytes:** the base is unchanged; `live`'s build is +14.1 KiB after wasm-opt, +4.6 brotli, against the base (part B: +11.5, +3.5, before gpui-kit 0.8.0). Part D splits the table's share from the feed's.

## Update → refreshed frame, 1k updates/s (C3)

The narrow shape at rest at the top (rows 0..28, page 0), the feed on for 1 s, then 5 s measured; a batch's latency is its mark (its start) to the first refreshed mark at or past its generation.

| Build | p50 | p95 | Max | Batches drawn | Refreshed frames/s | Spread (p50s) |
|---|---|---|---|---|---|---|
| HEAD's table (the spawn's `setTimeout(0)`) | 22.55 ms | 29.09 | 30.91 | 179 / 179 | 59.8 | 2.6% |
| **Re-reads landed in the turn that asks** | **7.16 ms** | 22.39 | 24.57 | 182 / 182 | 36.4 | 1.8% |

- **Within a frame at p50** (16.7 ms), from B5's 22.5. The p95 is a batch that arrives just after a frame and waits for the next one: no path in the table can draw before that.
- **Fewer re-reads:** ~36 refreshed frames a second, one per batch; before, a batch arriving while page 0's read was out was read again after it, ~60 a second.
- At 100 updates/s (3 runs): 7.24 ms p50 (p95 22.1). At 10/s (3 runs): 13.3 ms (p95 20.3), noisy (spread 24%, 50 batches a run) and not explained hop by hop: still within a frame at p50.
- The mark's move changed nothing on HEAD's path: 22.55 ms against B5's 22.52, since its invalidations did no reading.

## Experiments and controls

Interleaved in one session, 10 runs each unless noted (load average 4.1 → 3.0):

| Spike | Measured from | p50 | p95 | Spread |
|---|---|---|---|---|
| Poll once, re-reads only | the batch's end | 5.36 ms | 14.25 | 5.2% |
| `replace_page` (the host builds each changed page and hands it over) | the batch's end | 6.84 ms | 22.49 | 3.7% |
| Poll once, plans deferred to the update's end | the batch's start | 7.38 ms | 22.84 | 18.4% |
| `replace_page` | the batch's start | 7.38 ms | 23.2 | 1.8% |

- **The first comparison was unfair:** the mark was set after the update, so a page built during it (both spikes build one) was left out. Poll-once's 5.36 ms also hid ~16 page reads a batch: the feed invalidates row by row and each call re-read the page, which landed at once. Deferring the plan to the update's end makes it one read a batch; marking the batch's start counts the read.
- **Measured fairly, the two read the same** (7.38 ms p50 each). Poll-once was kept: it adds no API, and a host with the page in hand gets the push's latency by answering `load_page` with a ready future.
- **Negative control:** with the poll switched off (`reread && false`), `a_reread_answered_at_once_lands_in_the_turn_that_asked` fails: page 0's re-read is still in flight after the update (`(1, 0)` in flight and draining, not `(0, 0)`).

## After the code review

Fixed before the final runs: a failure or refusal answered at once lands from a task, as before (a host retrying on `ReadFailed` would have looped inside one update); a re-read answered `Cancelled` without the table cancelling it frees its place (it held a re-read's place for good) and waits for the next invalidation; a plan's ready pages land together, then one more plan, not one per page; the deferred plan checks the drag again when it runs; the host's mark moved after the feed's picking. The final numbers above are from that build.

## Checks

- **C1:** `just tall-table size --against 60ed458`: the base 9,680.5 KiB after wasm-opt at both (0 KiB; brotli 2,689.4 → 2,688.9, its noise); `14take_refreshed` in the base 0 times, in `live`'s build 6. `just tall-table test` passes off, with each feature, and with both (55 table tests, 8 host); `just tall-table lint` passes.
- **C2:** `src/state/fixtures/live.rs`'s `a_reread_answered_at_once_lands_in_the_turn_that_asked`: ten single-row invalidations of page 0 in one update read it once, at the update's end, landed there (nothing in flight or draining, bytes swapped, not added); the next frame draws it and emits `Refreshed` once, with the batch's last generation; a first read (a jump) still lands from its task and emits no `Refreshed`. The scripted delegate's other tests (reads answered later) and the paging fixture pass unchanged.
- **C4:** `just tall-table smoke` on the `live` build: every shape in Chromium, Firefox, and WebKit, and the narrow shape at `?live=1000` with its refreshed marks 0.27 ms (Chromium, WebGPU), 0.32 (Firefox, WebGL2), 1.10 (WebKit, WebGPU) after the frame's last GPU call, in its task; no placeholder row in a probed frame.

# M24 part B: a header's tap as one press, built (2026-11-22)

Measured on Apple M1, macOS 26.6.2, machine `local`: the wasm's bytes (the bare host's base, `clicks`, `clicks,sort,resize`, and `sort,resize`, each at `173e0c1` (HEAD, the code before this part: part A built none) and on this part's working tree), the symbols of unstripped builds, and the smoke check in Chromium (headless=new, DPR 2), Firefox, and WebKit (DPR 1) at 1440×900, Playwright 1.63.0, gpui-kit 0.10.0 (gpui-pre and gpui-pre-web 0.3.12). No frame reading: the setting draws nothing and adds no listener (a branch in two that were there). Read by hand on an iPhone 13 in Safari and Chrome (below).

Raw: `2026-11-22-m24-b-size.json` (`size --against HEAD`: every feature's bytes, the symbols, the base at both).

## What changed

- **The table:** `set_header_tap_is_press(bool)` and `header_tap_is_press()` on `clicks`, off by default. The arrow's (`sort`) and the band's (`resize`) left-press listeners hand a finger's press to the root's `press` under it (`tap_is_headers`: the setting on and `Window::last_input_was_touch()`); their long-press stop (`stops_header_context`, in place of `stops_context` on a header's band or arrow) reports the header's `Context` under it, unless something claimed the long press first. Without `clicks`, `header_click_stops` is the element unchanged.
- **The bare host:** `?header-tap` turns the setting on before the first frame.
- **The scripts:** the smoke check's two touch runs (below) and `--only <text>`, which runs the runs whose label holds the text (refused with `--screens`, a failure when none does). `shared-web/perf/`'s `open` takes `hasTouch` (off by default: no other app's context changes), which Playwright's `touchscreen.tap` needs.

## The smoke check's touch runs (B3, in the browsers)

With `?header-tap`, each gesture sent as touch `PointerEvent`s the page's script makes, in Chromium, Firefox, and WebKit, on the narrow shape's column 0:

| Gesture | Chromium | Firefox | WebKit |
|---|---|---|---|
| Tap on the arrow | `press` on column 0, unsorted | the same | the same |
| Tap on the band's left half | `press` on column 0, the widths unchanged | the same | the same |
| Tap on the icon | the icon's press, no `press` | the same | the same |
| A cell's long press | `context` on the cell, its tap dropped | the same | the same |
| The arrow's long press | `context` on column 0, unsorted | the same | the same |
| A pan up 200 px in the body | top 0 → 23.1, nothing reported | 0 → 21.8 | 0 → 19.3 |
| Playwright's real tap on the arrow | `press` on column 0, unsorted | the same | the same |
| CDP's long press on the arrow | `context` on column 0 | n/a | n/a |
| CDP's pan up 200 px | top 23.1 → 38.1, nothing reported | n/a | n/a |

Every pointerdown the page saw was of type `touch`. Without `?header-tap` (the control): a made-up tap on the arrow sorted (descending), and Playwright's real tap sorted again (ascending), in the three browsers, each pointerdown of type touch.

The whole smoke check on the final build (`clicks,sort,resize,select,header-icon`), after the code review's fixes: 57 runs in the three browsers (the base, `resize`, `select`, `sort`'s three, `clicks`, `header-icon`, `replace_rows`, and the two touch runs), passing.

## On a phone, by hand (B3)

An iPhone 13, in Safari and in Chrome, on the same wifi as the laptop serving the release build (`vite preview --host`, plain `http` on a LAN address: no WebGPU there, so WebGL2), the narrow shape. With `?header-tap`: a tap on an arrow selected its column and sorted nothing; a tap on a band selected the column on the side touched, no width changed; a tap on an icon selected and sorted nothing; a cell's long press selected the cell; an arrow's long press selected its column and sorted nothing; a pan scrolled and selected nothing. Without it (the control): a tap on the arrow sorted. The same in both browsers. No mouse on the phone: the mouse's half is the window tests' and the smoke check's.

**Found beside it:** every sort froze the table for a wait the owner called very noticeable, scrolling included, in both browsers. The bare host's in-memory source works out a column's order of 1.57 M rows inside the delegate's `sort` (`host/crate/src/rows.rs`), on the main thread, so no frame draws until it returns; on the laptop the same order takes a fraction of the time. Not the setting's: the control's sort froze the same. A host whose source sorts off the main thread (Tycho's DuckDB, in a worker) draws through it.

## Experiments and controls

- **The window tests' control** (`click::Control::ArrowIgnoresSetting`): the arrow's listener made to ignore the setting sorts on a finger's tap, so the first test's events aren't the ones it wants.
- **A double tap in a window test is two taps sent back to back:** gpui's recognizer counts a second tap within 400 ms of wall time (`Instant::now`), not of the test clock, and a draw between the two on a loaded machine could make the second a first (the code review's finding).
- **A touch step waits out the last pan's momentum** (3 s), as the spike found.

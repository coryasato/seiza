# M18 part A: a filter's count against its first page, a spike (2026-11-18)

Measured on Apple M1, Darwin 25.6.0 arm64, machine `local`, Node 26.12.1, native DuckDB 1.4.5 (`@duckdb/node-api` 1.4.5-r.1, Tycho's data tooling), one thread (`SET threads = 1`, as DuckDB-Wasm runs), the files on a local disk, warm in the OS cache after the first query. One run per query: these are orders of magnitude for the research (root [`docs/research/tall-table-features.md`](../../../../docs/research/tall-table-features.md), "`replace_rows`"), not a source's measured cost, which the DuckDB engine measures when Tycho builds its filter. DuckDB-Wasm runs slower than native, and over HTTP every byte a query reads is a range request (the engine's `CLAUDE.md`).

The question (the root research's "`replace_rows`", "The count that arrives later"): a filter's `count(*)` may answer after its first page could. Is `replace_rows` called once the count is known, or with an estimate that `set_rows` corrects? The spike's script wasn't kept (part A builds no shipped code); "Reproducing it" says what it did.

## The sources

| Source | Rows | Paged by | As Tycho holds it |
|---|---|---|---|

| Tycho's `gaia-dr3-bright.parquet` (11 columns, 1.57 GB, 409 row groups, in `source_id` order) | 25,067,889 | `file_row_number` | A Parquet file read by row-group range (`engines/duckdb/crate/src/tall_table.rs`, `ParquetFile::page_sql`) |

## What was measured

For each filter (a `WHERE` predicate, chosen for its share of the rows):

- **The count:** `SELECT count(*) … WHERE <p>`.
- **The first page:** the first 1,024 matches in the source's order (`… WHERE <p> ORDER BY rowid LIMIT 1024`; for the file, `ORDER BY file_row_number`), and with no `ORDER BY` (insertion order kept, so the same rows, and the scan can stop early).
- **The index:** the matches' row numbers written once, in order (`CREATE TABLE ix AS SELECT rowid AS r … WHERE <p> ORDER BY rowid`). Its row count is the filter's count.
- **A page at 50% of the matches:** by `OFFSET` (`… LIMIT 1024 OFFSET <k>`), and from the index (in memory, the index's slice joined to the table on `rowid`; for the file, the slice's first and last row numbers read as a range, with the predicate again).

## What it says

- **In memory, the count is never slower than the first page in the source's order.** For every filter it answers within that page's time or sooner (0–548 ms against 0–560), since the page needs the same scan. With no `ORDER BY` the scan can stop at 1,024 matches, and the first page can come sooner: by a few milliseconds for the simple predicates (`H > 16.9` 5 against a count of 8, `class = 'MBA' AND e > 0.2` 1 against 9; `neo`'s came later, 5 against 1), and by 309 ms for the global search (239 against 548), whose predicate is costly a row. So a host over rows in memory that calls `replace_rows` once the count is known waits at most the count's scan, which every page after the first needs anyway (below).
- **On a file read by row-group range, a common filter's first page is 10–30× sooner than its count** (10–17 ms against 181–346), because the scan stops after 1,024 matches while the count reads the predicate's column for every row group. Over HTTP the count downloads that column (`parallax`, ~190 MB compressed in the file: the M8 spike's figure). A rare filter is the other way round: its first page needs the whole scan, and the count is quicker (120 ms against 756), since it reads one column and the page reads every one.
- **Paging past the first page needs the index, and the index costs the count's scan** (in memory 0–545 ms, the file 3–392). `OFFSET` grows with depth (372 ms at 50% of the commonest filter in memory), as it did for `sort`. So a source that pages a filtered result builds the index, and its count comes with it: an estimate the count later corrects saves only the first page's wait, on a file, for a common filter.
- **A rare filter scatters its matches across the file**, so a page read as a range of row numbers reads the whole file (745 ms here, 1.57 GB over HTTP). How a source pages a filtered Parquet file (the index joined by row number, a filtered copy in memory, a refusal past the budget) is the DuckDB engine's research when Tycho builds its filter, as `sort`'s order was.

## Reproducing it

A Node script in a scratch directory, `@duckdb/node-api` loaded from `apps/tycho/data/` (`just tycho data-deps`): `SET threads = 1`; the CSV copied by `CREATE TABLE m.t AS SELECT * FROM read_csv('<fixture>', types = {'pdes': 'VARCHAR'}, quote = '"', escape = '"', sample_size = -1)` into `ATTACH ':memory:' AS m (COMPRESS)` (3.3 s; Tycho's own sniffing sets the types and quoting); Gaia read in place by `read_parquet('<file>', file_row_number = true)`. Each filter's queries ran in the order of the tables' columns, each timed by `performance.now()` around `runAndReadAll`, once.

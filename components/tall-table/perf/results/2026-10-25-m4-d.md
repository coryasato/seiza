# M4 part D: following's cost, and the close (2026-10-25)

Measured on Apple M1, Darwin 25.6.0 arm64, machine `local`, Chromium headless=new, 1440×900 at DPR 2, cold, median of 10, reference and throttled (CPU 4×, Fast 4G) (root CLAUDE.md, "Measurement protocol"), on the final build. Load average 4.9 at the first `follow` set, easing to 1.5–2.4 for the rest, 1.3–3.7 over the re-runs.

Raw: `2026-10-25-m4-d-size.json` (`just tall-table size --against 0199214`); `2026-10-25-m4-d-follow-<rate>[-throttled].json` (`just tall-table follow`, six files) and `2026-10-25-m4-d-rerun-follow-*.json` (four sets over the 6% spread, run again); `2026-10-25-m4-d-frames-follow.json` and `2026-10-25-m4-d-frames-base.json` (`just tall-table perf`, the `follow` build with the feed off, then the base), and `2026-10-25-m4-d-rerun-frames-{base,follow}-wide-throttled.json` (the wide shape throttled again, the base first).

## What changed

- **The measurement:** `perf/follow.ts` (`just tall-table follow`), the tail feed at `?rows=1000&append=<rate>&follow`, narrow. Three windows a run, each with nothing on the page but what it reads: (1) append → pixel (a batch's `tall-table:appended` mark to the first `tall-table:tail` mark at or past its rows) and reads; (2) the presented frames, through `shared-web/perf/`'s new `presentedRecorder` (the host's `__seizaFrameSample` in each presenting task's microtask checkpoint, installed for this window only, its GPU-call wrapper removed after), then scroll-back: five wheels up of 300 CSS px from the tail, each timed from the event to the first presented frame no longer following and to the first with every row real, the view checked to hold 200 ms while rows arrive, then End; (3) frame work from Chromium's trace and late frames from `frameRecorder`.
- **The bare host** (`follow`): its source counts the reads it was sent and those cancelled in flight (`rows.rs`'s `Reads`), each published as it changes (`__tallTableReadsSent`, `__tallTableReadsDrained`). The host's `__seizaFrameSample` carries the following flag.
- **No change to the table.**

**Re-run** (the four sets over 6%): 1k reference 8.32 ms p50 (spread 5.8%), 10k throttled 32.13 (12.8%), 100k reference 27.89 (35.6%), 100k throttled 331.00 (61.0%); every other column within a few percent of the first run. The medians hold; the spreads are the sets' own:
- **100k:** every batch (~1,600 rows a 16 ms tick) starts a new page, whose first read waits a turn, so a batch lands in the next frame or the one after: each run's p50 sits at ~23–24 or ~28 or ~33 ms.
- **10k throttled:** the throttled page draws ~30 frames a second, so its p50 sits at the edge of one frame (~33 ms): runs read 30.6–34.8.
- **100k throttled:** saturated (below); its lag is the backlog's.

**What it shows:**
- **D2, no first read polled when sent:** 10k reference reads 8.3 ms p50, a quarter of the two frames (33.3 ms) that would have specced it. Most batches stay in the grown tail page, which `live` re-reads in the turn that asks; those that start a page show in the p95. At 100k, where every batch starts one, it's still under two frames (27.7 p50, 33.2 p95). Logged in `docs/DECISIONS.md`.
- **No placeholder frame and no drained read at any rate,** as specced: the view is pinned to the loaded tail, and the table never cancels a grown page's read.
- **Reference keeps up at every rate:** no late frames; busy ~320 ms/s at 1k and 10k (live's ~310 under its feed), 348 at 100k. Work p50 is low at 1k and 10k because most frames Chromium begins draw nothing (the feed ticks ~30–45 times a second); work p95, a drawn frame, is ~10 ms.
- **Throttled 1k and 10k keep up** (≤1.4% late), a drawn frame ~26 ms, so the view moves ~30 times a second and append → pixel is about a frame.
- **Throttled 100k saturates the main thread** (~950 ms/s busy, 39% late): the view trails the source by ~0.3 s (~30k rows), still with no placeholder. The drawn frames are as many (30/s) and as costly (~26 ms) as at 10k; the extra ~370 ms/s goes with the reads (101 a second against 32: each a 1,024-row page the bare host's source materializes on the main thread, and the table lands). Splitting that between the source and the table needs a trace breakdown; not done. A host appending 100k rows a second on a slow machine would trail; the table offers no throttle of its own.
- **Scroll-back:** a wheel up during the feed reaches the screen in ~28 ms reference (~46–65 throttled), its rows real in the same frame (the rows above the tail are in the cache). It holds still while rows arrive in every input.

Run again in the other order (base first), 5.9% against 8.1%; over the 20 runs each, base 0.5–9.6% (median ~3.5), `follow` 4.0–12.1% (median ~8). Both builds' fling frames split between ~15 ms and ~30 ms work (p95), and `follow`'s runs land in the slower mode more often. No other segment, and not the narrow throttled fling (0.49% both), shows it. While not following, `follow`'s code on a wheel is `reader_moved`'s comparison and, on a page landing, the pin's early return. Nothing found explains it; it's in `PLAN.md`'s open questions.

## After the code review

The review was of the measurement (the table didn't change). Fixed before any number above was taken: scroll-back measured before the rAF recorder is installed; the GPU-call wrapper only in the window that reads presented frames, put back before the timed and traced ones (it had moved 100k's busy from ~320 to ~520 ms/s in a trial); the wrapper moved to `shared-web/perf/` (`presentedRecorder`) and the page's `global` reader to `perf/harness.ts`; a run with no scroll-back reading is dropped, not a NaN in the medians; a placeholder frame is any frame with a visible row not loaded (not only pending); the read counters published by the source as they change, not with each batch; the mark log's names checked quoted; frames filtered in the page; `--warmup` documented.

## Reproducing it

```sh
just tall-table size --against 0199214 --label m4-d-size
just tall-table build follow
just tall-table follow --rate 10000 --label m4-d-follow-10k          # and 1000, 100000; --profile throttled
just tall-table perf --label m4-d-frames-follow
just tall-table build && just tall-table perf --label m4-d-frames-base
```

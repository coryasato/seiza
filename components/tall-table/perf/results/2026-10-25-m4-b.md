# M4 part B: the grown tail page, and `set_rows` in the fixture (2026-10-25)

Measured on Apple M1, Darwin 25.6.0 arm64, machine `local`. Bytes only: this part changes no frame path the base draws, and `follow`'s frame work and append → pixel are part D's.

Raw: `2026-10-25-m4-b-size.json` (`just tall-table size --against 5878b27`).

## What changed

- **The table** (`live`, off by default): a short last page that `set_rows` grows is kept, stale, not dropped. It draws the rows it was read with (`row` answers `Pending` past them) and is read again on `live`'s path, never cancelled for growing; grown during a read, it's read once more after. A shrink clamps the page it ends in. Prefetch waits while a visible page has rows it wasn't read with; `Refreshed` names the rows the read holds; a flash compares only rows drawn before. With `live`, `set_rows` plans its reads at the end of the update, with `invalidate_rows` (`load_after_update`).
- **The fixture:** `paging.json`'s `rows` step and `without` field; base scenarios "the short last page grows" (without `live`) and "the rows shrink"; `live` scenarios "a grown last page is kept", "a last page grows during its first read", "a grown last page shrinks"; the `drop-grown` control. The TanStack contender skips scenarios with a `rows` step.

## After the code review

Fixed before the size run: a grown visible page now holds prefetch back (it counted as loaded, so prefetch raced its re-read); a shrink from a whole-page count clamps the page it ends in (the early return for the base's drop skipped it, and a re-read in flight landed rows from before the shrink); `Refreshed` names only the rows the landed read holds; one slot lookup in `loaded`. Left as the base has them, and noted in the README and `docs/DECISIONS.md`: a refused or failed re-read of a grown page leaves its new rows placeholders until the next growth, invalidation, or `retry_failed`. Left for a follow-up: a shrink by more than a page keeps the whole pages past the new end (the base's, before this part).

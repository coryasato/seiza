# M3 part B: `live`'s re-read path (2026-10-24)

Measured on Apple M1, Darwin 25.6.0 arm64, machine `local`, Chromium headless=new, 1440×900 at DPR 2, cold, median of 10, the reference run (root CLAUDE.md, "Measurement protocol"); the spec asks only for the reference run here, and the throttled one comes with the frame work in part D. Load average 7.0 → 4.1 over the run (the latency's p50s spread 1.9%).

Raw: `2026-10-24-m3-b-size.json` (`just tall-table size --against 24f8e76`), `2026-10-24-m3-b-live.json` (`just tall-table live --rate 1000`).

## What changed

- **The table** (`live`, off by default): `PageCache` keeps a loaded page's re-read state (stale, its read in flight and the generation it started at, a failed re-read, a landed one not yet drawn); `TallTableState::invalidate_rows` returns a generation; `TallTableEvent::Refreshed { rows, generation }` from render. In the base, `visible_rows()`.
- **The bridge:** `refreshed_mark` and `refreshed` (the highest generation drawn), the arm behind `live`. Tycho's `Publish` literal takes `..Default::default()`.
- **The bare host:** `?live=<updates/s>`, a seeded feed over the visible rows; the source mixes each row's version into its floats.
- **`fixtures/paging.json`:** the `invalidate` step, seven scenarios, two behavior controls; the TanStack contender's test skips them.
- **The scripts:** `size` checks `live`'s symbols; `smoke` runs the feed; `live` (new) measures invalidate → refreshed frame.

## Invalidate → refreshed frame, 1k updates/s (B5)

The narrow shape at rest at the top (rows 0..28, page 0), the feed on for 1 s, then 5 s measured. A batch's latency is its `tall-table:invalidated` mark to the first `tall-table:refreshed` at or past its generation.

| Rate | p50 | p95 | Max | Batches drawn | Refreshed frames/s | Spread (p50s) |
|---|---|---|---|---|---|---|
| 1,000/s (10 runs) | **22.52 ms** | 28.78 | 30.66 | 179 / 179.5 | 59.6 | 1.9% |
| 100/s (3 runs) | 22.86 | 29.01 | | | 59.9 | 1.4% |
| 10/s (3 runs) | 18.74 | 30.3 | | | 10.0 | 3.7% |

- **Over a frame (16.7 ms): a push path is specced** (`PLAN.md`, M3 part C).
- **Not the coalescing:** at 10 updates/s, with no read out when a batch arrives, it's still 18.7 ms. From 100/s on, every frame draws a re-read (~60 a second), and a batch arriving while page 0's read is out waits for it, ~4 ms more.
- **Where it goes:** the source answers at once, but the table's read is a spawned task, and gpui-pre-web 0.3.9 runs each one from a `setTimeout(0)` (`dispatcher.rs`, `schedule_runnable`), so the page lands a task or more after the invalidation and the frame after that draws it. Not measured hop by hop; part C measures the two fixes against this number.
- The feed sent ~642 invalidations a second at 1k updates/s: it invalidates each row once a batch, and 28 rows take ~16 updates a batch with repeats.

## Checks

- **Smoke** (`just tall-table smoke`, the `live` build): every shape in Chromium, Firefox, and WebKit as before, and the narrow shape at `?live=1000`: three refreshed marks each 0.22 ms (Chromium, WebGPU), 0.34 (Firefox, WebGL2), 0.24 (WebKit, WebGPU) after the frame's last GPU call, in its task; no placeholder row in a probed frame.
- **Native:** `just tall-table test`, off, with each feature, with both: 52 table tests and 8 host tests with both. The paging fixture's controls each fail where meant: `reread-unwanted` on "three visible pages change" (the unwanted re-read isn't cancelled) and "a stale page nobody wants" (`load 0`, `load 1` where none was expected); `restart-stale` on "a visible page changes" (`cancel 0`, `load 0`) and "a page changes during a drag".

## Reproducing it

```sh
just tall-table size --against 24f8e76 --label m3-b-size
just tall-table build live
just tall-table smoke
just tall-table live --rate 1000 --label m3-b-live
```

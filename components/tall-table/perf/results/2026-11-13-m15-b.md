# M15: `reorder`'s order (part B, 2026-11-13)

Measured on Apple M1, Darwin 25.6.0 arm64, machine `local`. Sizes only: part B builds the order and the host's way to set it; the drag (part C) and the frame work (part E) come later.

Raw: [`2026-11-13-m15-b-size.json`](2026-11-13-m15-b-size.json), `just tall-table size --against de32b04 --label m15-b-size` (M15's parent; part A changed no code), run after the code review and its fixes. One change came after it (below): the base's byte comparison, made by hand as `size` builds (`cargo build -p tall-table-host --release` alone, wasm-bindgen, `wasm-opt -Oz` with the apps' flags, brotli 11), `de32b04` in a git worktree with a target directory of its own, against the working tree.

## What changed

- The table's `reorder` feature: the order (`order`, `set_order`, `move_columns`, with `pin` `move_columns_pinned`, `ColumnsMoved`, `TallTableColumn::movable`), its rules pure in `src/reorder.rs`, the state's in `src/state/reorder.rs`; every site that reads a page or a column's settings through the column's index.
- The bare host's `reorder` feature (the table's and the bridge's): every column movable, `?order=reverse`, and with `?perf` the hooks `__tallTableMove` and `__tallTableOrder`.
- No app builds the table with `reorder` yet, so no app's wasm changes.

## Bytes

| `reorder` (the size run) | 9,816.5 KiB | 2,756.8 KiB | **+7.4 KiB** | **+2.1 KiB** |

- **The base:** the size run read it the same length after wasm-opt as at `de32b04`, but 1.1 KiB more brotli: the same bytes in another order. A new `impl LaidOutColumn` block (its `index`, a stand-in that builds in the base too) sat above `column.rs`'s other `impl`s and renumbered them in their mangled names, which reordered functions (M14's lesson). Moved to the file's end, the base is `de32b04`'s length again, and the two differ in 44 bytes, every one a panic location's line number: 43 in `components/tall-table/src/state.rs` (40 to 71 lines down, below the event's new variant and the setters' docs) and one in the bare host's `host.rs` (1012 → 1081). Same code. Brotli then reads 720 B less, line numbers alone.
- **`reorder`:** +7.4 KiB after wasm-opt, +2.1 KiB brotli, from the size run, before the `impl` move; the move changes only the order of the same functions, so the after-wasm-opt figure holds, and brotli swings by up to ~2 KiB when bytes shift (`size.ts`). The build includes the bare host's two hooks (their `Closure`s and the entry into GPUI: M13's lesson, a feature's first hook is most of its host's bytes). Part E measures it again on the final build.
- **No `reorder` symbol in the base** (`seiza_tall_table7reorder`, `seiza_tall_table5state7reorder`: 0 in the base, 3 and 4 in the `reorder` build). Every other feature's build reads the same after wasm-opt as the last run's (`2026-11-10-gpui-kit-0.9.1-size.json`), to 0.1 KiB, and its brotli within 1.5 KiB either way (`custom-cells` −1.5, `select` and `copy` +1.1): the shifted line numbers and the `impl` order, before the move.

## Experiments and controls

- The random test's new steps first took their stream from SHA-512's first word: the cache's `HoldingWithoutEnd` control then passed the default seed's 48 cases (a placed `set_order` cleared the `Cells` selection the one catching case copied), though seeds 1 to 3 and 200 cases caught it with the moves in. With the second word every control is caught (`docs/DECISIONS.md`, "Features").
- `ReadByPlace` (render reads a drawn cell's value by its place) fails the all-on cases at invariant 5.

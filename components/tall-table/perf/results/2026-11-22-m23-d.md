# M23 part D: the popover's settings, their cost and the close (2026-11-22)

Measured on Apple M1, macOS 26.6.2 (Darwin 25.6.0 arm64), machine `local`: the wasm's bytes (the bare host's `popover` builds alone, over `sort`, and with every feature, at part B's commit and at part C's, and each app that builds the table), frame work with the cue as built, faded, and with all three settings (Chromium headless=new, 1440×900 at DPR 2, cold, median of 10, the wide shape, the reference run alone: a cue changes what two cells draw, not how the table scrolls), and the smoke check in three browsers. On part C's table code (`f2bee44`, reviewed); part D changed no code of the table's, and one thing in the bare host (below).

Raw: frames, each `-reference.json`, run in this order on one `popover,select` build: `2026-11-22-m23-d-frames-cue-built`, `-cue-faded`, `-cue-all`, `-cue-built-again`. In the gitignored `raw/`: the frame runs' console with the load before each (`2026-11-22-m23-d-frames.txt`), the smoke runs' (`2026-11-22-m23-d-smoke-popover-select-custom-cells.txt`, `2026-11-22-m23-d-smoke-popover.txt`), and `m23-d-paste.ts` (the popover's drag and copy alone, below).

## What changed

- **The bare host:** with `custom-cells` and `?cells=heat`, the long text's cells (`?popover-long=`) are filled by their row, five steps across the floats' ramp, so a script reads a faded text over a fill. With it, a page's paint reads the shape's columns one place on past the long text, as its values always did: before, a float beside a long text was painted by its neighbor's value (no run had the two switches together). A native test, `heat_fills_the_long_text_and_paints_the_floats_a_place_on`. It adds 216 bytes to a build with both features and none to any other.
- **The scripts:** `perf.ts` gained `--cue built|faded|all` (on a `popover,select` build, with `--popover <chars>`), which runs the cue's two segments in place of every other: `cue-hover` and `cue-scroll` (below). The smoke check gained the settings' runs (D2, below). `perf/harness.ts` gained `inkStrength` (how strong the ink is across a screenshot, a device pixel column each).

## Frame work (D1)

The host with a column of 10,000-character texts (`--popover 10000`), its button labeled, so the popover as built cues every cell and the same cells are cued in each run; an active cell on row 2's long text (a press) and the pointer on row 4's. Three runs differ by the cue alone: as built (the "…" replaced by the expand mark), `fade()`, and all three settings (`fade()`, gpui-kit's chevrons with an open mark, `CutText`, a filled button).

- **`cue-hover`:** the pointer moved a row a move down the long text's column to the last row wholly in view and back (21 rows each way, 6 round trips, 252 moves, one every 8 ms). Every move cues another cut text, deciding it (under `CutText`, by its text) and drawing it faded, while the active cell's cue stands: two faded cells every frame, one of them new.
- **`cue-scroll`:** the protocol's steady scroll from the same start. Its first wheel clears the hover (the cells move under a still pointer) and takes the active cell out of view, so what's left is what a setting costs a scroll with nothing cued.

Work p50, ms, from Chromium's trace, the ten runs' range in brackets, then presented frames a second. 308 cells drawn a frame. No late frames in any segment's median. Load averages 4.4 to 6.3 at each run's start (the 1-minute figure).

| Segment (wide) | As built | Faded | All three settings | As built, again |
|---|---|---|---|---|
| `cue-hover` | 3.60 [3.53–3.74], 60.4/s | 3.58 [3.54–3.74], 60.1/s | 3.58 [3.45–3.65], 60.3/s | 3.63 [3.57–3.71], 60.4/s |
| `cue-scroll` | 4.55 [3.96–4.76], 56.4/s | 4.54 [4.45–4.66], 57.9/s | 4.58 [4.46–4.99], 58.4/s | 4.54 [4.48–4.74], 56.4/s |

- **The fade and the settings cost nothing a frame that shows.** Every reading is within 0.05 ms of the popover as built's two runs, each range overlapping theirs. The spike's reading (part A: a glyph's alpha within +0.16 ms with about 28 cells faded a frame) holds at the two cells a frame the built rule fades.
- The check named "the protocol's scroll with the pointer over a cut cell and an active cell, both faded": a scroll can't hold either (the hover is cleared at its first wheel, the active cell leaves the view), so `cue-hover` is the segment that fades both every frame, and `cue-scroll` the scroll.

## In the browsers (D2)

`just tall-table smoke`'s settings runs, both shapes, the button labeled and a 3,000-character text in the third column, all three settings on (`?popover-cells=cut&popover-fade&popover-icons&popover-fill`), over a striped row, and with `custom-cells` again over a fill (`?cells=heat`):

- no cue on a hovered number's cell, a button set;
- on a hovered cut text, the cue 2 px inside the cell's right edge, the probe's `faded`; on screen against the same cell at rest: no pixel of the text's start changed (to a glyph short of the fade's start), the strongest ink in each third of the ramp falling (0.90, 0.61, 0.30 of the text's whole ink in Chromium at DPR 2; 0.86, 0.61, 0.30 in Firefox and WebKit at DPR 1), 0.04 in its last 6 px and 0.04 past the clear point (the mark's edge), and the 3 px above the text, the row's stripe or the cell's fill, unchanged to the cue;
- the mark's press opening the popover, the cue's box then drawing another mark (the probe's `open`), the same pixels with the pointer elsewhere, and its press closing the popover;
- the button's row at the popover's left edge, its width, and flush with its bottom (398 px);
- with `select`: Enter on an active cut text opening its popover; Enter on an active number's cell opening none, its keydown not cancelled where the cut text's was (gpui-pre-web cancels only a key something handled), so the key goes on.

- **Not read: an emoji's half-alpha rule** (C3 left it to this part). The bare host loads IBM Plex Sans alone and a wasm build has no system fonts, so no emoji glyph is drawn on the web to read; the rule stays untested on screen and natively.

## Reproducing it

```sh
# The bytes: each build at 466d2f8 and f2bee44 in one worktree, its own target,
# `cargo build -p <crate> --target wasm32-unknown-unknown --release [--features …]`
# (tycho; tall-table-gpui with `fonts`; kirkwood; tall-table-host with none,
# popover, sort, sort,popover, every other feature, every feature),
# wasm-bindgen, wasm-opt with the apps' flags, wc -c, brotli -q 11.
just tall-table build popover,select
just tall-table perf --shape wide --profile reference --popover 10000 --cue built --label m23-d-frames-cue-built-reference
just tall-table perf --shape wide --profile reference --popover 10000 --cue faded --label m23-d-frames-cue-faded-reference
just tall-table perf --shape wide --profile reference --popover 10000 --cue all --label m23-d-frames-cue-all-reference
just tall-table perf --shape wide --profile reference --popover 10000 --cue built --label m23-d-frames-cue-built-again-reference
just tall-table build popover,select,custom-cells && just tall-table smoke
just tall-table build popover && just tall-table smoke
```

## Corrected 2026-11-22: the four frame files' protocol

The four `2026-11-22-m23-d-frames-cue-*-reference.json` recorded a protocol they didn't run: `perf.ts` wrote `flingMs`, `selectAllStanding`, `selectDrag`, and `popoverWheels` whenever their features were built, and a `--cue` run skips each of those segments for the cue's two (`scroll` stays: `cue-scroll` sends the steady scroll's wheels). The four keys were removed from each file's `protocol` by hand (nothing else in them changed: no result, no failure), and `perf.ts` now writes each key only when its segment ran. Found by the code review after the close ([`docs/milestones.md`](../../docs/milestones.md), "M23 follow-up").

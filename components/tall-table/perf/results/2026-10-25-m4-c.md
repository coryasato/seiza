# M4 part C: following (2026-10-25)

Measured on Apple M1, Darwin 25.6.0 arm64, machine `local`. Bytes and the smoke check only: `follow`'s frame work, append → pixel, and its cost against `live` under the tail feed are part D's, on the final build.

Raw: `2026-10-25-m4-c-size.json` (`just tall-table size --against 78373bc`).

## What changed

- **The table** (`follow`, off by default, which turns on `live`): `follow()`, `is_following()`, and the events `Following(bool)` and `TailDrawn { rows }`. Following is a flag the reader's vertical moves set and clear (`src/state/follow.rs`'s `Reach`); while it's on, the view's bottom is pinned to the loaded tail (`PageCache::loaded_through` from the view's top), moved on after `set_rows`, a page landing, a drag's release, and a resize (which keeps the bottom), only down, and not as a scroll. The visible pages are read bottom first while following. `TailDrawn` is emitted in render, from a filled frame's end.
- **The bridge** (`follow`): the following flag and the highest tail drawn on globals a host names, and the tail mark after the global.
- **The bare host** (`follow`): the tail feed (`?rows=<n>`, `?append=<rows/s>`, a batch about every 16 ms, one `set_rows` each, marked as sent: `tall-table:appended`, the rows on `__tallTableAppended`), `?follow` at open, the tail mark (`tall-table:tail`, `__tallTableTail`), and the flag (`__tallTableFollowing`).
- **The fixture:** `paging.json`'s `follow` and `scroll_x` steps, a step's `following` and `bottom` checks, nine `follow` scenarios, and four controls. The TanStack contender skips them (a feature it doesn't build).
- **The scripts:** `size.ts` measures `follow` against the base and against `live`, which it turns on, and checks its module (`state::follow`) is absent from the base; `smoke.ts` runs the tail feed with `follow` built.

## Smoke (the release build with `follow`)

`?rows=1000&append=1000&follow`, narrow, each browser: three tail marks, each right after a presented frame, the tail each one's frame drew further on than the last, and no placeholder row in those frames (both read in the microtask that sets the mark); a wheel up lets go (`__tallTableFollowing` false) and, once the wheel rests, the view holds for 500 ms while rows arrive; End follows again, three more tail marks.

The first run failed in Firefox and WebKit: the view went 10 rows further up after following stopped. Both deliver one scripted wheel in several events, and the first already let go; the check now waits for the view to rest before timing the hold (Chromium's arrives whole), and gives up with a failure after 2 s.

## After the code review

Fixed, then the size run, tests, lint, smoke, and the fixtures were run again (the numbers above are from after):
- **End, `jump_to`, and a wheel reaching the end planned their reads top first:** following was decided after the move had planned them. Each move now decides it first, from the top it will land on; three scenarios pin it ("reaching the end over two pages…", "a jump to the end…", "a wheel down to the end…"), each failed by `top-first`.
- **A trackpad's sideways swipe with a little vertical in it let go:** a wheel more sideways than vertical now leaves following as it is (`the_readers_moves_set_and_clear_it`).
- **A resize during a scrollbar drag moved the view** (the keep-the-bottom branch didn't check for a drag).
- **Returning to the tail of a source that stopped growing emitted no `TailDrawn`:** following starting forgets the tail drawn.
- **The bridge raised the tail global, so after a shrink it kept the old tail:** it's replaced now.
- **The smoke check read the tail and the placeholders after each mark, from later frames, and its rest wait had no bound:** both fixed (above).
- Cleanups: one "pin, then re-plan" helper for the two landing paths (`pin_and_want`); the two feeds share one rate counter and frame loop (`host.rs`'s `Rate`, `every_frame`); a needless `cfg` term.

# M8 part D: sort's cost, and the close (2026-10-29)

Measured on Apple M1, Darwin 25.6.0 arm64, machine `local`, Chromium headless=new, 1440×900 at DPR 2, cold, median of 10, reference and throttled (CPU 4×, Fast 4G) (root CLAUDE.md, "Measurement protocol"), on the final build (`9a2c9cb`, no change to the table in this part). The machine quiet (browsers closed); load average 1.6–2.5 over the perf runs, 9.4 for a minute at the start of the `sort` build's run (two release builds just before it), falling to ~3 by its throttled half.

Raw: `2026-10-29-m8-d-size.json` (`just tall-table size`); `2026-10-29-m8-d-frames-sort.json` and `2026-10-29-m8-d-frames-base.json` (`just tall-table perf`, the `sort` build, then the base); `2026-10-29-m8-d-sort.json` (`just tall-table sort`, on the `sort` build); `2026-10-29-m8-d-rerun-frames-sort-reference.json` (the `sort` build's reference run again, after the base, for the order and the load); `2026-10-29-m8-d-unsortable-reference.json` (an experiment: the `sort` build with the bare host's columns not sortable, below).

- **A cost, not noise: +0.15–0.24 ms a frame (2.5–5%) at the reference run,** the ranges apart from the base's in every segment. The re-run after the base (the load at 1.6–2.1) reads the first run's medians to within 0.02 ms, so it isn't the first run's load.
- **Most of it is the arrows.** The experiment's build is the `sort` build with the bare host's `sortable(true)` set to false (a one-line local change, built, measured, reverted; `perf` run as over the base, its sorted segments skipped): no arrow is drawn, and the scroll reads within 0.04–0.09 ms of the base. So the arrows cost ~0.13–0.15 ms a frame of a scroll (6.19 → 6.06 narrow, 7.23 → 7.08 wide): a dozen glyphs, each in its own box with its target, about `resize`'s bands' cost (+0.05–0.15 ms). What's left in the flings (+0.11–0.15 ms over the base, without arrows) is where pages land, the bare host's source (its read path built with `sort`) rather than the table's frame; not traced further.
- **Throttled, the same cost at 4× the CPU:** the sideways fling +0.56 ms (2.3%, the ranges apart), the wide fling +0.80 (6.4%); the scrolls and the narrow fling within their spreads (3.2–8.8%).
- **A sorted column costs nothing more a frame.** The sorted segments read at or under the unsorted ones in the same build (wide scroll 6.92 against 7.23; the flings 3.87–3.91 against 4.10–4.22), and the wide shape's under the base. They run second in each session, after the unsorted ones, so part of that is order (the wasm warmer by then); none of it is a cost.
- **The wide throttled fling's late frames:** base 3.0% (median; 0.5–5.6), `sort` 7.5% (3.5–13.2), as in every feature's build since `follow` (`PLAN.md`'s open question), with the work this time a little higher too (+0.80 ms). The sorted fling in the same session: 0.98%.

## A click's latency (D1, C2's numbers)

`just tall-table sort`: a click on a float column's arrow (the narrow shape's `H`, the wide's first column) through its cycle, three cycles a run, the order computed before the clicks, so a click is the order's swap and not its computation. The click's `pointerup` → the `tall-table:sorted` mark (the table's update), → the first presented frame drawing the new arrow, → the first presented frame at the top with every row real. Median of 10:

| | Narrow ref | Narrow throttled | Wide ref | Wide throttled |
|---|---|---|---|---|
| Reads answered at once: → sorted / → arrow / → filled | 0.88 / 13.76 / 37.47 ms | 1.48 / 18.98 / 53.84 | 0.79 / 17.13 / 41.88 | 1.62 / 20.52 / 70.18 |
| Held 200 ms, none out | 0.84 / 19.38 / 233.01 | 1.44 / 22.75 / 239.36 | 0.83 / 19.02 / 237.04 | 1.62 / 22.16 / 247.23 |
| Held, three out at the click | 0.68 / 16.26 / 275.43 | 1.29 / 17.02 / 268.58 | 0.53 / 16.07 / 281.70 | 1.31 / 16.38 / 272.27 |
| The top page's wait for the reads out | 42 ms | 29 ms | 45 ms | 25 ms |

- **The table's own work is under 2 ms** (→ sorted: the source told, the cache forgotten, the view at the top, the selection and the rest), 0.5–0.9 ms at reference. The arrow then waits for the next frame: → arrow is mostly the frame period (its spreads 13–85%, a frame's phase).
- **Filled at the top in ~40 ms at reference with reads answered at once** (54–70 throttled): the new order's top pages materialized from the source's order and drawn. A source's time adds to it: with 200 ms reads, 233–247 ms.
- **Three reads out at the click cost 25–45 ms more**, what was left of the oldest (each read held 200 ms, the click after three wheels' frames): every run drained 3. The README's limit says it.
- **A source's order isn't in these numbers:** the bare host computes it before the clicks. The cost of an order is a source's (the README's limits, the research's spike).

## Reproducing it

```sh
just tall-table size --label m8-d-size
just tall-table build sort && just tall-table perf --label m8-d-frames-sort
just tall-table sort --label m8-d-sort
just tall-table build && just tall-table perf --label m8-d-frames-base
just tall-table build sort && just tall-table perf --profile reference --label m8-d-rerun-frames-sort-reference
# the experiment: host/crate/src/rows.rs's `sortable(true)` set to false, then
just tall-table build sort && echo '{"features":""}' > components/tall-table/host/web/dist/build.json && just tall-table perf --profile reference --label m8-d-unsortable-reference
just tall-table build sort,select && just tall-table smoke
```

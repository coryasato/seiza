# M7 part A: how a copy reaches the clipboard, a spike (2026-10-26)

Measured on Apple M1, Darwin 25.6.0 arm64, machine `local`, Playwright 1.63 (Chromium 153 headless shell, Firefox 155, WebKit 26.6), headless, default viewport. No table: a plain page with a focusable canvas, so what's measured is the browsers' clipboard alone. One run per case: these are pass or fail, and the timings are a size's order, not a protocol run.

The spike's page and scripts weren't kept (part A builds no shipped code); "Reproducing it" below says what they did.

## What was measured

A keydown on the canvas (Cmd+C under Playwright's `ControlOrMeta+c`, a trusted key) wrote a tagged string to the clipboard in one of these ways; then a textarea took a real paste (`ControlOrMeta+v`), and the case passed if the paste was the tagged string:

- **sync:** `navigator.clipboard.writeText` in the keydown, after `preventDefault` (gpui-pre-web's `write_to_clipboard` for a handled key).
- **later:** `writeText` after a delay.
- **item:** `navigator.clipboard.write([new ClipboardItem({'text/plain': promise})])` in the keydown, the promise resolving to a Blob after a delay (**item-string:** to a string).
- **copy event:** the keydown left alone, and `document`'s `copy` event setting `clipboardData`.

## Results

| Write | Chromium | Firefox | WebKit |
|---|---|---|---|
| sync | pasted | pasted | pasted |
| copy event | pasted (target: canvas) | pasted (target: body) | pasted (target: canvas) |
| later, 0.1 / 1 / 3 s | pasted | pasted | pasted |
| later, 6 s | refused (`NotAllowedError`) | refused | refused |
| item, 0.1 / 1 / 3 / 6 / 12 s | pasted | pasted | pasted |
| item-string, 1 s | pasted | pasted | pasted |

Chromium as above only with the context granted `clipboard-write`. Without it, every async write (sync, later, item) was refused with `NotAllowedError`, and only the copy event pasted. A real Chrome grants a focused page `clipboard-write` without asking; headless doesn't.

**Large writes** (item, a Blob of TSV-like text built from 1,024-line parts, resolved 50 ms after the key; time from the key to the write's promise resolving):

| Size | Chromium | Firefox | WebKit |
|---|---|---|---|
| 16 MiB | 95 ms | 146 ms | 101 ms |
| 64 MiB | 236 ms | 425 ms | 243 ms |
| 96 MiB | | | 311 ms |
| 100, 104, 112, 120, 128, 160, 200 MiB | | | refused (`NotAllowedError`, in ~0.2–0.3 s) |
| 256 MiB | 790 ms | 2,260 ms | refused |

Chromium's 16, 64, and 256 MiB read back whole (`readText`, with `clipboard-read` granted). Firefox and WebKit weren't read back at size.

**Formatting** (native, `rustc -O`, the same M1): a wide page's text, 1,024 rows × 500 floats, each `{:?}` (the shortest round-trip text), tab-separated: 9.5 MB in 38–39 ms (75 ns a cell) after a first, cold 86 ms.

## What it means

- **A write later than ~5 s after the key is refused** in every engine (transient activation), and through GPUI it's silent: gpui-pre-web drops `writeText`'s promise. A copy that waits on reads can't rely on it.
- **A `ClipboardItem` opened in the key's task and resolved later always lands**, at 12 s too. The table's copy goes through it, opened by the host (the bridge) when the copy starts.
- **WebKit refuses a write from 100 MiB**, so the default cap sits under it (64 MiB).
- **A wide page formatted in one turn is a ~40 ms task natively**, so formatting is cut into turns of a few milliseconds.
- **Scripts that check a copy in headless Chromium grant `clipboard-write`.**
- Not checked: real Safari and Firefox (Playwright's WebKit isn't Safari), and a `ClipboardItem` resolved minutes after the key or with the page blurred or hidden meanwhile. The milestone's smoke check and manual check cover them: copies past 5 s and about 60 s, one finishing in the background, and one near the cap.

## Reproducing it

A page with `<canvas tabindex=0>` and a `<textarea>`, served from `localhost` (a secure context), its canvas's keydown doing each write above; a Playwright script per engine focusing the canvas, pressing `ControlOrMeta+c`, waiting the delay plus 0.6 s, then filling the textarea with a `ControlOrMeta+v` and comparing. Chromium's context gets `permissions: ['clipboard-write']` (and `clipboard-read` for the size read-back). WebKit on macOS writes the system pasteboard: the run overwrites what was copied.

## `paging.json`

`paging` is the table's `Paging::default()` (the test fails if they part), in the units a TS side uses: `page_rows`, `prefetch`, `budget_bytes`, `max_in_flight`, `scroll_settle_ms`, `drag_settle_ms`. Each scenario has `rows`, `viewport_rows` (the rows the viewport holds, fractional), `page_bytes` (what every answered page counts against `budget_bytes`), `steps`, and maybe `features`, the table's features it needs (`live`, `follow`, `sort`), run only by a build with them, and `without`, the features under which it's skipped (the base's drop of a grown page holds only without `live`). A step has one action, `expect`, maybe a `why`, and with `follow` maybe `following` and `bottom` (below):

| Action | What it does |
|---|---|
| `open: true` | Opens the table over `rows` rows with that viewport. |
| `scroll: <rows>` | Scrolls by that many rows (negative is up), as a wheel or a key does. |
| `scroll_x: <px>` | Scrolls sideways by that many pixels, as Shift+wheel does. The fixture's one column fits, so nothing moves; with `follow`, following stays as it was. |
| `jump: <row>` | Puts that row at the top, or as near as the end allows. |
| `fraction: <f>` | Scrolls to `f` of the way down (Home is 0, End is 1): the top row is `f × (rows − viewport_rows)`. |
| `drag: <f>` | Drags the scrollbar thumb so the top is at `f` (as `fraction`), starting a drag if none is on. A track press is a `drag` then a `release`. |
| `release: true` | Lets go of the thumb. |
| `wait: <ms>` | Time passes. Nothing else moves the clock: every other step happens at the same instant. |
| `answer: "all"` | Answers every open read in the order they were sent, one at a time, the reads they start included, until none is open. |
| `answer: [<page>, …]` | Answers the oldest open read of each page, in that order. |
| `fail: [<page>, …]` | As `answer`, but each read fails (not a broken source: only its rows show the error). |
| `rows: <n>` | The source now holds `n` rows (`set_rows`); the top row stays where it is, or as near as the new end allows. A short last page that grows is forgotten and read anew, its read cancelled if one is out; with `live` it's kept (below). Shrinking forgets a short last page either way, and every page wholly past the new end, loaded or being read (its read cancelled): grown back, they're read anew. |
| `follow: true` | `follow`: follows the end (`follow()`): the view goes to the end as a jump does, and from then stays at the loaded tail as rows arrive (below). |
| `let_go: true` | `follow`: the host lets go (`let_go()`): following off with the view where it is, nothing read or cancelled; rows arriving and reads landing no longer move it. Already let go, nothing changes. |
| `invalidate: [<start>, <end>]` | `live`: rows `start..end` (end-exclusive) changed in the source (`invalidate_rows`). Its pages loaded or being read go stale; the wanted ones are read again, a loaded one drawn as it is until its read lands. |
| `sort: {"column": <c>, "direction": "ascending" \| "descending"}` or `sort: null` | `sort`: the table sorted by that column (sortable in a `sort` scenario's table) or back to the source's own order (`set_sort`). The source is told first (`sort <c> <direction>`, `sort none`, the first of the step's `expect`); then every page is forgotten and every read out cancelled (one decision), the view goes to the top as a jump does (the sideways scroll kept) but prefetch doesn't lean, and the top pages are read once the step's update ends. The cancelled reads hold their places until they answer, and an answer to one is dropped, whatever it holds. The same sort again does all of it again. |

A cancelled read always answers as cancelled; the others answer with their page. After each step, everything that can run runs (answers land, reads start) before `expect` is compared.

`expect` lists what the table asked its source for during the step, in order: `load <page>` (rows `page × page_rows` up to the next page or the end), `cancel <page>` (the table no longer wants that read; it still counts as in flight until it answers), and with `sort` `sort <column> <direction>` or `sort none` (the order it told the source to read in). The cancels from one decision are a set, written in page order.

`expect` doesn't tell a re-read from a first read: both are `load <page>`. A stale page's re-read is never cancelled for being stale; a page invalidated during a read (a re-read or its first) is read once more after that read lands; a stale page that isn't wanted is dropped, and its re-read, if one is out, cancelled.

With `live`, a short last page that grows is stale the same way: it draws the rows it was read with (placeholders past them) and is read again, never cancelled for growing; grown during a read (a re-read or its first), it's read once more after that read lands.

With `follow`, following is a flag, off at open whatever the position. Each move decides it before moving, from where it will land, so a move that starts following reads bottom first. A wheel or key down keeps it on, or turns it on if the view ends at the end; `fraction` (End, a drag) and `jump` turn it on exactly when the view lands at the end (top = rows − viewport_rows) and off otherwise; a wheel or key up by any amount, Home (`fraction: 0`), and `let_go` turn it off; `scroll_x` and `rows` leave it. During a `drag` it holds as it was, and the `release` decides, as a landing. While it's on, the view's bottom is pinned to the loaded tail: once every row in view is loaded, the view moves down until its bottom is at the end of the rows drawn with their values (a grown page's up to the rows it was read with), only down, and never during a drag. A pin move isn't a scroll: prefetch doesn't lean and no settle timer starts. While following, the visible pages are read bottom first.

A step's `following: <bool>` checks the flag after it, and `bottom: <row>` the end of the rows in view (the row after the last one at least partly visible: `ceil(top + viewport_rows)`, at most `rows`).

`controls` each change one `paging` field, or (`cache`, in every build) name a way of keeping pages wrongly: `keep-past-end` keeps the pages wholly past a shrink's new end, forgetting only a short last page; or (with `live`) a way of re-reading wrongly: `reread-unwanted` keeps stale pages outside `wanted` and reads them again, `restart-stale` cancels a page's read when it's invalidated during it and reads it anew, `drop-grown` forgets a short last page that grows, as the base does; or (with `follow`, its `follow` field) a way of following wrongly: `follow-at-end` takes following to be the view at the end, `follow-ignores-reader` never lets go for the reader, `pin-to-rows` keeps the view at the last row whether it's loaded or not, `top-first` reads the visible pages top first while following, `let-go-to-end` moves the view to the end when the host lets go (as `follow` does) before letting go; or (with `sort`, its `sort` field) `keep-pages`, a sort that keeps every page and read. Every control must fail at least one scenario the build runs.

The TanStack contender runs every scenario its levels build: the base's on each level; the `live` ones and controls on its market level, but those with a `rows` step and `drop-grown` (its row count is fixed there); and on its tail level every scenario but `sort`'s and those skipped under `live`, with the `rows`, `follow`, `let_go`, and `scroll_x` steps (`scroll_x` moves nothing there), each step's `following` and `bottom`, and every `cache`, `live`, and `follow` control.

## `sort.json`

What a DOM contender's sort must match (`sort`; the table's README), not how it builds it. No contender sorts yet: the observatory adds the level when both its sides build it, and the TanStack contender's test names the file skipped.

- `cycle`: a column's `kind` (`text`, `integer`, `float`, `decimal`, `date`, `timestamp`, `boolean`) and `clicks`, the sort after each of three clicks on its arrow from unsorted: `ascending`, `descending`, or `null` (the source's own order). A click on another column's arrow starts that column's cycle. The native test clicks each column's arrow in a window of a table with a column of each kind.
- `orders`: a column's `values` (numbers, text, or booleans, one kind a case; `null` is NULL) and their order, `ascending` and `descending`: each the rows (0-based, in the source's own order) as the sorted rows read. Values compare as their kind (numbers as numbers, text by its bytes, false before true); ties keep the source's own order both ways (a stable sort, so descending isn't ascending reversed), and NULLs are last both ways. The native test runs the bare host's in-memory order (`rows::order`) over them, so the host the scripts sort is the one pinned.
- `cycle_controls`: `descending-first`, every kind descending first (`DataTable`'s cycle). `order_controls`: `nulls-first`, NULLs first both ways; `ties-reversed`, descending as ascending reversed. Each must fail its section.

## `cells.json`

`columns` are the float columns as the GPUI contender laid them out (its `ColumnProbe`): `name`, `kind`, `width` (CSS px), and `budget`, the characters a float may take. A DOM contender uses these budgets as they are: they come from GPUI's measured glyph advance, which a DOM measurement can miss by a character.

`cells` are values from the data file as the contender drew them: `column`, `row` (0-based, in file order), `value` (its shortest round-trip text, as JS's `String` writes it, or `null` for NULL), `exact` (the table's exact text, Rust's `{:?}`: `8.0` where JS writes `8`, and the tooltip's text), and `shown` (the cell's text). No value in the data file is too long for its column, so none is rounded there; `rounding` holds values that are, at the same columns' budgets, each with a `why` naming the case.

`cell_controls_fail` checks that each of these fails the fixture: a float's text written without the `.0` of a whole number (Rust's `Display`, as JS's `toString` does), and each budget a character smaller or larger.

`number_px` is GPUI's widest advance of the characters a number is written with (`0123456789.-+e`), in CSS px, at the cells' 14 px IBM Plex Sans: 8.4 (its digits' 600 units of 1000). A float column's budget at width `w` is `max(1, floor((w − 17) / number_px))`: the cell's 16 px of padding and a pixel short of the room. A DOM contender can't measure GPUI's advance, so a resized column takes its budget from this rule. The native test checks it gives each of `columns`' budgets; `cell-fixture.ts` keeps it and fails if the contender's budgets disagree.

`resize` (with `resize`) pins a set width's budget and text. `min_width` and `max_width` are the column defaults (40 and 1200 px) a set width is clamped to. `widths` are a float column's `set` width (`TallTableColumn::width`) → the `width` it's drawn at and its `budget`, at and past both clamps, each with a `why`. `cells` are values at a `set` width, with their `exact` and `shown` text as `rounding`'s are. `resize_controls_fail` checks that each budget a character smaller or larger, and widths laid out without the clamps, fail it. The TanStack contender runs it on the wide level's layout (`fixtures.test.ts`), with its controls.

`format` (with `format`) pins a formatted number column's text (the table's README, "Format"). `advances` are each character a format writes (the digits, `+`, `-`, `.`, `,`, `e`) and each suffix's (`%`), in CSS px at the cells' 14 px IBM Plex Sans: a formatted text's width is its characters' advances summed (a suffix's too), and it's drawn, whole, when that is at most the cell's width less 17 (the padding and a pixel), else the cell shows the automatic format. `cases` are a `format` (`decimals`, `null` for the exact text; `sign`, `negative` or `always`; `grouping`; `suffix`), a `kind` (`float`, `float32`, `integer`, `decimal`), a `value` (a float's text, an integer's or decimal's as the source writes it, `null` for NULL), the page's `decimals` for the cell (`null` for the column's; a float's only), and a set `width` → the `exact` text, the `shown` text (a fallback's before the cells' cut: `rounding`'s budget rule at `width`, an integer's or decimal's plain text), whether it's a `fallback`, and whether the format `rounded` it (the tooltip opens; `null` for a fallback, whose tooltip is the base's: rounded or cut), each with a `why`. The rules: a float at fixed decimals rounds its exact binary value half to even (Rust's `{:.N}`, not `toFixed` or `Intl`), the sign is the raw value's (`+0.00%`, `-0.00`) and an exact zero's none, grouping is a `,` every three whole digits of a plain text, never an exponent. `format_controls_fail` checks that each of these fails it: a `+` on an exact zero, the sign by the rounded text, ties rounded up from the shortest decimal, grouping by four, the fit by the character count at a digit's advance, and the page's decimals ignored. The characters' advances are GPUI's own on the web, the table's (its layout probe's `advances`), read from the bare host in Chromium (`just tall-table format-fixture`); a suffix's `%` isn't one of the table's (it shapes a suffix whole) and is the font's read natively with the web's shaper. They equal the font's read natively (`plex_sans_shapes_formats_at_their_advances`, which also checks the font shapes the pairs a format writes at their advances' sum, but `e-`, 0.01 em wider: once a text at most, inside the rule's pixel). The TanStack contender runs it on its market level (`src/data/number.ts`); a DOM contender without the format skips the section.

`timestamp_text` pins a zoneless `TIMESTAMP`'s text as live tail draws it (no table feature: each contender formats the value it reads, the GPUI contender in `src/tail.rs`, the TanStack contender in `src/data/tail.ts`, each test running it with controls: an unpadded day, a numeric month, a local-time conversion). Each case's `micros` is the value from the epoch, read as UTC, and `text` what's drawn: `13/Jul/1995 03:14:02`, the day two digits, the month's three English letters, the year four, 24-hour time, the fraction cut. Hand-written; `cell-fixture` keeps it as it is.

`scenarios` holds a section for each observatory scenario but the asteroids', by its id (`wide-sheet`, `admin-table`): its `source` (the file, its SHA-256, the `stop` it was drawn at, and the build), `columns` (the wide sheet's: a few of its float columns, the ones on screen at the sideways scroll's 0, laid out at that stop's density), and `cells` (as above, values from that file). A file of text alone (`admin-table`, every script in its names and the flags) has `text` columns, every one of the file's, each at the width its kind lays it out at; a cell's `value` is the text as the file holds it, and its `exact` and `shown` are that text unchanged (the table rewrites only a line break, which the file has none of). Its control is the text decoded wrong: its UTF-8 read as Latin-1 must fail. The native test runs each section as it runs the top one; a DOM contender at that level does too, at the same stop.

## `sql.json`

`pages` are the page query for some pages of `file` (the SQL name it's registered under), and `summary` the queries an open sends, in order (no metadata keys, so the keyed third isn't sent). The text must match exactly. `scenarios` holds the same for each observatory scenario's own file, by its id (`wide-sheet`, `live-tail`, `admin-table`: `file`, `pages`, `summary`); the test checks each. `controls` are page queries that must fail the comparison: the same rows by `LIMIT`/`OFFSET`, and the same query spaced differently.

A scenario whose pages are its host's own query has `query` naming it, and the plain-file runs (the engine's `sql_fixture`, the TanStack contender's `fixtures.test.ts`) check only its `summary`. `live-tail`'s is `"loop"`: `file` is the one opened by range (its summary), `loop_file` the file fetched whole and registered as a `File`, which every page reads; row *i* is `loop_file`'s row *i* mod `file_rows`, its time moved on by *i* div `file_rows` laps of `span_s` seconds, one SELECT per lap a page crosses, in row order. Its pages run in the GPUI contender's `src/tail.rs` and the TanStack contender's `test/tail.test.ts`, each with controls (no shift, the seam read as one SELECT, a lap off by one), and the observatory's prep runs each in native DuckDB against the file's rows.

## `paint.json`

What a DOM contender draws for a cell's paint (`custom-cells`; the table's README, "Use it"), at the protocol's DPR 2. The TanStack contender draws it on its wide level (its `flash` on its market level, through its paging); the observatory adds a level when both its sides build it.

- `cell`: the cell the bars are drawn in: `width` (CSS px, a float column's), `row_height`, `padding` (each side; the bar spans the inner width, `width − 2 × padding`), `bar_inset` (the bar's distance from the row's top and from the row line, which the fill and bar leave clear: they're `row_height − 1` tall).
- `tolerance`: `channel_steps`, 8-bit steps a channel may differ (rounding), and `bar_px`, CSS px a bar's edge may differ (one device pixel: GPUI rounds an x.5 edge down, the browser up).
- `ramps`: each ramp's `stops`, theme tokens evenly spaced over 0..1, and their resolved colors in `light` and `dark` (`#rrggbbaa`). The native test checks them against gpui-kit's default theme, so a theme change fails it.
- `tokens`: the other theme tokens the cases name, in the same form: the text colors (`foreground`, `background`), the rows' backgrounds (`table`; `table_even`, an odd row's stripe drawn over it; `table_active`, the jumped-to row's tint), and the bar's colors. Checked against the theme the same way.
- `bar`: the tokens a bar draws in, its `color` and its `below`.
- `colors`: a ramp, `as` a `fill` or a `text` color, a `value` (clamped to 0..1), and `expect`: the 8-bit RGBA drawn in light and dark. A value between stops `i` and `i + 1` at fraction `t` is `color-mix(in oklab, stop_i (1 − t) × 100%, stop_i+1)`; `expect` is what Chromium draws for that into a canvas.
- `bars`: a column's `zero`, whether it has a `below` color (`below: true`), and a `value` (both clamped to 0..1), and `expect`: the bar's `left` (CSS px from the cell's left: `padding + min(zero, value) × inner`), `width` (`|value − zero| × inner`), and the color it's drawn `in` (`below` where the column has one and the clamped value is left of the clamped zero, else `color`), or `null` where it draws none (`value` at zero).
- `text_over`: a fill through `ramp` at `value` in an `even`, `odd`, or `marked` `row` (the row a jump landed on), with no text color, and `expect`: the token its text is drawn in, in light and dark. The row's background (the table's, with an odd row's stripe or the marked row's tint over it), the fill over that, and on the marked row the tint again over the fill are drawn into a canvas and read back; the token is whichever of `foreground` and `background` has the Oklab lightness farther from that color's (ties to `foreground`). The script fails on a near tie (within 0.02). The drawn text must be the token's color exactly.
- `none`: paints that draw nothing (NaN).
- `flash` (`live` with `custom-cells`): a column's flash through `ramp` (one of `ramps`) for `duration_ms`, and its `cases`: a cell's `old` and `new` value (a number is a float, `"NaN"` a float NaN, `null` NULL, `{"text": …}` text), read again with every case's row changed at once, and drawn `elapsed_ms` later. `expect` is `null` where nothing is drawn (no change, or the flash is over), else `at`, its place in the ramp (a float's rise 1, its fall 0, any other change 0.5; two NaNs are equal), `opacity` (`1 − elapsed / duration`), and the 8-bit RGBA drawn in light and dark: the ramp's color at `at` (Chromium's mix, as `colors`) with `round(opacity × 255)` as its alpha, drawn over the cell's fill. The script writes `at` and `opacity` from the rule above, apart from the table's code.

`paint_controls_fail` checks that each of these fails it: every color two steps off, every bar 2 device pixels off, and the ramps mixed in sRGB instead of Oklab; `below_ignored_fails`, `nearer_token_fails`, and `composite_ignored_fails`, that bars drawn in `color` below zero, text in the token nearer the fill, and a fill read without the row under it and the marked row's tint over it fail the `bars` and `text_over` cases; `flash_fade_backwards_fails` and `flash_fall_as_rise_fails`, that a fade run from nothing to full and a fall flashed as a rise fail the `flash` cases. `just tall-table paint-fixture --check` fails if `expect` is out of date with the cases and stops.

## `selection.json`

What a DOM contender selects and scrolls to (`select`; the table's README), not how it holds it. The TanStack contender runs it, with its controls, against its wide level's port (`fixtures.test.ts`: the targets as points in the fixture's table, the base's keys and wheel where the selection doesn't take them).

The table: `columns` float columns, each `column_width` CSS px, over `rows` rows (a scenario's `rows` replaces it), in a view `viewport_rows` rows tall whose cells area (right of the row numbers, left of the vertical scrollbar) is `cells_width` px wide at open. A scenario's `selectable` lists the kinds on (`rows`, `columns`, `cells`; none is the base's input), and its `steps` each have one action, `expect`, and maybe a `why`.

A pointer target is a visible cell's middle (`{"cell": [row, column]}`), a visible row's number (`{"gutter": row}`), a visible column's header (`{"header": column}`), the header over the row numbers (`{"corner": true}`), or past the cells, level with a visible row on their right (`{"right": row}`) or under a visible column below them (`{"below": column}`).

| Action | What it does |
|---|---|
| `press: <target>` | A left press there, with `"shift"`, `"cmd"`, or `"ctrl"` held where true. It starts a drag unless it selected nothing or was on the corner. |
| `drag: <target>` | The pointer moves there with the button down. |
| `release: true` | The button comes up where the pointer is. |
| `wheel: {"rows": n, "at": <target>}` | A wheel of `n` rows (negative is up), the pointer at the target. |
| `key: "<keys>"` | Keys as GPUI writes them (`shift-down`, `cmd-shift-up`, `pagedown`, `space`, `escape`, `cmd-a`, `ctrl-a`). |
| `rows: <n>` | The source now holds `n` rows (`set_rows`). |
| `columns: true` | The same columns again (`set_columns`). |
| `jump: <row>` | `jump_to`. |

`expect` is what holds after the step: `selection`, `null` or its `kind` (`rows`, `columns`, `cells`), `anchor` (the active cell, `[row, column]`), and `head`; `top`, the view's top row (fractional in general; whole here); and `scroll_x`, the cells' sideways scroll in px.

The rules a step checks, in brief (the spec is the table's `PLAN.md`, `select`'s milestone; the decisions are its `docs/DECISIONS.md`, "Features"):

- A press selects the smallest kind that's on and holds what it's on: a cell, else its row; a row's number its row; a header its column (at the top visible row); the corner every column, else every row, else every cell. Otherwise it selects nothing and leaves the selection as it was. Cmd+press is a plain press; Ctrl+press selects nothing.
- Shift+press, a drag, and a wheel during a drag move the head: only along what the press picked (a cell both ways, a row's number its row, a header its column) and the range spans (`rows` up and down, `columns` across, `cells` both). The pointer is clamped to the visible cells, and past the last column to the last.
- A plain arrow moves the active cell one cell and collapses the range to the smallest kind that's on and holds it (a cell, a row, a column); Shift+arrow moves the head along the range's direction and nothing across it. Page keys move by the rows in view less one and scroll the base's page; Home, End, Cmd+Up and Down to the first and last row. At an end nothing moves; nothing loops. A moved cell is scrolled into view the least distance, down, up, and sideways.
- With nothing selected, the first arrow selects the first visible cell (by kind) without moving, and the other keys scroll as without the feature. Cmd+A and Ctrl+A as the corner. Escape clears.
- `set_rows` cuts a `rows` or `cells` range to the new end (clearing one wholly past it); a `columns` range stays. `set_columns` clears. `jump_to` selects the row (rows on), else the cell (cells on, in the active cell's column, else the first visible), else only scrolls.

`selection_controls_fail` checks that each of `controls` fails it: `loop` (a key past an end wraps), `center` (a moved cell centered instead of scrolled the least distance), `plain-moves-head` (a plain arrow moves the head, not the active cell), `extend-across` (Shift+arrow moves across a range's direction), `keep-past-rows` (`set_rows` doesn't cut the range).

## `pin.json`

What a DOM contender's pinned columns must match to draw the same cells (`pin`; the table's README), not how it draws them (a DOM grid's sticky cells). No contender pins yet: the observatory adds the level when both its sides build it.

Each of `cases` is a table's `cells_width` (CSS px, the cells area right of the row numbers), its columns' `widths` (laid out left to right from 0, each column's `x` the sum of the widths before it), the host's `count` (`set_pinned`), and a sideways `scroll_x`; its `hits` are screen x's (px from the cells' left) and its `into_view` column indices. `expect` holds:

- `pinned`: the run in effect, the first `count` columns clamped to the columns and cut to the leading ones whose right edge is within half `cells_width` (the table allows 0.001 px over, float rounding's, which no case comes near); none while `cells_width` is 0.
- `edge`: the run's right edge, *P* (its last column's right, at most `cells_width`; 0 with none pinned).
- `max_scroll_x`: the sideways scroll's range, `content − cells_width` (at least 0), the same pinned or not.
- `lefts`: each drawn column, `[index, left]` in order, its left edge on screen: a pinned column at its `x`, a scrolled one at `x − scroll_x`. A pinned column is drawn where it starts in the view; a scrolled one where it overlaps `P + scroll_x .. cells_width + scroll_x`, so one wholly under the run isn't drawn (one partly under it is, clipped at *P*).
- `hits`: `[x, column]`, the column under screen x `x` (`null` past the last): left of *P* the pinned columns' own x, right of it `x + scroll_x`.
- `into_view`: `[column, scroll_x]`, the sideways scroll after a key moves to that column (`select`): the least move that shows it right of *P* (`P + scroll_x .. cells_width + scroll_x`), then clamped to `0..max_scroll_x`; a pinned column moves nothing.

`pin_controls_fail` checks that each of `controls` fails it: `no-cap` (the count pinned whatever the view), `pinned-scroll` (the pinned columns scroll with the rest), `under-run` (a column wholly under the run still drawn), `into-view-at-gutter` (a column brought into view at the cells' left, under the run).


## `density.json`

What a DOM contender's lengths must match to draw the same cells at a density (`density`; the table's README): its CSS row height, font size, padding, and column widths, and the budgets a float rounds to. No contender builds a density yet: the observatory adds the level when both its sides build it, and until then its test names the file skipped.

`columns` are laid out in every case: their `name`, `kind`, and (`integer`) `max_chars`, and a set `width` (`TallTableColumn::width`) where given. Each of `cases` is a `rem` size (px), a `row_height` (px), a `text` size (`{"px": n}` or `{"rems": n}`), a `view_height` (px, the viewport's), a row count (`rows`, for the gutter), and `number_px`, the widest advance of the characters a number is written with at the case's text size. `expect` holds:

- `text_px`: the text in effect, the size resolved at the rem, at least 6. `row_height` and `header_height`: the row in effect, at least the text.
- `viewport_rows`: `view_height / row_height`.
- The scale: the text in effect over the default's in the text's own unit (a `px` text over 14 px, a `rems` text over 0.875 rem at the case's rem). At a scale of 1, every length below is the base's, unrounded; otherwise each is rounded to whole px.
- `padding`: the cells' padding on each side, 8 × scale.
- `gutter`: the row numbers' width, (7.5 × the characters of the row count written with commas + 24) × scale, rounded once on the total.
- `bar_inset`: `custom-cells`' bar from the row's top and bottom, row / 5, rounded.
- `columns`: each column's `width`, and a float's `budget`. A kind's width is its base width (boolean 72, float 120, text 200, …) × scale, at least the name's estimate (as the gutter's); an integer's is `max_chars × number_px + 2 × padding + 1`. A set width isn't scaled: it's clamped to 40 × scale and 1200. A float's budget is `max(1, floor((width − 2 × padding − 1) / number_px))`.

`number_px` is pinned from the bare host in Chromium (`just tall-table density-fixture`; `--check` compares): at each case's text size in effect, read in px, the narrow shape's `spkid` (20 characters) is `20 × number_px + 2 × padding + 1` wide in the layout probe. It's 0.6 em at every size, IBM Plex Sans's digits' 600 units, the test app's advance too, so the tests in a window lay out as the fixture does (`density_fixture_number_px_is_the_test_apps`).

`density_controls_fail` checks that each of `controls` fails it: `row-unclamped` (a row shorter than its text kept), `padding-fixed` (8 px a side at any text), `width-scaled` (a set width scaled by the text), `inset-fixed` (the bar's 6 px at any row), `scale-over-default-at-rem` (a `px` text's scale over the default resolved at the rem), `scale-over-14-for-rems` (a `rems` text's over 14 px), `name-rounded-per-character` (the estimate's character width rounded before it's multiplied), `least-fixed` (a set width's least at 40 px at any text).

## `copy.json`

What a DOM contender's copy must give (`copy`; the table's README), not how it reads for it: the order of the copy's reads and where its `Text` pieces break aren't pinned, since neither changes the text and both follow when a source's pages land. The TanStack contender's test runs it against its wide level's copy (`data/copy.ts`), with the controls.

- `options`: the table's `CopyOptions::default()` (`max_bytes`, `key_max_cells`, `headers`); the native test fails if they part. A case's `options` replace fields of it.
- `paging`: the table's `page_rows` and `prefetch` (0); `viewport_rows`, a key of its own beside `paging`: the rows the view holds. The view holds the first page's rows only, so the first page is loaded when a case copies and every other page is read for the copy.
- `sources`, by name: `columns` (each a `name` and a `kind`: `float`, `float32`, `integer`, `decimal`, `text`) and `rows`, a value a column. A float's value is a string a number parses from (`f64::from_str`, JS's `Number`; a `float32`'s then rounded to f32, `as f32`, `Math.fround`), so `-0.0`, `NaN`, and `Infinity` survive JSON; an integer's, a decimal's, and a text's are the text the source writes (a DOM side parses an integer into its own type); `null` is NULL.
- `cases`: a `name`, a `source`, maybe `options`, a `selection` as `selection.json` spells it (`kind`, `anchor`, `head`), `by` (`key`: Cmd+C, held to `key_max_cells`; `copy`: the host's `copy`, which isn't), a `why`, and `expect`: `started`, the copy's `rows` and `columns`, each `[first, last]` (absent where the key declines); `outcome`, one of `copied` (`rows`, `bytes`), `declined` (`rows`, `columns`), or `too_large` (`bytes`, `max_bytes`); with `copied`, `text`, every piece joined; and maybe `reads`, whether any page was read for the copy (the copy's own reads; no case has the view read a page meanwhile, so a side with one fetch path counts the same; a page the copy takes from a read the reader's view sent, as the table's does, isn't one).

The rules a case checks:

- A `rows` range copies every column of its rows, a `columns` range every row of its columns, a `cells` range its block; the anchor and head either way round copy the same.
- A tab between cells and `\n` between rows, no line break after the last; with `headers`, the copied columns' names first, then `\n`, the line counted in the bytes.
- A value's exact text: a float's is Rust's `{:?}` (`8.0`, `-0.0`, `0.30000000000000004`, `1e300`, `1e-7`, `NaN`, `inf`, `-inf`: an exponent below 1e-4 and from 1e16, without a `+`), a `float32`'s its own shortest round trip (`0.1`); any other as the source wrote it. A field holding a tab, `\n`, `\r`, or `"` is quoted, its quotes doubled (a header's name too); NULL and empty text are both empty.
- Bytes are UTF-8. The key declines past `key_max_cells` cells (rows × columns), reading nothing; at it, it copies. A copy whose separators alone (every value NULL: a tab between cells, a line break between rows, and the header line with its break) pass `max_bytes` is refused before a read, `bytes` those separators. Otherwise the text is counted a row at a time: past `max_bytes` it's refused, `bytes` the text through that row; and once a page's worth of rows (`page_rows`, counted from the copy's own first row, never to a page's end) is in with rows to come, it's refused if their bytes a row over the copy's rows (header bytes + (bytes − header bytes) / rows in × rows) pass twice `max_bytes`, `bytes` that projection cut to a whole byte. The header's bytes there are its line alone: the line break after it is counted with the first row.

`copy_controls_fail` checks that each of `controls` (a `name`, and `fails`: the cases it's there to catch, each of which must fail under it) fails it: `null-as-text` (NULL written `NULL`), `no-quoting`, `key-limit-off-by-one` (the key declines at `key_max_cells`), `whole-floats-bare` (a whole float or `float32` without its `.0`, as JS's `String` writes it), `trailing-break` (a `\n` after the last row), `utf16-bytes` (every count in UTF-16 code units, a JS string's `length`: the cap, and the header line in the check before a read).

## `reorder.json`

What a DOM contender's column move must give to draw the same columns after it (`reorder`; the table's README), and where its drag's release moves the block. No contender moves columns yet: the observatory adds the level when a scenario asks and both its sides build it, and until then its test names the file skipped.

Each of `moves` is a table of `columns` columns in the list's own order (`order[place]` is the index drawn at a place, 0 at the left), the host's pin `count` (`set_pinned`; 0 for none, and past the columns allowed), a `block` of places `[first, last]`, a `to` (the block's first place in the order after the move), a `side` (`null` for `move_columns`; `pinned` or `scrolled` for `move_columns_pinned`), and a `selection` before it as `selection.json` spells it (`kind`, `anchor`, `head`; each cell `[row, place]`), or `null`. `expect` holds:

- `order`: the order after, `null` where nothing moves: an empty block, one past the columns, a `to` past `columns − the block's length`, a `side` the `to` isn't on (below), or a move that changes neither the order nor the count. The block is lifted out and put back at `to` among the rest, each keeping its order.
- `count`: the host's count after. With *r* the run's columns outside the block (the count clamped to the columns, less the block's columns at places below it), a `to` below *r* lands the block pinned, above it scrolled, and at *r*, the run's end, on `side`'s side, or with no `side` its first column's (pinned if its place was below the clamped count). A `side` naming the other side from a `to` not at *r* is no move. If a column changed side, the count is the clamped count plus those that joined the run less those that left it; if none did, the host's count as it was, past the columns or not.
- `selection`: the selection after (`null` when cleared). `rows` is kept as it was. A `columns` or `cells` range's columns each go to their place after the move; if those places are side by side, it's kept as that run, its rows kept, the anchor at the run's end on the anchor's side (left if the anchor's column was left of the head's or the same, else right) and the head at the other; otherwise it's cleared. With no move, it's as it was.

Each of `gaps` is a drag's pointer over a table: the columns' `widths` (px, side by side in the list's order), the cells area's `cells_width`, the sideways `scroll_x`, the host's pin `count`, the dragged `block` of places `[first, last]`, and the pointer's `x` (the cells area's pixels, at any height; negative is over the row numbers), and maybe `features` (`pin`: run only by a build with it). The run in effect is `pin`'s (the count clamped and cut at half `cells_width`, its edge its last column's right). `expect` holds `gap` (the place the gap is before, `0` to the columns' count, or `null` for no gap: the release moves nothing), and with a gap `to` (the move's) and `side` (`pinned` or `scrolled`, `move_columns_pinned`'s side):

- **The region:** left of the run's edge (with a run) the pinned columns, else the scrolled ones; its visible columns are the run's that start in the view, or the scrolled ones overlapping the view right of the edge (a pinned column's left is its own, a scrolled one's less `scroll_x`).
- **The gap** is after the region's last visible column whose center on screen is left of `x`, else before its first: left of the cells, the region's first gap; past its last visible column, its last.
- **None** inside the block, and beside it (before its first place or after its last), except at the run's end (the run in effect's count) with the pointer on the other side of the edge from a block wholly on one side: a pin or an unpin where it is.
- **`to`** is the gap's place where it's left of the block, else the gap's place less the block's length. **`side`** is the pointer's region where `to` is the run's end as `moves`' `count` rule has it (the count clamped, less the block's columns below it), else the side `to` is on. And there's a gap only where that move changes the order or the count (`moves`' rule above).

`reorder_controls_fail` checks that each of `controls` (a `name`, a `why`, and `fails`: the cases it's there to catch, each of which must fail under it in a build that runs it) fails it: `count-kept` (a move across the run's edge leaves the count), `recount` (the count recounted from the columns even when nothing crossed, losing a count past them), `selection-unmoved` (the selection left at its places), `gap-by-left-edge` (the gap after the last column whose left edge, not center, is left of the pointer), `beside-the-block` (a gap beside the block is a gap), `no-edge-gap` (the run's end beside the block refused too). No two cases, moves or gaps, share a name.

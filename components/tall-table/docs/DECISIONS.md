# Decisions: table

Why the table component is built the way it is. Decisions that bind every app are in the root [`docs/DECISIONS.md`](../../../docs/DECISIONS.md).

One bullet per decision, under its area, oldest first: what was chosen, the numbers that chose it, and *[where they came from]*. A decision that replaces another marks the old one *Superseded* rather than deleting it. Decisions moved here from an app keep their dates and sources.

## Table and paging

The bullets up to 2026-10-09 moved here from Tycho's `docs/DECISIONS.md` when the table left it; their sources are Tycho's milestones, and their results files are under `apps/tycho/perf/results/`. "Queries" in them are the delegate's page reads, which in Tycho are DuckDB queries.

- **2026-09-25** · **Own table, not gpui-kit's `DataTable`:** its `uniform_list` positions rows in f32 pixels (4 px steps at 47 M px, 64 px at 25 M rows). It scrolls in f64 rows and owns its scrollbars, wheel, and keys; no column resizing, selection, or sorting. *[M4]*
- **2026-09-25** · Pages of **1024 rows, prefetch 2** (twice ahead while scrolling), 3 queries in flight, **64 MiB** LRU page cache. The sweep didn't separate 256/1024/4096 × 1/2/4 beyond noise; 1024 divides the row groups. *[M4 sweep]*
- **2026-09-25** · Cancelled page queries count against the 3-in-flight limit until DuckDB answers them (it keeps reading a started page); failed pages retry once scrolled away and back; prefetch leans ahead only while the rows move (250 ms). *[M4 code review]*
- **2026-09-25** · A scrollbar drag loads pages only once the pointer rests 80 ms, or on release: a started page read can't be cancelled (DuckDB's worker uses sync XHRs), and a stale one delayed the jump's target (throttled 4.3 → 2.2 s). *[M4]*
- **2026-09-27** · **Visible pages first:** no prefetch page starts while a visible page isn't loaded. DuckDB-Wasm round-robins query slices, so prefetch in flight delayed the visible page (1 GB first rows 2.7 s → 0.8 s with the cache fix; jump to 90% 133 → 92 ms). *[M5]*
- **2026-10-07** · The table reports its first rows with an event (`TableEvent::FirstRows`) and its paging and scrolling through `RowTable::stats`; the workbench decides what the panel shows (the open-questions note). Rows/s and cache hits cover the panel's 2 s window; a cache hit is a drawn frame with every visible row loaded. *[M7 part A]* *Its `TableEvent::FirstRows` was superseded 2026-10-13: the table emits `Filled` and the host marks it (below).*
- **2026-10-07** · **No cell-string cache.** Formatting every visible cell takes 0.075 ms p50 of a 13.1 ms draw on Gaia (0.045 of 11.8 on the asteroids), timed alone in an instrumented build. Gaia's cells hold 2.4× the characters and cost +11% work per draw. *[M7 part B]*
- **2026-10-07** · Pages stay **1024 rows × prefetch 2** on Gaia too. Re-run with work per frame, the sweep still barely separates: steady work 11.9 ms at 256-row pages vs 12.5 at 1024, first rows and jumps within noise, no placeholders in any steady scroll. *[M7 part B `apps/tycho/perf/results/2026-10-08-m7-sweep-gaia.json`]*
- **2026-10-09** · Cell overflow is solved by formatting, not measuring: cells are plain blocks so GPUI's `.truncate()` cuts text at the end; doubles round to fit their column like a spreadsheet's automatic format (scientific only when the whole part doesn't fit); integers are never rounded and are cut in the middle (`1234…789`) if still too wide; one tooltip on the hovered cell shows the exact value. Measuring each column's widest value covers only the pages measured, and a column can't widen under the reader. *[M7 part F, design discussion]*
- **2026-10-16** · **The settle times are `Paging` fields:** `scroll_settle` (250 ms, prefetch leaning ahead) and `drag_settle` (80 ms, a drag's loads), with today's values as defaults. They decide which pages are requested, so the observatory holds them equal on both sides (root `docs/DECISIONS.md`, "Comparison protocol"). Tycho keeps the defaults: +1.2 KB raw after wasm-opt (+0.01%), and its table checks are unchanged (jump to 90% 83.3 ms reference, 2.2 s throttled). *[observatory M2 part A, `apps/tycho/perf/results/2026-10-16-observatory-m2-a.md`]*
- **2026-10-28** · **A shrink forgets every page wholly past the new end,** loaded or being read: a loaded page's bytes freed, a read or `live`'s re-read cancelled and draining, as a short last page is forgotten; `PageCache::set_rows` returns every request to cancel (page order), not one. Then the page the new end falls in is clamped (`live`), and a short old last page forgotten, as before. Grown back, a page past the cut is read anew, never drawn from a read before it; with `live`, a page shrunk to its start is past the end too, so it's read again when the rows return. Rejected: keeping a loaded page past the end with its end clamped to its start, which needs every page's end kept without `live` too, for rows a shrink says are gone. *[hardening part C, `perf/results/2026-10-28-hardening-c.md`]*
- **2026-10-28** · **A closed table cancels nothing again:** `close` runs once (a second call returns), and `set_rows` on a closed table moves the scrollbar and leaves the cache as it was (`close` cancelled every read; one answered since is unknown to the source). Leaving the cache, not only the cancel: forgetting a page whose read `close` cancelled would count that read draining a second time, for good, since a closed table frees no place (found in part C's code review). Rejected: the cache forgetting its reads at `close`, a wider change for the same guarantee. *[hardening part C]*

## Component API

- **2026-10-13** · **Moved out of Tycho, as the repo's first component** (`seiza-table`, from Tycho's `crate/src/table/`). It depends on `gpui-kit` alone. *[Tycho M9 part C]* *Its name was superseded 2026-10-14: `seiza-tall-table`, in `components/tall-table/` (below).*
- **2026-10-13** · **A state entity, an element, and a delegate, as gpui-kit's `DataTable` does it:** `TableState<D: TableDelegate>` holds the scroll position, page cache, and hover, and draws the header and body; `Table<D>` (`RenderOnce`) adds the focus, keys, and border around it. The delegate reads pages (`load_page` returns a request id and a boxed future; `cancel`), and a page answers in the component's own `CellValue`s (`Null`, `Float`, `Float32`, `Text`): floats stay numbers so the table can round them to their column, everything else arrives as text, borrowed where the source has it. The column's `ColumnKind` (boolean, date, timestamp, integer with its widest value's characters, float, decimal, text) replaces Tycho's DuckDB type names. Named per gpui-kit's Coding Guides: a `<Control>State`, a `<Role>Delegate`, private fields with readers, `#[non_exhaustive]` on record-like structs. *[Tycho M9 part C, design]* *Its type names were superseded 2026-10-14: each carries `TallTable` (below).*
- **2026-10-13** · **Settings, not `seiza` calls.** Paging comes in as `Paging` (the host reads its URL overrides); the panel's window, clock, and visibility as `ActivityOptions` (`window_ms`, `clock`, `is_recording`); the Playwright probes as `probe_frames` and `probe_cells`. *[Tycho M9 part C]*
- **2026-10-13** · **Marks are the host's, from events emitted in render.** The first-rows and viewport-filled marks must land right after the frame that shows the rows. The table emits `TableEvent::Filled { first }` while that frame renders; GPUI flushes effects at the end of the update that draws and presents the frame (`App::update` → `finish_update` → `flush_effects`, gpui-pre 0.3.9's `on_request_frame`), so the host's subscriber runs in the same JS task, and its `mark_after_current_task` still lands in that task's microtask checkpoint, before the next task (and so before the browser can render anything else). It's queued after the present now, not during render, so it lands 0.005–0.045 ms later in that checkpoint: checked on the asteroids sample (first rows, the viewport filled, and after End; 5 runs each against the pre-extraction build, every mark before the next task in both). Rejected: an optional `seiza` feature on the component (a dependency on `seiza` the tiers forbid), and a callback hook (the event is the gpui-kit idiom and has the same timing). The probes and scrollbar targets go out the same way, only when they change. *[Tycho M9 part C, gpui-pre 0.3.9 source]*
- **2026-10-14** · **Renamed `tall-table` (`seiza-tall-table`), before the observatory's first comparison.** The types were gpui-kit's names with other meanings: `gpui_kit::component::table` exports `Table` (its simple static table), `TableState<D: TableDelegate>`, `TableDelegate`, and `TableEvent`, so a host using both had to alias. Every type that named the table now carries the prefix: `TallTable`, `TallTableState`, `TallTableDelegate`, `TallTablePage`, `TallTableEvent`, `TallTableStats`, `TallTableProbe`, `TallTableLayout`, and `TallTableColumn` (gpui-kit's table exports a `Column` too, and a host imports both unqualified); its actions are under `seiza_tall_table` and its key context is `TallTable`. `ColumnKind`, `CellValue`, `Paging`, `PageError`, `PageLoad`, `ActivityOptions`, `CellProbe`, and `ColumnProbe` keep their names: gpui-kit has none of them. "Tall" names what every feature level keeps, many rows never held at once, as MATLAB's tall arrays do (rows past memory, read lazily from a datastore). Rejected: `PagedTable` (reads as paginated), `ResidentTable` (the opposite of the design), `LocalTable` (a data path), `DataGrid` (editable), `DataView` (a built-in JS type), `CatalogTable` ("catalog" is the data in Tycho and metadata in DuckDB, Iceberg, and Unity; it names a use case, not the property), `LongTable` ("long" vs "wide" is a data shape: pandas' `melt`). The cost: "tall" also reads as an element's height, which the README's first lines answer. *[design discussion]*

## Fixtures

- **2026-10-17** · **The paging fixture runs the state itself, not `PageCache`.** The settle times and the drag's wait live in `TallTableState` (timers and `Direction`), outside the pure cache, so a cache-only test would leave the two `Paging` fields the observatory added unchecked. The scenarios drive a `TallTableState` in GPUI's test app through its own `scroll_by`, `jump_to`, `scroll_to_fraction`, and drag paths (a child module of `state`), on GPUI's test clock; the delegate answers a read only when the scenario says. Each of ten controls (each `Paging` field moved one way or the other) fails at least one of the seven scenarios. The cost is a dev-dependency on gpui-kit's `test-support`: 29 packages added to `Cargo.lock`, none of the pinned ones moved, and no build changes (dev-dependencies don't reach a wasm build). Rejected: extracting the settle logic into a pure model, a change to the table's internals for a test. *[observatory M2 part C]*
- **2026-10-17** · **Cancels from one decision are a set.** `PageCache::plan` finds stale reads in a hash map, so their order isn't the table's to promise; the fixture writes each run of cancels in page order, and both sides compare it so. Loads keep their order: most urgent first. *[observatory M2 part C]*
- **2026-10-17** · **The cell fixture rounds synthetic values too.** The observatory's data file never fills a float column (its longest float is 8 characters against a budget of 12), so its drawn cells pin only the exact text (`8.0`, `-2082.0`, `NULL`), and a budget a character off passes them. Its `rounding` cases (11, one per branch of `fit_float`, at the pinned budgets) are what the budget controls fail on. They're hand-written; the native test is what checks them. *[observatory M2 part C, `apps/observatory/perf/results/2026-10-17-m2-c.md`]*
- **2026-10-25** · **The flash's fixture lives in `paint.json`** (its `flash` section), beside the colors it reuses, and is checked through the whole path: the native test opens a table over the cases' old values, changes them all in one update, and reads each flash from the cell probe at its elapsed time on GPUI's test clock, in light and dark. Its expectations aren't the table's: `just tall-table paint-fixture` writes each case's place in the ramp and opacity from the rule in TS, as a DOM contender would, and its color from Chromium's mix. Its controls are a test-only `flash::Control` (a fade run backwards, a fall flashed as a rise), as the paging fixture's `live` controls are the cache's. *[M3 part D]*
- **2026-10-25** · **`paint.json`'s text-over-a-fill cases come from the browser's compositing too:** the script fills the row's background (an odd row's stripe over the table's), then the fill's `color-mix`, into a canvas, reads it back, and picks the token by Oklab lightness in its own code, failing on a near tie (within 0.02), where rounding could pick either. The pinned tokens (`tokens`: the text colors, the rows' backgrounds, the bar's two colors) are checked against the theme as the ramps' stops are. Two `marked` cases jump to a row of their own, where the tint is under the fill and over it. Three negative controls, each a test-only `paint::Control`: `below` ignored, the nearer token picked, and the fill's own lightness read without what's under and over it on screen. Only the half-translucent `active` cases in the dark theme (an even row's and the marked row's) tell the last apart: its own lightness (0.74) says dark text, on screen over the dark row it says light. No case tells the marked row's tint over the fill apart on its own: at its alpha (0.2) it flips only fills the script rejects as near ties. The test window widened to 2560 px for the extra columns. *[M2 follow-up]*
- **2026-10-27** · **A randomized test of the paging under every feature, in a hardening of its own before `sort`.** Each of `copy`'s two code reviews found races between `copy` and the paging (a copy's places leaking, a copy and prefetch reading one page at once, an end that freed a place without planning it) that no scenario test had, because each is a timing someone has to think of. A seeded random test reaches the ones nobody does, and a failure replays from its seed. *[M7 part B, planning discussion; between M7 and M8]*
- **2026-10-28** · **The hardening in three parts: research and spec, the test, the fixes.** Reviewing the test (are its invariants and controls real?) is a different review from reviewing a fix to the paging (does it open another race?), and one review over both covers each less well. How much fixing there is depends on what the test finds, and a fix changes shipped code, which needs `size --against` after its review. Rejected: the one session first planned, which would either rush the fixes or stop with the test failing. *[planning discussion]*
- **2026-10-28** · **A shrink by more than a page is fixed in the hardening, not left open.** `PageCache::set_rows` looks only at the old last page, so the pages wholly past a shrink's new end stay loaded and, grown back, draw their old rows as loaded (found in `follow`'s review). The random test shrinks and grows the rows, so it would hit this at once; avoiding it would have kept a known bug out of the test's reach. The fix is a few lines in the cache, plus a base scenario in `paging.json`, which the TanStack contender's test skips (it has no `rows` step). *[planning discussion, `src/pages.rs`; found in M4 part B]*
- **2026-10-28** · **The random test is proptest, driven by hand from a plain `#[test]`, not `#[gpui_kit::property_test]`.** Proptest shrinks a failing run to its few steps that matter, where a seed alone leaves a few hundred to read. GPUI's attribute doesn't compile at the pin: it passes `proptest_path`, which needs `proptest-macro` 0.6, and the lock has proptest 1.11.0 with `proptest-macro` 0.5.0. Done by hand, it's proptest's `TestRunner` over a scheduler seed and the steps, each case on `run_test_once` and a fresh `TestAppContext`, all exported by gpui-kit, so nothing joins the lock. The scheduler seed is drawn per case (`any::<u64>()`), not with `seed_strategy()`, which with `SEED` set gives every case of a run one task order. The steps are a range (`vec(step, 0..=n)`), or the length can't shrink; no failure file (a failure becomes a scenario test). Rejected: bumping proptest in `Cargo.lock` for the attribute; plain seeds (`#[gpui_kit::test(iterations)]`). Research: root `docs/research/tall-table-features.md`, "Hardening". *[hardening part A, spike]*
- **2026-10-28** · **The random test checks the source's truth after every step:** the cache's places equal the source's open reads (a leak and a forgotten read both fail), no page read twice at once but a visible one a copy also reads, nothing read after `close`, the budget, rows drawn of their current era, every copy ending, a copy's text, and no stall once every read is answered; after `close`, only that nothing is read (a closed table's places are never freed). A second read of a page is judged at the step it's sent, and the budget right after a landing, the only time the cache evicts. The source never answers `Cancelled` for a read the table didn't cancel. Values carry a version (`invalidate_rows`; drawn stale is allowed with `live`) and an era (rows cut by `set_rows`; never allowed stale), so a shrink by more than a page fails it. One test-only control per invariant, `copy`'s reviews' leaks and stall among them. *[hardening part A, its code review]*
- **2026-10-28** · **A delegate's request ids are never reused for the table's life,** said in `TallTableDelegate::Request`'s docs. The trait asked only `Copy + PartialEq`, and `copy_answered`'s comment named a source whose ids are a page's first row, but two open reads under one id can't be told apart: `cancel` names neither, and `finished` frees every draining read with that id when one answers. Every source the repo has is a counter (DuckDB's `RequestId`, the bare host's). Rejected: repeats supported, which asks the table to tell apart reads a cancel can't name, for a source nobody has; and ids unique only among the reads in flight, a looser rule nothing needs. *[hardening part A, its code review, planning discussion]*
- **2026-10-28** · *Superseded (2026-10-28, below: 48 and 16 cases).* **Counted in steps: 16 cases of up to 300 in the all-on run, 8 in each other run.** A step costs ~8 ms in a native debug build (the table's work more than its drawing); the all-on run's 39 s wall is set by `selection_controls_fail` (33.5 s), so ~25 s beside it adds nothing. A soak runs a release build with debug assertions and overflow checks on, ~1.4 ms a step: 4 `SEED`s × 500 cases in ~7 min once built (~10 min to build). *[hardening part A, spike]*
- **2026-10-28** · **48 cases of up to 300 steps in the all-on run, 16 in the others.** A step costs ~2.5 ms in the debug build, not the spike's 8 (frames are steps of their own here; the spike drew every step). With the same draw, 16 cases catch six of the nine controls at `SEED` 0 and 43 of 63 control runs across `SEED`s 0–6; 48 catch all nine at `SEED` 0 and 57 of 63. A soak case costs ~0.07 s in the release build: 4 `SEED`s × 500 in ~2.5 min once built. The cost: the all-on run's wall from 41–42 s to 46–47 s (eight cores, beside `selection_controls_fail`), against the spec's "nothing". *[hardening part B, `perf/results/2026-10-28-hardening-b.md`]*
- **2026-10-28** · **"Nothing stalls" and "every copy ends" hold whenever no read is open and no drag moves, not only after a drain.** The drain moves the clock past the settles, and the scroll's settle timer then planned the read that a missed plan left: the end-without-a-plan control passed every case. With no read open and no drag moving, nothing has a reason to wait; a timer that would plan later is a missed plan's latency, not an excuse. *[hardening part B]*
- **2026-10-28** · **A closed table takes eight more steps, then a drain and a new table over the source,** as a host replaces a table. The spec's "the case keeps stepping" cost each close the rest of its case (only invariant 3 holds after it), so closes had to be rare, and none came while a copy's reads were out. With a new table after it, `close` is about one step in fifty. *[hardening part B]*
- **2026-10-28** · **An exclusion is whichever leaves out the bug alone: a step generated, a step run, or a pair checked.** A shrink past a page is a step of its own (`ShrinkPast`, not generated); a closed table's cancels come from the rows' steps after `close` (skipped when they run: whether they follow a close is the case's); a copy's read beside the cache's read of a page that grew follows from no step alone (the pair left out of invariant 2's check). Each has an `#[ignore]`d scenario test, which runs without exclusions. *[hardening part B]*
- **2026-10-28** · **A read is judged as it went out:** the source records the reads open when it sends one (how many, and which of its page), and the cache logs what each read was started for (a read, a re-read, a copy's; test-only), so invariants 1's limit and 2 hold for a read answered when sent, which is no longer open, nor in the cache's books, when the step's checks run. The grown-page exclusion is each finding's order: the cache's re-read after the copy's read, or its read before the copy's holding fewer rows; wider, it excused copy and prefetch on one page. *[hardening part B, its code review]*
- **2026-10-28** · **The crate's own test delegates count their ids too,** as the contract says (above: "Every source the repo has is a counter" held for the sources, not the tests): the selection fixture's ids were a page's first row, and with `copy` it copies over them, a cache read and a copy read of one page sharing an id; the resize fixture's were the page, the paint fixture's `()`. *[hardening part B, its code review]*
- **2026-10-28** · **The budget's check runs after any step a page landed in, a landing being a page new to the cache** (each carries the read it answered), by the pages wanted before the step or after it. Skipped only while following with reads answered when sent: re-reads then land in plans the pin moves between. Checked only after answers, the no-eviction control passed most cases. *[hardening part B]*
- **2026-10-28** · **The cases are drawn toward the states the controls need, inside the spec's ranges:** half the tables fit the viewport (at most its 20 rows: their end in view); half of growths fill the last page (a full last page is what a shrink within it keeps); `max_in_flight` and the budget skewed low; selections far from the view three times in four; one failed answer in eight; a drain answers oldest or newest first. Without them a full last page came up by chance (one row count in `page_rows`), and copies had reads out in ~4% of steps. Two controls are caught as what they cause: an end without a plan by the copy it leaves waiting (6) as often as by the rows (8); a failed read stops its copy's turns rather than keeping the answered read, which `close` then cancelled again (caught at 1). *[hardening part B]*
- **2026-10-28** · **The exclusions go with their bugs, and the mechanism with them:** the `Exclusion` list, its argument, and its checks are removed, the five scenario tests kept as regressions. The next bug the test finds adds one back as part B's did (above). `ShrinkPast` is generated at weight 4 (of 427 in the all-on run): at 8, the copy-and-prefetch control was caught at 3 of 7 `SEED`s (a shrink often cuts the copy it needs), at 4 at 5 of 7, part B's rate, `SEED` 0 among them. *[hardening part C]*
- **2026-10-28** · **The shrink's old rule is a control of the cache in every test build** (`pages::Control` widened from `live`'s; `KeepPastShrink`): in `paging.json` a control of a new `cache` kind (`keep-past-end`), which fails the new scenario, a shrink past a page grown back; in the random test it fails at invariant 5 (old rows drawn) or 8 (with `live`, a page shrunk to its start never read again), the bug's two symptoms. The TanStack contender's test skips `cache` controls (a fault in the table's own code) as it skips the scenario (a `rows` step). *[hardening part C]*
- **2026-10-28** · **A change to the paging is soaked before its code review** (`CLAUDE.md`, rule 5), and a milestone that changed it closes on a soak of its final build. The soak's 2,000 cases found a bug the test's 48 hadn't (part B's fourth), and it costs ~4 min with its build, so it's a step of the change, not a run to plan around; before the review, so the review reads code the soak has passed. *[after the hardening's close, planning discussion]*
- **2026-10-28** · **The copy-and-prefetch control stays caught at 5 of 7 `SEED`s, a known limit.** Tried: half the cases drawn from a mix without `ShrinkPast` (the other half at weight 8), so shrinks couldn't cut the copies that control needs. It caught 65 of 70 control runs across `SEED`s 0–6 against one mix's 68, the weak control still missing one `SEED` and three others now missing one each: the cases' draw moved, nothing gained. `SEED` 0, which `just tall-table test` runs, catches it, and the soak's 2,000 cases reach it. Rejected: the two mixes; a mix weighted for each control, which tunes the draw to the controls' seeds. *[after the hardening's close]*
- **2026-10-29** · **The random test's `pin` steps are placed from each case's scheduler seed, never drawn.** As a weighted step (weight 4), the draw of every later case moved and two of the all-on run's controls (`KeepOnReread`, copy-and-prefetch's `IgnoreLoading`) passed all 48 cases at `SEED` 0; drawn after a case's other steps, the stream still moved and two others (`HoldingWithoutEnd`, `EndWithoutPlan`) passed: the controls are counted over a fixed draw, and any new draw reshuffles it. So up to eight `Step::Pin` are inserted among the drawn steps by a SplitMix64 of the seed already drawn (`with_pins`): every case's draw is the one without the feature, every control fails as before, and the same seed and steps place them again. Only the runner inserts them (`run`, never `run_case`), so a written scenario runs exactly its steps, and a failure prints the case as run, its pin steps among them, so its step index and a scenario copied from it agree; shrinking moves the pins as steps drop out, since their places follow the steps' count. Rejected: retuning the weights to the controls' seeds (rejected before, 2026-10-28). *[M9 part B, revised after its code review]*
- **2026-11-04** · **The smoke check keeps reference screens per commit** (`--screens save`, then `--screens <commit>`), beside the base build's first screens that `density`'s control reads. A change meant to keep the pixels (the cells' text from one element) is checked against the commit before it: each build's screens (each paint style, the dense default, the pin, a selection, two narrowed columns), first and after a wheel to a fractional row top and `scrollX`, saved under the commit (a tree with source changes under the commit and their hash, which no commit names), and a later tree's compared pixel for pixel, its landing checked first. Saving in the reference mode only, not every smoke run: a save is ~15 s a build and three browsers, and a commit's screens are wanted only when a change says its pixels hold. *[M11 part B, `perf/results/2026-11-04-m11-b-screens.md`]*

## Features

- **2026-10-23** · **The features are `DataTable`'s, each a Cargo feature, listed in `PLAN.md`; TanStack Table's extras are candidates there, not plans.** The inventory was read from gpui-component 0.7.3's `src/table/` (the pin). `select` is one feature for row, column, and cell selection, the host picking the mode at run time as `DataTable` does: a feature per mode multiplies the `cfg`s for little saved. *[planning discussion]*
- **2026-10-23** · **A feature's own cost is measured in a bare host crate of the component's (`host/`), not in an app.** A cost read in Tycho mixes in Tycho's code, and the observatory's GPUI contender can't carry code for a feature its DOM side lacks ("the same scope"). The host switches each feature on at run time, since a feature compiled but unused can be stripped and read as free, and answers pages from memory, so the bytes and frame work are the table's alone. *[planning discussion]*
- **2026-10-23** · **The bare host first, on its own, then `custom-cells`; each feature's research opens its own milestone.** The draft put a study of every feature's cost before any was built, sorting's data cost among them, which would have held back `custom-cells`, a feature that never reaches the data, while the observatory's wide sheet waits on it. The host's first milestone records the base's bytes and frame work, in the observatory's shape and a 500-column one, so every feature reads its cost against one baseline. *[planning discussion, M1–M2]*
- **2026-10-23** · **The order: the scenarios' features first** (`custom-cells` → `live` → `follow`), in the observatory's scenario order, **then Tycho's** (`resize` → `select` → `copy` → `sort` → `pin` → `reorder` → `context-menu` → `group-headers`).

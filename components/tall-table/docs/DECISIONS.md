# Decisions: table

Why the table component is built the way it is. Decisions that bind every app are in the root [`docs/DECISIONS.md`](../../../docs/DECISIONS.md).

One bullet per decision, under its area, oldest first: what was chosen, the numbers that chose it, and *[where they came from]*. A decision that replaces another marks the old one *Superseded* rather than deleting it. Decisions moved here from an app keep their dates and sources.

## Table and paging

The bullets up to 2026-10-09 moved here from Tycho's `docs/DECISIONS.md` when the table left it; their sources are Tycho's milestones, and their results files are under `apps/tycho/perf/results/`. "Queries" in them are the delegate's page reads, which in Tycho are DuckDB queries.

- **2026-09-25** · **Own table, not gpui-kit's `DataTable`:** its `uniform_list` positions rows in f32 pixels (4 px steps at 47 M px, 64 px at 25 M rows). It scrolls in f64 rows and owns its scrollbars, wheel, and keys; no column resizing, selection, or sorting. *[M4]*
- **2026-09-25** · Pages of **1024 rows, prefetch 2** (twice ahead while scrolling), 3 queries in flight, **64 MiB** LRU page cache. The sweep didn't separate 256/1024/4096 × 1/2/4 beyond noise; 1024 divides the row groups. *[M4 sweep]*
- **2026-09-25** · Cancelled page queries count against the 3-in-flight limit until DuckDB answers them (it keeps reading a started page); failed pages retry once scrolled away and back; prefetch leans ahead only while the rows move (250 ms). *[M4 code review]*
- **2026-09-25** · A scrollbar drag loads pages only once the pointer rests 80 ms, or on release: a started page read can't be cancelled (DuckDB's worker uses sync XHRs), and a stale one delayed the jump's target (throttled 4.3 → 2.2 s). *[M4]*
- **2026-09-27** · **Visible pages first:** no prefetch page starts while a visible page isn't loaded. DuckDB-Wasm round-robins query slices, so prefetch in flight delayed the visible page (1 GB first rows 2.7 s → 0.8 s with the cache fix; jump to 90% 133 → 92 ms). *[M5]*
- **2026-10-07** · The table reports its first rows with an event (`TableEvent::FirstRows`) and its paging and scrolling through `RowTable::stats`; the workbench decides what the panel shows (the open-questions note). Rows/s and cache hits cover the panel's 2 s window; a cache hit is a drawn frame with every visible row loaded. *[M7 part A]* *Its `TableEvent::FirstRows` was superseded 2026-10-13: the table emits `Filled` and the host marks it (below).*
- **2026-10-07** · **No cell-string cache.** Formatting every visible cell takes 0.075 ms p50 of a 13.1 ms draw on Gaia (0.045 of 11.8 on the asteroids), timed alone in an instrumented build. Gaia's cells hold 2.4× the characters and cost +11% work per draw. *[M7 part B]*
- **2026-10-07** · Pages stay **1024 rows × prefetch 2** on Gaia too. Re-run with work per frame, the sweep still barely separates: steady work 11.9 ms at 256-row pages vs 12.5 at 1024, first rows and jumps within noise, no placeholders in any steady scroll. *[M7 part B `apps/tycho/perf/results/2026-10-08-m7-sweep-gaia.json`]*
- **2026-10-09** · Cell overflow is solved by formatting, not measuring: cells are plain blocks so GPUI's `.truncate()` cuts text at the end; doubles round to fit their column like a spreadsheet's automatic format (scientific only when the whole part doesn't fit); integers are never rounded and are cut in the middle (`1234…789`) if still too wide; one tooltip on the hovered cell shows the exact value. Measuring each column's widest value covers only the pages measured, and a column can't widen under the reader. *[M7 part F, design discussion]*
- **2026-10-16** · **The settle times are `Paging` fields:** `scroll_settle` (250 ms, prefetch leaning ahead) and `drag_settle` (80 ms, a drag's loads), with today's values as defaults. They decide which pages are requested, so the observatory holds them equal on both sides (root `docs/DECISIONS.md`, "Comparison protocol"). Tycho keeps the defaults: +1.2 KB raw after wasm-opt (+0.01%), and its table checks are unchanged (jump to 90% 83.3 ms reference, 2.2 s throttled). *[observatory M2 part A, `apps/tycho/perf/results/2026-10-16-observatory-m2-a.md`]*

## Component API

- **2026-10-13** · **Moved out of Tycho, as the repo's first component** (`seiza-table`, from Tycho's `crate/src/table/`). It depends on `gpui-kit` alone. *[Tycho M9 part C]* *Its name was superseded 2026-10-14: `seiza-tall-table`, in `components/tall-table/` (below).*
- **2026-10-13** · **A state entity, an element, and a delegate, as gpui-kit's `DataTable` does it:** `TableState<D: TableDelegate>` holds the scroll position, page cache, and hover, and draws the header and body; `Table<D>` (`RenderOnce`) adds the focus, keys, and border around it. The delegate reads pages (`load_page` returns a request id and a boxed future; `cancel`), and a page answers in the component's own `CellValue`s (`Null`, `Float`, `Float32`, `Text`): floats stay numbers so the table can round them to their column, everything else arrives as text, borrowed where the source has it. The column's `ColumnKind` (boolean, date, timestamp, integer with its widest value's characters, float, decimal, text) replaces Tycho's DuckDB type names. Named per gpui-kit's Coding Guides: a `<Control>State`, a `<Role>Delegate`, private fields with readers, `#[non_exhaustive]` on record-like structs. *[Tycho M9 part C, design]* *Its type names were superseded 2026-10-14: each carries `TallTable` (below).*
- **2026-10-13** · **Settings, not `seiza` calls.** Paging comes in as `Paging` (the host reads its URL overrides); the panel's window, clock, and visibility as `ActivityOptions` (`window_ms`, `clock`, `is_recording`); the Playwright probes as `probe_frames` and `probe_cells`. *[Tycho M9 part C]*
- **2026-10-13** · **Marks are the host's, from events emitted in render.** The first-rows and viewport-filled marks must land right after the frame that shows the rows. The table emits `TableEvent::Filled { first }` while that frame renders; GPUI flushes effects at the end of the update that draws and presents the frame (`App::update` → `finish_update` → `flush_effects`, gpui-pre 0.3.9's `on_request_frame`), so the host's subscriber runs in the same JS task, and its `mark_after_current_task` still lands in that task's microtask checkpoint, before the next task (and so before the browser can render anything else). It's queued after the present now, not during render, so it lands 0.005–0.045 ms later in that checkpoint: checked on the asteroids sample (first rows, the viewport filled, and after End; 5 runs each against the pre-extraction build, every mark before the next task in both). Rejected: an optional `seiza` feature on the component (a dependency on `seiza` the tiers forbid), and a callback hook (the event is the gpui-kit idiom and has the same timing). The probes and scrollbar targets go out the same way, only when they change. *[Tycho M9 part C, gpui-pre 0.3.9 source]*
- **2026-10-14** · **Renamed `tall-table` (`seiza-tall-table`), before the observatory's first comparison.** The types were gpui-kit's names with other meanings: `gpui_kit::component::table` exports `Table` (its simple static table), `TableState<D: TableDelegate>`, `TableDelegate`, and `TableEvent`, so a host using both had to alias. Every type that named the table now carries the prefix: `TallTable`, `TallTableState`, `TallTableDelegate`, `TallTablePage`, `TallTableEvent`, `TallTableStats`, `TallTableProbe`, `TallTableLayout`, and `TallTableColumn` (gpui-kit's table exports a `Column` too, and a host imports both unqualified); its actions are under `seiza_tall_table` and its key context is `TallTable`. `ColumnKind`, `CellValue`, `Paging`, `PageError`, `PageLoad`, `ActivityOptions`, `CellProbe`, and `ColumnProbe` keep their names: gpui-kit has none of them. "Tall" names what every feature level keeps, many rows never held at once, as MATLAB's tall arrays do (rows past memory, read lazily from a datastore). Rejected: `PagedTable` (reads as paginated), `ResidentTable` (the opposite of the design), `LocalTable` (a data path), `DataGrid` (editable), `DataView` (a built-in JS type), `CatalogTable` ("catalog" is the data in Tycho and metadata in DuckDB, Iceberg, and Unity; it names a use case, not the property), `LongTable` ("long" vs "wide" is a data shape: pandas' `melt`). The cost: "tall" also reads as an element's height, which the README's first lines answer. *[design discussion]*

## Fixtures

- **2026-10-17** · **The paging fixture runs the state itself, not `PageCache`.** The settle times and the drag's wait live in `TallTableState` (timers and `Direction`), outside the pure cache, so a cache-only test would leave the two `Paging` fields the observatory added unchecked. The scenarios drive a `TallTableState` in GPUI's test app through its own `scroll_by`, `jump_to`, `scroll_to_fraction`, and drag paths (a child module of `state`), on GPUI's test clock; the delegate answers a read only when the scenario says. Each of ten controls (each `Paging` field moved one way or the other) fails at least one of the seven scenarios. The cost is a dev-dependency on gpui-kit's `test-support`: 29 packages added to `Cargo.lock`, none of the pinned ones moved, and no build changes (dev-dependencies don't reach a wasm build). Rejected: extracting the settle logic into a pure model, a change to the table's internals for a test. *[observatory M2 part C]*
- **2026-10-17** · **Cancels from one decision are a set.** `PageCache::plan` finds stale reads in a hash map, so their order isn't the table's to promise; the fixture writes each run of cancels in page order, and both sides compare it so. Loads keep their order: most urgent first. *[observatory M2 part C]*
- **2026-10-17** · **The cell fixture rounds synthetic values too.** The observatory's data file never fills a float column (its longest float is 8 characters against a budget of 12), so its drawn cells pin only the exact text (`8.0`, `-2082.0`, `NULL`), and a budget a character off passes them. Its `rounding` cases (11, one per branch of `fit_float`, at the pinned budgets) are what the budget controls fail on. They're hand-written; the native test is what checks them. *[observatory M2 part C, `apps/observatory/perf/results/2026-10-17-m2-c.md`]*

## Features

- **2026-10-23** · **The features are `DataTable`'s, each a Cargo feature, listed in `PLAN.md`; TanStack Table's extras are candidates there, not plans.** The inventory was read from gpui-component 0.7.3's `src/table/` (the pin). `select` is one feature for row, column, and cell selection, the host picking the mode at run time as `DataTable` does: a feature per mode multiplies the `cfg`s for little saved. *[planning discussion]*
- **2026-10-23** · **A feature's own cost is measured in a bare host crate of the component's (`host/`), not in an app.** A cost read in Tycho mixes in Tycho's code, and the observatory's GPUI contender can't carry code for a feature its DOM side lacks ("the same scope"). The host switches each feature on at run time, since a feature compiled but unused can be stripped and read as free, and answers pages from memory, so the bytes and frame work are the table's alone. *[planning discussion]*
- **2026-10-23** · **The bare host first, on its own, then `custom-cells`; each feature's research opens its own milestone.** The draft put a study of every feature's cost before any was built, sorting's data cost among them, which would have held back `custom-cells`, a feature that never reaches the data, while the observatory's wide sheet waits on it. The host's first milestone records the base's bytes and frame work, in the observatory's shape and a 500-column one, so every feature reads its cost against one baseline. *[planning discussion, M1–M2]*
- **2026-10-23** · **The order: the scenarios' features first** (`custom-cells` → `live` → `follow`), in the observatory's scenario order, **then Tycho's** (`resize` → `select` → `copy` → `sort` → `pin` → `reorder` → `context-menu` → `group-headers`). The three are small, leave the paging alone, and serve Tycho too (a growing CSV, a refreshed query). Rejected: Tycho's core first, which would have finished the wide sheet's later steps (`resize`, a range copied) before market watch could start. *[planning discussion]*
- **2026-10-23** · **`custom-cells` is a declarative paint** that a page answers with its values (a fill, a bar, a text color), not a host-built subtree per cell as `DataTable`'s `render_td` is. The table already draws an element per visible cell; the paint adds a fill, a bar, and a color to it (or quads in the body's pass), where a hook would run a host's closure and build its subtree for each of the wide sheet's 1–2 k cells a frame, which the table can neither bound nor pin. A fixture can pin a paint (colors, a bar's pixels) for a DOM contender to match. Its fields, the colors' home (the page, or a ramp per column, which a theme switch wouldn't re-read), the bar's origin, and how it's drawn are left to its milestone, to settle with numbers. *[planning discussion, M2]*
- **2026-10-23** · **Stripes, row lines, and the row-number gutter are the base's:** `render_body` already shades odd rows (`table_even`), draws a line under each (`table_row_border`), and labels each row in a gutter (`gutter_cells`, the row index + 1), so none is a setting or a feature, and `DataTable`'s `row_header` leaves the list. *[planning discussion, code review, `src/state.rs`]*
- **2026-10-23** · **The bare host's shape:** it bootstraps through `seiza` without the panel, as the observatory's GPUI contender does; `host/crate/` (`tall-table-host`) and `host/web/`, scripts in `perf/`, recipes in the component's own `justfile` (`just tall-table <recipe>`); its delegate answers from memory in two shapes (in `PLAN.md`, the spec that pins them), with an optional page delay; a build with every feature on is recorded too, once there are two. *[planning discussion]*
- **2026-10-23** · **One milestone per feature, numbered in the order now, and the features built in a run before the apps adopt them.** A milestone's spec and checks are written when the one before it closes, after its own research. Building the run first keeps one session's context on the component and lets each app adopt features in batches, against its budgets, once they exist. *[planning discussion, M1–M12]*
- **2026-10-23** · **No TanStack candidate joins the list for now;** the Cargo names stay drafts until each feature's milestone. *[planning discussion]*
- **2026-10-23** · **The component measures only itself, and every feature in the order is built.** Each feature is there because an app needs it, so its cost (wasm and frame work, in the bare host) tells a host what turning it on costs; it doesn't decide whether it's built, and research settles how. The table doesn't measure what a feature does to an app: each feature is off by default, its milestone checks the base build is unchanged with it off and that the native tests and fixtures pass with it off and on, and an app measures a feature against its own budgets when it adopts it. A cost an app can't carry comes back here as an optimization. A change to the base still records its effect on each app (root `CLAUDE.md`, rule 1). Data a source reads to answer a feature (a sort's `ORDER BY`) is the source's cost, the engine's. Superseded: the draft's research that decided which features to build, and the table measuring a feature against the apps' budgets. *[planning discussion]*
- **2026-10-24** · **`custom-cells`' paint is three 0..1 values a page answers (a fill, a bar's end, a text color), and each column holds what turns them into pixels:** a fill ramp and a text ramp, whose stops are theme tokens resolved each frame and mixed in Oklab, and a bar's zero point and color. Settles the spec's first two open points. A page holding colors would keep a theme's colors in the 64 MiB cache after a switch, and a page has no `cx` to read the theme; a ramp resolves on the frame the theme changes, as the table's other colors do. `paint` is a method like `value`, so a page stores nothing new. The ramp's mix looked a small share of a heat cell's cost (a hint only, from a run that failed the spread gate), too little to cache. A bar from a zero point (0 by default, the left edge) costs a subtraction over a left-edge bar, and the wide sheet's values are signed. Text color as a ramp value, not a named tone, so all three fields work one way and a fixture pins them alike. Research: root `docs/research/tall-table-features.md`, "`custom-cells`". *[M2 part A, `perf/results/2026-10-24-m2-spike.md`]*
- **2026-10-24** · **A fill and a bar both draw as quads, in one `canvas` under the cells layer, the fill first and the bar over it.** The spike's A/B (the wide shape, every float cell painted, reference, interleaved, 8 runs each), added work per frame over plain text, p50: a bar +0.74 ms in the steady scroll and +0.81 sideways as a quad, against +1.14 / +1.29 as a child element (spread 2.4–4.2%, inside the 6% gate): a child element is a layout node per cell, a quad is placed by the table's own arithmetic. A fill +0.56 / +0.78 as a quad against +0.62 / +0.60 on the cell's element, a comparison that failed the gate (7.7% and 11.9%), so no winner. The order decides it: a quad paints before the cells, so a fill on the cell's element would cover the bar in a cell with both. The two drawings' screenshots were byte-identical. Superseded the same day: a fill on the cell's element, read from the interquartile range instead of the gate's (max − min) / median, which also missed the covered bar (code review). *[M2 part A, `perf/results/2026-10-24-m2-spike.md`]*
- **2026-10-24** · **The API as built, two changes from part A's draft:** a `Stop` is `fn(&Theme) -> Hsla`, not `fn(&ThemeColor) -> Hsla`, so a stop can read the theme's `tokens` too (`ThemeColor` is what `Theme` derefs to, so `|theme| theme.chart_1` reads the same); and `Ramp::new` takes a slice, `&[Stop]`, not an iterator, because closures coerce to `fn` pointers only where the expected type is known: `Ramp::new([|t| t.background, …])` didn't infer. `Bar` gained `Bar::new(color)` and `.zero(z)` beside its public fields. `CellPaint`, `Ramp`, and `Bar` aren't `#[non_exhaustive]`: a host builds `CellPaint { fill, ..Default::default() }`, which that attribute forbids outside the crate. *[M2 part B]*
- **2026-10-24** · **A fill and a bar leave the row's line clear and a bar is inset:** both are `row height − 1` px tall, so the line under each row (drawn by the row's background, under the cells) still separates painted rows; a bar sits 6 px from the row's top and from that line. Pinned in `fixtures/paint.json`'s `cell`. *[M2 part B]*
- **2026-10-24** · **The jump's highlight is drawn over a filled cell, edged, only by `custom-cells`; the base's drawing is unchanged.** The base tints the jumped-to row under the cells (`table_active`, `#bfdbfe33` in the light theme), so a fill covered it. Drawn over the fill as the same tint, it vanished on a blue ramp (screenshot of a jump onto heat cells, the wide shape); with a 1 px top and bottom edge in `table_active_border` it shows on every fill. Only filled cells get it, in the same quad pass, so the base build and its frames are untouched. Rejected: keeping it under (the jump lands on a row nobody can find), and moving the base's highlight over the cells for every host (a change to the base for a feature's sake). *[M2 part B, `perf/results/2026-10-24-m2.md`, `perf/results/2026-10-24-m2-jump.png`]*
- **2026-10-24** · **`paint.json`'s colors come from Chromium, not from the table.** `just tall-table paint-fixture` fills each case's `color-mix(in oklab, …)` into a canvas and reads it back, so the native test checks the table's Oklab mix against the browser's, which a DOM contender would use; the stops are pinned by hand and checked against the theme. The table matched 34 of 36 colors exactly and 2 within one step. The cell probe reports colors as handed to GPUI, rounded to 8 bits, and the smoke check samples a drawn fill on screen in each browser against it. *[M2 part B]*
- **2026-10-24** · **"The base is unchanged" is read before brotli, with both builds at one path.** The spec asked for the base within 0.1 KiB brotli of the milestone's parent. Brotli can't hold that: the parent commit built twice in worktrees at two random paths came out 2,677.7 and 2,677.2 KiB, and the parent against the working tree, both at one fixed path, 2,676.9 against 2,678.1 KiB (2,679.1 in the final run), with the wasm the same size before brotli (9,645.3 KiB), the same 22,236 functions, the same data size, and 2 instructions more (`wasm-opt --metrics`). The build embeds its checkout's path in panic locations (the repo build is 1.4 KiB larger before brotli than a worktree's), and a few shifted bytes move brotli by up to ~2 KiB. So `just tall-table size --against <commit>` builds both bases in turn at one worktree path and gates on the size after wasm-opt (0.1 KiB), recording brotli; the symbol check is the other half. *[M2 part B, `perf/results/2026-10-24-m2-size.json`]*
- **2026-10-24** · **`live` re-reads; it doesn't patch.** A host names the rows that changed (`invalidate_rows`), and the table reads their pages again through the delegate's own `load_page`: no new delegate call. A page is the delegate's opaque type, so patching would need a mutation API every source writes (the DuckDB source's Arrow pages are immutable), and one call serves first reads and re-reads alike. A source holding values in memory answers a re-read from memory, at the cost of a spawn's round trip and a read slot per update; the build measures update → pixel with one, and a push path (`replace_page`) can be added later without breaking the delegate if it's needed: not rejected, not built. A host whose pages share storage it mutates can already call `cx.notify()` on the table (no per-cell cache), without a flash. Research: root `docs/research/tall-table-features.md`, "`live`". *[M3 part A]*
- **2026-10-24** · **A stale page draws until its fresh one lands, with one read per page in flight, never cancelled for being stale;** a page invalidated during its re-read is read once more after it. Cancel-and-restart would never land under updates faster than a read (at 50k updates a second, market watch's every row changes every frame), and DuckDB-Wasm keeps reading a cancelled page anyway. A stale visible page isn't missing, so it doesn't hold prefetch back, but it's re-read before prefetch (`wanted`'s order); a page with nothing to show goes before it, and re-reads hold at most `max_in_flight − 1` slots together, so constant updates can't keep a newly visible page waiting. A stale page that leaves `wanted` is dropped, not kept stale. A page invalidated during its first read is stale when it lands; an invalidation's loads wait out a scrollbar drag as a scroll's do (`drag_settle`); a failed re-read keeps the stale page drawn, read again at the next invalidation or `retry_failed`. The base's `set_rows` (which forgets a short last page) is unchanged. *[M3 part A]*
- **2026-10-24** · **Each invalidation returns a generation, and the first frame drawing a re-read page emits `Refreshed { rows, generation }` from render, if its rows are visible then,** so a host marks update → pixel as `Filled` marks first rows. A row range alone would mis-time an update that landed while a read of its page was out. *[M3 part A]*
- **2026-10-24** · **The flash is the table's, with both `live` and `custom-cells`, turned on per column (`flash(ramp, duration)`):** when a re-read lands, the table compares the old and new values in the invalidated rows of flashing columns (off the frame), flashes a float's rise at the ramp's 1, its fall at 0, and any other change at 0.5, fades it by opacity to nothing over the duration as a fill quad over the page's fill, keeps live flashes in a map removed as each ends, and asks for animation frames only while a flash is on screen; under `App::reduce_motion` it holds, without a fade. Rejected: the host naming changed cells (a wider API, and each DOM contender compares in its own cache); fading toward the ramp's middle, which leaves that color painted after the flash; a reduced-motion setting of the table's own (gpui's `App::reduce_motion` is the one switch, which the host sets). Rows invalidated during a read wait for the next read's comparison; two NaNs compare equal; a held flash under reduced motion ends on a timer, not frames. No spike: the quads cost what `custom-cells`' fills do, the comparison is bounded and off the frame, and the continuous frames are measured at each rate in the bare host. *[M3 part A]*

- **2026-10-24** · **Re-reads, as built:** a plan fetches the visible pages with nothing to show, then the visible stale pages, then the rest of `wanted` in its order, missing and stale pages alike (a stale prefetch page is read again as prefetch is, so only once no visible page is missing). The re-reads' limit is `max(max_in_flight − 1, 1)`, so a table reading one page at a time still re-reads. A page being read again isn't evicted (its read counts in flight; `plan` cancels it if the page leaves `wanted`), and with a short last page `set_rows` drops its re-read with it. Invalidating rows whose page isn't loaded or loading changes nothing and emits no `Refreshed`: their first read reads them as they are. Each rule is a native test and, where page requests show it, a `paging.json` scenario. *[M3 part B]*
- **2026-10-24** · **An invalidation during a drag loads at once only if the pointer has rested since its last move;** otherwise the drag's pending settle loads it with everything else. Likewise a read that lands then (one nearly always is out under a feed) plans nothing until the settle: in the base it plans at once, a difference only `live` makes, since only a feed keeps reads landing through a drag. Restarting the settle, as a move does, would let a feed invalidating every frame hold off a resting drag's loads for good. *[M3 part B]*
- **2026-10-24** · **`paging.json`'s `live` controls are behaviors, not paging fields** (`reread-unwanted`, `restart-stale`): the cache carries a test-only `Control` that gets re-reads wrong one way each, and a DOM contender with `live` would build the same switches. Scenarios name the features they need (`features`), and a build without them, the TanStack contender's today, runs the rest. *[M3 part B]*
- **2026-10-24** · **`TallTableState::visible_rows()` is in the base:** a host's feed picks visible rows with it, and a reader of the scroll model belongs with `rows()`. A host that doesn't call it links none of it (the base build is unchanged). *[M3 part B]*
- **2026-10-24** · *Superseded 2026-10-25 by "A re-read ready when sent lands in that turn", below.* **A push path is needed: invalidate → refreshed frame read 22.5 ms at 1k updates/s, over a frame.** The bare host's source answers at once, yet an isolated update (10 a second, no read out) took 18.7 ms: each GPUI spawn on the web is a `setTimeout(0)` (gpui-pre-web 0.3.9), so the page lands after the next frame. `replace_page` is specced as part C, with the alternative of polling a read that's ready when sent; part C keeps whichever lands within a frame. *[M3 part B]*
- **2026-10-25** · **A re-read ready when sent lands in that turn; there's no `replace_page`.** With `live`, the table polls a re-read's load once, with a no-op waker, as it sends it: an answer lands then (`page_done` once the plan's reads have all started), and a pending one is spawned as before. Measured from the batch's start in the bare host, 1k updates/s, reference, median of 10: 22.55 ms p50 before (p95 29.1), 7.16 ms with it (p95 22.4, spread 1.8%); a spike of `replace_page` (the host building each changed page and handing it over) read the same, 7.38 ms (p95 23.2), from the same build. Kept because it adds no API and covers the push's case: a host with the page in hand answers `load_page` with a ready future. Only re-reads are polled, so the base and a first read's timing are unchanged. Not built: `replace_page` (it would also need a superseded read's answer dropped, and gains nothing measured). It doesn't help a source that answers on a later turn (the DuckDB source, behind its worker), whose latency is its read's. The p95 over a frame is a batch landing just after a frame, which waits for the next; both paths showed it. *[M3 part C, `perf/results/2026-10-25-m3-c.md`]*
- **2026-10-25** · **Only a page lands in the turn that asked; a failure or a refusal still lands from a task.** A re-read failing at once with `read_failure` would emit `ReadFailed` inside the update, and a host retrying on it (`retry_failed`) would loop there; from a task, it's one round a turn, as before. A re-read the source answers `Cancelled` without the table cancelling it frees its place and keeps the page drawn, read again at its rows' next invalidation: kept reading, it held a re-read's place for good; marked stale again, a source that keeps refusing was asked every turn. The ready pages of a plan land together, then one more plan reads what's stale again (not a plan per page), and neither that plan nor an invalidation's deferred one runs while a drag is moving. *[M3 part C, after the code review]*
- **2026-10-25** · **An invalidation's reads are planned once, at the end of the update that made it** (`App::defer`, one pending at a time), not in `invalidate_rows` itself. A feed invalidates row by row (`invalidate_rows(row..row + 1)`), and with re-reads that land at once, each call read the page again: about 16 page reads a batch at 1k updates/s, where one does. Deferred work runs when the update's effects flush, in the same task, so no executor hop comes back. A source answering later is unaffected: its later calls only marked the page stale. *[M3 part C]*
## Hosts

- **2026-10-23** · **The event bridge is a host-side crate beside the table, `bridge/` (`tall-table-bridge`), used by every host.** Tycho (`table.rs`, `targets.rs`) and the observatory's GPUI contender (`contract.rs`) each turned the table's events into the filled mark, the scrollbar's targets, and the probe, layout, and cells as JS objects, field for field; the bare host would have been a third copy. It depends on `seiza` (marks, targets) and on the table, so it can live in neither: the table depends on gpui-kit alone, and `seiza` knows no table. Rejected: `seiza` helpers that take plain bounds, which would have left each host its JS-object conversions, the bulk of the copies. A host's own state (the contender's `__contender.state`, its replay geometry) stays in its own `match`. Effect on the apps' wasm (brotli 11, after wasm-opt): Tycho +0.6 KiB (−0.1 KiB before brotli), the contender −0.6 KiB (+0.2 KiB), the noise of the bytes moving; without `#[inline]` on `Publish::event` the contender grew 0.9 KiB, the arms it never uses kept. *[M1, `perf/results/2026-10-23-m1.md`]*
- **2026-10-23** · **The bare host's rows are materialized per page when the read resolves, and answered as the DuckDB source's Arrow pages are:** floats as floats, strings borrowed, integers, booleans, and dates as text made on each read. A value made on each read instead would put the generator's hashing into every frame; a page made in `load_page` would put it in whichever frame asked. Resolved on GPUI's next turn, outside the frames, as an engine's decoded page arrives. The narrow shape's values sit in the asteroids' ranges, `diameter` and `albedo` NULL in the same ~85% of rows, so the floats round to the same digits as the observatory's. *[M1]*
- **2026-10-24** · **The bare host's `custom-cells` paints every float column through its range, one style at a time** (`?cells=`): `heat` (a fill, the background to `chart_1`), `bars` (from the column's zero), `color` (the text through a three-stop ramp, `chart_bearish`, `foreground`, `chart_bullish`), and `text`, the control, which paints nothing. Each page maps its values through the column's range at run time, so the optimizer can't strip the paint. `color` isn't in the spec's measurement (text, heat, bars), but without it no host code ever set a text ramp, and the smoke check wouldn't see one drawn. Its drawn cells (`__tallTableCells`) and `?jump=<row>` exist only in the feature's build, so the base host is unchanged. *[M2 part B]*
- **2026-10-24** · **The bridge's `live` fields are in every build** (`refreshed_mark`, and `refreshed`, the global with the highest generation drawn); only their arm is behind `live`. A field behind a feature broke a host's struct literal when Cargo unified the feature in, and `..Default::default()` beside every field fails clippy's `needless_update` when it's off. Tycho's literal takes `..Default::default()`. The global is set while the frame renders, before the mark's microtask, so a script reading it as the mark is set reads that frame's generation. *[M3 part B]*
- **2026-10-24** · **The bare host's feed (`live`, `?live=<updates/s>`)** sends a batch about every 16 ms (a GPUI timer, not frames, so the feed asks for no frame of its own): `rate × elapsed` updates to random visible rows from a seeded splitmix64, each row once a batch, each bumping the row's version in the source and invalidated on its own (`invalidate_rows(row..row + 1)`). The source mixes a row's version into its floats' hash when a page is materialized; the other columns and which floats are NULL stay put, so a NaN stays NaN. Each batch is marked (`tall-table:invalidated`, its last generation on `__tallTableInvalidated`, set first), and `just tall-table live` pairs it with the first refreshed mark at or past it. Its view rests at the top, on one page, so the generation alone matches a batch to the frame that shows it (a run spanning two pages fails). *[M3 part B]*
- **2026-10-25** · **The bare host marks a batch from the moment its rows are picked** (`mark_at`), not after its update: a read landing in the update would otherwise be left out of update → pixel, and the feed's own picking (which grows with the rate) isn't the table's. HEAD's path read 22.55 ms either way (B5: 22.52), since its invalidations did no reading. *[M3 part C]*

# Decisions: table

Why the table component is built the way it is. Decisions that bind every app are in the root [`docs/DECISIONS.md`](../../../docs/DECISIONS.md).

One bullet per decision, under its area, oldest first: what was chosen, the numbers that chose it, and *[where they came from]*. A decision that replaces another marks the old one *Superseded* rather than deleting it. Decisions moved here from an app keep their dates and sources.

## Table and paging

The bullets up to 2026-10-09 moved here from Tycho's `docs/DECISIONS.md` when the table left it; their sources are Tycho's milestones, and their results files are under `apps/tycho/perf/results/`. "Queries" in them are the delegate's page reads, which in Tycho are DuckDB queries.

- **2026-09-25** · **Own table, not gpui-kit's `DataTable`:** its `uniform_list` positions rows in f32 pixels (4 px steps at 47 M px, 64 px at 25 M rows). It scrolls in f64 rows and owns its scrollbars, wheel, and keys; no column resizing, selection, or sorting. *[M4]*
- **2026-09-25** · Pages of **1024 rows, prefetch 2** (twice ahead while scrolling), 3 queries in flight, **64 MiB** LRU page cache. The sweep didn't separate 256/1024/4096 × 1/2/4 beyond noise; 1024 divides the row groups. *[M4 sweep]*
- **2026-09-25** · Cancelled page queries count against the 3-in-flight limit until DuckDB answers them (it keeps reading a started page); failed pages retry once scrolled away and back; prefetch leans ahead only while the rows move (250 ms). *[M4 code review]*
- **2026-09-25** · A scrollbar drag loads pages only once the pointer rests 80 ms, or on release: a started page read can't be cancelled (DuckDB's worker uses sync XHRs), and a stale one delayed the jump's target (throttled 4.3 → 2.2 s). *[M4]*
- **2026-09-27** · **Visible pages first:** no prefetch page starts while a visible page isn't loaded. DuckDB-Wasm round-robins query slices, so prefetch in flight delayed the visible page (1 GB first rows 2.7 s → 0.8 s with the cache fix; jump to 90% 133 → 92 ms). *[M5]*
- **2026-10-07** · The table reports its first rows with an event (`TableEvent::FirstRows`) and its paging and scrolling through `RowTable::stats`; the workbench decides what the panel shows (the open-questions note). Rows/s and cache hits cover the panel's 2 s window; a cache hit is a drawn frame with every visible row loaded. *[M7 part A]* *Its `TableEvent::FirstRows` was superseded 2026-10-13: the table emits `Filled` and the host marks it (below).*
- **2026-10-07** · **No cell-string cache.** Formatting every visible cell takes 0.075 ms p50 of a 13.1 ms draw on Gaia (0.045 of 11.8 on the asteroids), timed alone in an instrumented build. Gaia's cells hold 2.4× the characters and cost +11% work per draw. *[M7 part B]*
- **2026-10-07** · Pages stay **1024 rows × prefetch 2** on Gaia too. Re-run with work per frame, the sweep still barely separates: steady work 11.9 ms at 256-row pages vs 12.5 at 1024, first rows and jumps within noise, no placeholders in any steady scroll. *[M7 part B `apps/tycho/perf/results/2026-10-08-m7-sweep-gaia.json`]*
- **2026-10-09** · Cell overflow is solved by formatting, not measuring: cells are plain blocks so GPUI's `.truncate()` cuts text at the end; doubles round to fit their column like a spreadsheet's automatic format (scientific only when the whole part doesn't fit); integers are never rounded and are cut in the middle (`1234…789`) if still too wide; one tooltip on the hovered cell shows the exact value. Measuring each column's widest value covers only the pages measured, and a column can't widen under the reader. *[M7 part F, design discussion]*
- **2026-10-16** · **The settle times are `Paging` fields:** `scroll_settle` (250 ms, prefetch leaning ahead) and `drag_settle` (80 ms, a drag's loads), with today's values as defaults. They decide which pages are requested, so the observatory holds them equal on both sides (root `docs/DECISIONS.md`, "Comparison protocol"). Tycho keeps the defaults: +1.2 KB raw after wasm-opt (+0.01%), and its table checks are unchanged (jump to 90% 83.3 ms reference, 2.2 s throttled). *[observatory M2 part A, `apps/tycho/perf/results/2026-10-16-observatory-m2-a.md`]*

## Component API

- **2026-10-13** · **Moved out of Tycho, as the repo's first component** (`seiza-table`, from Tycho's `crate/src/table/`). It depends on `gpui-kit` alone. *[Tycho M9 part C]* *Its name was superseded 2026-10-14: `seiza-tall-table`, in `components/tall-table/` (below).*
- **2026-10-13** · **A state entity, an element, and a delegate, as gpui-kit's `DataTable` does it:** `TableState<D: TableDelegate>` holds the scroll position, page cache, and hover, and draws the header and body; `Table<D>` (`RenderOnce`) adds the focus, keys, and border around it. The delegate reads pages (`load_page` returns a request id and a boxed future; `cancel`), and a page answers in the component's own `CellValue`s (`Null`, `Float`, `Float32`, `Text`): floats stay numbers so the table can round them to their column, everything else arrives as text, borrowed where the source has it. The column's `ColumnKind` (boolean, date, timestamp, integer with its widest value's characters, float, decimal, text) replaces Tycho's DuckDB type names. Named per gpui-kit's Coding Guides: a `<Control>State`, a `<Role>Delegate`, private fields with readers, `#[non_exhaustive]` on record-like structs. *[Tycho M9 part C, design]* *Its type names were superseded 2026-10-14: each carries `TallTable` (below).*
- **2026-10-13** · **Settings, not `seiza` calls.** Paging comes in as `Paging` (the host reads its URL overrides); the panel's window, clock, and visibility as `ActivityOptions` (`window_ms`, `clock`, `is_recording`); the Playwright probes as `probe_frames` and `probe_cells`. *[Tycho M9 part C]*
- **2026-10-13** · **Marks are the host's, from events emitted in render.** The first-rows and viewport-filled marks must land right after the frame that shows the rows. The table emits `TableEvent::Filled { first }` while that frame renders; GPUI flushes effects at the end of the update that draws and presents the frame (`App::update` → `finish_update` → `flush_effects`, gpui-pre 0.3.9's `on_request_frame`), so the host's subscriber runs in the same JS task, and its `mark_after_current_task` still lands in that task's microtask checkpoint, before the next task (and so before the browser can render anything else). It's queued after the present now, not during render, so it lands 0.005–0.045 ms later in that checkpoint: checked on the asteroids sample (first rows, the viewport filled, and after End; 5 runs each against the pre-extraction build, every mark before the next task in both). Rejected: an optional `seiza` feature on the component (a dependency on `seiza` the tiers forbid), and a callback hook (the event is the gpui-kit idiom and has the same timing). The probes and scrollbar targets go out the same way, only when they change. *[Tycho M9 part C, gpui-pre 0.3.9 source]*
- **2026-10-14** · **Renamed `tall-table` (`seiza-tall-table`), before the observatory's first comparison.** The types were gpui-kit's names with other meanings: `gpui_kit::component::table` exports `Table` (its simple static table), `TableState<D: TableDelegate>`, `TableDelegate`, and `TableEvent`, so a host using both had to alias. Every type that named the table now carries the prefix: `TallTable`, `TallTableState`, `TallTableDelegate`, `TallTablePage`, `TallTableEvent`, `TallTableStats`, `TallTableProbe`, `TallTableLayout`, and `TallTableColumn` (gpui-kit's table exports a `Column` too, and a host imports both unqualified); its actions are under `seiza_tall_table` and its key context is `TallTable`. `ColumnKind`, `CellValue`, `Paging`, `PageError`, `PageLoad`, `ActivityOptions`, `CellProbe`, and `ColumnProbe` keep their names: gpui-kit has none of them. "Tall" names what every feature level keeps, many rows never held at once, as MATLAB's tall arrays do (rows past memory, read lazily from a datastore). Rejected: `PagedTable` (reads as paginated), `ResidentTable` (the opposite of the design), `LocalTable` (a data path), `DataGrid` (editable), `DataView` (a built-in JS type), `CatalogTable` ("catalog" is the data in Tycho and metadata in DuckDB, Iceberg, and Unity; it names a use case, not the property), `LongTable` ("long" vs "wide" is a data shape: pandas' `melt`). The cost: "tall" also reads as an element's height, which the README's first lines answer. *[design discussion]*

## Fixtures

- **2026-10-17** · **The paging fixture runs the state itself, not `PageCache`.** The settle times and the drag's wait live in `TallTableState` (timers and `Direction`), outside the pure cache, so a cache-only test would leave the two `Paging` fields the observatory added unchecked. The scenarios drive a `TallTableState` in GPUI's test app through its own `scroll_by`, `jump_to`, `scroll_to_fraction`, and drag paths (a child module of `state`), on GPUI's test clock; the delegate answers a read only when the scenario says. Each of ten controls (each `Paging` field moved one way or the other) fails at least one of the seven scenarios. The cost is a dev-dependency on gpui-kit's `test-support`: 29 packages added to `Cargo.lock`, none of the pinned ones moved, and no build changes (dev-dependencies don't reach a wasm build). Rejected: extracting the settle logic into a pure model, a change to the table's internals for a test. *[observatory M2 part C]*
- **2026-10-17** · **Cancels from one decision are a set.** `PageCache::plan` finds stale reads in a hash map, so their order isn't the table's to promise; the fixture writes each run of cancels in page order, and both sides compare it so. Loads keep their order: most urgent first. *[observatory M2 part C]*
- **2026-10-17** · **The cell fixture rounds synthetic values too.** The observatory's data file never fills a float column (its longest float is 8 characters against a budget of 12), so its drawn cells pin only the exact text (`8.0`, `-2082.0`, `NULL`), and a budget a character off passes them. Its `rounding` cases (11, one per branch of `fit_float`, at the pinned budgets) are what the budget controls fail on. They're hand-written; the native test is what checks them. *[observatory M2 part C, `apps/observatory/perf/results/2026-10-17-m2-c.md`]*

## Features

- **2026-10-23** · **The features are `DataTable`'s, each a Cargo feature, listed in `PLAN.md`; TanStack Table's extras are candidates there, not plans.** The inventory was read from gpui-component 0.7.3's `src/table/` (the pin). `select` is one feature for row, column, and cell selection, the host picking the mode at run time as `DataTable` does: a feature per mode multiplies the `cfg`s for little saved. *[planning discussion]*
- **2026-10-23** · **A feature's own cost is measured in a bare host crate of the component's (`host/`), not in an app.** A cost read in Tycho mixes in Tycho's code, and the observatory's GPUI contender can't carry code for a feature its DOM side lacks ("the same scope"). The host switches each feature on at run time, since a feature compiled but unused can be stripped and read as free, and answers pages from memory, so the bytes and frame work are the table's alone. *[planning discussion]*
- **2026-10-23** · **The bare host first, on its own, then `custom-cells`; each feature's research opens its own milestone.** The draft put a study of every feature's cost before any was built, sorting's data cost among them, which would have held back `custom-cells`, a feature that never reaches the data, while the observatory's wide sheet waits on it. The host's first milestone records the base's bytes and frame work, in the observatory's shape and a 500-column one, so every feature reads its cost against one baseline. *[planning discussion, M1–M2]*
- **2026-10-23** · **The order: the scenarios' features first** (`custom-cells` → `live` → `follow`), in the observatory's scenario order, **then Tycho's** (`resize` → `select` → `copy` → `sort` → `pin` → `reorder` → `context-menu` → `group-headers`). The three are small, leave the paging alone, and serve Tycho too (a growing CSV, a refreshed query). Rejected: Tycho's core first, which would have finished the wide sheet's later steps (`resize`, a range copied) before market watch could start. *[planning discussion]*
- **2026-10-23** · **`custom-cells` is a declarative paint** that a page answers with its values (a fill, a bar, a text color), not a host-built subtree per cell as `DataTable`'s `render_td` is. The table already draws an element per visible cell; the paint adds a fill, a bar, and a color to it (or quads in the body's pass), where a hook would run a host's closure and build its subtree for each of the wide sheet's 1–2 k cells a frame, which the table can neither bound nor pin. A fixture can pin a paint (colors, a bar's pixels) for a DOM contender to match. Its fields, the colors' home (the page, or a ramp per column, which a theme switch wouldn't re-read), the bar's origin, and how it's drawn are left to its milestone, to settle with numbers. *[planning discussion, M2]*
- **2026-10-23** · **Stripes, row lines, and the row-number gutter are the base's:** `render_body` already shades odd rows (`table_even`), draws a line under each (`table_row_border`), and labels each row in a gutter (`gutter_cells`, the row index + 1), so none is a setting or a feature, and `DataTable`'s `row_header` leaves the list. *[planning discussion, code review, `src/state.rs`]*
- **2026-10-23** · **The bare host's shape:** it bootstraps through `seiza` without the panel, as the observatory's GPUI contender does; `host/crate/` (`tall-table-host`) and `host/web/`, scripts in `perf/`, recipes in the component's own `justfile` (`just tall-table <recipe>`); its delegate answers from memory in two shapes (in `PLAN.md`, the spec that pins them), with an optional page delay; a build with every feature on is recorded too, once there are two. *[planning discussion]*
- **2026-10-23** · **One milestone per feature, numbered in the order now, and the features built in a run before the apps adopt them.** A milestone's spec and checks are written when the one before it closes, after its own research. Building the run first keeps one session's context on the component and lets each app adopt features in batches, against its budgets, once they exist. *[planning discussion, M1–M12]*
- **2026-10-23** · **No TanStack candidate joins the list for now;** the Cargo names stay drafts until each feature's milestone. *[planning discussion]*
- **2026-10-23** · **The component measures only itself, and every feature in the order is built.** Each feature is there because an app needs it, so its cost (wasm and frame work, in the bare host) tells a host what turning it on costs; it doesn't decide whether it's built, and research settles how. The table doesn't measure what a feature does to an app: each feature is off by default, its milestone checks the base build is unchanged with it off and that the native tests and fixtures pass with it off and on, and an app measures a feature against its own budgets when it adopts it. A cost an app can't carry comes back here as an optimization. A change to the base still records its effect on each app (root `CLAUDE.md`, rule 1). Data a source reads to answer a feature (a sort's `ORDER BY`) is the source's cost, the engine's. Superseded: the draft's research that decided which features to build, and the table measuring a feature against the apps' budgets. *[planning discussion]*

## Hosts

- **2026-10-23** · **The event bridge is a host-side crate beside the table, `bridge/` (`tall-table-bridge`), used by every host.** Tycho (`table.rs`, `targets.rs`) and the observatory's GPUI contender (`contract.rs`) each turned the table's events into the filled mark, the scrollbar's targets, and the probe, layout, and cells as JS objects, field for field; the bare host would have been a third copy. It depends on `seiza` (marks, targets) and on the table, so it can live in neither: the table depends on gpui-kit alone, and `seiza` knows no table. Rejected: `seiza` helpers that take plain bounds, which would have left each host its JS-object conversions, the bulk of the copies. A host's own state (the contender's `__contender.state`, its replay geometry) stays in its own `match`. Effect on the apps' wasm (brotli 11, after wasm-opt): Tycho +0.6 KiB (−0.1 KiB before brotli), the contender −0.6 KiB (+0.2 KiB), the noise of the bytes moving; without `#[inline]` on `Publish::event` the contender grew 0.9 KiB, the arms it never uses kept. *[M1, `perf/results/2026-10-23-m1.md`]*
- **2026-10-23** · **The bare host's rows are materialized per page when the read resolves, and answered as the DuckDB source's Arrow pages are:** floats as floats, strings borrowed, integers, booleans, and dates as text made on each read. A value made on each read instead would put the generator's hashing into every frame; a page made in `load_page` would put it in whichever frame asked. Resolved on GPUI's next turn, outside the frames, as an engine's decoded page arrives. The narrow shape's values sit in the asteroids' ranges, `diameter` and `albedo` NULL in the same ~85% of rows, so the floats round to the same digits as the observatory's. *[M1]*

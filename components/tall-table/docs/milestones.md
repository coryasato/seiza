## M2: `custom-cells`, a cell's fill, bar, and text color (closed 2026-10-24)

**Results:** [`perf/results/2026-10-24-m2-spike.md`](../perf/results/2026-10-24-m2-spike.md) (part A), [`perf/results/2026-10-24-m2.md`](../perf/results/2026-10-24-m2.md) (part B)

The spec as written before the build. As built, `Stop` takes `&Theme` and `Ramp::new` a slice (`docs/DECISIONS.md`, "Features", "The API as built"); the README has the API as it is.

**What it adds** (behind the `custom-cells` feature, off by default): a page can answer a **paint** for each cell next to its value, and the table draws it. The paint is declarative (`docs/DECISIONS.md`, "Features"): data the table draws in its own cell, not a subtree a host builds per cell, so a DOM contender matches it from numbers a fixture can pin.

```rust
// The page (delegate.rs), behind `custom-cells`.
trait TallTablePage {
    fn value(&self, row: usize, column: usize) -> Option<CellValue<'_>>;
    #[cfg(feature = "custom-cells")]
    fn paint(&self, row: usize, column: usize) -> CellPaint { CellPaint::default() }
}

/// Each field 0..=1 (clamped). `None`, NaN, or a field whose column has no
/// ramp or bar draws nothing (the last a debug assertion: a host's mistake).
#[derive(Debug, Default, Clone, Copy, PartialEq)]
pub struct CellPaint {
    pub fill: Option<f32>, // through the column's fill ramp: the whole cell
    pub bar: Option<f32>,  // the bar's end across the cell's inner width, drawn from the column's zero
    pub text: Option<f32>, // through the column's text ramp: the value's color
}

// The column (column.rs), behind `custom-cells`: what turns them into pixels.
impl TallTableColumn {
    pub fn fill(self, ramp: Ramp) -> Self;
    pub fn bar(self, bar: Bar) -> Self;
    pub fn text_ramp(self, ramp: Ramp) -> Self;
}
/// A theme token, resolved each frame (a fixed color is `|_| hsla(…)`).
pub type Stop = fn(&ThemeColor) -> Hsla;
/// Two or more stops, evenly spaced over 0..=1, mixed in Oklab.
pub struct Ramp { /* stops */ }
/// `zero`: where the bar starts, 0..=1 of the inner width (0, the left edge, by default).
pub struct Bar { pub zero: f32, pub color: Stop }
```

- **What it covers:** the wide sheet's heat-map and data-bar cells, and the color of market watch's flash (a three-stop ramp: down, none, up). The flash's fade over time is `live`'s: `custom-cells` draws what a page answers, and redraws when a page changes.
- **What stays the table's:** the value's text, its rounding and cutting, and the tooltip (the exact value), unchanged; a placeholder or failed row paints nothing (only a loaded row asks its page); a theme switch recolors every paint on its frame, with no page read again.
- **What's the host's:** each column's ramps and bar, and the 0..1 values (a host maps each value through its column's range, read from its source, as the observatory would from SQL).
- **How it's drawn** (decided, `docs/DECISIONS.md`, "Features"): a fill and a bar both as quads, collected in the row loop and painted by one `canvas`, the cells layer's first child: each cell's fill, then its bar over it, all under the text. The research and the spike: root [`docs/research/tall-table-features.md`](../../../docs/research/tall-table-features.md), "`custom-cells`"; [`perf/results/2026-10-24-m2-spike.md`](../perf/results/2026-10-24-m2-spike.md).

## M3: `live`, changed rows re-read and redrawn in place (closed 2026-10-25)

**What it adds** (behind the `live` feature, off by default): a host says which rows changed, and the table reads their pages again and redraws them, the scroll unmoved; with `custom-cells` too, a column can flash the cells whose values changed. The research and the options weighed: root [`docs/research/tall-table-features.md`](../../../docs/research/tall-table-features.md), "`live`"; the decisions: [`docs/DECISIONS.md`](DECISIONS.md), "Features" (2026-10-24, M3 part A).

```rust
// The state (state.rs), behind `live`.
impl<D: TallTableDelegate> TallTableState<D> {
    /// `rows` changed in the source. Their pages that are wanted, loaded or
    /// loading, are read again (`load_page`), a loaded one drawn as it is
    /// until the new page lands; the others are dropped. Loads as a scroll
    /// does: during a scrollbar drag, once the pointer rests. Returns this invalidation's generation, which
    /// grows with each call.
    pub fn invalidate_rows(&mut self, rows: Range<u64>, cx: &mut Context<Self>) -> u64;
}

pub enum TallTableEvent {
    // …
    /// A re-read page is drawn for the first time, its rows visible.
    /// Emitted in render, as `Filled` is; none for a page re-read off screen. Its read started after every invalidation up to
    /// `generation`.
    #[cfg(feature = "live")]
    Refreshed { rows: Range<u64>, generation: u64 },
}

// The column (column.rs), behind `live` and `custom-cells`.
impl TallTableColumn {
    /// When a re-read changes a cell's value: a float's rise at the ramp's 1,
    /// its fall at 0, any other change at 0.5; faded by opacity to nothing
    /// over `duration`.
    pub fn flash(self, ramp: Ramp, duration: Duration) -> Self;
}
```

- **How the cache re-reads** (decided): one read per page in flight; a page invalidated during its read (a re-read or its first) is read once more after it lands, and never cancelled for being stale; an invalidation's loads wait out a scrollbar drag (`drag_settle`) as a scroll's do; a failed re-read keeps the stale page drawn, read again at the next invalidation or `retry_failed` (a `read_failure` still emits `ReadFailed`); a re-read's page swaps its bytes for the old page's, counts in flight, and is cancelled by `close`; a page with nothing to show goes first, then a stale visible page's re-read, then prefetch (a stale page doesn't hold prefetch back); re-reads hold at most `max_in_flight − 1` slots together; a stale page outside `wanted` is dropped; a re-read in flight for a page that leaves `wanted` is cancelled, as any read is. Placeholders only where a page isn't loaded; a re-read emits no `Filled`.
- **What stays the same:** `set_rows`, including the base forgetting a short last page (a host re-running a query with a new count calls `set_rows`, then `invalidate_rows(0..rows)`); the scroll, the hover, and the tooltip, which reads the new value on the next frame.
- **What's the host's:** knowing which rows changed (the engine's feed, in market watch), and mapping an update to the generation it got back. Patching a page in place isn't a feature: a host whose pages share storage it mutates calls `cx.notify()` on the table, and gets no flash. A host that has the new page in hand answers the re-read with a ready future, which lands in the turn that asked (part C); there's no push call.
- **The flash** (decided): compared in `page_done`, off the frame, over the invalidated rows of flashing columns only (rows invalidated during a read wait for the next read's comparison; two NaNs are equal); kept in a map of live flashes, each removed as it ends; drawn as a fill quad in `custom-cells`' pass over the page's fill, faded by opacity (the order settled with a screenshot); frames requested (`Window::request_animation_frame`) only while a flash is on screen; under `App::reduce_motion`, held at its first color for the duration, no fade and no frames, cleared by a timer. The clock is GPUI's (`BackgroundExecutor::now`).

## M2 follow-up: `custom-cells`' follow-ups (closed 2026-10-25)

**Results:** [`perf/results/2026-10-25-m2-follow-up.md`](../perf/results/2026-10-25-m2-follow-up.md)

The spec as written before the build, and its checks with their evidence. As built, beyond it: the text's contrast reads the color on screen on the jumped-to row too (the tint over the fill), a NULL keeps its muted color, `Domain` asserts its order in debug builds, and the probe's bar carries its color (`docs/DECISIONS.md`, "Features", "Fixtures").

From a design review after M2 and a comparison with other tables' heat and bar cells (Perspective, Excel, pandas' Styler, Great Tables, Grafana), 2026-10-24. Each judged on the table's merits, none for the observatory's sake.

**Before an app adopts it:** one session, after M3 and before any app's milestone builds a column's paint, whichever comes first (the observatory's wide sheet is the first; its "Waiting on" row points here). Commit as `tall-table: custom-cells follow-ups (M2 follow-up)`.

- **A bar's color below zero:** `Bar::below(stop)`, the color of a bar that ends left of its zero, as Excel's, pandas', and Perspective's negative bars are; `None` draws both sides in `color`. A branch per bar, no extra quad. **And `Bar` becomes `#[non_exhaustive]`:** today a host can build `Bar { zero, color }`, which any added field breaks. `Bar` has no `Default`, so unlike `CellPaint` (`docs/DECISIONS.md`, "Features", the API as built) the attribute takes nothing a host needs: it builds with `Bar::new(color).zero(z).below(stop)`. This is the one breaking change here, so it lands before a host names `Bar`'s fields.
- **Text over a fill picks its own contrast:** a cell with a fill and no text color draws its text in `foreground` or `background`, whichever's Oklab lightness is farther from the fill's (the mix has it in hand; a translucent fill is composited over the row's background first). Two theme tokens that already contrast with each other, so no threshold to tune, and a theme switch flips them on its frame. Oklab L, not WCAG or APCA: this picks one of two colors, it doesn't score a contrast, and it costs a compare per cell. A text ramp still wins; a host that wants one fixed color gives a two-stop ramp of it. The flash (M3) reads the page's fill only, not its own fading quad. Without it, every heat column needs a text ramp to stay readable in both themes.
- **The range rule, written down, and a helper:** `CellPaint`'s docs and the README say a value maps through its whole column's range (from the source's stats, or fixed), never one page's minimum and maximum, or colors jump at page boundaries. `Domain { lo, mid, hi }` with `unit(v) -> f32` (`mid` maps to 0.5, each side scaled on its own; NaN stays NaN), pure, behind `custom-cells`, in the component: a bar's zero (`unit(0.0)`) must agree with its values' mapping, which the bare host does by hand today (`rows.rs`), and the observatory's wide sheet will be its second user. Where the range comes from stays the source's (for DuckDB, its column stats).
- **Forwarding the feature:** a crate that implements `TallTablePage::paint` turns on `custom-cells` itself; the README says so. `seiza-duckdb`'s `tall-table` source has no forwarding feature; it gains `tall-table-custom-cells` in the milestone of the first app that paints DuckDB pages (the engine's work is planned in the app that drives it).

## M4: `follow`, the view kept at the tail as rows arrive (closed 2026-10-25)

**What it adds** (behind the `follow` feature, off by default, which turns on `live`): a reader who goes to the end (or a host calling `follow()`) follows it as `set_rows` grows the rows, the view pinned to the rows read so far, until the reader scrolls up; and, with `live`, a short last page that grows is kept drawn and read again, not dropped. The research and the options weighed: root [`docs/research/tall-table-features.md`](../../../docs/research/tall-table-features.md), "`follow`"; the decisions: [`docs/DECISIONS.md`](DECISIONS.md), "Features" (2026-10-25, M4 part A).

```rust
// The state (state.rs), behind `follow`.
impl<D: TallTableDelegate> TallTableState<D> {
    /// Scrolls to the end and follows it: as `set_rows` grows the rows, the
    /// view stays at the last rows read, until the reader scrolls up.
    pub fn follow(&mut self, cx: &mut Context<Self>);
    /// Whether the view is following the end.
    pub fn is_following(&self) -> bool;
}

pub enum TallTableEvent {
    // …
    /// Following started (`true`) or stopped: for a host's "back to the
    /// tail" button.
    #[cfg(feature = "follow")]
    Following(bool),
    /// While following, the drawn tail grew: every row below `rows` is drawn
    /// with its values. Emitted in render, as `Filled` is; a host that called
    /// `set_rows(n)` takes the first at or past `n`.
    #[cfg(feature = "follow")]
    TailDrawn { rows: u64 },
}
```

- **Following** (decided): a flag, off at open. Set by an action that reaches the end (End, a wheel or key ending there, a drag released there, `jump_to` landing there, `follow()`); cleared by vertical input leaving the end, by any amount, and by `jump_to` elsewhere; sideways scrolling leaves it; rows arriving and resizes never set it. A drag holds the view until release.
- **Pinned to the loaded tail** (decided): while following, the view's bottom is the last row the cache can draw, with every row above it in view loaded; it moves on as reads land and never back. At `follow()`, before a tail read lands, the view goes to `rows()` as a jump does. A follow move keeps the direction, starts no settle timer, and clears the hover; the visible pages are listed bottom first.
- **The grown tail page** (decided, in `live`): `set_rows` growing a short loaded page marks it stale; it draws the rows it was read with, placeholders past them (the cache answers `Pending` past the count read, not the page's `None`, which draws as NULL), and is read again on `live`'s path (one read in flight, never cancelled for growing, read once more after a read growth overtook, `Refreshed` when drawn). Growing a short page whose first read is out reads it once more after it lands. Shrinking still drops what's past the end. With `live`, `set_rows` plans its reads at the end of the update, as `invalidate_rows` does. Without `live`, the base drops the page and plans at once, as now.
- **What's the host's:** batching appends (one `set_rows` a frame), calling `follow()` to follow from the start (a log view), a "back to the tail" button on `Following(false)`, and timing appends by `TailDrawn`.

## M2: `custom-cells`, a cell's fill, bar, and text color (closed 2026-10-24)

**Results:** [`perf/results/2026-10-24-m2-spike.md`](../perf/results/2026-10-24-m2-spike.md) (part A), [`perf/results/2026-10-24-m2.md`](../perf/results/2026-10-24-m2.md) (part B)

The spec as written before the build. As built, `Stop` takes `&Theme` and `Ramp::new` a slice (`docs/DECISIONS.md`, "Features", "The API as built"); the README has the API as it is.

**What it adds** (behind the `custom-cells` feature, off by default): a page can answer a **paint** for each cell next to its value, and the table draws it. The paint is declarative (`docs/DECISIONS.md`, "Features"): data the table draws in its own cell, not a subtree a host builds per cell, so a DOM contender matches it from numbers a fixture can pin.

```rust
// The page (delegate.rs), behind `custom-cells`.
trait TallTablePage {
    fn value(&self, row: usize, column: usize) -> Option<CellValue<'_>>;
    #[cfg(feature = "custom-cells")]
    fn paint(&self, row: usize, column: usize) -> CellPaint { CellPaint::default() }
}

/// Each field 0..=1 (clamped). `None`, NaN, or a field whose column has no
/// ramp or bar draws nothing (the last a debug assertion: a host's mistake).
#[derive(Debug, Default, Clone, Copy, PartialEq)]
pub struct CellPaint {
    pub fill: Option<f32>, // through the column's fill ramp: the whole cell
    pub bar: Option<f32>,  // the bar's end across the cell's inner width, drawn from the column's zero
    pub text: Option<f32>, // through the column's text ramp: the value's color
}

// The column (column.rs), behind `custom-cells`: what turns them into pixels.
impl TallTableColumn {
    pub fn fill(self, ramp: Ramp) -> Self;
    pub fn bar(self, bar: Bar) -> Self;
    pub fn text_ramp(self, ramp: Ramp) -> Self;
}
/// A theme token, resolved each frame (a fixed color is `|_| hsla(…)`).
pub type Stop = fn(&ThemeColor) -> Hsla;
/// Two or more stops, evenly spaced over 0..=1, mixed in Oklab.
pub struct Ramp { /* stops */ }
/// `zero`: where the bar starts, 0..=1 of the inner width (0, the left edge, by default).
pub struct Bar { pub zero: f32, pub color: Stop }
```

- **What it covers:** the wide sheet's heat-map and data-bar cells, and the color of market watch's flash (a three-stop ramp: down, none, up). The flash's fade over time is `live`'s: `custom-cells` draws what a page answers, and redraws when a page changes.
- **What stays the table's:** the value's text, its rounding and cutting, and the tooltip (the exact value), unchanged; a placeholder or failed row paints nothing (only a loaded row asks its page); a theme switch recolors every paint on its frame, with no page read again.
- **What's the host's:** each column's ramps and bar, and the 0..1 values (a host maps each value through its column's range, read from its source, as the observatory would from SQL).
- **How it's drawn** (decided, `docs/DECISIONS.md`, "Features"): a fill and a bar both as quads, collected in the row loop and painted by one `canvas`, the cells layer's first child: each cell's fill, then its bar over it, all under the text. The research and the spike: root [`docs/research/tall-table-features.md`](../../../docs/research/tall-table-features.md), "`custom-cells`"; [`perf/results/2026-10-24-m2-spike.md`](../perf/results/2026-10-24-m2-spike.md).

## M3: `live`, changed rows re-read and redrawn in place (closed 2026-10-25)

**What it adds** (behind the `live` feature, off by default): a host says which rows changed, and the table reads their pages again and redraws them, the scroll unmoved; with `custom-cells` too, a column can flash the cells whose values changed. The research and the options weighed: root [`docs/research/tall-table-features.md`](../../../docs/research/tall-table-features.md), "`live`"; the decisions: [`docs/DECISIONS.md`](DECISIONS.md), "Features" (2026-10-24, M3 part A).

```rust
// The state (state.rs), behind `live`.
impl<D: TallTableDelegate> TallTableState<D> {
    /// `rows` changed in the source. Their pages that are wanted, loaded or
    /// loading, are read again (`load_page`), a loaded one drawn as it is
    /// until the new page lands; the others are dropped. Loads as a scroll
    /// does: during a scrollbar drag, once the pointer rests. Returns this invalidation's generation, which
    /// grows with each call.
    pub fn invalidate_rows(&mut self, rows: Range<u64>, cx: &mut Context<Self>) -> u64;
}

pub enum TallTableEvent {
    // …
    /// A re-read page is drawn for the first time, its rows visible.
    /// Emitted in render, as `Filled` is; none for a page re-read off screen. Its read started after every invalidation up to
    /// `generation`.
    #[cfg(feature = "live")]
    Refreshed { rows: Range<u64>, generation: u64 },
}

// The column (column.rs), behind `live` and `custom-cells`.
impl TallTableColumn {
    /// When a re-read changes a cell's value: a float's rise at the ramp's 1,
    /// its fall at 0, any other change at 0.5; faded by opacity to nothing
    /// over `duration`.
    pub fn flash(self, ramp: Ramp, duration: Duration) -> Self;
}
```

- **How the cache re-reads** (decided): one read per page in flight; a page invalidated during its read (a re-read or its first) is read once more after it lands, and never cancelled for being stale; an invalidation's loads wait out a scrollbar drag (`drag_settle`) as a scroll's do; a failed re-read keeps the stale page drawn, read again at the next invalidation or `retry_failed` (a `read_failure` still emits `ReadFailed`); a re-read's page swaps its bytes for the old page's, counts in flight, and is cancelled by `close`; a page with nothing to show goes first, then a stale visible page's re-read, then prefetch (a stale page doesn't hold prefetch back); re-reads hold at most `max_in_flight − 1` slots together; a stale page outside `wanted` is dropped; a re-read in flight for a page that leaves `wanted` is cancelled, as any read is. Placeholders only where a page isn't loaded; a re-read emits no `Filled`.
- **What stays the same:** `set_rows`, including the base forgetting a short last page (a host re-running a query with a new count calls `set_rows`, then `invalidate_rows(0..rows)`); the scroll, the hover, and the tooltip, which reads the new value on the next frame.
- **What's the host's:** knowing which rows changed (the engine's feed, in market watch), and mapping an update to the generation it got back. Patching a page in place isn't a feature: a host whose pages share storage it mutates calls `cx.notify()` on the table, and gets no flash. A host that has the new page in hand answers the re-read with a ready future, which lands in the turn that asked (part C); there's no push call.
- **The flash** (decided): compared in `page_done`, off the frame, over the invalidated rows of flashing columns only (rows invalidated during a read wait for the next read's comparison; two NaNs are equal); kept in a map of live flashes, each removed as it ends; drawn as a fill quad in `custom-cells`' pass over the page's fill, faded by opacity (the order settled with a screenshot); frames requested (`Window::request_animation_frame`) only while a flash is on screen; under `App::reduce_motion`, held at its first color for the duration, no fade and no frames, cleared by a timer. The clock is GPUI's (`BackgroundExecutor::now`).

## M2 follow-up: `custom-cells`' follow-ups (closed 2026-10-25)

**Results:** [`perf/results/2026-10-25-m2-follow-up.md`](../perf/results/2026-10-25-m2-follow-up.md)

The spec as written before the build, and its checks with their evidence. As built, beyond it: the text's contrast reads the color on screen on the jumped-to row too (the tint over the fill), a NULL keeps its muted color, `Domain` asserts its order in debug builds, and the probe's bar carries its color (`docs/DECISIONS.md`, "Features", "Fixtures").

From a design review after M2 and a comparison with other tables' heat and bar cells (Perspective, Excel, pandas' Styler, Great Tables, Grafana), 2026-10-24. Each judged on the table's merits, none for the observatory's sake.

**Before an app adopts it:** one session, after M3 and before any app's milestone builds a column's paint, whichever comes first (the observatory's wide sheet is the first; its "Waiting on" row points here). Commit as `tall-table: custom-cells follow-ups (M2 follow-up)`.

- **A bar's color below zero:** `Bar::below(stop)`, the color of a bar that ends left of its zero, as Excel's, pandas', and Perspective's negative bars are; `None` draws both sides in `color`. A branch per bar, no extra quad. **And `Bar` becomes `#[non_exhaustive]`:** today a host can build `Bar { zero, color }`, which any added field breaks. `Bar` has no `Default`, so unlike `CellPaint` (`docs/DECISIONS.md`, "Features", the API as built) the attribute takes nothing a host needs: it builds with `Bar::new(color).zero(z).below(stop)`. This is the one breaking change here, so it lands before a host names `Bar`'s fields.
- **Text over a fill picks its own contrast:** a cell with a fill and no text color draws its text in `foreground` or `background`, whichever's Oklab lightness is farther from the fill's (the mix has it in hand; a translucent fill is composited over the row's background first). Two theme tokens that already contrast with each other, so no threshold to tune, and a theme switch flips them on its frame. Oklab L, not WCAG or APCA: this picks one of two colors, it doesn't score a contrast, and it costs a compare per cell. A text ramp still wins; a host that wants one fixed color gives a two-stop ramp of it. The flash (M3) reads the page's fill only, not its own fading quad. Without it, every heat column needs a text ramp to stay readable in both themes.
- **The range rule, written down, and a helper:** `CellPaint`'s docs and the README say a value maps through its whole column's range (from the source's stats, or fixed), never one page's minimum and maximum, or colors jump at page boundaries. `Domain { lo, mid, hi }` with `unit(v) -> f32` (`mid` maps to 0.5, each side scaled on its own; NaN stays NaN), pure, behind `custom-cells`, in the component: a bar's zero (`unit(0.0)`) must agree with its values' mapping, which the bare host does by hand today (`rows.rs`), and the observatory's wide sheet will be its second user. Where the range comes from stays the source's (for DuckDB, its column stats).
- **Forwarding the feature:** a crate that implements `TallTablePage::paint` turns on `custom-cells` itself; the README says so. `seiza-duckdb`'s `tall-table` source has no forwarding feature; it gains `tall-table-custom-cells` in the milestone of the first app that paints DuckDB pages (the engine's work is planned in the app that drives it).

## M4: `follow`, the view kept at the tail as rows arrive (closed 2026-10-25)

**What it adds** (behind the `follow` feature, off by default, which turns on `live`): a reader who goes to the end (or a host calling `follow()`) follows it as `set_rows` grows the rows, the view pinned to the rows read so far, until the reader scrolls up; and, with `live`, a short last page that grows is kept drawn and read again, not dropped. The research and the options weighed: root [`docs/research/tall-table-features.md`](../../../docs/research/tall-table-features.md), "`follow`"; the decisions: [`docs/DECISIONS.md`](DECISIONS.md), "Features" (2026-10-25, M4 part A).

```rust
// The state (state.rs), behind `follow`.
impl<D: TallTableDelegate> TallTableState<D> {
    /// Scrolls to the end and follows it: as `set_rows` grows the rows, the
    /// view stays at the last rows read, until the reader scrolls up.
    pub fn follow(&mut self, cx: &mut Context<Self>);
    /// Whether the view is following the end.
    pub fn is_following(&self) -> bool;
}

pub enum TallTableEvent {
    // …
    /// Following started (`true`) or stopped: for a host's "back to the
    /// tail" button.
    #[cfg(feature = "follow")]
    Following(bool),
    /// While following, the drawn tail grew: every row below `rows` is drawn
    /// with its values. Emitted in render, as `Filled` is; a host that called
    /// `set_rows(n)` takes the first at or past `n`.
    #[cfg(feature = "follow")]
    TailDrawn { rows: u64 },
}
```

- **Following** (decided): a flag, off at open. Set by an action that reaches the end (End, a wheel or key ending there, a drag released there, `jump_to` landing there, `follow()`); cleared by vertical input leaving the end, by any amount, and by `jump_to` elsewhere; sideways scrolling leaves it; rows arriving and resizes never set it. A drag holds the view until release.
- **Pinned to the loaded tail** (decided): while following, the view's bottom is the last row the cache can draw, with every row above it in view loaded; it moves on as reads land and never back. At `follow()`, before a tail read lands, the view goes to `rows()` as a jump does. A follow move keeps the direction, starts no settle timer, and clears the hover; the visible pages are listed bottom first.
- **The grown tail page** (decided, in `live`): `set_rows` growing a short loaded page marks it stale; it draws the rows it was read with, placeholders past them (the cache answers `Pending` past the count read, not the page's `None`, which draws as NULL), and is read again on `live`'s path (one read in flight, never cancelled for growing, read once more after a read growth overtook, `Refreshed` when drawn). Growing a short page whose first read is out reads it once more after it lands. Shrinking still drops what's past the end. With `live`, `set_rows` plans its reads at the end of the update, as `invalidate_rows` does. Without `live`, the base drops the page and plans at once, as now.
- **What's the host's:** batching appends (one `set_rows` a frame), calling `follow()` to follow from the start (a log view), a "back to the tail" button on `Following(false)`, and timing appends by `TailDrawn`.

## M5: `resize`, a column's width dragged at its header edge (closed 2026-10-26)

**What it adds** (behind the `resize` feature, off by default): a band at each visible column's right edge in the header; dragging it sets the column's width live, within its min and max, and double-clicking it fits the column to what's drawn; the new widths come out in an event at the release, for a host to keep and give back. It adds the width model `pin`, `reorder`, and `group-headers` build on. The research and the options weighed: root [`docs/research/tall-table-features.md`](../../../docs/research/tall-table-features.md), "`resize`"; the decisions: [`docs/DECISIONS.md`](DECISIONS.md), "Features" (2026-10-26, M5 part A).

```rust
    /// A drag released or a fit changed a width: each column's set width

    /// its kind's, in the order of `columns()`, for a host to keep (by
    /// column name, if its columns change) and give back through `width`.
```

- **The width model** (decided): a column's width is its kind's, laid out as today (at least its header's), unless the host set one (`width`) or a drag or fit did; a set width is clamped to its `min_width` (40 px default) and `max_width` (1200 px), a kind's width isn't (so an unresized column draws as without the feature). It's kept in the state; `set_columns` replaces it with what the host passes. The event reports set widths only, so a host giving them back never freezes a kind's width (an integer column's follows the font's number advance). A float column's budget follows its width, so a drag re-rounds its floats on the frame that widens it.
- **The band** (decided): 4 px on each side of a 1 px hairline at each visible resizable column's right edge, in the header only (`table_row_border`; `border` while hovered or dragged), with the column-resize cursor, painted after the header's cells. The body draws no guide line. Nothing of it is drawn without the feature.
- **The drag** (decided): the table's own, followed by the move and release handlers the body's `canvas` registers every frame, not GPUI's typed drag. It's a field of its own (`resizing`), not a `Drag` variant: `drag.is_some()` holds page reads until a scrollbar drag rests, and a column drag isn't a scroll, so paging during it (a vertical wheel) is the base's. Width = the width at the press + the pointer's move since, clamped. The sideways scroll holds still until the release, which clamps it: during the drag sideways input (a wheel's sideways part, Shift+wheel, the horizontal scrollbar) is ignored, nothing clamps `scroll_x` (a move re-lays out the columns without `lay_out`'s clamp), and the content counts as at least `scroll_x` + the cells' width, so the horizontal thumb stays where the view is; vertical scrolling works as without. No auto-scroll past an edge. The resize cursor holds window-wide while dragging. No tooltip during the drag. `set_columns` ends it with no event. The layout probe is reported once at the release (moves don't bump its generation; the release does), not per move.
- **The fit** (decided): a double-click on the band fits the column to its header's name and its visible, loaded rows, clamped; the drag the second press starts is ignored until the next single press. A numeric column (float, integer, decimal) fits its widest exact text by character count at the number advance (`chars × number_px` + padding + 1, `column_layout`'s rule), so a fitted float's budget holds every digit; any other fits its widest shown text (`cell_text`: one line, `¶` for breaks), cut to what `max_width` could hold, shaped in the cells' font, plus padding. It never asks the delegate. Not public in this milestone.
- **What's the host's:** keeping widths from `ColumnWidthsChanged` and giving them back (`width`) across `set_columns` or sessions; a column it doesn't want resized (`resizable(false)`).

## M6: `select`, rows, columns, and blocks of cells selected (closed 2026-10-26)

**What it adds** (behind the `select` feature, off by default): a press on a cell, the row-number gutter, a header, or the corner selects a cell, a row, a column, or everything; Shift+press, a drag, and Shift+keys extend it to a range; the keys move it. Held as one range from an anchor to a head, so a million rows cost what one does. Drawn as one tint under the text. An event when it changes, for a host (and for `copy`, next). The research and the options weighed: root [`docs/research/tall-table-features.md`](../../../docs/research/tall-table-features.md), "`select`"; the decisions: [`docs/DECISIONS.md`](DECISIONS.md), "Features" (2026-10-26, M6 part A).

```rust
// selection.rs, behind `select`.
/// A cell: a row and a column (an index into `columns()`).
pub type Cell = (u64, usize);

/// What's selected: one range from `anchor` (the active cell, where a
/// plain arrow moves from) to `head` (where Shift moves), either way round.
/// The kind says how far it spans; the cells are where the reader is.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
#[non_exhaustive]
pub enum TallTableSelection {
    /// The rows between, every column.
    Rows { anchor: Cell, head: Cell },
    /// The columns between, every row, rows that arrive later included.
    Columns { anchor: Cell, head: Cell },
    /// The block between.
    Cells { anchor: Cell, head: Cell },
}

impl TallTableSelection {
    /// The rows it covers, given the table's `rows`; `None` if none.
    pub fn rows(&self, rows: u64) -> Option<RangeInclusive<u64>>;
    /// The columns it covers, given the table's `columns`; `None` if none.
    pub fn columns(&self, columns: usize) -> Option<RangeInclusive<usize>>;
    pub fn contains(&self, row: u64, column: usize) -> bool;
    pub fn anchor(&self) -> Cell;
    pub fn head(&self) -> Cell;
}

/// Which kinds a reader can select: all on by default.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
#[non_exhaustive]
pub struct Selectable { pub rows: bool, pub columns: bool, pub cells: bool }

impl Default for Selectable { /* all on */ }

impl Selectable {
    pub fn all() -> Self;
    pub fn none() -> Self;
    pub fn rows(self, on: bool) -> Self;
    pub fn columns(self, on: bool) -> Self;
    pub fn cells(self, on: bool) -> Self;
}

impl<D: TallTableDelegate> TallTableState<D> {
    pub fn selection(&self) -> Option<TallTableSelection>;
    /// Sets or clears it (no scroll), emitting `Selected` if it changed.
    pub fn select(&mut self, selection: Option<TallTableSelection>, cx: &mut Context<Self>);
    /// Which kinds are on; turning one off clears a selection of its kind.
    pub fn set_selectable(&mut self, selectable: Selectable, cx: &mut Context<Self>);
}

pub enum TallTableEvent {
    // …
    /// The selection changed (a press, a drag, a key, `select`, `jump_to`,
    /// `set_rows` cutting it, `set_columns` clearing it). Not emitted when
    /// an input leaves it as it was.
    #[cfg(feature = "select")]
    Selected(Option<TallTableSelection>),
}
```

The spec below is what part B builds; why each rule is so is in [`docs/DECISIONS.md`](DECISIONS.md), "Features", and the root's research.

- **The model:** one range, `Rows`, `Columns`, or `Cells`, its anchor and head cells in every kind (a gutter press records the first visible column, a header press the top visible row). The host turns rows, columns, and cells on at run time (`Selectable`, all on by default). A selection takes the smallest kind that's on and holds what was pressed or moved to: a cell, else its row, else (for a key) its column; a cell press with only columns on selects nothing. `set_rows` shrinking cuts a `Rows` or `Cells` range (a corner past the end moves to the last row) and clears one wholly past it; a `Columns` range covers every row, those that arrive too. `set_columns` clears it.
- **`jump_to`:** selects the row with rows on, else the cell with cells on (in the active cell's column, or the first visible column with nothing selected), emitting `Selected`. It sets `marked` as today (the probe), but a mark whose jump selected is never drawn. With only columns on, it marks and draws as today.
- **The pointer:** a press on a cell, the gutter, a header cell (the resize band wins its 9 px), or the corner (every column; every row with columns off) starts a range; Shift+press moves the head, keeping the anchor and the kind. A drag moves the head to the cell under the pointer, clamped to the cells at the edges: the table's own drag (`selecting`, followed by the body's per-frame move and release handlers), the event and a redraw only when the selection changes. During it a wheel anywhere in the window scrolls the body as the base's wheel does, and the head follows the cell now under the pointer; no auto-scroll past an edge. No tooltip during the drag. Cmd+press is a plain press; Ctrl+press selects nothing (it's a Mac browser's right-click, `context-menu`'s), nor do double- and right-click.
- **The keys:** actions of their own, bound in a context (`TallTableSelect`) the element adds only while a kind is on; space and Shift+Space keep the base's paging. A plain arrow (left and right too) moves the active cell and collapses to the smallest kind that's on and holds it; Shift+arrows move the head along the range's direction (up and down in `Rows` and `Cells`, left and right in `Columns` and `Cells`) and do nothing across it, the active cell included; at an end, nothing. Page up and down move by the rows in view, Home and End and Cmd+Up and Down to the first and last row in the active cell's column, scrolling as the base does, and with Shift extend; in a `Columns` range plain Home and End collapse as an arrow does and with Shift do nothing. Cmd+A and Ctrl+A select every column (every row with columns off; every cell with only cells on); Escape clears, and propagates with nothing selected. The first arrow with nothing selected selects the first visible cell (its row, its column, by kind) without moving; page keys, Home, and End with nothing selected scroll as the base's. A moved head scrolls into view the least distance, sideways too, through the base's scroll paths. Tab isn't bound.
- **What's drawn:** the range's visible part as one element in `table_active` with a 1 px `table_active_border` edge, after `custom-cells`' quads and before the text; the active cell edged 2 px in `table_active_border`, in every kind, while the table has focus; the gutter cells of selected rows and the header cells of selected columns in `table_active`. Nothing without the feature.
- **The fixture:** `fixtures/selection.json`, scenarios of steps (presses with and without Shift on a cell, the gutter, a header, the corner; drags; a wheel during a drag; keys; `set_rows`; `set_columns`; `jump_to`) → the selection, the top row, and `scroll_x` after each, under each `Selectable` kind; a DOM contender matches what's selected and scrolled to, not how it's held.
- **What's the host's:** the kinds (`set_selectable`); acting on `Selected` (a count in a status bar, `copy`'s source); a selection kept across `set_columns` (`select` after it).

## M7: `copy`, a selection to the clipboard (closed 2026-10-27)

**What it adds** (behind the `copy` feature, which turns on `select`; off by default): Cmd+C or Ctrl+C, or a host's `copy`, copies the selection as a spreadsheet's TSV of exact values. Rows that aren't loaded are read from the delegate a page at a time, beside the cache. The table builds the text and reports it through events; the host writes the clipboard (the bridge, through a `ClipboardItem` it opens when the copy starts, so a copy that takes longer than the browser's ~5 s for a key still lands). A cap in bytes refuses a copy too large for the browsers. The research and the options weighed: root [`docs/research/tall-table-features.md`](../../../docs/research/tall-table-features.md), "`copy`"; the spike: [`perf/results/2026-10-26-m7-a-spike.md`](../perf/results/2026-10-26-m7-a-spike.md); the decisions: [`docs/DECISIONS.md`](DECISIONS.md), "Features" (2026-10-26, M7 part A).

```rust
// copy.rs, behind `copy`.
/// Names a copy in its events.
#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
pub struct CopyId(u64);

/// How a copy is made: the host's settings.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
#[non_exhaustive]
pub struct CopyOptions {
    /// Refused past this many bytes of text: 64 MiB by default, under
    /// WebKit's ~100 MiB limit on a clipboard write. The most ever
    /// attempted, not a size a key copies.
    pub max_bytes: usize,
    /// The most cells (rows × columns) Cmd+C copies: 100 k by default.
    /// Past it the key copies nothing and emits `Declined`; a host that
    /// asks the reader calls `copy`, which this doesn't limit.
    pub key_max_cells: u64,
    /// The column names as a first line: off by default.
    pub headers: bool,
}

impl Default for CopyOptions { /* 64 MiB, 100 k cells, no headers */ }

impl CopyOptions {
    pub fn max_bytes(self, bytes: usize) -> Self;
    pub fn key_max_cells(self, cells: u64) -> Self;
    pub fn headers(self, on: bool) -> Self;
}

/// A copy's progress, in order: `Started`, any number of `Text`, then
/// `Copied` or `Failed`.
#[derive(Debug, Clone, PartialEq)]
#[non_exhaustive]
pub enum TallTableCopy {
    /// Cmd+C on a selection past `key_max_cells`: nothing copied, nothing
    /// read. A host may ask the reader, and call `copy` if they confirm
    /// (the confirming click is a gesture of its own).
    Declined { rows: u64, columns: usize },
    /// In the task that asked for it (the key, or `copy`): a host writing
    /// to the web's clipboard opens its write here.
    Started { id: CopyId, rows: RangeInclusive<u64>, columns: RangeInclusive<usize> },
    /// The text's next piece, to append; `rows_done` rows are in so far.
    Text { id: CopyId, text: String, rows_done: u64 },
    /// Every piece sent.
    Copied { id: CopyId, rows: u64, bytes: usize },
    /// Ended without its text: a host drops the pieces it has and leaves
    /// the clipboard as it was.
    Failed { id: CopyId, reason: CopyFailure },
}

#[derive(Debug, Clone, PartialEq)]
#[non_exhaustive]
pub enum CopyFailure {
    /// Its text passed `max_bytes`, or its first page's worth of rows said
    /// it would.
    TooLarge { bytes: usize, max_bytes: usize },
    /// A page read for it failed (with `read_failure`, the table's
    /// `ReadFailed` too, for the host to repair the source).
    Read(String),
    /// A second copy, `set_columns`, `set_rows` shrinking under it, or
    /// `cancel_copy` (`close` ends a copy without an event).
    Cancelled,
}

/// A running copy's progress.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct CopyProgress { pub id: CopyId, pub rows_done: u64, pub rows: u64 }

impl<D: TallTableDelegate> TallTableState<D> {
    pub fn set_copy_options(&mut self, options: CopyOptions);
    /// Copies the selection, as Cmd+C does but past `key_max_cells` too;
    /// `None` with nothing selected.
    pub fn copy(&mut self, cx: &mut Context<Self>) -> Option<CopyId>;
    /// The copy running, if any: its id, rows done, and rows.
    pub fn copying(&self) -> Option<CopyProgress>;
    /// Ends the copy running, if any, with `Failed(Cancelled)`.
    pub fn cancel_copy(&mut self, cx: &mut Context<Self>);
}

pub enum TallTableEvent {
    // …
    #[cfg(feature = "copy")]
    Copy(TallTableCopy),
}
```

The spec below is what part B builds; why each rule is so is in [`docs/DECISIONS.md`](DECISIONS.md), "Features", and the root's research.

- **The keys:** Cmd+C and Ctrl+C, bound in `TallTableSelect` (both, as Cmd+A is), copy the selection of at most `key_max_cells` cells; past it they emit `Declined` and read nothing, so a reflex Cmd+C on a select-all costs nothing; with nothing selected the key propagates. A host's menu, or its confirmation of a declined copy, calls `copy`. Escape while a copy runs cancels it and keeps the selection; the next Escape clears the selection as `select`'s does.
- **What's copied:** a `Cells` block; a `Rows` range's every column; a `Columns` range's every row the table has at the key (rows arriving later aren't copied). Columns in the table's order, no row numbers.
- **The text:** tab-separated, a row a line (`\n`), no newline after the last, so one cell's copy is its value alone. A value holding a tab, `\n`, `\r`, or `"` is quoted, its quotes doubled. Each value's exact text (`CellValue`'s `Display`, the tooltip's), never the rounded or cut text drawn; NULL an empty field. With `headers`, the column names (quoted by the same rule) as a first line.
- **The reads:** each page at its turn (every page before it sent) comes from the cache if it's loaded then and holds every row the copy wants from it, as drawn then (with `live`, a stale page's drawn rows), and is read through `load_page` otherwise (a last page `set_rows` grew holds fewer rows than it now spans, so it's read): a page not loaded when the copy reads ahead is read ahead, and one loaded then but evicted by its turn is read at its turn. Never cached. A copy's reads and `live`'s re-reads together at most `(max_in_flight − 1).max(1)`, counted against `max_in_flight` with the cache's, so with `max_in_flight` 2 or more a visible page always finds a place (at 1, it waits behind the copy's one read); none started while a visible page is loading; ahead of prefetch. Reads in flight when the reader scrolls aren't cancelled. Pages that land out of order wait for their turn.
- **The pieces:** formatting runs off render, a turn at a time, each turn at most a budget counted in cells (~16 k, a constant: about 1–2 ms natively, measured in the build; wasm has no `Instant`, and a count is the same in a test as in a browser), each turn's text sent as one `Text` and dropped, so the wasm heap holds the pages in flight and one piece, never the copy. A copy whose rows are all loaded and whose cells fit one turn emits `Started`, its `Text`, and `Copied` in the task that asked.
- **The cap:** before any read, a copy whose least text passes `max_bytes` is refused at once: any value may be NULL (empty), so the least is its separators (a tab between cells, a line break between rows) and, with `headers`, the header line. A column's kind bounds nothing above (an integer can pass `max_chars`, a date arrives as text, and DuckDB writes BC dates and years past 9999 wider than 10). Otherwise it reads: refused early when the bytes a row of its first page's worth of rows (`page_rows` of them, wherever the selection starts) × the copy's rows pass twice `max_bytes`, and else as soon as the text passes it, checked a row at a time. `Failed(TooLarge)`, nothing sent after it. Never cut short. The cap is the copy's from its start: options set during it are the next copy's.
- **Ending:** a read that fails fails the copy (`Failed(Read)`, never retried; with `read_failure`, the table's `ReadFailed` too, so the host repairs the source, and the reader copies again). A second copy cancels the first (its `Failed(Cancelled)` before the new `Started`), as do `set_columns`, `set_rows` shrinking below the copy's last row, and `cancel_copy`; a copy's reads in flight are cancelled through the delegate and drain as the cache's do. `close` cancels its reads too, but emits nothing (it takes `&mut App`): a host closing the table tells its bridge, which rejects a write still open. Escape cancels it (`Failed(Cancelled)`, the selection kept); the selection changing and scrolling don't.
- **What's the host's:** writing the clipboard (the bridge, part C), its progress (`copying`, or each `Text`'s `rows_done`) and result shown to the reader, a cancel button (`cancel_copy`), asking the reader about a declined copy, and the limits (`set_copy_options`).
- **The bridge** (part C): at `Started`, `navigator.clipboard.write([new ClipboardItem({'text/plain': promise})])`; each `Text` kept as a JS string; at `Copied`, the promise resolved with a Blob of them, the strings dropped once it's built (the peak is about twice the text, plus the clipboard's copy); at `Failed`, rejected. Without `ClipboardItem` but with `navigator.clipboard` (an old browser), `writeText` at `Copied`, which lands within ~5 s of the key; without `navigator.clipboard` (an insecure context, where `writeText` doesn't exist either), the refusal published at `Started` and the host told the copy can't be written, which calls `cancel_copy` then, so nothing is read or formatted. At the host's word that the table closed, a write still open rejected. **If a write resolved minutes after the key, or in the background, fails** (C1's checks), a copy that reads changes flow: the table reads, then the host asks the reader to press Cmd+C again, which copies from the text it holds, in that key's task. The outcome (written, or the browser's refusal, or failed) on a global the host names, and to a callback the host gives.

## Hardening: a random test of the paging, and its fixes (closed 2026-10-28)

Not a feature: work of its own after M7 closes and before M8 opens (decided 2026-10-27, after M7 part B's two code reviews each found races between `copy` and the paging that no scenario test had). Three parts, one session each (split 2026-10-28, [`docs/DECISIONS.md`](DECISIONS.md), "Fixtures"). Its commits read `tall-table: … (hardening part <X>)`; it closes into [`docs/milestones.md`](milestones.md) as "Hardening".

**What it adds:** a randomized test of the paging under every feature at once, on GPUI's seeded test executor, so a failure replays from its seed. It drives the table through random sequences: scrolls, jumps, scrollbar drags (moving and resting), `set_rows` growing and shrinking, `invalidate_rows`, `follow`'s moves, copies started, cancelled, and replaced, `close`, and reads answered in random order, failed, refused, or answered after a cancel. After every step it checks the invariants: reads in flight (the cache's, re-reads, a copy's, draining) never past `max_in_flight`; with every read answered, no place held; every copy ends (`Copied` or `Failed`), and a `Copied` copy's text is the TSV of its rows as a source read then; no page read twice at once but a visible one a copy also reads; nothing reads after `close`; the cache within its budget but for wanted pages.

**And a fix to the base: a shrink by more than a page** (an open question until 2026-10-28). `PageCache::set_rows` looks only at the old last page, so a shrink by more than a page keeps the whole pages past the new end, and grown back they draw their old rows as loaded, with or without `live`. A shrink forgets every page past the new end: a loaded one's bytes freed, a read or re-read out cancelled and draining, as a short last page is forgotten today. `paging.json` gains a base scenario for it. The TanStack contender's fixture test skips every scenario with a `rows` step (its row count is fixed), so no DOM change. The random test's source changes its values across a shrink and a grow, so the bug fails the test before it's fixed.

**Part A: research and spec** (2026-10-28, the session that split it). Recorded in the root's [`docs/research/tall-table-features.md`](../../../docs/research/tall-table-features.md), "Hardening" (the source, the steps, the invariants, the controls, the cost), its decisions in `docs/DECISIONS.md`, "Fixtures". In short: proptest driven by hand from a plain `#[test]` (GPUI's `property_test` doesn't compile at the pin), each case a scheduler seed and up to 300 steps on a fresh `TestAppContext`, in a window; a source whose values carry a version (`invalidate_rows`) and an era (rows cut by `set_rows`), whose answers come in any order, fail, refuse, or win a cancel's race; eight invariants checked against the source's own log after every step (after `close`, only that nothing is read); each case's `Paging` drawn (`max_in_flight` 1 to 4, small pages and budget).

**Part B: the test and its controls.** In `src/state/random.rs`, a child of `state` (the fixtures' access to the cache): the source, the steps, the invariants, the controls, the printing; and a `just tall-table soak` recipe. ## M8: `sort`, one column, ascending or descending (closed 2026-10-29)

**What it adds** (behind the `sort` feature, off by default): an arrow at the right of each header a host makes sortable; a click sorts the table by that column, its kind's first direction, then the other, then off. The table tells its source the order (`TallTableDelegate::sort`), which reads pages in it from then on or refuses; the table forgets its pages and reads the new order's from the top. One column at a time. The research and the options weighed: root [`docs/research/tall-table-features.md`](../../../docs/research/tall-table-features.md), "`sort`"; the spike: [`perf/results/2026-10-29-m8-a-spike.md`](../perf/results/2026-10-29-m8-a-spike.md); the decisions: [`docs/DECISIONS.md`](DECISIONS.md), "Features" (2026-10-29, M8 part A, revised after its code review).

```rust
// sort.rs, behind `sort`.
/// Which way a column sorts.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum SortDirection {
    Ascending,
    Descending,
}

/// The order the table reads its rows in: one column's values.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
#[non_exhaustive]
pub struct Sort {
    /// The column's index among the columns the table was given, as
    /// `TallTablePage::value` reads it.
    pub column: usize,
    pub direction: SortDirection,
}

impl Sort {
    pub fn new(column: usize, direction: SortDirection) -> Self;
}

/// Why a source can't sort a column: for the host to show.
#[derive(Debug, Clone, PartialEq)]
#[non_exhaustive]
pub struct SortRefused {
    pub message: String,
}

impl SortRefused {
    pub fn new(message: impl Into<String>) -> Self;
}

/// The arrows as SVGs from the host's asset source, in place of the
/// glyphs (`↑`, `↓`, `↕`): gpui-kit's `IconName::SortAscending`,
/// `SortDescending`, and `ChevronsUpDown`'s paths, say, bundled by the host
/// (`icon_assets!`), or its own.
#[derive(Debug, Clone, PartialEq)]
#[non_exhaustive]
pub struct SortIcons {
    pub ascending: SharedString,
    pub descending: SharedString,
    pub unsorted: SharedString,
}

impl SortIcons {
    pub fn new(
        ascending: impl Into<SharedString>,
        descending: impl Into<SharedString>,
        unsorted: impl Into<SharedString>,
    ) -> Self;
}

// delegate.rs
pub trait TallTableDelegate: 'static {
    // …
    /// Reads in `sort`'s order from now on (`None`: the source's own), or
    /// refuses. Ascending or descending by the column's values, ties in the
    /// source's own order and NULLs last, both ways: a total order, so
    /// pages read apart join up. A source that needs to prepare (an index,
    /// a sorted copy) starts here and holds its reads until it's ready.
    /// Reads out when this is called are cancelled after it returns `Ok`;
    /// their answers are dropped, whichever order they hold. Called inside
    /// the table's update, as `load_page` is: nothing it starts may touch
    /// the table (or an entity being updated around it) before its first
    /// await. By default every sort is refused and going back to none
    /// accepted.
    #[cfg(feature = "sort")]
    fn sort(&mut self, sort: Option<Sort>, cx: &mut App) -> Result<(), SortRefused>;
}

// column.rs
impl TallTableColumn {
    /// Whether its header has an arrow to sort by it (`sort`): off unless
    /// set, since the source must be able to sort it.
    pub fn sortable(self, sortable: bool) -> Self;
}

// state.rs
impl<D: TallTableDelegate> TallTableState<D> {
    /// The order the rows are read in.
    pub fn sort(&self) -> Option<Sort>;
    /// Sorts by `sort` (`None`: the source's own order), as a click on its
    /// arrow does; the same sort again re-reads every row (a host whose rows
    /// moved within the order). The source's refusal is returned, and
    /// nothing changes; so is the table's own, for a column past the end or
    /// not sortable (and a debug assertion), and on a closed table, whose
    /// source is never told anything again.
    pub fn set_sort(
        &mut self,
        sort: Option<Sort>,
        cx: &mut Context<Self>,
    ) -> Result<(), SortRefused>;
    /// Draws the arrows from `icons` (`None`: the glyphs). Each path is
    /// loaded from the asset source once, here; if any doesn't load, the
    /// glyphs are drawn (and a debug assertion names it).
    pub fn set_sort_icons(&mut self, icons: Option<SortIcons>, cx: &mut Context<Self>);
}

pub enum TallTableEvent {
    // …
    /// The order changed, by a click or `set_sort`.
    #[cfg(feature = "sort")]
    Sorted(Option<Sort>),
    /// A click's sort the source refused; the order is as it was.
    #[cfg(feature = "sort")]
    SortRefused(Sort, SortRefused),
}

// probe.rs: `TallTableProbe::sort`, with `sort`.
```

The spec below is what part B builds; why each rule is so is in [`docs/DECISIONS.md`](DECISIONS.md), "Features", and the root's research.

- **Sortable is the host's word:** a column is sortable only when the host says so (`sortable(true)`), as `DataTable`'s are, since only the host knows its source can sort it. A table whose columns don't say so draws, lays out, and hit-tests exactly as without the feature, so the fixtures pinned without `sort` hold in the all-on run unchanged.
- **The arrow:** every sortable column's header draws one at its right: `↕` at half the header's text color when the column isn't the sort (full while hovered), `↑` ascending, `↓` descending, as glyphs of the header's face, or the host's SVGs (`set_sort_icons`) in the same colors and states. Its box is one fixed width for every column and both kinds of arrow (the widest of the three glyphs' advances, at least the icon size), the arrow centered in it; a 4 px gap before it. The box and gap are counted in a sortable column's name estimate (`column_layout`) and in `resize`'s fit, so a sort, or icons set, changes no width. The name's text box ends at the gap, so a name wider than its room (a set width, a name that shapes wider than its estimate) is cut with "…" there, never drawn under the arrow; a numeric column's name stays right-aligned, against it. A column narrower than its padding, the gap, and the box draws no arrow and has no target. The target is the box with 4 px on each side, the header's height, ending where `resize`'s band begins; a press there sorts (on release inside it) and doesn't select (`select`'s press goes to the rest of the header). The pointer cursor over it.
- **The host's icons:** checked once when set, each path loaded through the asset source (`App::asset_source`); any that doesn't load, and the glyphs are drawn for all three (a debug assertion names it), so a typo or an icon the host forgot to bundle never leaves a blank target. GPUI's SVG renderer is already linked in every build, so icons cost the `svg()` element's code.
- **The cycle:** a text column ascending first, every other kind descending first, then the other direction, then off (`None`). A click on another column's arrow starts that column's cycle; the old column's arrow goes back to `↕`. No key.
- **What the source is told:** `sort` before anything else changes; refused, nothing changes (a click emits `SortRefused`, `set_sort` returns it). `set_sort` on a column past the end or not sortable tells the source nothing and returns the table's own refusal, naming the column (and a debug assertion), with no event.
- **What an accepted sort does:** every page forgotten, its read cancelled and draining as any cancelled read does (with `live`, re-reads and their invalidations too; with `live` and `custom-cells`, flashes cleared); the view at row 0, the sideways scroll kept (with `follow`, following lets go, unless every row fits); a `Rows` or `Cells` selection cleared (`Selected(None)`), a `Columns` one kept with its anchor's and head's rows moved to 0, the top, so the keys go on from the view and not from a row of the old order (`Selected` with it); the jump's highlight, hover, and the tooltip cleared; a copy running cancelled (`Failed(Cancelled)`); `Sorted` emitted; the new order's reads planned once the update ends (`live`'s and `copy`'s way). A read sent before the sort that answers after it is never stored, whatever it holds. Those reads drain and hold their places (`max_in_flight`) until they answer, as after a jump, so the new order's top page waits for them on a source that can't stop a read it started: a sort made while reads are out costs up to an old read more, which C2 measures and the README says.
- **`set_columns`** keeps the sort when the column at its index has the name it had and is sortable; otherwise it clears it as `set_sort(None)` would (the source told), before laying out. A `Sort` names a column by index, so a host that moves the sorted column (a column dropped before it, later `reorder`) calls `set_sort` with its new index. **`set_rows`** and **`invalidate_rows`** mean the sorted source's rows and positions, nothing more: a change that moves rows within the order is the host's to settle with `set_sort` (the same sort re-reads).
- **What's the host's:** which columns can be sorted (`sortable`), the source's order and its preparation, a refusal's message shown to the reader, the arrows' icons if it wants its own (`set_sort_icons`), and a menu that sorts (`set_sort`).
- **The bare host** (part B, so `size` measures it; its scripts part C): every column sortable; its source sorts from memory, a column's order (ascending, ties by row; descending, ties by row) computed at its first sort in that direction and kept while it's the last column sorted (every column's kept, a sort across the wide shape would pass wasm32's 4 GiB: revised after part B's code review), its reads then answered as before. `?sort-icons` draws gpui-kit's three sort icons, which it bundles (`icon_assets!`), so the `sort` build holds the icons' code whichever runs. `?sort=<column>,<asc|desc>` opens sorted (part C).
- **The bridge** (part C): `Sorted` published on a global the host names (`{column, direction}` or `null`) and as a mark (`tall-table:sorted`), and the probe's `sort`.
- **Fixtures:** `paging.json` gains a `sort` step (the source told, every page forgotten and its read cancelled, the view at the top, the top pages read) with a negative control (a sort that keeps the pages); `fixtures/sort.json` pins the cycle by kind and the order a source answers (values with NULLs and ties → their order, ascending and descending), run natively through the element and against the bare host's in-memory order, each with a negative control. A DOM contender's test names them skipped until the observatory builds a sort level.
- **The random test** gains a `sort` step (a column and direction, or none, its cases' columns drawn sortable or not, so a refused sort is a step too): its source answers under a new permutation and bumps every row's era, so invariants 5 and 7 cover the swap; two controls, a sort that keeps the cache's pages and one that forgets the loaded pages but leaves the reads out in their slots, each caught. A sort changes the paging: `just tall-table soak` before the code review (`CLAUDE.md`, rule 5).

## M9: `pin`, the first columns fixed at the left (closed 2026-10-29)

**What it adds** (behind the `pin` feature, off by default): the first *n* columns, as a host sets them, drawn fixed at the cells' left while the rest scroll sideways under them, with a line at their edge. A count, not a flag per column, so the drawn order stays the index order; while they'd take more than half the cells' width, fewer pin. The research and the options weighed: root [`docs/research/tall-table-features.md`](../../../docs/research/tall-table-features.md), "`pin`"; the decisions: [`docs/DECISIONS.md`](DECISIONS.md), "Features" (2026-10-29, M9 part A).

```rust
// state.rs, behind `pin`.
impl<D: TallTableDelegate> TallTableState<D> {
    /// Pins the first `columns` columns at the left (0: none), kept across
    /// `set_columns` and clamped to the columns there are. Moves no scroll.
    pub fn set_pinned(&mut self, columns: usize, cx: &mut Context<Self>);
    /// The count the host set.
    pub fn pinned(&self) -> usize;
    /// The columns pinned now: the count, clamped to the columns, and cut
    /// to the leading ones whose right edge is within half the cells' width.
    pub fn pinned_in_effect(&self) -> usize;
}

pub enum TallTableEvent {
    // …
    /// The columns pinned in effect changed: by `set_pinned`,
    /// `set_columns`, the view's width, or a width (`resize`).
    #[cfg(feature = "pin")]
    Pinned(usize),
}

// probe.rs: `TallTableLayout::pinned` (in effect), with `pin`; column `c`'s
// left edge is `left + columns[c].x`, less `probe.scroll_x` when
// `c >= pinned`.
```

The spec below is what part B builds; why each rule is so is in [`docs/DECISIONS.md`](DECISIONS.md), "Features", and the root's research.

- **The run:** the first `pinned_in_effect()` columns, laid out first as today (x from 0 to *P*, their widths' sum). The host's count is kept as set; in effect it's clamped to the columns and cut to the leading columns whose right edge is within half `cells_width`, so the scrolled columns keep at least half the view, and a wider view pins the rest again. Computed wherever the columns or the view's width change (`set_pinned`, `set_columns`, a fit, a `resize` release, and `set_body`, which takes a new width without `lay_out`), never on a drag's moves. Before the first frame's width the cells' width is 0 and `pinned_in_effect()` is 0; the run takes effect at the first `set_body`. `Pinned` is emitted when the run in effect changes (so once at the first frame when a count was set), never at construction.
- **The geometry:** a pinned column is drawn at its x, a scrolled one at `x − scroll_x`, clipped to the cells right of *P*; a scrolled column wholly under the run isn't drawn. The sideways scroll's range is unchanged (`content_width − cells_width`): pinning never moves the scroll, and at `scroll_x = 0` every cell is where it is unpinned. One mapping each way, a column's screen left and a screen x's content x, used at every site (the header, the cells, `custom-cells`' quads, flashes, and the jump's edge, the cell probe, the tooltip, the hit tests, `resize`'s bands, `sort`'s arrows, `select`'s tint, active cell, and `scroll_into_view`, and the horizontal thumb's press and drag, `press_track` and `drag_to`, which measure from *P* over the track). A table with nothing pinned draws and hit-tests exactly as without the feature.
- **What's drawn:** two clipped cells layers, pinned (the gutter's edge to *P*) and scrolled (*P* to the scrollbar), each with its own `custom-cells` canvas and `select` canvas, over the one layer of row backgrounds; the header split the same way, its bands and arrows in their column's region. A 1 px line in `border` at *P* through the header and body, over both layers, while a column is pinned in effect. The horizontal scrollbar's track starts at *P* (track and view `cells_width − P`, content `content_width − P`). A failed row's message stays across the cells.
- **With `resize`:** a pinned column's band drags as any other (its hairline under the edge line), moving *P* and the scrolled columns with it, its width clamped so the run stays within half the cells' width (or its `max_width`, the lesser), so a release unpins nothing. The run in effect is held through the drag and computed again at the release; the view narrowed during a drag can still pass the half, so while held *P* is clamped to the cells' width, the scrolled region and the thumb's track never negative. A scrolled column's band under the run isn't drawn.
- **With `select`:** a press left of *P* is on a pinned column, right of it on a scrolled one; a drag reaches the pinned columns from the scrolled ones (clamped to the visible cells, as now). A range across the boundary spans the scrolled columns under the run too and draws in two pieces, one per layer, each edged; the active cell's edge is in its layer. A key move to a scrolled column brings it into view right of *P*; to a pinned one, scrolls nothing sideways.
- **With `sort`:** a pinned column's arrow draws and clicks as any other. **`copy`, `live`, `follow`:** unchanged.
- **What's the host's:** the count (a menu: "Pin first column", later `context-menu`'s), moving a column into the run (`set_columns`, later `reorder`), and saying why fewer pin when `Pinned` reports it.
- **The bare host** (part B, so `size` measures it; its scripts part C): `?pin=<n>`, by default 2 in the narrow shape (`spkid`, `full_name`) and 1 in the wide; `?pin=0` builds the feature with nothing pinned, the control that splits the code's cost from the drawing's. With `?perf`, `__tallTablePin(n)` (the table's `set_pinned`, through GPUI's foreground executor).
- **The bridge** (part C): `Pinned` on a global the host names, and the layout probe's `pinned`.
- **Fixtures:** `fixtures/pin.json`: cases of the cells' width, the columns' widths, the count, and a `scroll_x` → the run in effect, the scroll's range, each visible column's screen left, hit tests (a screen x → a column, or none), and columns brought into view (→ the `scroll_x` that shows each right of *P*, as `select`'s keys bring the active cell); run natively against the table's own functions, with negative controls (`no-cap`, `pinned-scroll`, `under-run`, `into-view-at-gutter`), each failing. A property test of the two mappings beside it (proptest, natively: random widths, counts, cells' widths, and scrolls; a screen x → a column → its screen span holding the x, and no screen x mapping to a column wholly under the run). A DOM contender's test names it skipped until the observatory builds a pin level. The fixtures pinned without `pin` unchanged in the all-on run (nothing pinned).
- **The random test** gains a `pin` step (a count from 0 to past the columns), no invariant or control. No soak: the paging is untouched (`CLAUDE.md`, rule 5); if part B's code does touch it, the soak runs.
